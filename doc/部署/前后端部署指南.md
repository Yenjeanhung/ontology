# KnowSource 前后端部署指南

> 一套 Docker 命令通吃所有环境（本机 Docker Desktop / Linux 服务器完全相同），仅文件路径按实际环境替换。
> 两种镜像形态按需选择：**纯后端镜像**（推荐，前端独立托管）或**全家桶镜像**（前端 dist 打进镜像）。

---

## 1. 部署形态总览

```
浏览器 ──► Nginx（托管前端 dist + /api 反代）──► knowsource-backend 容器（FastAPI/uvicorn）
                                                      │
                    ┌─────────────────────────────────┼──────────────────────┐
                    ▼                 ▼                 ▼                      ▼
              PostgreSQL          Neo4j             Milvus            vLLM 模型服务
            （关系库/主数据）    （图数据库）      （向量库，含 etcd+MinIO）  （独立 GPU 机器）
```

| 仓库内文件 | 用途 |
|---|---|
| `backend/Dockerfile` + `backend/.dockerignore` | **纯后端镜像**（API-only，不含前端） |
| `Dockerfile`（根目录） | 全家桶镜像（多阶段：前端构建 + 后端） |
| `docker-compose.yml` | 中间件编排：PostgreSQL / Neo4j / Milvus(etcd+MinIO) / Attu |
| `deploy/k8s/` | K8s 清单（Deployment/PVC/Service/Ingress），与两种镜像兼容 |

## 2. 前置准备（一次性）

### 2.1 Docker

确认 Docker 已安装且守护进程在运行：

```bash
docker version        # Client 与 Server 都有版本号即正常
```

### 2.2 国内网络加速（关键，否则镜像拉不下来）

**① Docker Hub 镜像加速器**——编辑守护进程配置 `~/.docker/daemon.json`（Windows 在 `C:\Users\<用户名>\.docker\daemon.json`），追加：

```json
"registry-mirrors": [
  "https://docker.m.daocloud.io",
  "https://docker.1ms.run",
  "https://hub.rat.dev"
]
```

**必须重启 Docker 守护进程生效**（Linux：`sudo systemctl restart docker`；Desktop：重启应用）。验证：

```bash
docker info --format '{{json .RegistryConfig.Mirrors}}'   # 输出数组而非 [] 即生效
```

若加速器全部失效，可绕过：直接从加速器全名拉取再打官方标签：

```bash
docker pull docker.m.daocloud.io/library/python:3.11-slim
docker tag  docker.m.daocloud.io/library/python:3.11-slim python:3.11-slim
```

**② pip / HF 加速已固化进 `backend/Dockerfile`**（清华 PyPI 源 + CPU 版 torch + HF 镜像），无需额外配置。

> 基础镜像：`python:3.11-slim`（~190MB）。首次拉取走上面任一路径。

## 3. 中间件启动（docker compose）

```bash
cd <项目路径>
docker compose up -d                      # 全套：PG / Neo4j / Milvus / etcd / MinIO / Attu
docker compose ps                         # 等待全部 healthy（Milvus 首次初始化需 30~60s）
```

| 服务 | 容器名 | 端口 | 用途 |
|---|---|---|---|
| PostgreSQL 16 | `ontology-postgres` | 5432 | 主数据（生产库，勿用 SQLite） |
| Neo4j 5.26 | `ontology-neo4j` | 7474 / 7687 | 图数据库（7474 浏览器管理台） |
| Milvus 2.5 | `ontology-milvus` | 19530 / 9091 | 向量库 |
| MinIO / etcd | `ontology-milvus-minio` / `-etcd` | 9000/9001 | Milvus 依赖 |
| Attu | `ontology-attu` | 8001 | Milvus 可视化（可选） |

数据全部落在 compose 匿名卷（`docker volume ls`），`docker compose down` 不删数据，`down -v` 才会清库。

## 4. 后端镜像构建

```bash
cd <项目路径>/backend
docker build -t knowsource-backend:v1.0.0 .
```

- 末尾 `.` 是**构建上下文**（= `backend/` 目录），必须在 `backend/` 下执行
- `backend/.dockerignore` 会剔除 `data/`、`uploads/`、`logs/`、`test/`、`.env` 等运行时数据；**`sql/` 必须保留**（`init_db` 启动建表 + 增量迁移依赖 `schema.sql`/`migrations.sql`）

**构建耗时规律（层缓存）**：

| 改动 | 重建耗时 |
|---|---|
| 只改业务代码（.py） | 几秒（只重跑 COPY 层） |
| 改 `requirements.txt` | 数分钟（依赖层失效重装） |
| 换基础镜像 / `--no-cache` / 清构建缓存 | 全量重来 |

首次构建需下载 CPU 版 torch（~190MB）+ 全部依赖（走清华源），约 3~5 分钟；成品镜像约 3.6GB。

## 5. 后端容器运行

前提：中间件已启动（§3）。

```bash
cd <项目路径>/backend

docker run -d --name knowsource-backend \
  --network ontology_default \
  -p 8000:8000 \
  --env-file .env \
  -e DATABASE_URL="postgresql+asyncpg://ontology:ontology123@ontology-postgres:5432/knowsource" \
  -e MILVUS_HOST=ontology-milvus \
  -e NEO4J_URI="bolt://ontology-neo4j:7687" \
  -e HF_ENDPOINT=https://hf-mirror.com \
  -v knowsource-data:/srv/backend/data \
  -v knowsource-uploads:/srv/backend/uploads \
  knowsource-backend:v1.0.0
```

> Windows 终端不支持 `\` 续行，粘贴时合并为一行即可；参数本身所有环境一致。

参数说明：

| 参数 | 作用 |
|---|---|
| `--network ontology_default` | 加入 compose 网络 → **用容器名互连**（`.env` 里的 `localhost` 在容器内指容器自己，必须覆盖） |
| `-e DATABASE_URL / MILVUS_HOST / NEO4J_URI` | 三个连接串的容器名覆盖版（PG / Milvus / Neo4j） |
| `--env-file .env` | 其余配置注入（`.env` 不进镜像，运行时给） |
| `-e HF_ENDPOINT=https://hf-mirror.com` | 嵌入模型首次下载走国内镜像，防 huggingface.co 直连卡死 |
| `-v knowsource-data:/srv/backend/data` | **命名卷**持久化：模型缓存 / 图库（所有平台行为一致，不依赖宿主机路径） |
| `-v knowsource-uploads:/srv/backend/uploads` | 上传文件原件持久化 |

命名卷管理（与容器生命周期无关，`rm` 容器数据不丢）：

```bash
docker volume ls                          # 查看
docker volume inspect knowsource-data     # 查看实际存储位置
```

**验证**：

```bash
docker logs -f knowsource-backend          # 观察建表/迁移/模型加载（Ctrl+C 退出不停容器）
curl http://127.0.0.1:8000/api/healthz     # 进程探针，返回 200 即通
```

浏览器开 `http://localhost:8000/docs` 见接口文档页即部署成功。纯后端镜像没有页面托管，页面访问见 §6。

**日常管理**：

```bash
docker stop knowsource-backend     # 停
docker start knowsource-backend    # 启
docker restart knowsource-backend  # 重启（改 .env 后需要）
docker rm -f knowsource-backend    # 删容器（命名卷数据仍在）
docker logs --tail 100 knowsource-backend
```

## 6. 前端部署

### 6.1 开发模式（日常开发）

```bash
cd <项目路径>/front
npm ci            # 首次 / 依赖变更后
npm run dev       # Vite dev server，http://localhost:3000
```

`vite.config.js` 已配好代理：`/api`、`/docs`、`/openapi.json` → `http://127.0.0.1:8000`（含 SSE keep-alive），前后端可各自热更新。

### 6.2 生产模式：Nginx 托管 dist + 反代

```bash
cd <项目路径>/front
npm ci
npm run build     # 产物：front/dist
```

把 `front/dist` 放到 Nginx 服务器（或直接在部署机跑一个 Nginx 容器挂载 dist），参考配置：

```nginx
server {
    listen 80;
    server_name your-domain.com;

    # 前端静态资源 + history 路由回退（router 用 createWebHistory，必须 try_files）
    root /var/www/knowsource/dist;
    index index.html;
    location / {
        try_files $uri $uri/ /index.html;
    }

    # API 反代到后端容器/进程
    location /api/ {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        # SSE 必备：多智能体/工作流流式输出
        proxy_buffering off;
        proxy_read_timeout 3600s;
        proxy_cache off;
    }
    location /docs { proxy_pass http://127.0.0.1:8000; }
    location /openapi.json { proxy_pass http://127.0.0.1:8000; }
}
```

SSE 三条纪律：**关缓冲、拉长读超时、（多实例时）ip_hash 或粘性会话**。

### 6.3 备选：全家桶镜像（不推荐生产，胜在省事）

根目录 `Dockerfile` 多阶段构建，前端 dist 由 FastAPI 直接托管：

```bash
cd <项目路径>
docker build -t knowsource:v1.0.0 .
docker run -d -p 8000:8000 --env-file backend/.env ... knowsource:v1.0.0
# 浏览器直接访问 http://localhost:8000 即是完整页面
```

`server.py` 对 `front/dist` 的托管带 `exists()` 判断，纯后端环境自动跳过，两种镜像可共存。

## 7. 发布流程（推镜像到其他机器 / K8s）

运行命令与 §5 **完全相同**，唯一区别是镜像从仓库拉取而非本地构建：

```bash
# 构建机：打仓库标签并推送（阿里云 ACR / Harbor / 任一 registry）
docker tag knowsource-backend:v1.0.0 <registry>/knowsource-backend:v1.0.0
docker push <registry>/knowsource-backend:v1.0.0

# 目标机：拉取后按 §5 原样 docker run（中间件同样按 §3 起）
docker pull <registry>/knowsource-backend:v1.0.0
```

版本纪律：镜像用明确版本号（`v1.0.0`），不要用 `latest` 上生产，方便回滚与追溯。

K8s 部署：`deploy/k8s/`（00-namespace → 01-config 填 Secret → 02-app），要点：单副本约束（进程内嵌 APScheduler + 本地嵌入模型，扩容前须拆调度器）、探针打 `/api/healthz`、Ingress 关闭 `proxy-buffering`。详见 `deploy/k8s/README.md`。

模型服务（LLM/Embedding/Reranker）独立 GPU 机器 vLLM 部署，见 `doc/模型部署/模型部署.md`；后端只通过 `.env` 的 OpenAI 兼容地址对接。

## 8. 已踩坑速查（实战记录）

| 坑 | 现象 | 正确姿势 |
|---|---|---|
| Dockerfile 续行后注释 | `Syntax error - can't find = in "#"` | `\` 续行把下一行拼进同一条指令，行尾 `#` 不是注释；注释必须独占一行 |
| 改 daemon.json 不重启 | `docker info` 里 Mirrors 仍为 `[]`，拉取仍超时 | 必须重启 Docker 守护进程；`docker info --format '{{json .RegistryConfig.Mirrors}}'` 验证 |
| `backend/sql` 被 ignore | 全新数据库漏建表（存量库看不出来） | `sql/`（schema.sql + migrations.sql）必须进镜像 |
| 容器内 localhost | 后端连不上 PG/Milvus/Neo4j | 容器内 `localhost` 是容器自己；加 compose 网络用容器名，或 `host.docker.internal` |
| HF 模型下载卡死 | 启动时下载嵌入模型无响应 | `-e HF_ENDPOINT=https://hf-mirror.com` |
| CUDA torch 白占 3GB | 镜像虚胖、构建慢 | Dockerfile 预装 CPU 版 torch（`--index-url https://download.pytorch.org/whl/cpu`），后续依赖安装自动复用 |
| pypi 直连慢 | pip 层构建 20 分钟+ | `-i https://pypi.tuna.tsinghua.edu.cn/simple` |
| SSE 被反代缓冲 | 流式输出整段延迟/一次性吐出 | `proxy_buffering off` + `proxy_read_timeout 3600s` |

## 9. 部署后健康检查与排查

```bash
curl http://127.0.0.1:8000/api/healthz            # 进程存活（探针端点）
curl http://127.0.0.1:8000/api/agent/multi/tools  # 工具链自检（内置 + MCP 状态）
```

- **组件级诊断**：`/api/monitor/*`（PG/Neo4j/Milvus/LLM 各组件健康），页面「接口追踪」`/trace`（OTel 链路）
- **日志**：`docker logs -f knowsource-backend`；容器内 `data/` 下有 `otel_traces.db`（命名卷，宿主机可直接查）
- **启动失败优先看**：中间件是否 healthy → 连接串容器名是否写对 → 首次启动是否在下载嵌入模型（HF 镜像）
- **LLM/Key 配置**：不走环境变量，页面「配置中心」维护、持久化于数据库，镜像保持无密钥
