# 数据迁移教程（backup.sh / restore.sh）

> 适用：从开发环境切到生产栈、跨机器搬迁、定期备份。
> 脚本位置：`deploy/docker/backup.sh` / `deploy/docker/restore.sh`
> 一句话原理：**PG 用逻辑导出，其余数据卷冷拷贝打包；新环境先灌数据再起服务。**

---

## 1. 迁移的是什么

| 数据 | 存放卷（来源环境） | 导出方式 | 产物 |
|---|---|---|---|
| 关系库（文档/切片/实体元数据/任务记录） | `ontology_postgres_data` | `pg_dump -Fc` 在线导出 | `postgres.dump` |
| 图谱（Neo4j 图数据 + CSV 导入件） | `ontology_neo4j_data`、`ontology_neo4j_import` | 停库后 tar 冷拷贝 | `neo4j_data.tgz`、`neo4j_import.tgz` |
| 向量库（Milvus + 元信息 etcd + 对象存储 MinIO） | `ontology_milvus_data`、`ontology_etcd_data`、`ontology_minio_data` | 停服务后 tar 冷拷贝，**三件必须成套** | 三个 `.tgz` |
| 后端应用数据（嵌入模型缓存、上传原件） | `knowsource-data`、`knowsource-uploads` | tar 冷拷贝 | 两个 `.tgz` |

> Milvus 的完整状态 = milvus_data + etcd_data + minio_data 三者之和，缺一起不来。

## 2. 前置检查（两边各过一遍）

**来源环境（跑 backup）：**

- [ ] `ontology-postgres` 容器在运行（脚本要在线导出）
- [ ] 磁盘剩余空间 ≥ 数据卷总量 × 1.5（`docker system df -v` 看卷大小）
- [ ] 记下当前密码：PG `ontology/ontology123`、Neo4j `neo4j/ontology123`、MinIO `minioadmin`

**目标环境（跑 restore）：**

- [ ] 代码已同步（含 `deploy/docker/`），Docker 已就绪
- [ ] `docker-compose.prod.yml` 中间件密码与来源环境**一致**（不一致先改 compose + `backend/.env`）
- [ ] LLM 的 Key 不用迁移——在页面「配置中心」维护，不随数据卷走
- [ ] 磁盘剩余空间同上

## 3. 场景一：跨机器迁移（最常用）

```bash
# ── 旧机器：导出（约几分钟，取决于数据量）──
cd /path/to/ontology/deploy/docker
bash backup.sh                       # 生成 backup_<时间戳>/
# 脚本会自动：停 neo4j/milvus/etcd/minio 做一致性冷拷贝、清掉手工 run 的后端容器
# PG 不停机，在线导出

# 导出完成后，旧栈的写库处于停止状态：
#   还要用旧环境 → docker start ontology-neo4j ontology-milvus ontology-milvus-etcd ontology-milvus-minio
#   确定弃用     → 什么都不做，后面直接 down

# ── 拷贝到新机器（备份目录整体就是一个迁移单元）──
scp -r backup_20260923_* user@new-host:/srv/knowsource/

# ── 新机器：导入并起全栈 ──
cd /srv/knowsource/deploy/docker
bash restore.sh /srv/knowsource/backup_20260923_*
# 脚本流程：down 本栈 → 起 PG 等 healthy → pg_restore 导入 → 冷灌 7 个卷 → up 全栈
```

## 4. 场景二：同一台机器，开发栈切到生产栈

数据卷**不直连**（两套环境彻底隔离），统一走脚本：

```bash
cd /path/to/ontology/deploy/docker

bash backup.sh                       # 1. 从开发栈导出
cd ../.. && docker compose down      # 2. 停开发栈（不带 -v！旧卷留着当回退保险）
cd deploy/docker
bash restore.sh backup_20260923_*    # 3. 灌入生产栈并起全栈
```

> 注意：本机开发时 embed 模型缓存随 `knowsource-data` 卷一起迁过去，新栈**不用重新下载模型**。

## 5. 场景三：定期备份（只跑 backup，不 restore）

```bash
bash backup.sh /srv/backups/knowsource_$(date +%Y%m%d)   # 指定输出目录
# 建议策略：每日一备，保留最近 7 份 + 每月一份。cron 示例（每天 02:00）：
# 0 2 * * * cd /srv/knowsource/deploy/docker && bash backup.sh /srv/backups/$(date +\%Y\%m\%d)
```

恢复演练：拿备份目录在新机器（或本机改名卷后）跑一次 `restore.sh`，能起能查才算备份有效。

## 6. 迁移后验证清单

```bash
docker compose -f docker-compose.prod.yml ps     # ① 全部 healthy / running
curl http://127.0.0.1/api/healthz                # ② 经前端反代探后端
```

| 检查 | 方法 | 说明 |
|---|---|---|
| 关系库 | 页面登录，文档列表与旧环境一致 | 建表与数据都在 |
| 向量库 | 任选旧文档做检索/问答 | 命中说明 Milvus 集合完整 |
| 图谱 | 图谱页加载旧图谱 | Neo4j 数据完整 |
| 上传件 | 打开旧文档详情/下载原件 | `knowsource-uploads` 完整 |
| 模型缓存 | 后端日志启动迅速、无 HF 下载 | `knowsource-data` 完整 |

## 7. 常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| `backup.sh` 报 `No such container: ontology-postgres` | 来源环境的 PG 容器名不是默认名 | 改脚本头部容器名变量，或先 `docker ps` 确认 |
| `pg_restore` 报密码/连接错误 | 来源 PG 未运行，或凭据被改过 | 起 PG 再导；凭据改过的同步改脚本 |
| restore 后 Neo4j 起不来 / 认证失败 | 目标 compose 的 `NEO4J_AUTH` 与备份数据里的密码不一致 | 统一为目标环境期望的密码后重灌 |
| restore 后 Milvus 报 etcd/minio 连接或元数据错误 | 三个卷没成套（缺迁或错版本混灌） | 三卷一起重新灌；确认三个镜像版本与来源一致 |
| restore 后文件 404 / 文档打不开 | `knowsource-uploads` 没灌或路径变了 | 重灌该卷；路径由后端配置决定，默认即卷内相对路径 |
| 备份目录里缺某个 `.tgz` | 对应卷在来源环境不存在（如从未上传过文件） | 正常现象；确认缺的是否为可选项 |

## 8. 回退方案

- **同机切换失败**：旧开发栈的卷从未删除（`down` 不带 `-v`）——
  `docker compose down`（生产栈）→ 回根目录 `docker compose up -d`，即回到迁移前。
- **迁移后数据异常**：修正问题后重跑 `restore.sh`（脚本清空目标卷重灌，可安全重复执行）。
- **需要彻底重来**：`docker compose -f docker-compose.prod.yml down -v`
  会删掉生产栈全部卷（**慎用**），之后重新 `up -d --build` + `restore.sh`。

---

## 附：两个脚本各做什么

**`backup.sh [输出目录]`**
1. 停止写入型服务（neo4j / milvus / etcd / minio），清理手工 run 的后端容器
2. PG 在线 `pg_dump -Fc`（不停机）
3. 7 个数据卷逐个 tar 冷拷贝
4. 产物：`postgres.dump` + 7 个 `.tgz`，全部在一个目录里

**`restore.sh <备份目录>`**
1. `compose down` 本栈（卷保留，保证没有容器占用数据卷）
2. 只起 PostgreSQL 并等 healthy
3. `pg_restore --clean --if-exists` 覆盖导入（清掉后端自动建的空表）
4. 7 个目标卷（`knowsource_*` 前缀）清空后回灌
5. `compose up -d` 起全栈（Milvus/Neo4j 首启直接使用回灌好的数据）
