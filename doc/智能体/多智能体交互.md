# 多智能体交互（Multi-Agent Collaboration）设计文档

> 定位：**设计文档**（先设计后实现）。在现有单智能体架构上落地生产级多智能体协作系统，
> 覆盖四大核心机制：通信协议与消息机制、任务分解与编排、冲突消解、分层记忆体系，
> 以及可靠性 / 性能 / 可观测性三条工程底线。
> **选型结论先行：编排直接用 LangGraph（能用的框架直接用）；AutoGen/MetaGPT/AgentScope/Camel 评估后不用（§2 给出源码级理由）；LangGraph 的坑与对策也明说（§2.3）。**
> **落位与原型见 §13：功能长在现有对话页里（入口即升级），不是新开孤岛。**

---

## 1. 背景与目标

### 1.1 现状（单智能体）

用户经 HTTP/SSE 进入 FastAPI，由 OAG 智能体服务（`oag_service`）执行：
检索用「向量 + BM25 + 图谱三路 RRF 融合 + Rerank」；上下文注入实体属性与 1 跳关系（图谱事实）；
记忆分短期（窗口+滚动摘要）与长期（mem0 + Milvus）；输出先下发过程数据，再流式 token。

- 智能体 = 知识库(KB) + 技能(Skills) + 人设(System Prompt)，配置态已抽象（`agent_service`）；
- 执行态是**单循环**：一个 LLM 上下文里完成规划、检索、推理、作答。

### 1.2 单智能体的四个瓶颈（多智能体的动机）

| 瓶颈 | 表现 | 多智能体的解法 |
|---|---|---|
| 上下文过载 | 规划+多源检索+推理塞进一个窗口，互相稀释 | 分工：每个智能体只携带自己需要的上下文 |
| 单视角无校验 | 生成即终稿，幻觉无从拦截 | Critic 独立审查，冲突显式消解 |
| 串行延迟 | 三路检索并行，推理仍单线 | 子任务 fan-out 并行执行 |
| 复杂任务无规划 | 无显式任务图，失败无法局部重试 | Planner 产出 DAG，节点级重试/恢复 |

### 1.3 目标场景（贴合本项目业务）

1. **复杂问答协作**（主场景，落地路径最短）：规划智能体分解问题 → 检索智能体与图谱分析
   智能体并行取证 → 评审智能体交叉验证 → 汇总智能体合成答案。
2. **本体建模辅助**（辅场景，体现辩论与收敛）：本体设计智能体提方案 → 抽取规则智能体评估
   可落地性 → 质量审查智能体挑刺 → 多轮修订收敛 → 人审（复用 `human_task_service`）。

### 1.4 设计原则

- **优先框架**：能用现成框架直接用（编排用 LangGraph），不为"自研"而自研；
  框架确实覆盖不了或用起来不合适的，写清楚为什么再自研（见 §2）；
- **复用优先**：复用现有 `chat_service` / `memory_store` / `rag_service` / `oag_service`，不重建检索与记忆；
- **降级可用**：任一环节失败退化为单智能体直答，协作链路永不阻塞主问答；
- **过程透明**：协作全过程可观测、可回放（复用 OAG「先过程后答案」的前端契约）。

## 2. 框架选型：优先直接用框架，不用/不好用的明说

### 2.1 选型原则

**能用现成框架就直接用**；只有框架确实覆盖不了、或引入成本大于收益时才自研，
且必须写清楚为什么。不为"显得懂原理"而自研，也不为"省事"而硬套不合适的框架。

### 2.2 逐个评估（结论先行）

**LangGraph —— 直接采用 ✅（本设计的主编排框架）**

| JD 要的机制 | LangGraph 内建能力 | 自研替代要写的东西 |
|---|---|---|
| 任务分解与编排 | `StateGraph` 显式状态图 + 条件边 + **`Send` API**（运行时动态 fan-out/fan-in，同角色 n 个并行实例） | 自研拓扑调度器 + 并行分组 + fan-in 汇聚 |
| 断点恢复 | `checkpointer`（AsyncSqliteSaver，正好配项目 SQLite）每超步自动快照，同 thread_id 续跑 | 自研节点状态机落库 + 恢复扫描 |
| 人审挂起/恢复 | `interrupt()` 暂停 + `Command(resume=...)` 恢复 | 自研挂起/唤醒协议 |
| 节点重试 | `RetryPolicy` 内建 | 自研 retry 装饰器 |
| 可观测 | `astream_events` 结构化吐出节点级事件（开始/结束/token） | 自研事件总线 |
| 多轮辩论 | 回边（循环边）+ `recursion_limit` | 自研轮次控制 |

且与项目**同源**：项目已基于 LangChain providers 体系，LangGraph 是 LangChain 生态官方编排层，
消息对象（HumanMessage/AIMessage）、模型接入（ChatOpenAI）、工具协议全部复用，引入零胶水。

**AutoGen —— 不用 ❌（源码级理由）**

1. 旧版 `GroupChat` auto 模式：`GroupChatManager` 把各 Agent 的简介拼成 prompt 让 LLM 选下一个
   发言人——轮数不可控、token 成本不可预算、错误选人会带偏整场；我们要的是显式 DAG 依赖调度；
2. 0.4 重写的 actor 模型（`AgentRuntime` 单例 + 主题广播）与 LangGraph 功能整体重叠，
   为用它的广播再引第二套运行时不值得；
3. 自带消息模型与项目 LangChain 消息体系不同源，胶水层成本实打实。

**MetaGPT —— 不用 ❌**：SOP 流水线范式为软件开发场景固化，本体/知识问答领域迁移成本高；
黑板（Environment）无版本管理，断点恢复需自建。

**AgentScope —— 不用 ❌**：显式 `Msg` 传参与内建 retry/fallback 设计不错，但与 LangChain 栈
不同源；其收益（显式、容错）LangGraph + RetryPolicy 已覆盖，没有切换理由。

**Camel —— 不用 ❌**：AI User × AI Assistant 成对角色扮演，研究向；Workforce 只做单层任务分解，
多角色团队编排能力弱。

**A2A / MCP —— 暂不引入（留观察）**：A2A 是跨系统/跨厂商 Agent 互联协议，本项目所有 Agent
同进程同团队，用不上这个重量级；未来若要把智能体能力对外暴露成标准工具服务，可对齐 MCP。

### 2.3 LangGraph"用了不好"的诚实预警（坑与对策）

用框架不等于闭眼用。以下是已知的坑，逐条给出对策；哪天触发了升级条件，按 §2.4 预留的边界换方案：

| 坑 | 影响 | 对策 |
|---|---|---|
| `SqliteSaver` 单写者并发限制 | 多 worker 水平扩展时 checkpoint 写冲突 | P1/P2 单进程部署无影响；P3 多 worker 换 `AsyncPostgresSaver`（接口不变，换配置） |
| 图结构编译期固定 | 运行时不能增删**节点类型** | 用 `Send` 做同角色多实例（重规划=加实例+改路由，够用）；真需要运行时变图结构，再评估 AutoGen 0.4 runtime 或自研 |
| 共享 State 全局可变 | 节点间隐性耦合、调试困难 | 纪律：节点只写自己的 key（`Annotated` reducer 隔离）；Schema 集中定义 + code review 把关 |
| 版本升级有破坏性变更史 | 0.0.x → 0.2 期间 API 变过多次 | 锁定版本（pyproject 钉死）；包一层薄 `graph_factory` 适配模块，业务节点代码不直接散落框架 API，升级只改一处 |
| 图执行调用栈深，报错不直观 | 排查成本高 | `langgraph dev` Studio 可视化调试 + `astream_events` 全量落库回放（§9） |

### 2.4 用框架与自研的边界（最终结论）

| 模块 | 决定 | 理由 |
|---|---|---|
| 编排 / 调度 / 并行 fan-out | **用 LangGraph** | StateGraph + Send + 条件边完整覆盖 |
| 断点恢复 / 人审挂起 | **用 LangGraph** | checkpointer + interrupt 原生 |
| 节点重试 / 事件流 | **用 LangGraph** | RetryPolicy / astream_events |
| Agent 间"黑板" | **用 LangGraph 共享 State** | State + reducer 本质就是黑板模式，不再自建消息总线 |
| 旁路后台任务（长期记忆异步写入、审计） | **薄自研**（asyncio.Queue，几十行） | LangGraph 只管图内执行，图外异步任务它不管 |
| 角色运行时（把现有 oag/rag/图谱能力包成节点） | **自研**（任何框架都绕不开的业务胶水） | 这部分本来就是项目私有逻辑 |
| 证据卡 / claim 卡 schema + 五步冲突消解 | **自研**（领域核心逻辑） | 没有任何框架替你定义"你的证据谁可信" |
| SSE 协作事件协议 | **自研**（对齐前端既有契约） | 复用 OAG「先过程后答案」模式，astream_events 做数据源 |

一句话：**框架管"怎么跑"（编排/状态/恢复），我们写"跑什么"（角色能力/冲突消解/证据契约）。
自研的部分从原来估的几百行编排代码，缩减为纯业务代码。**

## 3. 总体架构

```
接入层      POST /api/chat/multi-agent (SSE)   /api/agent-teams CRUD
   │
编排层      LangGraph StateGraph（框架，不自研调度器）★
   │         ├─ planner 节点       任务分解 → 子任务清单（schema 校验）
   │         ├─ Send 动态分发      同角色多实例并行（fan-out / fan-in）
   │         ├─ 条件边路由         依赖就绪判定 / fallback 分支 / 简单问题直答
   │         ├─ checkpointer       每超步快照（AsyncSqliteSaver → P3 换 Postgres）
   │         ├─ interrupt          人审挂起 / Command(resume) 恢复
   │         └─ RetryPolicy        节点级重试（内建）
   │
智能体节点   六类角色节点（自研业务胶水，全部复用现有能力）
   │         planner │ retriever │ graph_agent │ executor │ critic │ synthesizer
   │         （Retriever=现有三路融合检索；GraphAgent=现有图谱事实注入；
   │           Executor=oag_service 单智能体全能力；Critic=冲突消解子图 §6）
   │
通信模型     主链路：共享 State 即黑板（Annotated reducer 合并并行写入）
   │           + astream_events 事件流 → SSE（前端"先过程后答案"契约）
   │         旁路：asyncio.Queue 后台任务队列（长期记忆异步写入、审计落库）
   │
记忆层      L1 Agent 私有短期（窗口+摘要）   L2 任务共享 State + 轻量黑板表（导出副本）
   │         L3 团队长期（mem0 team 命名空间） L4 用户×智能体长期（现有 mem0 不变）
   │
支撑层      SQLite(任务/黑板导出/事件trace) + Milvus(记忆) + 图谱库 + monitor/audit
```

**关键取舍**：编排不写调度器——并行、路由、重试、快照、恢复全部交给 LangGraph；
我们写的代码集中在两类：①把现有单智能体能力包成角色节点（胶水）；
②冲突消解子图与证据卡 schema（领域逻辑）。
`Retriever` 内部就是现有三路融合检索，`GraphAgent` 内部就是现有图谱事实注入。
**多智能体是编排方式的升级，不是检索/记忆的重写。**

> 具体放到哪个模块、界面长什么样、用户怎么用、为什么不违和——见 §13。

## 4. Agent 间通信机制（主链路交给框架，旁路薄自研）

> 重新评估后的变化：不再自研 MessageBus 消息总线。LangGraph 的共享 State 本质就是黑板模式，
> Agent 间"发消息"被"更新共享状态 + 事件流"取代——这正是黑板架构对消息传递的简化。

### 4.1 主链路：共享 State 即黑板（LangGraph 原生）

所有节点读写同一个 TypedDict State，并行写入用 `Annotated` reducer 声明合并策略：

```python
from typing import Annotated, TypedDict
import operator

class TeamState(TypedDict):
    goal: str                                   # 用户目标（入口写入）
    plan: list[SubTask]                         # planner 写：分解结果
    evidence: Annotated[list[EvidenceCard], operator.add]   # 各检索节点追加，并行安全
    claims:   Annotated[list[ClaimCard], operator.add]      # critic 写
    conflicts: Annotated[list[Conflict], operator.add]
    answer: str                                 # synthesizer 写（流式聚合）
    missing:  Annotated[list[str], operator.add]  # fallback=skip 的缺证声明
    replan_count: int                           # 重规划计数（上限控制）
```

- 并行检索节点各自向 `evidence` 追加，reducer（`operator.add`）自动合并——
  **"多个 Agent 同时写"的竞争问题在框架层面就不存在**；
- 节点只写自己的 key、只读依赖节点的 key——**读写边界即通信协议**；
- trace/correlation 需求由 LangGraph 的 `thread_id` / `run_id` / config 承载，不自建信封字段。

### 4.2 执行事件流：astream_events → SSE

`astream_events(version="v2")` 把图执行的结构化事件全部吐出，直接映射前端既有契约：

| 框架事件 | 映射 SSE 事件 |
|---|---|
| `on_chain_start`（节点名） | `node_start` |
| `on_chat_model_stream`（token 块） | `node_delta` |
| `on_chain_end`（节点输出摘要） | `node_done` |
| State 中 conflicts 变化（自定义订阅） | `conflict` |
| planner 节点输出 | `plan` |

不自研事件广播总线——框架事件流就是消息通道，我们只写一个订阅器做"事件 → SSE + 落库"的转发。

### 4.3 旁路：后台任务队列（唯一薄自研的通信件）

长期记忆异步写入（mem0）、审计落库这类**低优先级任务不进图**（避免拖慢主链路）：
进程内 `asyncio.Queue` + 消费者协程，信封只需 `task_type + payload + trace_id` 三个字段，
消费失败重试 2 次后落 dead 表由 monitor 告警。

- 为什么自研这一小块：LangGraph 只管图内执行，图外异步任务它不管；
- 为什么不用 Redis/NATS：当前是单进程部署，`asyncio.Queue` 够用；将来多 worker
  只换这一个类的实现（几十行），不影响主链路——**框架管主链路，自研只补框架的空隙**。

### 4.4 通信开销优化（JD 关注点，措施不变、载体更新）

1. **State 传结构化小对象**：Agent 间只传证据卡/claim 卡（结构化摘要），不传全文对话；
   对话史留在各节点私有 L1 记忆，跨节点只见结论；
2. **大产物引用化**：完整检索结果集/子图不进 State（会膨胀 checkpoint）——State 放摘要卡，
   原始数据由下游节点按需自取（重查或读黑板导出表）；
3. **定向注入**：编排时只把依赖节点的 key 注入下游 prompt，不做全员广播；
4. **主旁路隔离**：后台任务走旁路队列慢消费，不阻塞首字延迟。

## 5. 角色定义与任务分解编排

### 5.1 角色清单（团队 = 角色 × 绑定的现有智能体配置）

| 角色 | 职责 | 绑定的现有能力 | 模型分级 |
|---|---|---|---|
| Planner | 问题理解 → 任务分解 → 产出 DAG；失败时重规划 | LLM + 会话历史 | 小模型（快） |
| Retriever | 向量/BM25 检索取证，产出证据卡 | `rag_service` | 纯检索，零 LLM |
| GraphAgent | 图谱多跳分析、路径解释，产出事实卡 | 图谱 provider（只读） | 小模型 |
| Executor | 需要生成/计算的子任务执行 | `oag_service` 单智能体全能力 | 大模型 |
| Critic | 证据交叉验证、claim 冲突检测 | LLM + 证据卡比对 | 大模型（判得准） |
| Synthesizer | 消解后合成最终答案，SSE 流式 | LLM + 引用规范（复用 [来源N]/[事实]） | 大模型 |

### 5.2 任务分解：Planner 产出结构化 DAG

Planner 的输出**不是自由文本，是过 schema 校验的 JSON DAG**（校验失败自动重试一次）：

```jsonc
{
  "goal": "对比A、B两个机型的放行标准差异并给出风险提示",
  "nodes": [
    {"id": "n1", "role": "retriever", "goal": "检索A机型放行标准",
     "depends_on": [], "retry": 1, "timeout_s": 30, "fallback": "skip"},
    {"id": "n2", "role": "retriever", "goal": "检索B机型放行标准",
     "depends_on": [], "retry": 1, "timeout_s": 30, "fallback": "skip"},
    {"id": "n3", "role": "graph", "goal": "查询两机型标准相关图谱子图",
     "depends_on": [], "retry": 1, "timeout_s": 30, "fallback": "skip"},
    {"id": "n4", "role": "critic", "goal": "对比证据差异与矛盾点",
     "depends_on": ["n1", "n2", "n3"], "retry": 1, "fallback": "degrade"},
    {"id": "n5", "role": "synthesizer", "goal": "合成答案",
     "depends_on": ["n4"], "retry": 0, "fallback": "degrade"}
  ],
  "constraints": {"max_nodes": 8, "max_parallel": 3, "budget_tokens": 30000}
}
```

**分解三步**：依赖分析（可并行子任务拆开）→ 角色匹配（goal 语义路由到角色）→ 约束收敛
（节点数/并行度/token 预算钳制，防止 Planner 过度分解——显式预算是对"LLM 自由轮转失控"的防线）。

### 5.3 调度：并行、重试、快照全部交给 LangGraph（不自研状态机）

| 原需求 | LangGraph 实现 |
|---|---|
| 拓扑序调度 / fan-out 并行 | 图编译时按 `depends_on` 建边；planner 节点用 `Send("retriever", subtask)` 对 n 个子任务发 n 个并行实例，图自动 fan-in 汇聚到 critic |
| `max_parallel` 限流 | Send 前按 constraints 分批，或节点函数内包 `asyncio.Semaphore` |
| 节点重试 | `RunnableConfig` 挂 `RetryPolicy(retry_on=..., max_attempts=2)`，内建 |
| fallback=skip | 节点内 try/except：返回空证据卡 + 向 `missing` 写缺证声明，下游被告知 |
| fallback=degrade | except 分支切换大模型直答实现 |
| fallback=abort | 抛出让图失败 → 条件边路由 planner 重规划或整体降级 |
| 节点状态落库 | **不需要自建 task_nodes 表**：checkpointer 每超步自动快照全部节点状态 |
| 断点恢复 | 同 `thread_id` 重新 invoke，从最后 checkpoint 续跑，已完成节点不重跑——"中断任务后恢复"框架原生 |

框架能力边界（诚实说明）：图的**节点类型**（六种角色）是编译期固定的；运行期动态的是**实例**
——`Send` 决定给某角色发几个、发什么。我们的"重规划"只是加实例、改路由，
不需要运行时增删节点类型，所以框架边界覆盖得住（见 §2.3 预警表）。

### 5.4 动态重规划：条件边回 planner + Send 增量补发

触发条件（任一）：① 关键节点 abort；② Critic 发现证据缺口（"缺少 C 机型标准，无法对比"）；
③ 中途发现复杂度超预期（需三跳图谱查询）。

实现：节点把 `replan_hint` 写进 State → 条件边读到后路由回 planner 节点 →
planner 从 State 读已有证据卡（checkpointer 保留，已完成的不丢），只对缺口
`Send` **增量补发**新子任务 → 汇聚继续。`State.replan_count` 计数，**上限 2 次**，
超过走整体降级单智能体直答（防死循环、防成本失控）。
不需要自研"回传/合并执行"流程——State 与 checkpointer 天然承载。

### 5.5 Human-in-the-loop：interrupt 原生

高风险动作（本体写入、图谱清理等）前调 `interrupt(payload)`：图暂停、状态已快照；
复用现有 `human_task_service` 做人审任务分发与前端通知；人审完成后
`Command(resume=decision)` 恢复执行，decision 进图继续流转。
断线重连按 `thread_id` 续看——挂起/恢复机制框架原生，不自研。

## 6. 冲突消解机制

按发生层次分三类，**每类用不同手段**——这是设计核心，不混为一谈：

### 6.1 目标冲突（规划层）

多 Agent 子目标互相牵制（如"尽量多召回" vs "控制 token 预算"）。
手段：目标冲突在 Planner 单点显式化——约束全部写进 DAG 的 `constraints`，Planner 消解后才下发。
**运行时 Agent 无权改目标**，只能通过 `replan_hint` 申请改规划。单点决策，避免分布式扯皮。

### 6.2 资源竞争（执行层）

共享写资源：图谱（本体写入）、记忆库（mem0 写入）、黑板导出表。

- **State（黑板）**：并行写竞争已被 reducer 在框架层消解（各节点只写自己的 key，
  `operator.add` 追加合并）；对同一 key 的"改写"（非追加）场景才需要协调——
  节点粒度天然串行（LangGraph 超步间顺序提交），不额外加锁；
- **黑板导出表**：任务结束时单写者导出，无并发写，不需要乐观锁；
- **图谱/记忆写**：按资源 key 的进程内异步锁串行化（P3 多 worker 换分布式锁），写操作走旁路队列削峰；
- **幂等**：mem0 写入已有去重判决；节点重试以 checkpoint 边界为准，重跑节点副作用需幂等
  （写操作带 `thread_id+node_id` 幂等键）。

### 6.3 结果冲突（内容层，重点）

多个 Agent 产出的**事实性结论互相矛盾**（如 Retriever 的文档证据 vs GraphAgent 的图谱事实）。
消解五步，**优先级从硬到软**：

```
① 证据分级（确定性规则，非 LLM）
   图谱事实 > 带明确出处的文档片段 > 模型自身知识
   （复用 OAG 既有原则"图谱事实结构化可信优先采信"——项目已验证的规则升级为协议）
② Claim 结构化对齐（代码）
   各 Agent 产出拆成 claim 卡：{subject, predicate, object, source, confidence, evidence_ref}
   代码按 subject+predicate 归组，只有同主同谓不同宾才构成冲突——避免 LLM 泛化误判
③ LLM 裁判（ConflictResolver 的一次调用）
   冲突组 + 全部证据卡 → 单次 LLM 调用输出裁决：采信方/理由/是否需补证
   （与 mem0 写入判决同构：检索圈定候选 → LLM 语义判决 → 代码确定性执行）
④ 辩论收敛（高价值场景才启用，轮次≤2）
   实现：LangGraph 回边（critic ⇄ executor 循环边，recursion_limit=2 控制轮次）
   ——这就是 AutoGen GroupChat 多轮对话的受控版：轮次上限由框架参数钳死，
   不靠 LLM 自由轮转；仍不一致则按置信度加权取优并标注分歧
⑤ 人审兜底
   置信度低 + 高风险动作 → interrupt() 挂起交人（§5.5）
```

**消解时机**：与记忆写入时消解一致的取舍——**合成前消解**（Synthesizer 只消费已消解的证据集），
不把矛盾原文全塞给最终 LLM 碰运气；同时保留 prompt 层兜底：低置信度分歧以
「存在不一致记载」显式标注进答案，由用户判断（呼应现有记忆系统"两道防线"的设计哲学）。

## 7. 分层记忆体系（复用现有 + 最小扩展）

| 层 | 名称 | 载体 | 作用域 | 复用/新增 |
|---|---|---|---|---|
| L1 | Agent 私有短期记忆 | 现有 `chat_messages` + 滚动摘要 | 单 Agent 会话内（窗口+预算+摘要） | **复用** `chat_service` 原逻辑 |
| L2 | 任务共享记忆（黑板） | LangGraph 共享 State + checkpointer；查询用轻量导出表 | 单次任务全团队读写 | **框架承载**（State 即黑板） |
| L3 | 团队长期记忆 | mem0，命名空间 `user:{uid}:team:{team_id}` | 跨任务、同团队共享 | **扩展**命名空间 |
| L4 | 用户×智能体长期记忆 | mem0，命名空间 `user:{uid}:agent:{aid}` | 单用户单智能体 | **复用现有不变** |

### 7.1 L2 任务黑板：State 承载运行时，导出表承载查询

- **运行时**：共享记忆就是 LangGraph State（§4.1）+ checkpointer 快照——黑板模式框架已实现，
  断点恢复、冲突对齐、节点间传递全部从 State 读，单一事实源，不自建黑板总线；
- **查询/回放**：checkpointer 是序列化 blob，不便 SQL 查询。任务结束时把关键产物
  （plan / 证据卡 / claim 卡 / conflicts）从 State **导出**到轻量表，供任务详情页与审计：

```sql
CREATE TABLE agent_blackboard (
  id          TEXT PRIMARY KEY,
  task_id     TEXT NOT NULL,              -- 所属任务 = LangGraph thread_id
  key         TEXT NOT NULL,              -- 如 "plan" / "n1.evidence" / "claims"
  value       TEXT NOT NULL,              -- JSON 导出副本
  writer      TEXT NOT NULL,              -- 产出 agent 角色（可追溯）
  updated_at  TEXT NOT NULL,
  UNIQUE(task_id, key)
);
```

- **生命周期与任务绑定**：导出记录保留 N 天供回放，之后归档清理（可观测性数据源之一）；
- **为什么不互发消息而共享 State**：消息瞬态易丢，共享状态持久可回放——这个黑板架构的经典论断
  在 LangGraph 里直接成立，不需要自己实现黑板基础设施。

### 7.2 隔离矩阵（安全边界）

| 记忆 | 谁可读 | 谁可写 |
|---|---|---|
| L1 私有短期 | 该 Agent 本人 | 该 Agent 本人 |
| L2 任务 State | 同任务全部节点 + 编排（读） | 各节点只写自己的 key（reducer 合并） |
| L3 团队长期 | 同团队同用户 | 团队写入管道（消解判决后） |
| L4 个人长期 | 该用户该智能体 | 现有 mem0 管道 |

- 团队记忆不落用户隐私（用户偏好仍走 L4），只沉淀团队级事实（术语表、领域结论、流程约定）；
- 写入 L3 前过**同一条消解管线**（向量圈候选 → LLM 判 ADD/UPDATE/DELETE/NONE → 代码执行），
  多个 Agent 对同一事实的写入天然收敛为一份不矛盾版本——
  **冲突消解与记忆治理共用一套判决机制**。

## 8. 可靠性与性能设计

### 8.1 可靠性（每个环节都有退路）

| 故障 | 防线 | 最终降级 |
|---|---|---|
| 某检索 Agent 失败/超时 | RetryPolicy（内建）+ 超时 | fallback=skip，向 State.missing 写缺证声明，答案中告知用户 |
| Critic 失败 | RetryPolicy | fallback=degrade：跳过验证，提示 Synthesizer 降低断言语气 |
| Planner 产出非法任务清单 | schema 校验 + 重试 1 次 | 退化为固定流水线模板（检索/图谱并行 → 汇总） |
| 整条协作链路异常 | 服务层 try | **单智能体直答**（现有 OAG 链路原样兜底） |
| 进程崩溃 | checkpointer 自动快照 | 同 thread_id 重新 invoke，从最后 checkpoint 续跑，已完成节点不重跑 |
| 旁路队列堆积 | 有界队列 + 失败落 dead 表 | monitor 告警，不影响主链路 |

### 8.2 性能（优化执行效率、降低推理延迟）

1. **并行**：`Send` 动态 fan-out 并行子任务，`max_parallel` 限流防 LLM 并发打满配额；
2. **模型分级**（成本与延迟双优化）：Planner/Critic 摘要用小模型，最终合成才用大模型；纯检索节点零 LLM；
3. **预算前置**：constraints 里 token 预算钳制，Planner 分解时就控住总成本（而不是跑超了再拦）；
4. **首字延迟优化**：SSE 不等全图完成——`plan` 事件先发（用户立刻看到任务图），
   astream_events 转发的 `node_start/delta/done` 实时推送（复用 OAG"先过程后答案"契约）；
5. **缓存**：检索结果按 (kb_id, query 哈希) 短 TTL 缓存；同会话重问命中直接复用证据卡。

## 9. 可观测性体系

### 9.1 全链路 Trace

- `trace_id` 从用户请求进入时生成，映射 LangGraph `thread_id`，贯穿：图执行 → 节点 → LLM 调用 → SSE 事件 → 日志；
- 每个 LLM 调用一个 span：
  `{trace_id, node_id, agent_role, model, prompt_tokens, completion_tokens, latency_ms, cost, status}`。

### 9.2 落库与回放

```sql
-- 数据源：一个 astream_events 订阅器（框架事件 → 本表 + SSE 转发，唯一的自研采集点）
CREATE TABLE multi_agent_messages (
  id TEXT PRIMARY KEY, trace_id TEXT, task_id TEXT,
  node_id TEXT, role TEXT, event TEXT,     -- node_start/node_delta/node_done/conflict
  payload_summary TEXT,               -- 摘要全文，大产物指向黑板导出表
  latency_ms INTEGER, status TEXT, created_at TEXT
);
CREATE INDEX idx_ma_msg_trace ON multi_agent_messages(trace_id);
```

- 任务详情页按 `trace_id` 回放完整协作过程（时序图：哪个节点何时做了什么、耗时多少）；
- 复用 `monitor_service` 暴露指标：任务成功率、平均节点时延、重规划率、冲突率、
  各角色 token 消耗占比、降级触发次数——**降级率突增即为系统健康告警信号**。

### 9.3 前端协作可视化

复用 OAG 既有模式：SSE 先推 `plan`（任务图）→ 节点级状态实时点亮 → 冲突/消解过程展示 →
最后流式答案。用户看到的不只是答案，是**可解释的协作过程**——这也是产品差异化。

```
├──────────────┬─────────────────────────────────────────────────┤

│              │  └─────────────────────────────────────────────┘ │

├──────────────┴─────────────────────────────────────────────────┤
│ [输入框…                                             ] [发送]   │
└────────────────────────────────────────────────────────────────┘
```

**SSE 事件协议：新增 5 个 type，其余全部复用现有契约**（`oag_service` 现有
`skills/entities/subgraph/chunks/token/reasoning` 原样不动）：

| SSE type | 来源 | 前端渲染 | 与现状关系 |
|---|---|---|---|
| `team` | 团队元信息 | 面板标题（团队名/成员） | 新增，形态类似现有 `skills` |
| `plan` | planner 节点 | 任务分解卡（子任务+依赖） | 新增（"先过程"的协作版） |
| `node_start`/`node_done` | astream_events 转发 | 节点卡片状态流转（灰→转圈→✓） | 新增 |
| `conflict` | critic 节点 | 冲突卡（双方证据+消解结论） | 新增 |
| `missing` | fallback=skip 节点 | 答案区"缺证声明"提示条 | 新增（可并入 conflict） |
| `token`/`reasoning` | synthesizer 流式输出 | **复用现有渲染，不变** | 现有 |
| `entities`/`subgraph`/`chunks` | 检索/图谱节点产出 | **复用现有富面板，不变** | 现有 |

关键：**答案本身的流式输出与引用协议完全不变**——用户看到的答案区和单智能体一模一样，
只是"过程区"从单个思考块变成了协作时间线。

### 13.3 使用流程（三类角色）

**管理员（一次性配置）**：
1. 智能体配置页照常建 2~4 个专用智能体（如"标准文献研究员""图谱审计员"）——现有功能，无新概念；
2. `/agent/teams` 新建团队：从现有智能体挑成员、绑定六角色、选编排模板
   （预置"研究团队"模板开箱即用）、设 token 预算与重规划上限；
3. 权限沿用 `agent:view` 族，新增 `agent:team:manage` 控制团队配置权。

**终端用户（零学习成本）**：
1. 对话页智能体下拉选"研究团队"——和选普通智能体是**同一个下拉、同一个交互**；
2. 提问 → 过程区实时看到任务分解/并行节点/冲突标注 → 答案带引用；
3. 简单问题（"XX 是什么"）条件边直接单步直答，过程区只显示一行"单步直答"——协作噪音不打扰日常问答。

**审批人**：团队建议写入本体等高风险动作 → `/human-tasks` 待办中心照常审批，
与现有工作流人审完全同一体验。

### 13.4 为什么不违和：四条论证

1. **业务真实性（不是技术找场景）**：本平台的真实痛点是**跨源口径不一致**——
   文档 A、文档 B、图谱三方对同一属性说法不一。这正是现有 `/graph-cleanup`、
   `/ontology/suggestions` 在治理的问题的**问答侧形态**：治理是"改数据"，多智能体是"答问题时把分歧摆清楚"。
   证据分级（图谱事实 > 有出处文档 > 模型知识）就是本平台的领域规则。没有图谱和知识库，
   这套多智能体就没有灵魂——它只能长在这个系统里，搬到别的项目反而不成立。
2. **入口即升级，不是新大陆**：用户视角只是"智能体下拉里多了一个选项"，答案区渲染协议不变。
   P1 上线甚至可以不开协作面板——用户唯一感知是"复杂问题答得更好了"。
3. **成员即现有资产**：团队成员不是新造的 Agent，是现有智能体配置的重新组合——
   配置、技能、人设、记忆全部沿用。团队之于智能体，就像技能分组之于技能。
4. **渐进可见，随时可退**：团队任一环节失败/超预算自动降级单智能体直答（§8.1）——
   最坏情况退化回今天的系统，主链路零风险。**表演型功能挂了很扎眼，融合型功能挂了无感**，
   这是"功能融合"与"功能表演"的分界线。

## 14. 场景落地：航班运行监控（业务底稿：《G 航空公司航班运行风险管理研究》）

> 论文方法链：**风险识别**（人机环 + SHEL 模型 → 风险事件清单）→ **风险评估**（贝叶斯网络建模条件依赖 + 敏感度分析找关键节点）→ **风险控制**（Drools 规则引擎告警：单条件/组合条件 → 低/中/高三级响应、自动升级）→ **效果验证**（混淆矩阵 + ROC：38376 架次，召回率 0.60→0.96，F1 0.61→0.81）。
> 多智能体在这条链上的位置一句话说清：**规则引擎管"发现"（快、准、召回高），多智能体管"研判"（跨源取证、冲突消解、解释留痕）**。不是替代论文的 Drools，是接在它告警之后的"大脑"。

### 14.1 痛点即入口：论文数据已经把需求算出来了

论文 §5.4 的对比实验（人工监控 vs 规则引擎，2025 年 1 月 38376 架次）给出两个关键数字：

| 指标 | 人工监控 | 规则引擎 | 含义 |
|---|---|---|---|
| 召回率 | 0.60 | **0.96** | 引擎几乎不漏报（FN 8792→879），"发现"环节已被解决 |
| 精准率 | 0.63 | 0.70 | 仍有 **8923 起误报（FP）**，每起都要运行控制人员人工核查 |
| F1 | 0.61 | 0.81 | 缺口不在"发现"，在**研判** |

这就是多智能体的切入口，对应四个具体痛点：

| 痛点 | 论文中的表现 | 为什么单智能体顶不住 | 多智能体解法（对应章节） |
|---|---|---|---|
| 数据多源异构 | 航班动态、气象、机组资质/时限、机场保障、运行手册分属不同系统 | 一个上下文装不下，全量检索稀释注意力 | Retriever 并行分域取证（§5.1） |
| 研判要跨源比对 | 气象源/动态源/历史处置口径常不一致，值班记录与规则结论打架 | 单模型"听最后看到的"，没有裁定规则 | GraphAgent 事实卡 + Critic 证据分级五步消解（§6） |
| 写入要留痕可追责 | 高风险需上报主管部门、处置录入运行日志 | 模型直接写库不可接受 | Executor 起草 + interrupt 人审（§5.5） |
| 过程要可见可交接 | 低/中/高对应不同牵头部门（首响岗位→主责部门→总值班室），中风险 5min、高风险 3min 响应时限 | 黑盒答案跨部门不认账，交接断片 | SSE 协作时间线（§13.2）+ checkpointer 断点恢复（§8） |

### 14.2 六角色对论文四环节的映射

| 论文环节 | 团队角色 | 场景中的具体工作 |
|---|---|---|
| 风险识别（信息汇聚） | Planner → Retriever | 分解监控问题；并行拉气象实况/报文、机组资质与飞行时限、SHEL 风险事件清单、运行手册条款 |
| 风险评估（结构化事实） | GraphAgent | 查"航班-机组-机场-风险事件"本体子图：谁执飞、时限余量、历史同类事件与处置结论 |
| 风险控制（研判与裁定） | Critic | 证据分级（图谱事实 > 有出处文档 > 模型知识），五步冲突消解，分歧标记人审 |
| 分级响应（建议产出） | Synthesizer | 按论文三级响应制度生成处置建议：维持跟踪 / 升级中风险 / 升级高风险 + 引用 + 响应时限提示 |
| 复盘归档（写入） | Executor | 风险事件/复核结论起草成图谱节点，人审通过后写入本体 |

团队配置沿用 §13 机制：建两个团队——**告警研判团队**（只读，问答流水线）与**事件归档团队**（带人审的写流程）；班后复盘可复用全链路编排。

### 14.3 场景一：组合告警复核（最高频，直接对着 FP 象限讲故事）

**触发**：Drools 命中组合规则（如"晚关门 + 雷雨/流控"双条件告警，论文图 5.8），告警卡片推送至席位。值班员不想只看"触发了"，想知道"要不要升级"——点告警卡片上的 **AI 复核**，进入团队会话。

**流水线走查**：

```
planner: 拆 4 个子任务（航班动态现状 / 气象实况与趋势 / 机组时限余量 / 历史同类处置）
  ├─ retriever ×3 并行: 气象报文 · 运行手册条款 · SHEL 风险事件清单     ← Send fan-out
  ├─ graph: 航班/机组/历史风险事件本体子图
  ├─ critic: 气象源口径冲突（场面观测 vs 航路预报）→ 按证据分级裁定，存疑项标"需人核"
  └─ synthesizer: 结论 + 引用 + 建议动作（维持跟踪 / 升级中风险 / 升级高风险 + 时限提示）
```

**界面呈现**：聊天区出结论卡（建议 + [来源N]/[事实] 引用），右侧协作时间线出 `team/plan/node_start/node_done/conflict` 事件流（§13.2 协议，全部走现有 SSE 通道，不加新通道）。

**数据来源（真实数据优先）**：取证不再用内置演示数据，目标卡逐条标注来源徽标——
- **ops（航班动态）**：实体库真实航段实体（SOBT/AOBT/ETA/SIBT 实算延误）+「衔接前序」真实关系；
- **rule（规则阈值）**：告警规则资产实体（threshold_low/mid/high、牵头部门）+ 运行告警触发记录；
- **resource（机组与机队）**：「由机组执飞 / 执飞航空器」真实关系 + `is_crew_changed` 属性；
- **weather（气象）**：平台暂未接入气象源，按约定**生成补充证据卡**，分级降为 `model_knowledge` 并显著标注「模拟生成」；
- **数据量保障**：真实组合告警不足 3 条时，按规则实体阈值为真实活跃航段（登机晚点≥15min / 巡航到达延误≥10min）生成补充告警——结构与人审入库完全一致、`ALR-GEN` 前缀幂等、真实写回实体库（`services/multi_agent/flight_store.py`）；平台完全无数据才回落内置演示告警。

**价值锚点**：论文 FP = 8923 起，每起人工核查约 5–10 分钟。多智能体不承诺消灭误报，承诺把每起复核从"翻 4 个系统"变成"看一张有引用的结论卡"——这是能拿数字讲的故事。

### 14.4 场景二：跨源口径冲突消解（Critic 主场，论文"阈值可修订"的问答侧形态）

**提问**："XX1234 晚关门已 25 分钟未解除，按制度该升级中风险吗？"

三方证据天然打架：

- **图谱事实卡**：近一年同类事件 80% 在 20–30min 未解除时升级为中风险（历史处置统计）
- **手册文档卡**：告警规则"低风险持续 20–30min 未解除 → 升级中风险"（论文图 5.9 原规则）
- **值班记录**：当时已提前协调机坪保障、旅客开始登机，值班员判断无需升级

Critic 五步消解（§6）：识别冲突 → 列证据卡 → 硬规则裁定（图谱事实与手册规则同向 → 建议升级）→ 值班记录作为**新近人工事实**不能被规则覆盖，标"存在例外，需人裁" → 输出对比表 + 双结论（按制度应升级 / 如维持需记录豁免理由）。

**为什么贴合论文**：论文明确告警阈值需按季节修订（冬季"晚关门"放宽、夏季"超时未落"收紧）——规则改了，但历史图谱里的处置事实不变。**规则管当下，图谱管历史，Critic 管两者打架时谁说了算**。这正是把 `/ontology/suggestions` 的治理思想搬到问答侧。

### 14.5 场景三：风险事件归档写入本体（写操作必须过人审）

**触发**：高风险告警（如"超时未落"）处置完毕（论文表 5.2：联系空管、评估备降、必要时启动公司级应急响应、向主管部门报告），值班经理说："把这起归档。"

1. Planner 识别为**写操作** → 切到事件归档团队；
2. Executor 起草事件节点：航班、触发条件、时间线、处置动作、引用来源，产出**待写 diff**（不直接落库）；
3. LangGraph interrupt 挂起（§5.5）→ 签派员在**现有任务中心**审批（复用 human_task 与 `/human-tasks`，零新交互）；
4. 通过后写入 Kuzu 本体；驳回则带批注退回重起草。

**飞轮**：归档越多 → GraphAgent 查"历史同类事件"越准 → 场景一/二的研判越有底气。写入受控 + 数据反哺，是"功能融合"而非"功能表演"的实证。

### 14.6 场景四（简）：3 分钟时限与断点恢复

论文要求高风险告警 **3min 内响应**、处置跨多部门持续数十分钟——这种会话最怕中途断线从头再来。checkpointer 按 thread_id 持久化每步 State（§8）：复核会话断线后重开，从最近 checkpoint 继续；处置结论存疑时可时间旅行回 planner 的分解步骤，换一种拆法重跑未完成节点，已完成产物不重算。

### 14.7 克制：哪些监控场景明确不用多智能体

| 场景 | 处理方式 | 理由 |
|---|---|---|
| 单条件低风险告警（SOBT 超 10min 未关舱门） | 规则引擎已给结论，条件边路由单智能体直答 | 多智能体是能力上限，不是所有告警的必经之路 |
| 纯阈值判断（"超时 35 分钟算什么等级"） | 查表即答 | LLM 参与只增加延迟与成本 |
| 无图谱/无知识库数据源 | 退化为单智能体直答（§8.1 降级矩阵） | 没有证据分级，多智能体失去灵魂 |

一句话边界：**规则引擎负责"快"，多智能体负责"难"——组合告警、跨源冲突、写入留痕才进团队流程。**

### 14.8 面试讲法

**一段话版本**：
> 论文里规则引擎把风险识别召回率从 0.60 提到 0.96，但留下 8923 起误报要人工核查；研判要跨气象、动态、资质、手册多源取证，口径还经常打架。我做的多智能体接在告警之后：Retriever 并行取证、GraphAgent 查本体历史、Critic 按证据分级消解冲突、Synthesizer 按三级响应制度出有引用的处置建议，高风险事件归档走人审写回本体。规则引擎管发现，多智能体管研判，写入走审批，全程 SSE 时间线可追溯。

**预置追问**：
- **"为什么不让规则引擎直接升级告警，还要多智能体？"**——规则升级是"当下一致"的判断（图 5.9 的 20–30min 规则），但值班记录、临时豁免、季节性阈值修订都会造成规则与事实的分歧。规则发现分歧靠人翻系统，多智能体把分歧摆上桌并给出裁定依据——这是论文"阈值需持续修订"结论的系统化落地。
- **"误报多，为什么不直接调阈值？"**——降 FP 必然抬 FN（论文 ROC 曲线就是在找平衡点），且阈值是全局的、研判是个案的：全局交给规则 + ROC 调参，个案交给多智能体复核，两层各管各的。

## 附 B：高频追问预案

- **"为什么用 LangGraph 而不是 AutoGen？"**——两个方向都能讲：选 LangGraph 是因为它内建了
  编排要的全部硬能力（StateGraph/Send/checkpointer/interrupt/RetryPolicy）且与项目 LangChain
  栈同源零胶水；不选 AutoGen 讲源码级理由：旧版 GroupChat auto 模式靠 LLM 拼简介选下一个发言人，
  轮数和成本不可控，0.4 的 actor runtime 又与 LangGraph 功能重叠——引两套运行时没有收益。
  同时主动讲 LangGraph 的坑（§2.3 表），说明不是无脑上框架。
- **"哪些是自己写的？为什么不连冲突消解也找框架？"**——角色节点包装（业务胶水）、
  证据卡/claim 卡契约、五步冲突消解。因为"你的证据谁可信"是领域知识：
  图谱事实优先采信是本项目验证过的原则，任何框架都不会替你定义——框架管"怎么跑"，我们写"跑什么"。
- **"多智能体比单智能体慢怎么办？"**——并行 fan-out 换回延迟；模型分级降单步成本；
  简单问题条件边直接路由回单智能体直答（多智能体是能力上限，不是所有问题的必经之路）。
- **"Agent 之间会互相污染（一个幻觉带偏全场）吗？"**——会，所以证据分级是硬规则先行：
