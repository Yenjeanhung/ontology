## 1. 背景与目标

### 1.1 背景

当前系统为「本体 + 知识库 + 智能体」的一体化平台，底层依赖大量**可插拔**组件：

- **关系数据库**（SQLAlchemy + `DATABASE_URL`，默认 SQLite，可切换 PostgreSQL/MySQL 等）
- **图数据库**（`GRAPH_STORE_PROVIDER`：Kuzu / Neo4j）
- **向量数据库**（`VECTOR_STORE_PROVIDER`：Chroma / Milvus）
- **嵌入模型**（`EMBEDDING_PROVIDER`：本地 HuggingFace / OpenAI）
- **LLM**（`LLM_PROVIDER`：OpenAI 兼容 / Anthropic，配置持久化在数据库 `Config` 表）
- **文档解析器**（轻量专用解析 + Tika 兜底）
- **爬虫采集器**（requests + Jina Reader 回退）
- **搜索引擎**（Tavily / Bing / DuckDuckGo）
- **调度引擎**（APScheduler）
- **工作流引擎**、**技能系统**、**OAG 智能体** 等运行服务

这些组件通过 `.env` / 数据库配置切换，**用户无法直观看到"当前系统实际启用了哪些组件、每个组件是否健康"**。当系统出现故障（如向量库连不上、Tika 未启动）时，没有统一的排查入口。

### 1.2 目标

新增「系统监控」模块（挂在「系统配置」下），提供：

1. **组件全景**：列出系统**后端**所有可插拔组件，标注当前使用的 Provider、配置项、启用状态。
2. **运行状态检测**：对每个组件做健康检查（连通性/可用性），显示正常/异常/未启用/未配置。
3. **系统运行信息**：Python 版本、平台、内存、磁盘占用、服务运行时长等。
4. **LLM 手动调用**：页面提供「调用模型」按钮，手动点击时真实调用当前 LLM，并**流式输出**回答。

> 说明：数据统计（知识库数量、实体数等）**不在本模块实现**，后续作为独立模块。

下表为系统全部**后端**可插拔/可监控组件清单（基于当前代码盘点）：

| # | 组件 | 分类 | 当前 Provider 配置项 | 可选 Provider | 配置来源 |
|---|------|------|----------------------|---------------|----------|

| 2 | 图数据库 | 数据存储 | `GRAPH_STORE_PROVIDER` | kuzu / neo4j | `.env` |
| 3 | 向量数据库 | 数据存储 | `VECTOR_STORE_PROVIDER` | chroma / milvus | `.env` |
| 4 | 嵌入模型 | AI 能力 | `EMBEDDING_PROVIDER` | local / openai | `.env` |

| 6 | 文档解析器 | 解析采集 | `TIKA_FALLBACK_ENABLED` | 专用库 / tika | `.env` |

### 2.1 各组件现状

#### 1. 关系数据库（SQLAlchemy 2.0 Async）
- 位置：`backend/database.py`
- 检测方式：执行 `SELECT 1`（异步会话），测连通性。
- 已知信息：数据库类型（sqlite/postgresql/mysql）、URL（隐藏密码）、连接池状态。

#### 2. 图数据库
- 位置：`backend/providers/graph_store/__init__.py`
- `KuzuAdapter` / `Neo4jAdapter` 均已实现 `health_check()`。
- 检测方式：调用当前 adapter 的 `health_check()`，返回 `(ok, message)`。
- 已知信息：provider 名、数据库路径/URI、节点数、边数。

#### 3. 向量数据库
- 位置：`backend/providers/vector_store/__init__.py`
- `ChromaAdapter` / `MilvusAdapter`，当前**没有** `health_check()`，需新增。
- Chroma 检测：`client.heartbeat()`；Milvus 检测：尝试 `list_collections` 或建立连接。

#### 4. 嵌入模型
- 位置：`backend/providers/embedding/__init__.py`
- 当前**没有** `health_check()`，需新增。
- 检测方式：构造 embedding 实例并 `embed_query("ping")`（本地模型会触发加载，耗时较长，需超时保护）。

#### 5. LLM
- 位置：`backend/providers/llm/__init__.py`，配置持久化在 Config 表（`config_service`）。
- **健康检查**：做**真实连通性调用**，但不调用模型生成。通过向 LLM API 发送轻量请求（校验 API Key / Base URL / Model 是否有效）判断连通性，不产生模型计费。现有 `build_llm()` 可复用。
- **手动调用模型**：页面提供「调用模型」按钮，点击后走 SSE 流式接口真实调用当前 LLM（含思考链），前端流式输出回答。

#### 6. 文档解析器
- 位置：`backend/providers/parser/__init__.py`
- 检测：Tika 兜底是否启用、Tika server 端点连通性（若启用）；专用解析库是否可导入。

#### 7. 爬虫采集器
- 位置：`backend/services/crawl_service.py`
- 检测：`CRAWL_ENABLED` 开关、Jina 回退是否启用、配置完整性。

#### 8. 搜索引擎
- 位置：`backend/services/search_service.py`
- 检测：`SEARCH_PROVIDER` 及对应 API Key 是否配置。

#### 9. 调度引擎
- 位置：`backend/services/scheduler_engine.py`
- 已有 `is_running()`。检测：调度器是否运行、当前注册 job 数量、最近运行记录。

#### 10. 工作流引擎 / 11. 技能系统 / 12. OAG 智能体
- 均为内置服务，检测：模块可导入、开关状态、核心依赖就绪。

## 3. 功能设计

### 3.1 页面入口

「系统监控」挂在「**系统配置**」分组下（二级菜单），入口路径 `/monitor`。

页面结构（单页 + 多卡片分区）：

```
┌────────────────────────────────────────────────────────────┐
│ 系统监控                              [刷新]                │
├────────────────────────────────────────────────────────────┤
│ 组件状态总览（Top 摘要条）                                  │
│  正常 N  异常 M  未启用 K  未配置 L                          │
├──────────────────────┬─────────────────────────────────────┤
│ 数据存储              │ AI 能力                              │
│ [关系数据库] [图数据库]│ [嵌入模型] [LLM]                    │
│ [向量数据库]          │                                     │
├──────────────────────┼─────────────────────────────────────┤
│ 解析采集              │ 运行服务                             │
│ [文档解析] [爬虫]     │ [调度引擎] [工作流] [技能] [OAG]     │
│ [搜索引擎]            │                                     │
├──────────────────────┴─────────────────────────────────────┤
│ LLM 调用（展开面板）                                       │
│   [调用模型] 输出区域（流式渲染思考链 + 回答）               │
├────────────────────────────────────────────────────────────┤
│ 系统信息                                                 │
│  Python 版本 / 平台 / 服务启动时间 / 运行时长 / 内存 / 磁盘  │
└────────────────────────────────────────────────────────────┘
```

### 3.2 组件卡片信息

每个组件卡片展示：

| 字段 | 说明 |
|------|------|
| 组件名 | 如「图数据库」 |
| Provider | 当前使用的 Provider（如 kuzu / neo4j），与可选列表 |
| 配置项摘要 | 关键配置（API Key 掩码显示） |
| 状态徽标 | ✅ 正常 / ❌ 异常 / ⚪ 未启用 / 🚫 未配置 |
| 详情 | 错误信息或附加信息（如节点数、库大小） |
| 检测耗时 | 本次健康检查耗时（ms） |

### 3.3 刷新策略（SSE 定时推送）

- 打开监控页面后，前端建立 **SSE 长连接**（`EventSource`），由**服务端定时执行健康检查并推送**，前端被动接收实时更新，**不使用前端轮询**。
- 推送周期：默认 **30s** 推送一次全量组件状态（可配置 `MONITOR_PUSH_INTERVAL_SECONDS`）。
- 页面提供手动「刷新」按钮，点击时调用 `POST /api/monitor/check` 立即执行一次检测，结果实时广播给所有已连接的 SSE 客户端。
- 切换路由离开页面时前端主动关闭 SSE 连接，服务端停止该连接的推送（无连接时服务端不执行定时检测）。

### 3.4 LLM 调用面板

- 位于页面底部「LLM 调用」折叠面板，点击展开。
- 「调用模型」按钮：点击后通过 **SSE 流式接口**请求当前配置的 LLM，输出区域实时渲染。
- 思考链（reasoning）与最终回答分区展示，流式追加。
- 调用期间按钮置灰并显示「生成中…」，可停止/等待完成。

## 4. 后端设计

### 4.1 新增文件

```
backend/
├── services/
│   └── monitor_service.py      # 监控收集服务（组件注册、健康检查聚合）
└── routers/
    └── monitor.py              # /api/monitor 路由
```

### 4.2 API 定义

统一前缀 `/api/monitor`。

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/monitor/overview` | 组件全景 + 状态摘要 + 系统信息（页面首次加载用，拉一次全量快照） |
| GET | `/api/monitor/components` | 仅组件清单（含状态） |
| GET | `/api/monitor/system` | 仅系统运行信息 |
| GET | `/api/monitor/stream` | **SSE 长连接**：服务端每 30s 定时执行健康检查并推送组件状态 / 系统信息 |
| POST | `/api/monitor/check` | 手动触发一次全量健康检查，结果实时广播到所有已连接的 SSE 客户端（支持 `?key=xxx` 只查单个组件） |
| POST | `/api/monitor/llm/stream` | SSE 流式调用当前 LLM，实时输出思考链与回答 |

### 4.3 数据结构

`GET /api/monitor/overview` 响应：

```json
{
  "status": "ok",
  "checked_at": "2026-08-24T15:30:00+08:00",
  "summary": { "total": 12, "ok": 8, "error": 1, "disabled": 2, "unconfigured": 1 },
  "components": [
    {
      "key": "graph_store",
      "name": "图数据库",
      "category": "data_store",
      "provider": "kuzu",
      "providers_available": ["kuzu", "neo4j"],
      "status": "ok",
      "latency_ms": 3,
      "message": "health check passed",
      "config": {
        "GRAPH_STORE_PROVIDER": "kuzu",
        "KUZU_DB_PATH": "data/kuzu"
      },
      "extra": { "node_count": 1234, "edge_count": 5678 }
    }
  ],
  "system": {
    "python_version": "3.12.x",
    "platform": "Windows-10-...",
    "started_at": "2026-08-24T09:00:00+08:00",
    "uptime_seconds": 23400,
    "memory": { "total_mb": 32768, "used_mb": 10240, "percent": 31.2 },
    "disk": { "total_gb": 256, "used_gb": 100, "free_gb": 156, "data_dir_gb": 3.2 },
    "cpu_percent": 12.5
  }
}
```

`GET /api/monitor/stream`（SSE）推送的消息格式：

```text
event: snapshot                    # 周期推送 / 手动 check 触发后广播
data: {"checked_at": "...", "summary": {...}, "components": [...], "system": {...}}

event: heartbeat                   # 每 15s 心跳，保活并检测连接
data: {"ts": "..."}
```

- `snapshot` 事件数据结构与 `overview` 响应一致。
- 首次连接时立即推送一次 `snapshot`，之后每 30s 推送一次。
- 手动点击「刷新」时，`POST /api/monitor/check` 执行完成后广播最新 `snapshot`，前端无需额外请求。

### 4.4 组件状态定义

| 状态 | 含义 |
|------|------|
| `ok` | 健康检查通过 |
| `error` | 健康检查失败（组件已启用但不可用） |
| `disabled` | 未启用（开关关闭，如 `OAG_ENABLED=false`） |
| `unconfigured` | 已启用但配置不完整（如缺 API Key） |

### 4.5 健康检查实现

`monitor_service.py` 维护一个组件注册表，每项包含：

```python
@ComponentRegistry.register(
    key="graph_store",
    name="图数据库",
    category="data_store",
    enabled_func=lambda: True,
    check_func=lambda: check_graph_store(),   # 返回 (ok, message, latency, extra)
)
```

各组件检测实现：

| 组件 | 实现 |
|------|------|
| 关系数据库 | 打开 async session 执行 `SELECT 1` |
| 图数据库 | 调用 `graph_store` 当前 adapter 的 `health_check()` |
| 向量数据库 | **新增** `health_check()`：Chroma `client.heartbeat()`；Milvus 连接测试 |
| 嵌入模型 | **新增** `health_check()`：`embed_query("ping")`，带超时（本地模型加载可能慢） |
| LLM | **真实连通性调用**（不调模型）：用当前配置构造 LLM，发起轻量 API 校验请求确认 Key/Base URL/Model 有效 |
| 文档解析 | 检测专用库导入 + Tika 开关/端点连通性 |
| 爬虫 | 检测 `CRAWL_ENABLED` + 依赖可用性 |
| 搜索引擎 | 检测 `SEARCH_PROVIDER` + 对应 API Key |
| 调度引擎 | `scheduler_engine.is_running()` + job 数 |
| 工作流/技能/OAG | 开关状态 + 模块可导入 |

**超时与并发**：健康检查整体在后台线程池执行，单个组件设置超时（默认 5s，嵌入模型本地首次加载放宽到 60s）。全量检测结果可短暂缓存（默认 10s），避免重复压测外部组件。

**SSE 广播**：`routers/monitor.py` 维护一个「已连接 SSE 客户端」集合（`asyncio.Queue`）。定时任务或手动 `check` 完成后，将最新 snapshot 广播到所有客户端；无客户端连接时不执行定时检测（节省资源）。

### 4.6 LLM 流式调用（SSE）

`POST /api/monitor/llm/stream`：

- 请求体：`{ "prompt": "你好，请介绍一下你自己" }`（可带默认 prompt）。
- 响应：`text/event-stream`，事件结构沿用现有流式约定：

```text
data: {"type": "reasoning", "content": "..."}   # 思考链增量
data: {"type": "content", "content": "..."}     # 回答增量
data: {"type": "done", "content": ""}           # 结束
```

- 复用现有 `providers/llm` 的 `create_llm()`、`extract_reasoning()`、`chunk_text()`。

### 4.7 配置脱敏

响应中所有涉及密钥的配置项（`OPENAI_API_KEY`、`TAVILY_API_KEY` 等）统一脱敏，仅显示前 4 位 + `***`，防止泄露。

## 5. 前端设计

### 5.1 新增文件

```
front/src/
├── components/
│   └── monitor/
│       ├── MonitorPage.vue        # 页面容器（管理 SSE 连接生命周期）
│       ├── ComponentCard.vue      # 单个组件卡片
│       ├── LlmCallPanel.vue       # LLM 调用面板（SSE 流式）
│       └── SystemInfoPanel.vue    # 系统信息面板
└── api/monitor.js                 # API 封装（overview/check + EventSource 封装）
```

### 5.2 路由与菜单

- 路由：在 `router/index.js` 注册 `/monitor` → `MonitorPage.vue`。
- 菜单：在 `App.vue` 侧边栏「系统配置」分组下新增「系统监控」子菜单。

### 5.3 交互细节

- 组件卡片按 4 个分类分块展示，每块使用网格布局（响应式，2~3 列）。
- 状态徽标颜色：正常=绿、异常=红、未启用=灰、未配置=橙。
- 顶部摘要条显示 4 种状态的数量。
- 异常组件卡片展开显示错误详情。
- LLM 调用面板：默认折叠；「调用模型」点击后 SSE 流式渲染，思考链与回答分区；调用中按钮置灰。

### 5.4 SSE 连接生命周期

- **进入页面**：`MonitorPage.vue` 的 `onMounted` 先拉一次 `GET /api/monitor/overview` 快速展示，随后建立 `EventSource('/api/monitor/stream')`，监听 `snapshot` 事件实时刷新组件状态与系统信息。
- **周期推送**：服务端每 30s 推送 `snapshot`，前端被动更新，无轮询请求。
- **手动刷新**：调用 `POST /api/monitor/check`，服务端执行完广播 `snapshot`，前端通过 SSE 收到更新。
- **离开页面**：`onBeforeUnmount` / `onDeactivated` 中调用 `eventSource.close()`，连接断开，服务端停止对该客户端推送。

## 6. 开发任务拆解

### 阶段一：后端（核心）

1. `backend/services/monitor_service.py`
   - 组件注册表（12 个组件）
   - `run_health_checks()` 聚合检测，含超时/缓存
   - 系统信息采集（platform、memory、disk、uptime）
   - 配置脱敏工具
2. 为 `vector_store`、`embedding` 补充 `health_check()` 方法
3. `backend/routers/monitor.py`
   - 实现 5 个监控 API（overview/components/system/check/llm-stream）
   - 实现 `GET /api/monitor/stream` SSE 长连接（定时推送 + 心跳 + 广播）
   - 实现 `POST /api/monitor/llm/stream` SSE 流式接口
4. `server.py` 注册 monitor 路由

### 阶段二：前端

1. `front/src/api/monitor.js`（overview/check 封装 + EventSource 封装）
2. `ComponentCard.vue`、`SystemInfoPanel.vue`、`LlmCallPanel.vue`
3. `MonitorPage.vue`（布局、SSE 连接生命周期管理、手动刷新）
4. 注册路由 + 「系统配置」菜单

### 阶段三：联调与打磨

1. 掩码验证、超时验证
2. 异常场景测试（停掉 Kuzu 数据目录、填错 API Key 等）
3. SSE 定时推送、断线重连、多客户端广播验证
4. SSE 流式渲染与思考链分区验证
5. 响应式布局适配
