# KnowSource 项目总览

> 一句话定位：**KnowSource 是一个「本体约束驱动的 RAG + 知识图谱」一体化知识库系统**——你定义领域本体（有哪些实体、有哪些关系），系统就按这套"规矩"从文档里抽取实体和关系、构建图谱，再融合向量检索与图谱事实来回答问题。

本文档是整套功能说明的「总纲」，适合先通读一遍建立全局认识，再按菜单深入各子文档。

---

## 一、这个项目解决什么问题（为什么做）

绝大多数 RAG 系统只有「文档 → 切片 → 向量 → 检索 → 回答」这一条线，存在三个硬伤：

| 痛点 | KnowSource 的解法 |
|------|-------------------|
| **LLM 抽取实体/关系是"随机的"**——同一批文档，每次抽出来的实体类型、关系五花八门，无法沉淀成结构化资产 | 引入**本体管理**：用户预先定义"允许的实体类型 + 属性 + 三元组关系约束"，抽取时动态生成约束 Prompt + 代码后处理双重校验，保证图谱 schema 一致 |
| **纯向量检索查不到"关系型问题"**——问"A 公司投资了谁""张三是哪些公司的董事"，向量相似度召回无能为力 | 构建**知识图谱**（Kùzu 图数据库），并做**向量 + 图谱融合检索（OAG）**，把命中的实体属性与一跳关系作为"图谱事实"注入 LLM |
| **知识库质量难治理**——重复实体、噪声实体、无语义关系堆积 | 提供**图谱清洗**（相似度合并、噪声删除）与**实体管理**双库一致性编辑能力 |

一句话：**先定义本体规矩，再建库抽取，最后向量+图谱融合问答，全程可治理。**

│  │  LLM(OpenAI兼容/Ollama) │ Parser(txt/pdf/docx/Tika)      │ │
│  │  GraphStore(Kùzu / Neo4j 双 adapter)                     │ │
│  └──────────────────────────┬──────────────────────────────┘ │
└─────────────────────────────┼────────────────────────────────┘
                              │
┌─────────────────────────────▼────────────────────────────────┐
│                       三库分工的数据层                          │
│  SQLite (权威元数据)   │   ChromaDB (向量)   │   Kùzu (图)     │

**可插拔设计**：所有核心组件（嵌入、向量库、LLM、解析器、图库）都基于 LangChain 统一接口或自抽象，通过 `.env` + 数据库配置切换实现，**业务代码零修改**。例如把 ChromaDB 换成 Milvus、把 LLM 换成 Ollama 本地模型，只改配置即可。

## 三、技术栈

| 层 | 技术 | 说明 |
|----|------|------|
| 前端 | Vue 3 + Vite | 侧边栏导航 + KeepAlive 缓存 + 深浅色主题 |
| Web 框架 | FastAPI + Uvicorn | 异步、自动 OpenAPI 文档 |
| 数据库 | SQLite (aiosqlite + SQLAlchemy 2.0) | 权威元数据存储，零运维单文件 |
| 向量库 | ChromaDB（可切 Milvus） | 嵌入式，按知识库分 collection |
| 图数据库 | **Kùzu**（可切 Neo4j） | 高性能嵌入式图库，存实体关系图谱 |
| 智能体框架 | LangChain | 统一抽象 Embedding / VectorStore / LLM |
| 嵌入模型 | bge-small-zh-v1.5（512 维，本地 CPU 可跑） | 中文语义向量，可切在线 API |
| LLM | OpenAI 兼容接口 | 支持 OpenAI / DeepSeek / 通义 / 智谱 / Ollama 等 |
| 文档解析 | pypdfium2 / python-docx / Apache Tika | 支持 txt/md/pdf/docx 及 doc/ppt/xls 等 |
| 配置管理 | pydantic-settings | .env 启动兜底 + 数据库运行时配置 |

## 四、核心概念（务必先理解）

这套系统最大的特点是**严格区分"定义层"与"实例层"**，这是理解所有菜单的钥匙：

| 概念 | 所属层 | 是什么 | 通俗比喻 |
|------|--------|--------|----------|
| **本体类别** | 定义层 | 一个领域的完整 schema（如"金融领域本体"） | 一整套"图纸" |
| **本体** | 定义层 | 实体类型定义（如"人物""机构"），带属性 | 图纸里的"一类零件" |
| **本体属性** | 定义层 | 本体的字段（如"姓名 string 必填"） | 零件的"参数规格" |
| **属性模板** | 定义层(全局) | 可跨领域复用的属性组（如"自然人基础属性"） | 通用的"标准件库" |
| **关系字典** | 定义层 | 允许的关系类型词汇（如"任职于"） | 允许的"连接方式" |
| **本体关系(三元组约束)** | 定义层 | (起点本体)–[关系]→(终点本体) 的合法组合 | "谁能和谁、用什么方式连"的规则 |
| **实体** | 实例层 | 从文档抽取出来的具体实例（如"张三"） | 真实造出来的"零件" |
| **关系(实例)** | 实例层 | 实体间真实的关系（如 张三–任职于→A公司） | 真实的"连接" |
| **知识库** | 组织层 | 顶层容器，文件/向量/图谱/本体绑定都挂在它下面 | 一个"仓库" |

> **关键设计**：本体定义全部存在 SQLite（11 张表，**无数据库外键**，关联由 service 层代码维护）；实体实例**双写**——SQLite 作权威存储（供实体管理菜单列表/编辑），Kùzu 作图谱（供可视化与图遍历）。

## 五、核心业务流程（端到端）

这是整个系统最重要的主线，面试讲清楚这条线就抓住了灵魂：

```
① 定义本体（本体管理菜单）
   创建本体类别 → 定义本体(人物/机构…)与属性 → 维护关系字典 → 配置三元组约束
        │  (人物)─姓名/年龄   (机构)─名称     任职于/投资于     (人物)─任职于→(机构)
        ▼
② 建库并绑定本体（知识库菜单）
   创建知识库 → 绑定一个本体类别（决定抽取按谁的规矩来）
        │  知识库「金融研报」 ←绑定→ 本体类别「金融领域」
        ▼
③ 上传文件并处理（文件菜单）
   分片上传 → 解析(txt/pdf/docx) → 文本分块 → 向量化入库(Chroma)
        │
        ▼
④ 本体约束驱动的实体/关系抽取（核心环节）
   加载本体约束 → 动态生成约束 Prompt → LLM 批量抽取
        │
        ├─ 后处理硬校验：实体类型不在白名单→丢弃；三元组不匹配→丢弃；属性类型规整
        │
        ▼
   双库写入：SQLite(entities/relations，权威) + Kùzu(图谱)
        │  (无本体绑定时：自由抽取 + 自动反推候选本体供审核)
        ▼
⑤ 治理（实体菜单 / 图谱菜单）
   实体管理：本体树浏览、属性编辑、实体合并（双库同步）
   图谱清洗：重复实体合并(并查集)、噪声删除、无语义关系清理
        │
        ▼
⑥ 问答（智能体菜单 / 数据·知识库检索）
   纯向量 RAG：向量召回 Top-K → LLM 生成（带来源标注）
   OAG 智能体：向量召回 ∪ 图谱召回 → RRF 融合重排 → 注入图谱事实 → 流式生成（推理过程可视化）
```

## 七、数据架构（三库分工）

```
┌─────────────────────────┐  ┌──────────────────────┐  ┌─────────────────────┐
│        SQLite            │  │      ChromaDB         │  │        Kùzu          │
│  (权威元数据 / 关系数据)  │  │   (向量检索)           │  │   (图遍历 / 可视化)   │
├─────────────────────────┤  ├──────────────────────┤  ├─────────────────────┤
│ knowledge_bases 知识库   │  │ 按 kb_id 分 collection │  │ 节点: KB/Document/   │
│ files / file_assets 文件 │  │ 每分片一条向量记录     │  │  Chunk/Entity/Relation│
│ chunks 分块元数据        │  │ metadata: file_id/    │  │ 边: HAS_DOCUMENT/    │
│ 本体定义 11 张表         │  │  chunk_index/offset   │  │  MENTIONS/RELATES…   │
│ entities / relations 实例│  │                       │  │                     │
│ llm_configs 模型配置     │  │                       │  │                     │
└─────────────────────────┘  └──────────────────────┘  └─────────────────────┘
        ▲                              ▲                        ▲
        │          抽取时双写           │       抽取时双写         │
        └──────────┬───────────────────┴────────────────────────┘
                   │
            GraphExtractionService
```

- **SQLite 是唯一权威源**：实体/关系的增删改以 SQLite 事务为准，成功后 best-effort 同步 Kùzu（失败仅告警不回滚，最终一致）。
- **按 kb_id 物理隔离**：三个库都以 kb_id 为边界，删知识库即彻底回收向量 collection、图节点、上传目录，无跨库污染。
- **实体实例 ID 复用**：Kùzu 的 Entity/Relation 节点 id 直接复用 SQLite 实例 id，保证实体菜单的编辑/删除能精确同步到图。

## 八、项目亮点（面试重点提炼）

> 以下是整个系统最值得讲的工程亮点，每个都附"为什么这样做"。详细展开见各子文档。

1. **本体约束驱动的知识图谱抽取（最大亮点）**
   不是让 LLM 自由抽，而是根据知识库绑定的本体动态生成约束 Prompt（允许的实体类型+属性+三元组），并在后处理用 `constraint_set`（O(1)）做硬校验兜底。**Prompt 引导 + 代码兜底 = 双保险**，从源头保证图谱 schema 一致性。
   → 详见 [01-本体管理.md](./01-本体管理.md)、[02-文件.md](./02-文件.md)

2. **OAG：向量 + 图谱融合检索（区别于普通 RAG）**
   智能体不止向量召回，还通过"向量分片反查 MENTIONS"做图谱召回，用 **RRF（Reciprocal Rank Fusion）** 融合重排，并把命中实体的属性+一跳关系作为"图谱事实"注入 Prompt。推理过程（实体→子图→分片→token）全程 SSE 可视化。无本体/无图谱时自动降级为纯向量。
   → 详见 [06-智能体.md](./06-智能体.md)

3. **"先抽取后建模"的本体建议闭环**
   没建本体的知识库也能用——自由抽取后 LLM 自动归纳候选本体（启发式兜底），生成"本体建议"供人工审核；审核通过时智能合并到已有类别（同名只补属性不重建）并**回填孤儿实体**，降低本体建模门槛。
   → 详见 [01-本体管理.md](./01-本体管理.md#本体建议)

4. **图谱清洗的工程化护栏**
   用**并查集**做重复实体相似度聚簇合并（带"型号编码防误合"和 O(n²) 爆栈防护），噪声实体/无语义关系删除。三道护栏：只读建议+显式 apply 两段式、删除比例阈值（默认 50% 中止）、刻意不删孤岛（避免反复清洗级联清空）。注释里直写"曾导致数据全丢"的血泪教训。
   → 详见 [05-图谱.md](./05-图谱.md#图谱清洗)

5. **双库一致性 + 可插拔架构**
   SQLite(权威) + Kùzu(图) 双写，Kùzu 单写事务用全局锁串行化；所有组件（嵌入/向量库/LLM/解析器/图库）基于接口可插拔，配置即切换。
   → 详见 [04-实体.md](./04-实体.md)、[08-配置.md](./08-配置.md)

6. **模型配置的数据库持久化 + 热更新**
   多套 LLM 配置存数据库，页面改完即生效（单例 reset→rebuild，无需重启）；api_key 掩码回显 + `KEY_UNCHANGED` 哨兵，堵住"掩码值被当明文回写"的经典坑。
   → 详见 [08-配置.md](./08-配置.md)

## 九、快速开始

```bash
# 后端
cd backend
python -m venv .venv && .venv\Scripts\activate     # Windows
pip install -r requirements.txt
cp .env.example .env                                # 填入 LLM API Key 等
python server.py                                    # http://localhost:8000

# 前端
cd front
npm install
npm run dev                                         # http://localhost:3000
```

生产部署：`npm run build` 后后端自动托管 `front/dist/`，直接访问 `http://localhost:8000`。
