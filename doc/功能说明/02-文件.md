# 文件（Files）

> 一句话定位：**把文档变成知识资产的"加工流水线"**——上传文件，自动完成解析、分块、向量化入库，并**按知识库绑定的本体抽取实体和关系、构建图谱**。还内置爬虫，能按关键词自动采集网络资料整理入库。

「文件」菜单是知识库的数据入口，也是**本体约束真正落地执行**的地方。如果说本体管理是"立法"，文件处理就是"执法"。

---

## 一、这个菜单做什么

| 能力 | 说明 |
|------|------|
| **文件库管理** | 统一的物理文件仓库，支持目录树、资产增删改、文本类在线编辑、预览 |
| **知识库文件处理** | 把文件库的资产挂到知识库，触发完整的处理流水线 |
| **实体/关系抽取** | 处理流水线的最后一步，按本体约束抽取并构建图谱（核心） |
| **爬虫采集** | 按关键词搜网页 → 抓正文 → LLM 整理成 Markdown → 入库 |
| **实时进度** | SSE 推送处理进度，可取消，僵尸任务自动清理 |

> **重要架构决策**：文件库是**唯一物理存储权威**（`_assets/` 目录），知识库文件只是对资产的**逻辑引用**。同一份文件可挂到多个知识库，避免重复存储。

---

## 二、完整处理流水线（核心主线）

```
用户上传文件（前端分片）
       │
       ▼  最后一个分片到达
 合并分片 → 保存为文件库资产（FileAsset，统一存 _assets/）
       │
       ▼  挂到知识库并触发处理  POST /files/{id}/process
 ┌─────────────────────────────────────────────┐
 │  1. 文档解析 parser/                          │
 │     txt/md → 直接读；pdf → pypdfium2；         │
 │     docx → python-docx；其他 → Tika 兜底       │
 ├─────────────────────────────────────────────┤
 │  2. 文本分块 core/chunker（流式）              │
 │     fixed/sentence/semantic 三策略可配         │
 │     中文分隔符优先，回填 PDF 页码               │
 ├─────────────────────────────────────────────┤
 │  3. 向量化 + 入库（边切边写，攒批 flush）       │
 │     bge-small-zh 嵌入 → ChromaDB(kb_id 分库)  │
 │     同时写 Chunk 元数据到 SQLite               │
 ├─────────────────────────────────────────────┤
 │  4. 实体/关系抽取（本体约束驱动）⭐             │
 │     加载本体约束 → 动态约束 Prompt → LLM 批量抽 │
 │     → 后处理硬校验 → 双库写入                  │
 └─────────────────────────────────────────────┘
```

**流式 pipeline 设计**：不是"先全切完再写"，而是边分块、边攒批、边写向量库。进度按字符偏移比例实时上报（分块进度与向量化进度分开计，前端可见两条并发推进的进度条），避免内存峰值与等待感。

## 三、文档解析（策略模式 + 兜底）

`get_parser(file_path)` 按扩展名精确匹配，匹配不到走 Apache Tika 兜底：

| 格式 | 解析器 | 说明 |
|------|--------|------|
| txt/md | TxtParser | 内置读文本 |
| pdf | PdfParser | pypdfium2，记录每页文本 + 字符偏移 page_map（供分块回填页码、前端高亮溯源） |
| docx | DocxParser | python-docx，段落级提取 |
| 其他（doc/ppt/xls…） | TikaParser | Apache Tika，支持本地 JVM 或外部 server，懒加载可选 |

返回统一格式 `{ filename, format, content, metadata }`。

---

## 四、文本分块（三种策略可配）

`CHUNK_STRATEGY` 配置三选一，默认 `fixed`（CHUNK_SIZE=500、CHUNK_OVERLAP=50）：

- **fixed（递归字符分割）**：分隔符优先级中文优先 `("\n\n", "\n", "。", "！", "？", "；", ".", "!", "?", ";", " ")`；在窗口内**从后往前找最近分隔符**作切点，避免切碎句子；下一块 `start = end - overlap` 实现重叠。
- **sentence（按句切）**：按句末标点正则（中英兼顾）切句，缓冲区超阈值出块。
- **semantic（按段切）**：按 `\n\n` 分段，超长降级按句切，短段聚批。

**中文优化**：分隔符列表中文标点在前；`_find_page` 用 page_map 把每个 chunk 关联回 PDF 页码。

## 五、实体/关系抽取（本体约束驱动）⭐ 全系统最有讲头的部分

> 详细的本体定义见 [01-本体管理.md](./01-本体管理.md)，这里讲**抽取如何执行约束**。

### 5.1 加载本体约束
```
ontology_constraint = OntologyService.get_kb_extraction_constraints(db, kb_id)
```
查询知识库绑定的本体类别 → 取该类别下所有本体、属性、关系、三元组约束。返回结构预计算了：
- `ontology_by_name`: `{"人物": {id, attributes}}` ← O(1) 按名查
- `constraint_set`: `{("人物","任职于","机构")}` ← O(1) 校验

未绑定本体时返回 `None` → 抽取走**自由模式**降级。

### 5.2 动态构建 Prompt（有约束 vs 无约束）
- **有约束** → `_build_constrained_system_prompt`：把本体约束渲染成自然语言注入 System Prompt：
  ```
  【本体约束 - 必须严格遵守】
  允许的实体类型及其属性：
    - 人物：属性 编码:name 姓名 string 必填；编码:age 年龄 number
  允许的关系（仅以下三元组成立，不得越界）：
    - (人物) ─任职于（编码:works_at）→ (机构)
  ```
  并要求 LLM 对每个实体输出 properties 字段。
- **无约束** → `GRAPH_EXTRACTION_SYSTEM_PROMPT`：弱约束（实体类型用中文、关系必须具体不得用"涉及/提到/关联"）。

### 5.3 批量并发抽取
- 候选 chunk 过滤：内容长度 ≥ `GRAPH_MIN_CHARS_FOR_EXTRACTION`（默认 80 字），太短跳过。
- 分批：`GRAPH_EXTRACTION_BATCH_SIZE`（默认 6 chunk/批），`GRAPH_EXTRACTION_CONCURRENCY`（默认 3 并发）用 `asyncio.Semaphore` 控制。
- `asyncio.as_completed` 收敛，每批结果立即回调写库 + 上报进度。

### 5.4 后处理硬校验（兜底，`_merge_payload`）
即使 LLM 不守约束，这里强制兜底：
- 实体类型不在 `ontology_by_name` → **丢弃**；
- 关系三元组 `(source_type, relation_type, target_type)` 不在 `constraint_set` → **丢弃**；
- 属性 `_normalize_properties`：剔除未定义字段，按 data_type 强转（number→float、boolean 转 true/是/1）；
- 回填 `ontology_id` / `relation_def_id`，让实例挂到本体定义上；
- **低价值实体过滤**（`_is_low_value_entity_name`）：日期、纯数字+量纲（`45,046辆`/`26.7万`/`45%`）、URL、版本号、>24 字、含断句标点 → 丢弃；
- **无语义关系黑名单**（`GRAPH_GENERIC_RELATION_BLOCKLIST`）：涉及/提到/关联 → 丢弃。

### 5.5 双库写入
- **有约束模式**：先写 SQLite 权威存储（upsert by `kb_id+entity_type+name`），拿到实例 id 回填；再用**合并后的属性/描述**写 Kùzu（MERGE 语义，不覆盖更丰富的旧值）→ 保证双库一致。
- **无约束模式**：直接写 Kùzu（向后兼容）。

### 5.6 无本体绑定的降级（亮点闭环）
自由抽取完成后，**后台异步**调 `generate_ontology_suggestion`：统计实体类型频次/属性/关系样本 → LLM 归纳候选本体（失败退化为启发式）→ 写入本体建议供审核。即**"先自由抽，再反推本体"**，详见 [01-本体管理.md#本体建议](./01-本体管理.md)。

## 六、爬虫（CrawlService，四阶段管线）

关键词采集 → 自动整理成 Markdown 入库，每阶段独立进度：

| 阶段 | 做什么 |
|------|--------|
| **search** | 按 `SEARCH_PROVIDER`（tavily/bing/duckduckgo）搜 URL 列表 |
| **fetch** | 逐 URL 抓正文。直连（完整浏览器头 + 指数退避重试）失败或正文 <200 字（多为 SPA/JS 渲染）→ **回退 Jina Reader（r.jina.ai）服务端渲染**抓干净 Markdown |
| **llm** | 多网页摘录喂 LLM 整理成结构化 Markdown（按 analysis_depth 控制深度），保留来源链接不编造；LLM 失败回退拼接原文 |
| **save** | 生成 `{keyword}.md` 入文件库；若配 `auto_attach_kb_id` 则直接挂知识库并可自动处理 |

**亮点**：直连 + Jina Reader 双引擎，自动应对反爬/SPA 页面，提高正文获取率。

## 七、实时进度与任务管理

- **SSE 推送**：`GET /files/{id}/events` 发布订阅队列推 SSE，15s keepalive，前端实时看分块/向量化/抽取各阶段进度。
- **可取消**：`POST /files/{id}/cancel` 通过 cancel_event + task.cancel 双通道取消，并清理已入库数据。
- **僵尸任务清理**：服务重启后 `cleanup_zombie_tasks` 把 `processing` 状态的文件重置为 `uploaded`，避免悬空任务。
- **重新处理**：`POST /files/{id}/reprocess` 先清旧索引再重跑。

## 八、关键 API

**知识库文件（routers/files.py）**：

| 方法 | 路径 | 作用 |
|------|------|------|
| POST | `/upload/chunk` | 分片上传（支持断点续传） |
| POST | `/files/{id}/process` | 启动处理流水线 |
| POST | `/files/{id}/reprocess` | 重新处理（先清旧索引） |
| GET | `/files/{id}/status` | 查状态/进度 |
| GET | `/files/{id}/events` | SSE 实时进度推送 |
| POST | `/files/{id}/cancel` | 取消处理 + 清已入库数据 |
| DELETE | `/files/{id}` / `POST /files/batch-delete` | 删文件 |
| GET | `/files/{id}/preview` | 预览 |

**文件库 + 爬虫（routers/library.py）**：

| 方法 | 路径 | 作用 |
|------|------|------|
| GET/POST/PUT/DELETE | `/file-directories[...]` | 目录树 CRUD |
| GET | `/assets` | 列资产（目录/关键词过滤） |
| POST | `/assets/upload/chunk` | 分片上传资产 |
| GET/PUT/DELETE | `/assets/{id}...` | 预览/编辑/删除（被 KB 引用则禁删） |
| POST | `/kb/{kb_id}/assets` | 资产挂知识库（可 auto_process） |
| POST | `/crawl-jobs` | 建爬虫任务 |
| GET | `/crawl-jobs/{id}`、`/latest` | 查任务 |

## 九、面试可讲的难点与亮点

1. **本体约束驱动的知识图谱抽取（最大亮点）**
   不是让 LLM 自由抽，而是根据绑定本体动态生成约束 Prompt + 代码后处理双重校验，从源头保证图谱 schema 一致。**为什么？** LLM 输出不可控，schema 一致性是质量硬指标。

2. **双库一致性写入（SQLite 权威 + Kùzu 图）**
   抽取结果先 upsert 进 SQLite（去重合并）拿实例 id，再用合并后属性写 Kùzu（MERGE 不覆盖旧值），保证两库一致且不丢更丰富信息。

3. **"自由抽取 → 反推本体"闭环**
   无绑定时自动抽取并 LLM 归纳候选本体（启发式兜底），降低建模门槛。

4. **流式分块-向量化 pipeline**
   边切边写、按字符偏移双进度上报，避免"先全切完再写"的内存峰值与等待感。

5. **SSE 实时进度 + 可取消 + 僵尸任务清理**
   发布订阅推 SSE；cancel 双通道取消并清数据；重启清理僵尸任务。体现了长时异步任务的工程化管理。

6. **文件库统一存储 + 知识库逻辑引用**
   物理文件只存一份，多知识库共享引用，避免重复存储；解析器策略模式 + Tika 兜底覆盖几乎所有常见格式。

7. **爬虫直连 + Jina Reader 双引擎**
   自动应对 SPA/反爬，正文获取率高；LLM 整理而非简单拼接，输出可读 Markdown。
