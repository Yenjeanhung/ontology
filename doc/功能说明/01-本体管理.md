# 本体管理（Ontology）

> 一句话定位：**定义"知识图谱该长什么样"的规矩**——你告诉系统这个领域有哪些实体类型、每个类型有哪些属性、哪些实体之间允许什么关系，系统就照这套规矩从文档里抽取，保证图谱 schema 一致、可复用、可治理。

这是整个系统**技术密度最高、最有讲头**的菜单，也是 KnowSource 区别于普通 RAG 的核心所在。

---

## 一、为什么需要本体管理

不做本体约束时，让 LLM 从文档抽取实体/关系，会出现：

- **类型随机**：同一段文字，这次抽出"企业"、下次抽出"公司"、再下次"机构"，本质是同一个东西却散落成多个类型。
- **关系随意**：抽出来"涉及""提到""有关"这类无语义关系，图谱变成一团乱麻。
- **属性缺失/混乱**：该有的字段没有，字段类型对不上。
- **无法沉淀**：每次抽取结果不可复现，知识图谱无法作为可信的结构化资产。

本体管理的本质是：**把"领域知识"前置成显式约束，用工程手段让 LLM 的自由抽取收敛到可控的 schema 内。**

---

## 二、子功能总览

「本体」是侧边栏第一个分组菜单，含 5 个二级菜单，构成 **"定义层 → 约束层 → 应用层"** 的闭环：

| 子菜单 | 路由 | 职责 | 性质 |
|--------|------|------|------|
| **本体模板** | `/ontology/templates` | 跨领域复用的属性集合 | 全局，不归属任何类别 |
| **本体管理** | `/ontology/ontologies` | 本体类别 / 本体 / 属性 / 分类 的定义 | 核心定义 |
| **关系字典** | `/ontology/relations-dict` | 允许的关系类型词汇库 | 定义层 |
| **本体关系** | `/ontology/constraints` | 三元组约束（核心！） | 约束层 |
| **本体建议** | `/ontology/suggestions` | 自动归纳候选本体供审核 | 自学习/冷启动 |

> **建议的配置顺序**：先建本体类别与本体（含属性）→ 维护关系字典 → 配置三元组约束 → 绑定到知识库。本体模板是可选的提效工具。

---

## 三、数据模型全景（11 张表，全部无外键）

所有本体定义存 SQLite，**刻意不用数据库外键约束**，关联完全由 service 层代码维护。

| 表名 | 作用 | 关键字段 |
|------|------|----------|
| `ontology_categories` | 本体类别（领域） | name, **is_system** |
| `ontologies` | 本体（实体类型） | category_id, name, **color**, sort_order |
| `ontology_attributes` | 本体自有属性 | ontology_id, name, **code**, data_type, is_required |
| `ontology_relations` | 关系字典 | category_id, name, **code** |
| `ontology_relation_constraints` | 三元组约束 | source_ontology_id, relation_id, target_ontology_id |
| `ontology_attribute_templates` | 属性模板 | name, **is_system** |
| `ontology_template_attributes` | 模板下的属性 | template_id, name, data_type |
| `ontology_template_bindings` | 本体↔模板 多对多绑定 | ontology_id, template_id, sort_order |
| `kb_ontology_bindings` | 知识库↔类别绑定 | kb_id, category_id |
| `ontology_suggestions` | 本体建议 | suggestion_data(JSON), status, score |
| `entities` / `relations` | 实体实例层（抽取产物） | ontology_id, relation_def_id |

**为什么不用外键？** 因为实体实例存在 Kùzu 图库、本体定义存在 SQLite，跨库根本无法用外键；且无外键让表结构迁移、级联删除更灵活（代价是 service 层手写级联删除逻辑，代码中已完整实现：删类别 → 删本体 → 删属性 → 删模板绑定 → 删关系 → 删三元组 → 删 KB 绑定）。这是**有意识的架构权衡**。

## 四、子功能详解

### 4.1 本体模板（属性模板）

**解决什么**：跨领域共性属性重复定义的问题。例如"自然人基础属性"（姓名、性别、身份证号）在金融领域的"人物"和医疗领域的"患者"里都要用，维护一份模板两边引用即可，比复制更不易失同步，比继承更松耦合。

**怎么用**：
1. 创建模板（仅 name + description）→ 展开卡片用通用属性编辑器编辑属性（属性名/编码 code/数据类型/是否必填/默认值/排序/描述）。
2. 保存走**全量覆盖策略**：先删该模板下所有属性，再按新列表整体插入，保证排序一致。
3. 在"本体管理"页让本体引用模板（多对多）。
4. 系统内置模板（`is_system=1`）不可删除；删除模板仅解除所有本体的引用，不影响本体自有属性和已抽取数据。

**核心机制——属性合并规则**（`get_merged_attributes`，模板机制的灵魂）：
本体的最终属性 = 模板属性（合并）+ 本体自有属性，合并算法：
1. 按模板绑定顺序（`sort_order`）依次加载每个模板的属性；
2. 以属性 **`name` 为去重键**，先入为主；
3. **本体自有属性最后加载，覆盖同名模板属性**（自有优先，体现"本体特化"）；
4. 同名冲突记入 `conflicts` 列表返回前端透明提示；
5. 每条属性带 `source` 标记（`template:{id}` 或 `own`），前端可区分展示。

> **为什么用 name 而非 code 做合并键？** 因为 code 可选、name 必填，且业务语义以 name 为准。冲突项返回前端提示而非静默覆盖，让用户感知。

---

### 4.2 本体管理（类别 / 本体 / 属性 / 分类）

主战场。**左右分栏布局**：左侧本体类别列表（可搜索、新建、选中），右侧选中类别后展示类别详情 + `OntologyEditor` 编辑本体与属性。

- **本体类别 = 一个领域的完整 schema**（如"金融领域本体"下含人物、机构、产品等本体）。注意：**本体类别是领域/业务场景，不是知识库**，多个知识库可共享同一个本体类别。
- **本体**：实体类型定义，可设名称、描述、**图谱展示颜色 color**、排序。
- **本体分类**：类别内的自定义分组（如"人员类""机构类"），本体可**拖拽归组**，便于大规模本体组织。通过 `sort_order` 实现拖拽排序后批量保存。
- **自有属性编辑**：属性名、数据类型（string/number/boolean/date/datetime/text/enum）、必填、枚举值、默认值，支持整体保存。

**工程细节**：
- 批量创建本体用 `flush()` 逐条拿 id 但不逐条 commit，最后一次性 commit，兼顾 id 回填与性能。
- 删除本体时同步清理引用它的三元组（source/target 两侧都要清）。

---

### 4.3 关系字典

维护某本体类别下"允许的关系类型"词汇库（仅 name + code + description，不含起终点）。

- **作用**：为三元组约束提供"关系"字段的下拉选项。
- **code 唯一性**：类别内 code 唯一，单条创建/更新/批量创建三个入口都做校验（批量创建用 set 内存去重 + DB 查重双保险）。
- 例：定义"任职于""持有""投资于"等关系。
- 删除关系时级联删除引用它的三元组约束。

---

### 4.4 本体关系（三元组约束）⭐ 核心

> **这是整个本体模块最核心、最出彩的部分。**

把"(源本体) + 关系 + (终点本体)"组装成**合法三元组**，构成图谱抽取的"约束白名单"。例如 `(人物) ─任职于→ (机构)`。

**端到端流程（必讲）**：

```
① 人定义约束         在约束页配置 (source_ontology_id, relation_id, target_ontology_id)
        │              同一对 source-target 只能建一条（防重复）
        ▼
② 知识库绑定本体类别   KB 通过 /kb/{kb_id}/ontology 绑定一个本体类别
        ▼
③ 抽取时加载约束       OntologyService.get_kb_extraction_constraints(kb_id)
        │              预计算两个加速结构：
        │              · ontology_by_name: {"人物": {...}}   ← O(1) 按名查
        │              · constraint_set: {(人物,任职于,机构)} ← O(1) 校验
        ▼
④ 动态构建约束 Prompt  _build_constrained_system_prompt 把约束渲染成自然语言：
        │              【本体约束 - 必须严格遵守】
        │              允许的实体类型及其属性：
        │                - 人物：属性 编码:name 姓名 string 必填；...
        │              允许的关系（仅以下三元组成立，不得越界）：
        │                - (人物) ─任职于（编码:works_at）→ (机构)
        ▼
⑤ 后处理双重过滤（硬约束，兜底）
        │              · 实体类型不在 ontology_by_name → 丢弃
        │              · 三元组 (src_type, rel_type, tgt_type) 不在 constraint_set → 丢弃
        │              · 合法实体回填 ontology_id，关系回填 relation_def_id
        │              · 属性 _normalize_properties 类型规整
        ▼
⑥ 双库写入            SQLite(权威) + Kùzu(图谱)
```

**双保险机制（面试重点）**：
- **Prompt 引导 + 代码后过滤 = 双保险**。仅靠 Prompt 引导 LLM 不可靠（输出本质不可控），所以用 `constraint_set`（Python set，O(1)）在代码层兜底，确保图谱严格符合 schema。
- **预计算优化**：约束结构在抽取批次开始前一次性构建，批次内复用，避免每个 chunk 重复查库。
- **无绑定则自由抽取**：未绑定时返回 None，抽取回退到无约束自由模式，系统向后兼容。

### 4.5 本体建议（Suggestion）⭐ 自学习/冷启动

> **"先抽取后建模"的闭环利器，降低本体建模门槛。**

没建本体的知识库也能用：自由抽取后，系统自动归纳候选本体供人工审核。

**流程**：
1. **生成**（`POST /ontology-suggestions/generate`）：从 Kùzu 拉取该 KB 已抽取的实体/关系 → LLM 按 `ONTOLOGY_SUGGESTION_PROMPT` 归纳出候选 schema（类别名、本体列表、属性、关系、三元组约束）+ 统计信息 → 存为 `suggestion_data`（JSON），状态 `ready`，带置信度 `score`。
   - LLM 失败时退化为**启发式建议**：按频次取 top15 类型、属性按频次、关系直接取样本，保证总有结果。
   - 无本体绑定的知识库处理文件后，会**后台自动触发**建议生成（`source_mode=free_extraction`）。
2. **审核**：用户在审核页编辑建议内容 → approve / reject。
3. **approve 的智能合并**（`OntologySuggestionService.approve_suggestion`，最复杂的方法）：
   - 判断 KB 是否已绑定类别 → **合并模式**（并入已有类别）vs **新建模式**；
   - **合并模式**：同名本体跳过重建、只补充新增属性（不覆盖已有）；关系/三元组按维度去重；
   - 统一处理 code 内存去重、三元组 `(src, rel_id, tgt)` 去重；
   - 自动绑定到 KB（仅新建模式），返回详细的 `added_*` / `skipped_*` 计数。

**实体回填（加分项）**：approve 后触发 `_backfill_entities_after_approval`——扫描 Kùzu 中 `ontology_id` 为空的孤儿实体，按 `entity_type == 本体名` 精确匹配回填 ontology_id，并双写到 SQLite。这让"先抽取后建模"产生的游离实体重新挂接到正式本体上，**实现数据治理闭环**。

**状态机**：`generating → ready → approved / rejected`。

**为什么这么设计？** 真实场景下知识库会持续抽取新数据，本体 schema 需要增量演进而非每次重建，合并策略保护了已有人工标注成果。

## 五、知识库绑定（连接定义与应用的桥梁）

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/kb/{kb_id}/ontology` | 查看知识库绑定的本体类别 |
| PUT | `/kb/{kb_id}/ontology` | 绑定/换绑本体类别（先删后插） |
| DELETE | `/kb/{kb_id}/ontology` | 解绑 |

- 绑定关系存 `kb_ontology_bindings`（kb_id ↔ category_id），**一个知识库只绑一个类别**（UNIQUE(kb_id)）。
- 绑定与否**决定抽取模式**：有绑定 → 约束抽取；无绑定 → 自由抽取 + 自动反推本体。同一套代码两种行为。

## 七、面试可讲的难点与亮点

1. **三元组约束的「Prompt + 后处理」双保险**
   仅靠 Prompt 引导 LLM 不可靠，所以用 `constraint_set`（Python set）在代码层做 O(1) 兜底过滤。**为什么这么做？** LLM 输出本质不可控，而图谱 schema 一致性是知识库质量的硬指标，必须在工程上闭环保证。

2. **属性模板的合并复用机制**
   自有覆盖模板、按 name 去重、source 标记来源、冲突透明提示。解决了"通用属性跨领域复用"与"本体特化覆盖"的矛盾。**为什么用 name 做 key？** code 可选、name 必填，业务语义以 name 为准。

3. **本体建议的「智能合并审核」策略**
   approve 时区分合并/新建模式，同名本体只补属性不重建、全维度去重、返回 added/skipped 计数。**为什么？** 本体需要增量演进而非每次重建，合并策略保护已有人工标注。

4. **「先抽取后建模」的实体回填治理**
   approve 后扫描孤儿实体按类型回填 ontology_id 并双写。**为什么需要？** 冷启动场景用户常先上传自由抽取、后建本体，回填让这批数据挂接到正式本体，实现治理闭环。

5. **无外键 + 代码维护关联 + 完整级联删除**
   11 张表全不用外键，跨库（SQLite 存定义、Kùzu 存实例）也无法用外键。代价是手写级联，收益是迁移与跨库灵活。可作为"为什么不用外键"的反问应答。

6. **预计算加速结构**
   `ontology_by_name` / `constraint_set` 一次性构建、批次复用，把后处理校验从线性扫描降到 O(1)。体现了"在批次边界做一次重计算、内部复用"的性能意识。
