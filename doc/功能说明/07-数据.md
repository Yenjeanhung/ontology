# 数据（检索 · 向量）

> 一句话定位：**知识库的"消费"与"巡检"出口**——「知识库检索」是纯向量 RAG 问答；「向量」是向量数据的对账与调试工具，能定位"解析成功但向量化丢失"的坏数据。

「数据」是侧边栏分组菜单，含「知识库检索」和「向量」两个二级菜单。检索是面向终端用户的问答，向量管理是面向运维/开发的数据质量工具。

---

## 一、子功能总览

| 子菜单 | 路由 | 定位 |
|--------|------|------|
| **知识库检索** | `/query` | 纯向量 RAG 问答（流式，带来源标注） |
| **向量** | `/vectors` | 向量数据查看、相似度实测、对账导出 |

> 与智能体（OAG）的区别：本菜单的检索是**纯向量**；OAG 是**向量+图谱融合**。详见 [06-智能体.md](./06-智能体.md)。

## 二、知识库检索（纯向量 RAG）

### 2.1 检索流程
1. `POST /query`（`{kb_id, query}`），先校验 KB 存在；
2. **向量检索**：query 经 `create_embeddings()` 嵌入，在该知识库向量库做 `similarity_search_with_score`，召回 **Top-K=50**；检索包在 `asyncio.to_thread` 里避免阻塞事件循环；
3. **阈值过滤**：Chroma 返回的是距离 distance，代码用 `1 - distance` 换算相似度，再以 `SIMILARITY_THRESHOLD`（默认 **0.3**）过滤低相关分片；
4. **构建上下文**：命中分片带元数据（file_id/file_name/score/start_offset/end_offset/page_number），按序号拼成 `[来源1]...[来源2]...`；
5. **LLM 生成**：SystemMessage + HumanMessage 调 `llm.astream` 流式生成。

### 2.2 流式 SSE 设计（两段式协议）
- 响应 `text/event-stream`，响应头 `Cache-Control: no-cache` + **`X-Accel-Buffering: no`**（专门禁 Nginx 缓冲，保证 token 实时推到前端）；
- **先一次性发 `{type:"chunks", chunks:[...]}`** 让前端秒出引用来源卡片，**再逐 token 发 `{type:"token", content}`**，最后 `[DONE]`。
- **"先给来源、再给回答"的两段式是体验亮点**：首屏体感好，又保证生成完整。

### 2.3 Prompt 设计（强约束 + 来源标注）
- **System**：明确"仅依据资料回答；无依据时如实说明、不得编造"，并强制"每个引用了资料的事实都标注来源"；
- **User**：上下文以 `[来源N]` 分段注入，末尾再次强调标注来源。**双向约束**保证可追溯、压低幻觉。

### 2.4 与 OAG 的区别（关键对比）

| | 纯向量 RAG | OAG 智能体 |
|---|---|---|
| 检索 | 仅向量 Top-50 | 向量 ∪ 图谱，RRF 融合 Top-12 |
| 上下文 | 原文分片 | 分片 + 图谱事实 |
| 引用 | `[来源N]` | `[来源N]` + `[事实]` |
| 可视化 | chunks | entities→subgraph→chunks→token |

## 三、向量管理（双源对账式巡检）⭐ 亮点

### 3.1 核心设计：业务库 × 向量库 双源对账
最大亮点不是"看向量库"，而是**把业务表（chunks/files）和真实向量库（Chroma）交叉校验**：
- `_fetch_rows`：从 `chunks ⋈ files ⋈ knowledge_bases` 查出"应该存在的向量记录"；
- `_enrich_items`：再调 `enrich_vector_index_records(kb_id, group)` 去**真实向量库**核对每条 chunk 是否真写入，打上 `store_found` 标记；
- `unsynced_only=True`：只留 `store_found is False` 或无 `embedding_id` 的记录——即**"业务库有、向量库丢"的不一致项**，是排查脏数据/重建索引的利器；
- `provider` 自识别：根据当前向量库 provider（chroma/milvus）返回对应物理表名，前端展示底层结构。

**为什么这么做？** 单纯看向量库 Admin UI 做不到这种对账——能精准定位"解析成功但向量化丢失"的坏数据，这是工程级的向量数据治理。

### 3.2 三个能力
| 能力 | 说明 |
|------|------|
| **分页查看** | limit 1–200、offset，按文件创建时间倒序；支持 kb_id 过滤、q 模糊匹配（文件名/分片内容/embedding_id） |
| **相似度实测** | `similarity_test` 直接打向量库，top_k 限 1–20，返回 rank/score/分片文本，人工验证检索质量 |
| **导出摘要** | 按知识库聚合统计每文件 chunk 数、synced/unsynced 计数；支持 `json` 和 `md` 两种格式 |

### 3.3 provider 无关抽象
表名映射、enrich 都按 provider 分支，Chroma/Milvus 可平滑替换，前端逻辑零改动。

## 五、面试可讲的难点与亮点

1. **阈值过滤 + 距离转相似度**
   主动用 `1 - distance` 归一化并做 `SIMILARITY_THRESHOLD` 兜底，避免"召回一堆低质分片污染 LLM"。一个常被忽略但影响回答质量的细节。

2. **两段式 SSE 协议**
   先推 chunks（前端秒出引用卡）再逐 token 出答案，兼顾首屏体感与生成完整度；`X-Accel-Buffering: no` 解决反向代理缓冲问题。

3. **Prompt 双重来源约束**
   System + User 两处反复要求标注 `[来源N]`，从工程上压低幻觉与无据作答。

4. **双源对账式向量巡检**
   业务表 × 向量库交叉校验，精准定位"解析成功但向量化丢失"的坏数据，这是单纯看 Admin UI 做不到的，是真正面向运维的数据治理工具。

5. **把"调试工具"做成产品功能**
   相似度实测 + 一键导出 md 报告，对排查召回质量、向客户/评审交付证据链非常实用。

6. **provider 无关抽象**
   表名映射、enrich 按 provider 分支，Chroma/Milvus 平滑替换，前端零改动，呼应整个系统的可插拔架构。
