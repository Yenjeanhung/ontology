# 智能体（OAG · 本体增强生成）

> 一句话定位：**向量检索 + 知识图谱融合的增强问答**——不止用向量召回文本，还通过图谱召回相关分片、用 RRF 融合重排，并把命中实体的属性与一跳关系作为「图谱事实」注入 LLM，推理过程全程可视化。

OAG（Ontology-Augmented Generation，本体增强生成）是 KnowSource 最能体现"RAG + 知识图谱"价值的模块。普通的纯向量 RAG 见 [07-数据.md](./07-数据.md)，本菜单是它的"加强版"。

---

## 一、为什么需要 OAG（纯向量 RAG 的短板）

纯向量 RAG 只能回答"语义相似"的问题，遇到**关系型/结构型问题**就力不从心：

| 问题类型 | 例子 | 纯向量 RAG |
|----------|------|-----------|
| 语义查找 | "公司的退货政策是什么" | ✅ 能答 |
| 关系查询 | "A 公司投资了哪些企业" | ❌ 召回不到"投资"关系 |
| 多跳推理 | "张三担任董事的公司投资了谁" | ❌ 需要图遍历 |
| 属性查询 | "某产品的规格参数" | ⚠️ 文本里有就能答，结构化不准 |

OAG 的解法：**把知识图谱（实体、属性、关系）作为额外的事实源，与向量检索融合，注入 LLM**。

---

## 二、OAG vs 纯向量 RAG 对比

| | 纯向量 RAG（`rag_service`） | OAG（`oag_service` + `/agent/query`） |
|---|---|---|
| **检索来源** | 仅向量召回 Top-50 | 向量召回 ∪ 图谱召回（实体 MENTIONS 反查分片），**RRF 融合重排**取 Top-N=12 |
| **上下文** | 原文分片 | 原文分片 + **图谱事实**（命中实体属性 + 1 跳关系，软上限 1600 字符） |
| **引用标注** | `[来源N]` | `[来源N]` + `[事实]`，且"图谱事实优先、冲突时指出" |
| **可视化** | chunks | entities → subgraph → chunks → token，**推理过程全透明** |
| **降级** | — | 未绑本体/无图谱/无实体链接时**自动退化为纯向量** |

## 三、OAG 核心流程（7 步管线）

```
用户问题 + kb_id
     │
     ▼
① 总开关判断   OAG_ENABLED 关闭 → 直接降级纯向量
     │
     ▼
② 向量召回     query 嵌入 → Chroma similarity_search_with_score(k=50)
              距离转相似度(1-distance) → SIMILARITY_THRESHOLD(0.3) 过滤
              重建 chunk_id(=file_id_chunk_index) 对接图谱
     │
     ▼
③ 实体链接（双通道）
     │  通道A：词面匹配（实体名出现在 query 中）
     │  通道B：向量分片反查 MENTIONS（分片提及的实体）
     │  合并去重 → 词面命中优先 + mention 计数排序 → 取 top-M 种子实体
     ▼
④ 图谱召回 + 子图事实
     │  种子实体 → chunks_mentioning_entities 图谱召回补充分片
     │  种子实体 → entity_neighborhood 取 1 跳邻居 → 序列化为「图谱事实」文本
     ▼
⑤ RRF 融合重排
     │  向量 rank_list + 图谱 rank_list → _rrf_fuse (k=60)
     │  score = Σ 1/(k + rank + 1)  →  取 Top-N(12)
     │  标记每条来源：vector / graph / both
     ▼
⑥ 下发推理过程事件（SSE，先于回答）
     │  {type:"entities", entities:[...]}        ← 命中的种子实体
     │  {type:"subgraph", facts, retrieval_path} ← 图谱事实 + 检索路径统计
     │  {type:"chunks", chunks:[...]}            ← 融合后的分片（带来源标注）
     ▼
⑦ 流式生成回答（SSE token）
        Prompt = 图谱事实 + [来源N] 参考资料 + 问题
        → LLM astream → 逐 token 下发 → [DONE]
```

## 四、关键设计详解

### 4.1 实体链接双通道
- **通道 A（词面匹配）**：拉知识库实体列表，名字出现在 query 中的命中（score=1.0）；
- **通道 B（向量分片反查）**：用向量召回的分片 id，反查这些分片 MENTIONS 了哪些实体，按 mention_count 排序；
- **合并去重**：词面命中优先，mention 补充；取 top-M 作为种子实体驱动后续图谱召回。

**为什么双通道？** 词面匹配准但漏召（同义词/指代），向量反查能补上"query 没明说但相关分片里出现的实体"，互补。

### 4.2 RRF 融合重排（Reciprocal Rank Fusion）
两个有序分片列表（向量、图谱）按 RRF 公式融合：
```
score(chunk) = Σ  1 / (k + rank + 1)      # k = OAG_RRF_K = 60
```
- 不需要校准两路分数的绝对值（向量相似度 vs 图谱 mention 次数量纲不同），只用**排名**融合，简单稳健；
- 两路都召回的分片（`retrieval=both`）天然得分更高；
- `retrieval_path` 统计 vector/graph/both 各多少条、是否降级，前端可见"这次回答走了哪条检索路径"。

### 4.3 图谱事实注入
`_format_subgraph_facts` 把种子实体的 1 跳子图序列化为结构化文本：
```
- 实体[华为公司]（类型:ORG） 属性:{成立时间:1987, 总部:深圳}
  ─ 投资 → [某初创公司]（ORG）
  ─ 任职于 → [任正非]（PERSON）   # 关系方向取决于建模
```
软上限 1600 字符，避免 prompt 过长。System Prompt 明确"**图谱事实是结构化、可信的，优先采信；与参考资料冲突时指出**"。

### 4.4 推理过程可视化（SSE 事件序列）
回答开始前，先下发三类事件让前端实时渲染推理链：**命中的实体 → 图谱子图事实 → 引用分片**，再逐 token 出答案。用户能直观看到"智能体是怎么一步步找到答案的"，这是体验亮点。

### 4.5 路由层的细节处理
`/agent/query` 在开 SSE 前**先预加载本体 schema**：
```python
ontology_schema = await OntologyService.get_kb_extraction_constraints(db, kb_id)
```
**为什么？** db 会话在 HTTP 响应返回后就释放，而 SSE 生成器是异步迭代、生命周期更长，不能在生成器里持有 db session。这种边界处理体现了对异步生命周期的理解。

## 五、优雅降级

OAG 在多种"不理想条件"下自动退化为纯向量（行为等同 [07-数据.md](./07-数据.md) 的问答）：

| 条件 | 行为 |
|------|------|
| `OAG_ENABLED=False` | 总开关关，完全走 `_stream_vector_only` |
| 知识库未绑定本体 | 实体链接/图谱召回为空 → retrieval_path.degraded=True |
| 无图谱数据 / 实体链接为空 | 同上，自动降级 |
| 向量召回为空 | 直接返回"未找到相关内容" |

降级路径仍保持相同的事件结构（entities/subgraph 为空），前端无需区分处理。

## 六、Prompt 设计（强约束 + 双重来源标注）

**System Prompt**：
> 你是基于知识库与知识图谱的智能体。回答必须依据【参考资料】与【图谱事实】。图谱事实是结构化、可信的关系与属性，**优先采信**；若与参考资料冲突，请指出。引用参考资料时标注 `[来源N]`，引用图谱事实时标注 `[事实]`。如果都没有相关信息，请如实说明，不要编造。

**User Template**：`【图谱事实】... 【参考资料】[来源N]... 用户问题...`

双向约束保证可追溯、压低幻觉。

## 七、关键 API

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/agent/query` | OAG 智能体查询（SSE 流式） |

请求体 `{ kb_id, query }`，响应 `text/event-stream`，响应头设 `Cache-Control: no-cache` + `X-Accel-Buffering: no`（禁反向代理缓冲，保证 token 实时推送）。

## 八、面试可讲的难点与亮点

1. **向量 + 图谱双路召回 + RRF 融合**
   不止向量检索，还通过"向量分片反查 MENTIONS"做图谱召回，用 RRF 按排名融合（避开量纲校准难题），两路都命中的分片天然得分高。**为什么用 RRF？** 向量相似度和图谱 mention 次数量纲不同，RRF 只用排名，简单稳健。

2. **实体链接双通道（词面 ∪ 向量反查）**
   词面匹配准但漏召，向量分片反查补同义/指代，互补提升种子实体召回率，是图谱融合质量的入口。

3. **图谱事实注入 + 冲突指示**
   把命中实体的属性 + 1 跳关系作为结构化、可信的事实注入 Prompt，并要求"事实优先、冲突指出"。让 LLM 回答关系型问题有据可依，这是纯向量 RAG 做不到的。

4. **推理过程全程可视化**
   先下发实体→子图→分片，再流式 token，用户看到"智能体怎么找到答案的"。不只是黑盒回答，增强可信度与可解释性。

5. **优雅的多级降级**
   总开关、未绑本体、无图谱、实体链接为空，任一条件都自动退化为纯向量且事件结构一致，前端无感。体现了"功能增强不能牺牲可用性"的工程意识。

6. **异步生命周期的边界处理**
   路由层先预加载 schema 再开 SSE，避免 db session 在生成器里被释放。是对 FastAPI 异步生成器与依赖注入生命周期的深入理解。
