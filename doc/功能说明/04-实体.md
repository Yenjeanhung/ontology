# 实体（Entities）

> 一句话定位：**实例层的数据管理台**——浏览、编辑、合并由文档抽取出来的实体与关系实例。核心交互是「左侧本体树 + 右侧实体列表」，所有增删改都**双库同步**（SQLite 权威 + Kùzu 图）。

实体/关系实例由文件处理流水线自动抽取生成（见 [02-文件.md](./02-文件.md)），本菜单以**浏览与人工修正**为主，是图谱质量治理的日常入口。

---

## 一、这个菜单做什么

| 子功能 | 路由 | 说明 |
|--------|------|------|
| **实体列表** | `/entities` | 左侧本体树 + 右侧分页实体表，按本体类型联动过滤 |
| **实体详情** | `/entities/:id` | 编辑属性、查看关联关系、原文溯源高亮 |
| **关系实例列表** | `/entities/relations` | 浏览/删除实体间的关系实例 |
| **实体合并** | （列表内操作） | 把多个重复实体并入一个规范实体 |

---

## 二、实体列表：本体树联动过滤

经典「左树右表」分栏：

- **左侧本体树**：两级结构「本体类别 → 本体」。拉取全部类别，每个类别取其下本体及 `entity_count`，组装成树。支持树内搜索、展开折叠、节点计数徽标（如"人物 (128)"）。
- **联动过滤**：点击本体叶子节点 → 右侧按 `ontology_id` 过滤；切换过滤后分页重置。面包屑显示当前筛选上下文（如"金融领域本体 / 人物"），支持一键清除回到全部。
- **右侧表格**：实体名、本体类型、属性概要（前 3 个 KV）；带关键词搜索（防抖 300ms）、知识库下拉筛选、分页。

> **定义层与实例层解耦**：本体树由定义层接口驱动，实体是实例层，二者通过 `entity.ontology_id` 逻辑关联（无外键），便于本体演进时不锁死历史数据。

---

## 三、实体详情

- **属性编辑**：顶部基本信息 + 属性 KV 表（可增删行，前端编辑模式），保存调 `PUT /entities/{id}`。
- **关联关系区**：列出该实体作为 source 或 target 参与的全部关系，每条带角色（source/target）、对端实体名/类型、关系定义名。
- **原文溯源**：点"查看原文"按 source_file_id 拉文件内容，在原文中**正则高亮实体名**并计数，支持预览/编辑双模态。
- **删除**：`DELETE /entities/{id}`，二次确认提示"关联关系一并删除、Kùzu 同步"。

---

## 四、双库一致性（SQLite 权威 + Kùzu 同步）⭐ 核心

**核心原则**（代码注释明确）：SQLite 为权威存储，Kùzu 只承担可视化与图遍历；每次增删改 **best-effort** 同步 Kùzu，失败仅 `logger.exception` 不阻断主流程（事务不回滚）。

| 机制 | 实现 |
|------|------|
| **同步桥梁** | `_sync_upsert_entity / _sync_delete_entity / _sync_upsert_relation / _sync_delete_relation` 四个包装函数，统一捕获异常 |
| **ID 复用** | Kùzu 的 `Entity.id`/`Relation.id` **直接复用 SQLite 实例 id**，保证编辑/删除能精确同步到图 |
| **删除级联** | 删实体时 SQLite 先删该实体参与的 relations 再删实体；Kùzu 端 `delete_entity` DETACH DELETE 触及 Relation 节点，双侧级联语义一致 |
| **关系 upsert** | Kùzu 先删旧 RELATION_SOURCE/TARGET 边再 MERGE 新边 + 直连 RELATES 边，避免遗留幽灵边 |
| **写锁** | Kùzu 同一时刻只允许一个写事务，`_kuzu_write_lock = threading.Lock()` 全局串行化所有写操作 |

**为什么不让 Kùzu 也参与事务？** SQLite 与 Kùzu 是异构存储，无法做分布式事务，权衡后选择**最终一致 + 日志告警**——业务可用性优先于强一致。

---

## 五、实体合并（merge_entities）⭐ 重点

LLM 抽取必然产生同一实体的多种写法/重复抽取，合并不可少。合并语义：

1. **关系端点重写 + 去重**：把被合并实体参与的关系端点改写到规范实体（canonical），自环和重复关系物理删除。
2. **属性增量累积合并**（`_merge_properties`）：**新值非空才覆盖，旧字段不丢**；描述取更长者；被合并实体的旧名写入 `canonical.properties.aliases` 做软别名，免数据迁移。
3. **双库同步**：复用 `EntityService.merge_entities`，自动 best-effort 同步 Kùzu。

**关键工程坑——"先删后改"顺序**：合并时必须**先物理删自环/重复关系并 flush，再改存活关系端点**。否则 ORM 在 commit 时 UPDATE 先于 DELETE 落库，会撞上 relations 表的 `(kb, src, type, tgt)` 唯一约束。这是非常具体、面试能加分的工程细节。

---

## 六、upsert 而非盲插

- 实体按 `(kb_id, entity_type, name)` 大小写不敏感去重；
- 关系按 `(kb_id, source, type, target)` 去重。

**意义**：抽取流程反复跑不会产生重复行，天然幂等。

## 七、关键 API（routers/entity.py）

| 方法 | 路径 | 作用 |
|------|------|------|
| GET | `/entities` | 实体分页列表（kb_id/ontology_id/entity_type/q 过滤） |
| GET | `/entities/stats` | 实体/关系总数 + entity_type 分布 |
| GET | `/entities/{id}` | 实体详情（含关联关系、来源文件名） |
| POST | `/entities` | 创建实体（upsert：同 kb+type+name 已存在则更新） |
| PUT | `/entities/{id}` | 更新名称/描述/属性 |
| DELETE | `/entities/{id}` | 删实体（级联删关系，双库同步） |
| POST | `/entities/merge` | 多实体并入规范实体 |
| POST | `/entities/batch-delete` | 批量删实体 |
| GET/POST/PUT/DELETE | `/relations...` | 关系实例完整 CRUD |
| POST | `/relations/batch-delete` | 批量删关系 |

> 图谱清洗相关端点（`/graph-cleanup/suggestions`、`/graph-cleanup/apply`）也注册在此，详见 [05-图谱.md](./05-图谱.md)。

## 八、面试可讲的难点与亮点

1. **双库一致性 + best-effort 容错**
   SQLite 事务为权威，Kùzu 同步包 try/except 不阻断业务；写操作全局锁串行化规避 Kùzu 单写事务限制。**为什么？** 异构存储无法分布式事务，选最终一致 + 告警，业务可用性优先。

2. **实体合并的"先删后改"顺序陷阱**
   必须先物理删自环/重复关系并 flush 再改端点，否则 ORM 的 UPDATE 先于 DELETE 落库撞唯一约束。非常具体的工程坑，说明真的踩过。

3. **属性"增量累积"合并语义**
   新值非空才覆盖、旧字段不丢、描述取更长、旧名做软别名。贴合"LLM 多次抽取逐步补全"的真实场景，免数据迁移。

4. **upsert 幂等抽取**
   实体/关系按自然键去重，抽取反复跑不产生重复行，是数据质量的基础保障。

5. **定义层与实例层解耦**
   本体/关系字典与实体/关系实例无外键，仅靠 ontology_id/relation_def_id 逻辑关联，本体演进不锁死历史数据。
