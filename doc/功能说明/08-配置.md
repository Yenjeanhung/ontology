# 配置（模型配置）

> 一句话定位：**多套 LLM 模型配置的数据库持久化管理**——页面上增删改查多套模型方案、一键切换生效配置，改完即生效（无需重启），api_key 掩码回显保证安全。

「配置」是侧边栏分组菜单，目前含「模型配置」一个二级菜单。它解决的是"系统该用哪个 LLM、怎么管多套模型、怎么安全存密钥"的问题。

---

## 一、这个菜单做什么

| 能力 | 说明 |
|------|------|
| **多套配置管理** | 保存多个 provider/模型组合（OpenAI、DeepSeek、通义、智谱、Anthropic…），增删改查 |
| **一键切换生效** | 把某套配置设为 `is_active`，立即生效（热更新，无需重启） |
| **测试连接** | 用任意参数临时构造 LLM 发 ping，验证连通性 |
| **密钥安全** | api_key 掩码回显，前端永远拿不到明文 |

---

## 二、数据模型（`llm_configs` 表）

| 字段 | 说明 |
|------|------|
| id | 主键 |
| name | 配置名（如"DeepSeek 生产"） |
| provider | openai \| anthropic |
| api_key | API 密钥（掩码回显，详见下文） |
| base_url | 接口地址（兼容 Ollama/Azure 等） |
| model | 模型名（如 deepseek-chat、qwen2.5:7b） |
| max_tokens | 默认 4096 |
| temperature | 默认 0.7 |
| **is_active** | 0 \| 1，**同一时间至多一条为 1** |

---

## 三、为什么用数据库持久化（而非只读 .env）

| 维度 | 只读 .env | 数据库持久化（本项目） |
|------|-----------|------------------------|
| 多套方案 | 只能存一组 | 可保存多套，一键切换 |
| 运行时改 | 改完要重启进程 | 页面改完即生效 |
| 角色 | **启动兜底默认值** | 主配置源 |

**协同机制**：`config.py` 里 LLM 字段都有默认值（空串）作启动兜底；`load_active_into_settings` 在**启动时**把 DB 中 `is_active` 的那条覆盖进内存 settings，保证 `create_llm` 单例能拿到配置。即 **.env 兜底 + 数据库主配** 的双层设计。

## 四、api_key 的安全处理

### 4.1 掩码回显
`mask_key` 只保留 `前3位 + •••• + 后4位`，前端永远拿不到明文；同时返回 `has_key` 布尔。

### 4.2 `KEY_UNCHANGED` 哨兵（堵经典坑）
前端编辑配置时若不改密钥，回传 `"__unchanged__"` 或空串；`_resolve_key` 据此**沿用当前已生效密钥**。

**解决了什么坑？** 配置管理最常见的 bug：编辑表单加载了掩码值（`sk-••••1234`），用户没动密钥直接保存，掩码值就被当真值存回去 → 密钥损坏。哨兵机制用最小代价堵住这个坑。

### 4.3 测试连接复用同一逻辑
`POST /config/llm/test` 在密钥为空/哨兵时也沿用已存密钥，支持"直接 ping 当前配置"。

> **短板（建议主动在面试里说）**：api_key 在 DB 中**明文存储**，未做对称加密。生产级改进方向：用 Fernet/AES + 环境变量托管 KEK 加密列存储，或接 KMS / Secret Manager。主动暴露短板反而显得有生产意识。

## 五、切换激活如何生效（热更新链路）⭐ 核心亮点

`apply_plan / create_plan / update_plan / delete_plan` 在写库后，若涉及当前生效项，都会调 `_apply_to_settings(...)`：

```
① 写内存 settings     (LLM_PROVIDER / OPENAI_API_KEY / ...)
        │
        ▼
② reset_llm()          把 providers/llm/__init__.py 的模块级单例 _llm = None
        │
        ▼
③ create_llm()         立即按新 settings 重建单例
                        重建失败（密钥错/网络）不抛异常、不阻塞操作
                        留待"测试连接"去诊断
```

**配套逻辑**：
- 删除生效项时：自动把"剩下中最早创建的一条"激活；若一条不剩，清空 settings 并 reset（降级为"未配置"）。
- 新建第一条配置：**自动 `is_active=1`**，零配置即可用。
- `build_llm`（不缓存）专供"测试连接"——**临时实例不污染全局单例**。

**为什么用单例 + reset？** LLM 客户端连接重、构造成本高，用模块级单例缓存；切换配置时 `reset→rebuild` 实现"无需重启即生效"，是性能与灵活性的折中。

## 六、关键 API（routers/config.py）

| 方法 | 路径 | 作用 |
|------|------|------|
| GET | `/config/llm` | 当前生效配置（掩码） |
| POST | `/config/llm/test` | 用任意参数临时构造 LLM，发 `invoke("ping")` 验证连通 |
| GET | `/config/llm/plans` | 列出所有配置方案 |
| POST | `/config/llm/plans` | 新建配置 |
| PUT | `/config/llm/plans/{id}` | 更新配置 |
| DELETE | `/config/llm/plans/{id}` | 删除配置 |
| POST | `/config/llm/plans/{id}/apply` | 切换为生效 |

---

## 七、面试可讲的难点与亮点

1. **单例 + reset 的热更新模式**
   LLM 客户端构造成本高用单例缓存，切换配置 `reset→rebuild` 无需重启即生效。**为什么？** 性能与灵活性折中，避免每次请求重建连接。

2. **`KEY_UNCHANGED` 哨兵 + 掩码回显**
   前端只拿掩码，编辑表单天然不会把掩码当明文回写——用最小机制堵住配置管理最常见的密钥腐败 bug。

3. **测试连接用独立 `build_llm`（绕过单例）**
   "拿别人家参数试连"不会污染正在生效的全局 LLM，体现了对共享状态边界的克制。

4. **删除生效项的自动接续**
   删掉激活配置会自动激活下一条，避免"删完直接 LLM 不可用"的事故。有生产稳健性意识。

5. **.env 兜底 + 数据库主配的双层设计**
   .env 保证启动有默认值，数据库支持运行时多套配置与热切换，两者协同。

6. **主动暴露短板（明文存 key）**
   能说出"当前明文存储，生产应升级为 Fernet/AES 加密列或 KMS 托管"，反而体现工程成熟度与改进意识。
