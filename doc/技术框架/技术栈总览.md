# 技术栈与框架使用位置

后端 Python + FastAPI，前端 Vue 3 + Vite。下表按「框架 → 用在哪 → 用到什么程度」组织。

## 一、总览

| 层 | 技术 | 主要位置 | 说明 |
|---|---|---|---|
| Web | FastAPI + Uvicorn | `backend/server.py`、`backend/routers/*`（27 个模块） | 全项目 HTTP 层 |
| 校验/配置 | Pydantic v2 + pydantic-settings | `backend/config.py`、`backend/schemas.py` | Settings 单例 |
| ORM | SQLAlchemy 2.0 + aiosqlite / asyncpg | `backend/database.py`、`models.py` | 异步会话 |
| **LLM / RAG** | **LangChain** | 见第二节 | 模型调用、向量库、嵌入 |
| **工作流** | **LangGraph** | `backend/services/workflow_engine.py` | 动态建图执行 |
| 图数据库 | Kùzu / Neo4j | `backend/providers/graph_store/` | `GRAPH_STORE_PROVIDER` 切换 |
| 向量库 | Chroma / Milvus | `backend/providers/vector_store/` | 经 LangChain 封装接入 |
| 关键词检索 | rank-bm25 + jieba | `backend/providers/bm25/` | 中文分词后 BM25 |
| 精排 | sentence-transformers | `backend/providers/rerank/` | CrossEncoder，可选开启 |
| 嵌入 | HuggingFace / OpenAI | `backend/providers/embedding/` | 本地默认走前者 |
| 文档解析 | pypdfium2、python-docx、Tika、openpyxl | `backend/providers/parser/` | **自研，未用框架** |
| 文本分片 | langchain-text-splitters | `backend/core/chunker.py`、`core/splitter_langchain.py` | **自研为主，可选切 LangChain** |
| 调度 | APScheduler + croniter | `backend/services/scheduler_engine.py` | 定时任务 |
| 认证 | PyJWT + bcrypt | `backend/routers/auth.py`、`core/deps.py` | 自写 JWT，未用 OAuth2 框架 |
| 前端 | Vue 3 + Vue Router + Vite | `front/src/` | 无 UI 组件库，手写样式 |
| 前端画布 | @vue-flow/core | 工作流/图谱画布编辑器 | 拖拽编排 |
| 前端编辑器 | CodeMirror 6 | 代码/表达式编辑节点 | Python 语法高亮 |
| PDF 预览 | pdfjs-dist | `front/src/components/` | 前端渲染 PDF |
| Markdown | marked | 富文本渲染 | — |

## 二、LangChain：用在哪、用到多深

依赖以子包形式按需安装（`requirements.txt` 中 `langchain-core` / `-openai` / `-anthropic` / `-huggingface` / `-chroma` / `-milvus` / `-community` / `-text-splitters` / `-experimental`）。

### 2.1 只借用数据类型（浅层）

大量模块只是用 LangChain 的**消息模型**来组织 prompt，并未使用 Chain / Agent 等高层抽象：

| 位置 | 用到什么 | 用途 |
|---|---|---|
| `services/rag_service.py` | `SystemMessage` / `HumanMessage` | 知识问答 RAG 生成 |
| `services/oag_service.py` | 同上 | OAG 本体增强生成 |
| `services/graph_extraction_service.py` | 同上 | 图谱实体/关系抽取 |
| `services/workflow_engine.py` | 同上 | 工作流 LLM 节点执行 |
| `routers/ontology_service.py`、`ontology_function.py` | 同上 | 本体服务/函数生成 |
| `routers/agent.py`、`monitor.py` | `HumanMessage` | 智能体、连通性探测 |
| `services/file_service.py` | `langchain_core.documents.Document` | 分片写入向量库的载体 |
| `providers/vector_store/base.py` | `langchain_core.embeddings.Embeddings` | 向量库适配层的类型契约 |

### 2.2 真正承担职责（深层）

| 位置 | 组件 | 说明 |
|---|---|---|
| `providers/llm/__init__.py` | `ChatOpenAI` / `ChatAnthropic` | 所有 LLM 的唯一出口；并对 langchain-openai 打补丁，保留 DeepSeek/Qwen 的 `reasoning_content` |
| `providers/embedding/__init__.py` | `HuggingFaceEmbeddings` / `OpenAIEmbeddings` | 嵌入模型单例 |
| `providers/vector_store/chroma.py` | `langchain_chroma.Chroma` | Chroma 集合读写 |
| `providers/vector_store/milvus.py` | `langchain_milvus.Milvus` | Milvus 读写 |
| `providers/rerank/__init__.py` | `langchain_community.cross_encoders.HuggingFaceCrossEncoder` | 召回精排（可选，默认关闭） |
| `core/splitter_langchain.py` | `RecursiveCharacterTextSplitter` / `MarkdownHeaderTextSplitter` / `SemanticChunker` | 文本分片可选后端（`CHUNK_BACKEND=langchain`） |

**结论**：LangChain 在本项目中是**模型与存储的适配层 + 消息抽象**，不是编排层。没有使用 `Chain`、`RunnableSequence`、`AgentExecutor`、`Retriever` 体系，retrieval 是项目自己写的（`providers/retrieval/rrf_fuse`）。因此迁移成本可控——只需替换上述 provider 即可脱离 LangChain。

## 三、LangGraph：唯一使用场景是工作流引擎

全项目 LangGraph 只出现在 `backend/services/workflow_engine.py`：

- **动态建图**：运行时把前端画布的 JSON 定义（nodes/edges）翻译成 `StateGraph`——逐节点 `add_node`，按出边类型 `add_edge` / `add_conditional_edges`，最后 `g.compile()`。
- **条件路由**：分支节点根据节点输出决定走向 `END` 或下一节点。
- **状态传递**：`GraphState` 在节点间流转，支持 `{{var}}` / `var()` 模板取值。
- **流式与回调**：SSE 推送节点输出与执行进度。

**状态：checkpointer 未启用。** `langgraph-checkpoint-sqlite` 已在 `requirements.txt` 声明，但代码里只预留了 `thread_id`（`workflow_engine.py:2046`），没有真正挂载 checkpointer，因此**当前不支持断点恢复/重放**。

## 四、LlamaIndex：未使用

全仓库（含前端、依赖清单）搜索 `llama_index` / `llama-index` 命中 **0 处**，本项目没有引入 LlamaIndex。

对应关系是：**LlamaIndex 原本负责的那部分工作，本项目是自研的。**

| LlamaIndex 的能力 | 本项目的替代实现 |
|---|---|
| `SimpleDirectoryReader` / LlamaParse 文档解析 | `providers/parser/` 自研（pypdfium2/docx/Tika），带 PDF 页码回填、断行重排 |
| `SemanticSplitterNodeParser` 等切分 | `core/chunker.py` 自研 5 策略 + `core/doc_profiler.py` 策略推荐 |
| `IngestionPipeline`（去重/缓存/增量） | `services/file_service.py:_process_file_bg` 手写流式流水线 |
| `VectorStoreIndex` 检索 | `providers/vector_store/` + `services/rag_service.py` 自研（向量 + BM25 + RRF） |
| `KnowledgeGraphIndex` / `PropertyGraphIndex` | `providers/graph_store/` + `services/graph_extraction_service.py` 自研抽取 |

未引入的原因（也是当前的取舍）：

- **解析要深度定制**：需要保留页码偏移、标题层级、章节结构以支撑来源定位，通用 Loader 给不了。
- **图谱要受本体约束**：`graph_extraction_service.py` 的约束模式是按本体 Schema 抽取的，`PropertyGraphIndex` 的自由抽取模式不匹配。
- **避免双套抽象**：Document / Node 与 LangChain 的 Document 并存会增加转换层。

如果后续要补的能力是**增量入库去重、断点续跑、标准化 ingestion**，那 LlamaIndex 的 `IngestionPipeline` 是唯一值得引入的模块；其余部分替换收益不大。

## 五、边界小结

```
文档解析 ──► 自研（parser/）              ┐
文本分片 ──► 自研为主 + 可选 LangChain     ├─ RAG 数据侧：自研占主导
向量存储 ──► LangChain 封装（chroma/milvus）│
混合检索 ──► 自研（BM25 + RRF）            ┘
LLM 调用 ──► LangChain 封装（openai/anthropic）─┐
流程编排 ──► LangGraph（仅工作流）              ├─ LLM 应用侧：框架占主导
提示组织 ──► LangChain messages                ┘
```

**一句话**：LangChain 负责「怎么连模型和向量库」，LangGraph 负责「工作流怎么跑」，其余数据加工链路主要自研，LlamaIndex 未引入。
