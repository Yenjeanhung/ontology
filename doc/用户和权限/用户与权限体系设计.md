# KnowSource 用户与权限体系设计文档

> 目标：为 KnowSource 补齐**用户管理、权限管理、操作日志、上下线管理（强制下线）**四大能力。
> 状态：**已确认并按方案 A 实现**（P0–P5 全部完成），详见第 16 章「落地说明」
> 版本：v1.1 (2026-09-11)

---

## 1. 背景与目标

### 1.1 现状

| 维度 | 现状 |
|------|------|
| 认证 | **完全没有**。backend 全量检索 `login/auth/jwt/session/permission/role` 零命中 |
| 授权 | **没有任何鉴权**。21 个 router 全部裸奔，`server.py` CORS 为 `allow_origins=["*"]` |
| 数据库 | 45 张表，**无** `users/roles/permissions/sessions` 任何一张 |
| 前端 | Vue 3 + vue-router，**无路由守卫、无 `meta.requiresAuth`**；菜单硬编码在 `App.vue:93-146` |
| 日志 | `middleware/access_log.py` 只写**文件**（IP/方法/路径/状态码/耗时），**不入库**；`core/tracing.py` 服务层 AOP 方法日志，不入库 |
| "人"的概念 | 仅自由文本：工作流人工节点 `operator`（前端 localStorage 自报姓名，不做校验）、本体版本 `created_by`/`reviewer` |

### 1.2 目标（本次要做）

| 编号 | 能力 | 说明 |
|------|------|------|
| G1 | **用户管理** | 用户的增/删/改/查、启停用、重置密码、归属用户组、密码策略 |
| G2 | **权限管理** | 角色 + 权限点（菜单/接口/按钮）的授权模型，支持按用户组批量授权 |
| G3 | **操作日志** | 登录/登出/被踢等认证事件 + 各类业务操作审计，可查询、可导出 |
| G4 | **上下线管理** | 在线会话可视化，支持单会话/单用户/全局强制下线，登录策略可控 |
| G5 | 平滑接入 | 不破坏现有 21 个 router 的业务语义，可灰度开关 |

## 2. 对标：Palantir 的用户与权限体系是怎么做的

> 直接回答"也是基于角色吗"：**是，但不止于角色。** Foundry 是
> **「身份（Users/Groups）→ 自主控制（Project + Roles，类 RBAC）→ 强制控制（Markings / Classification / Organizations）→ 全量审计」** 的叠加模型。

### 2.1 四层模型

```
┌──────────────────────────────────────────────────────────────┐
│ ① 身份层  Users / Groups / Service Accounts                  │
│    来源：企业 IdP（SAML / OIDC / SCIM 同步），平台内组为补充   │
├──────────────────────────────────────────────────────────────┤
│ ② 自主访问控制（DAC）Projects + Roles                         │
│    Project 是一等安全边界；Role 授予"用户或组"而非个人优先     │
│    默认角色：Owner > Editor > Viewer > Discoverer             │
├──────────────────────────────────────────────────────────────┤
│ ③ 强制访问控制（MAC）Markings / Classification / Orgs & Spaces │
│    与 Role 并行生效，Role 再大也绕不过                        │
├──────────────────────────────────────────────────────────────┤
│ ④ 审计  Audit：认证事件 + 资源访问 + 管理动作全量留痕           │
└──────────────────────────────────────────────────────────────┘
```

### 2.2 关键设计点（值得抄的）

| 设计点 | Palantir 做法 | 为什么 |
|--------|--------------|--------|
| **角色不是层级，是"操作集合"** | "Roles are independent sets of operations rather than a strict hierarchy. A more powerful role is not guaranteed to include every operation granted by another role." | 避免"高级角色 = 全部低级权限并集"的僵化，可按职能切分（如"能发布但不能删"） |
| **按组授权，不按人授权** | "We recommend granting group roles at the project level… reducing the clutter of individual role grants." | 权限治理成本从 O(人×资源) 降到 O(组×资源) |
| **只在边界层授权，禁止逐资源授权** | 项目设置里默认**关闭**文件夹/文件级 role grant，强制在项目级授权 | 权限可解释、可收敛；否则权限碎片化无法审计 |
| **强制标记 Markings（MAC）** | 语义为 **AND**：用户必须满足资源上**所有** marking 才能访问；标记**随数据沿依赖链传播**（派生数据集自动继承）；**Owner 也摘不掉**标记——摘标记需要单独的 `Expand Access` 权限 | 职责分离（separation of duties），防止"数据所有者自己扩大访问面" |
| **Marking 只用于限制，不用于授予** | "Markings should not be used to provision access." 有 PII 资格 ≠ 有 PII 数据访问权，还得有 Role | 资格（eligibility）与授权（grant）分离 |
| **访问申请闭环** | 无权限时可发起 Access Request，Owner 审批，走 Approvals 收件箱 | 权限变更有流程、有留痕 |
| **会话作用域 Scoped Sessions** | 登录后选择本次会话使用哪几个 Marking，做工作场景隔离 | 降低误操作与越权面 |
| **全量审计** | 认证事件、资源读写、管理动作统一进审计，DPO 可追溯 | 合规基线 |

> 补充：Palantir **Gotham**（面向政府/国防）比 Foundry 更偏 MAC：数据分类密级 + need-to-know + 基于目的（purpose）的访问控制。**Foundry 才是我们该对标的那一套**（数据平台 + 应用层）。

### 2.3 对 KnowSource 的启示（本设计的取舍）

| 启示 | 本设计落地方式 |
|------|--------------|
| 角色 = 权限集合（非层级） | ✅ 采用：`roles` + `permissions` 多对多，角色之间无继承 |
| 按组授权 | ✅ 采用：`user_groups`（部门/组），组可挂角色；也允许直接挂人以支持例外 |
| 在"边界"授权而非逐条数据 | ✅ 采用：主授权边界 = **功能权限（菜单/接口）**；数据边界用**知识库/本体类别**授权（P2） |
| Markings 强制标记 | 🔶 预留：`data_markings` 表结构先设计，P1 只建表不启用；P2 用于知识库/实体的敏感级控制 |
| 全量审计 | ✅ 采用：认证日志 + 操作审计双表，中间件自动采集 + 业务埋点 |
| 访问申请/审批 | ⬜ 不做：已有工作流人工节点能力，二期可复用，P1 不引入 |

## 3. 总体设计

### 3.1 分层架构

```
┌─────────────────────────────────────────────────────────────┐
│ Vue3 前端                                                     │
│  路由守卫(未登录→/login) │ 菜单按权限过滤 │ v-perm 按钮级控制  │
└───────────────┬─────────────────────────────────────────────┘
                │ Authorization: Bearer <jwt>
┌───────────────▼─────────────────────────────────────────────┐
│ 中间件层  backend/middleware/                                 │
│  ① AuthMiddleware   认证：解析 JWT + 校验会话状态（可踢）      │
│  ② PermMiddleware   授权：method+path → perm_code → 校验      │
│  ③ AuditMiddleware  审计：请求/响应 → 异步队列 → 落库          │
├─────────────────────────────────────────────────────────────┤
│ 路由层  routers/auth.py  user.py  role.py  session.py  audit.py│
├─────────────────────────────────────────────────────────────┤
│ 服务层  services/auth_service.py  user_service.py             │
│         role_service.py  session_service.py  audit_service.py │
├─────────────────────────────────────────────────────────────┤
│ 数据层  PostgreSQL 16（asyncpg）                               │
│  users │ user_groups │ roles │ permissions │ user_sessions    │
│  auth_logs │ audit_logs │ security_settings                   │
└─────────────────────────────────────────────────────────────┘
```

### 3.2 核心决策（需确认，见第 12 章）

| 决策点 | 本方案选择 | 备选 |
|--------|-----------|------|
| 认证凭证 | **JWT（含 sid）+ 服务端会话表**（无状态与可撤销兼得） | 纯 Session Cookie / 纯 JWT（不可踢，❌） |
| 踢人即时性 | 内存缓存（TTL 10s）+ 主动失效 → 单worker **立即**、多worker **≤10s** | 引入 Redis Pub/Sub（当前未部署） |
| 授权模型 | **RBAC 为主**（用户-角色-权限），组为推荐授予对象 | ABAC（复杂，P2 预留） |
| 权限粒度 | **菜单 + 接口 + 按钮** 三级 | 仅菜单（不安全） |
| 密码哈希 | **bcrypt**（passlib） | argon2 |
| 会话存储 | **DB 表 `user_sessions`**，不引入 Redis | Redis |
| 日志落库 | **异步队列 + 批量写入**，不阻塞业务 | 同步写（❌ 影响性能） |
| 时间字段类型 | **VARCHAR(ISO8601)** —— 与项目现有 45 张表保持一致 | TIMESTAMP |

## 4. 认证设计（G1 基础）

### 4.1 登录流程

```
POST /api/auth/login {username, password[, captcha]}
   │
   ├─ 校验用户存在 / status=active / 未锁定（失败次数 < N）
   ├─ bcrypt 校验密码
   │    ├─ 失败 → 失败次数+1，达阈值锁定 lock_minutes，写 auth_logs(result=fail)
   │    └─ 成功 → 失败次数清零
   ├─ 检查同账号会话数上限 max_sessions_per_user（默认 5）
   │    └─ 超限 → 挤掉最旧的会话（记 kicked，reason=max_sessions）
   ├─ 生成 sid(uuid4) → 写 user_sessions(online, ip, ua, login_at, last_active_at)
   ├─ 签发 JWT: {sub:user_id, sid, username, ver:token_version, iat, exp}
   └─ 返回 {access_token, refresh_token, expires_in,
            user:{id,username,nickname,avatar,roles[]}, permissions:[perm_code...]}
```

**JWT 有效期**：access 2 小时 / refresh 7 天（可配置）。
**刷新**：`POST /api/auth/refresh` → 校验 refresh_token → 校验会话仍 online → 签发新 access_token。

### 4.2 鉴权中间件流程（`AuthMiddleware`）

```
1. 路径白名单 → 直接放行（/api/auth/login、/api/auth/refresh、/api/health、/docs*、静态资源）
2. 取 Authorization: Bearer <token>；缺失 → 401
3. 验签 + 验 exp；失败 → 401（code=TOKEN_INVALID，前端跳登录）
4. 内存缓存查 sid 状态（TTL 10s，miss 回 DB）
   ├─ status != online（kicked/offline/expired）→ 401 KICKED → 前端提示"已被强制下线"
   ├─ user.status != active（disabled/locked）→ 401 DISABLED
   ├─ jwt.ver != user.token_version → 401（改密/禁用/踢全部会 +1）
   └─ 空闲超时：now - last_active_at > idle_timeout → 置 expired → 401
5. 通过 → request.state.user = {user_id, username, sid, roles, permissions}
6. 节流刷新 last_active_at（30s 一次），并刷新内存缓存
```

> **为什么不引入 Redis**：当前 docker-compose 未部署 Redis，且 KnowSource 为单机/小规模部署。用「DB 权威 + 进程内 10s 缓存」即可满足踢人需求；未来多副本部署时把缓存换 Redis 即可，`SessionService` 接口不变。

### 4.3 退出与强制下线

| 动作 | 触发 | 实现 |
|------|------|------|
| 主动退出 | `POST /api/auth/logout` | 当前 session → `offline`，清前端 token，写 auth_logs |
| 踢单会话 | `DELETE /api/sessions/{sid}` | `status='kicked'`, `kicked_by`, `kick_reason`；**主动失效内存缓存**（同进程立即生效） |
| 踢某用户全部 | `POST /api/sessions/user/{uid}/kick-all` | 该用户所有 online 会话 → kicked |
| 全局踢出 | `POST /api/sessions/kick-all` | 除当前操作者外全部踢出（应急场景，二次确认 + 审计） |
| 禁用用户 | `PATCH /api/users/{uid}` status=disabled | 踢全部会话 **且** `token_version += 1`（双保险） |
| 改密/重置密码 | — | `token_version += 1`，其他设备全部失效 |
| 空闲超时 | 中间件判定 | `last_active_at` 超时自动置 expired |

## 5. 授权设计（G2）

### 5.1 模型

```
        ┌────────┐        ┌─────────────┐        ┌────────────┐
        │  User  │──M:N──▶│  UserGroup  │──M:N──▶│    Role    │
        └────────┘        └─────────────┘        └────────────┘
             │                                          │
             │  ┌── user_roles（直接挂角色）─────────────┤
             │                                          │ M:N
             │  └── user_permissions（例外授权，慎用）   ▼
             └──────────────────────────────▶┌──────────────────┐
                                             │   Permission     │
                                             │ (menu/api/action)│
                                             └──────────────────┘
```

**有效权限 =（用户直接角色 ∪ 所属组的角色）展开的权限 ∪ 用户例外权限 − 显式拒绝(预留)**
**超级管理员 `super_admin`：内置、不可删除、不可改权限，鉴权时直接放行。**

### 5.2 权限点（Permission）定义

字段：`code` / `name` / `module` / `type`（`menu` 菜单可见 | `api` 接口 | `action` 按钮）/ `resource`（接口匹配用：`METHOD /path` 支持 `*` 通配）/ `sort_order` / `is_system`

命名规范：`<module>:<action>`，系统管理类用 `<module>:<sub>:<action>`

| 模块 | 权限码示例 |
|------|-----------|
| 知识库 | `kb:view` `kb:create` `kb:update` `kb:delete` `kb:query` |
| 文件 | `file:view` `file:upload` `file:delete` `file:crawl` |
| 本体 | `ontology:view` `ontology:create` `ontology:update` `ontology:delete` `ontology:version:manage` `ontology:suggestion:review` |
| 实体/图谱 | `entity:view` `entity:edit` `graph:view` `graph:sync` `graph:analysis` |
| 向量 | `vector:view` `vector:manage` |
| 智能体/技能 | `agent:view` `agent:run` `agent:manage` `skill:manage` |
| 工作流 | `workflow:view` `workflow:design` `workflow:run` `workflow:task:handle` |
| 定时 | `schedule:view` `schedule:manage` |
| 配置 | `config:llm:manage` `config:monitor:view` |
| **系统** | `system:user:manage` `system:role:manage` `system:audit:view` `system:audit:export` `system:session:manage` `system:settings:manage` |

接口匹配示例：`DELETE /api/kb/{kb_id}` → `kb:delete`；`POST /api/ontology-services/{id}/invoke` → `workflow:run`（或 `ontology:service:invoke`）。
> P1 只覆盖**写操作 + 敏感读**；全量 GET 默认放行（避免 300+ 接口逐个登记），由菜单权限控制可见性。

### 5.3 预置角色

| 角色 code | 名称 | 说明 |
|-----------|------|------|
| `super_admin` | 超级管理员 | 内置，**全放行**，不可删除/改权限 |
| `system_admin` | 系统管理员 | 用户/角色/日志/会话/配置全管 + 业务只读 |
| `knowledge_admin` | 知识库管理员 | 知识库+文件+实体+图谱全权限，不含用户管理 |
| `ontology_engineer` | 本体工程师 | 本体定义全权限 + 版本/建议审核 |
| `data_operator` | 数据运营 | 文件/知识库/实体增删改，无本体定义权 |
| `analyst` | 分析员 | 查询/图谱/智能体/工作流运行，只读为主 |
| `auditor` | 审计员 | 全模块只读 + `system:audit:view/export` |
| `viewer` | 访客 | 全模块只读 |

### 5.4 数据级权限（P2 预留，对标 Markings）

- 授权边界：**知识库（kb_id）/ 本体类别（category_id）**
- 表：`data_markings`（标记定义）、`resource_markings`（资源↔标记）、`user_markings`（用户/组↔标记）
- 语义：**AND**，用户需满足资源上全部标记；标记随派生传播（本体重建/实体抽取时继承）
- P1 只建表 + 管理界面留占位，**不启用校验**

## 6. 操作日志设计（G3）

### 6.1 双表

| 表 | 内容 | 保留期 |
|----|------|-------|
| `auth_logs` | 登录成功/失败、登出、被踢、会话过期、改密、重置密码、锁定解锁 | 默认 365 天 |
| `audit_logs` | 业务操作：增删改、权限变更、配置变更、导入导出、运行/发布等 | 默认 180 天 |

> 分表原因：认证日志是安全基线（保留更久、查询模式不同），操作日志量大会被高频筛选。

### 6.2 `audit_logs` 字段

| 字段 | 说明 |
|------|------|
| `id`, `created_at` | 主键、时间（ISO8601，索引） |
| `user_id`, `username`, `nickname` | 操作人（**冗余存快照**，用户被删也能追溯） |
| `session_id` | 会话（可关联到 IP/UA） |
| `module`, `action`, `action_label` | 模块（kb/ontology/system…）、动作码（create/update/delete/login…）、中文名 |
| `target_type`, `target_id`, `target_name` | 操作对象（如 `knowledge_base` / `kb_abc123` / "金融知识库"） |
| `method`, `path`, `query` | HTTP 信息 |
| `params` | 请求参数 JSON（**已脱敏**） |
| `before_value`, `after_value` | 变更前/变更后 JSON（关键实体变更才记，用于 diff 回看） |
| `result` | `success` / `fail` |
| `status_code`, `error_msg` | HTTP 状态码、错误信息 |
| `ip`, `user_agent`, `request_id` | 溯源信息 |
| `duration_ms` | 耗时 |
| `source` | `http` / `system` / `schedule`（定时/系统自动执行也留痕） |

### 6.3 采集方式

```
① 中间件自动采集（覆盖 80%）
   AuditMiddleware：按 (method, path) → 匹配 perm_code → 得到 module/action
   ├─ 白名单过滤：GET 列表/详情/轮询/健康检查 默认不记（可配置 LOG_GET=true）
   ├─ 只记写操作 + 显式标记的敏感读（如日志查询、导出）
   └─ 敏感字段脱敏后再入队

② 业务埋点（覆盖关键 20%）
   AuditService.record(db, module, action, target, before, after, ...)
   用于：用户/角色/权限变更（必须记 before/after diff）、配置变更、本体发布、工作流运行等

③ 异步落盘
   asyncio.Queue(maxsize=5000) + 后台 worker：每 1s 或满 100 条批量 INSERT
   队列满 → 丢弃并计 WARN（绝不阻塞业务）；落库失败 → 转写 logs/audit_fallback.log
```

### 6.4 脱敏规则

`password` `new_password` `old_password` `confirm_password` `token` `access_token` `refresh_token` `api_key` `secret` `authorization` `cookie` 等 key 的值统一替换为 `***`，递归处理嵌套 JSON，截断超长值（>2000 字符）。

### 6.5 查询与导出

- 列表：`GET /api/audit/logs` 支持 `user_id / module / action / result / keyword（目标名或用户名模糊）/ start / end` 过滤 + 分页 + 排序
- 详情：弹窗展示 `params / before / after` 的**结构化 diff**
- 导出：`GET /api/audit/logs/export?...` → CSV（`system:audit:export` 权限，且导出动作本身记审计）
- 归档：复用已有 `scheduler_engine`，每月 1 号清理超期数据（可按配置改为导出 CSV 到 `data/audit_archive/` 后删除）
- **审计日志不可编辑、不可单条删除**（`is_system` 保护），仅能按策略归档清理

## 7. 上下线管理（G4）

### 7.1 在线会话列表字段

| 列 | 来源 |
|----|------|
| 用户（用户名/昵称/头像） | users |
| 状态 | online / offline / kicked / expired |
| IP、UA（解析出浏览器+OS） | user_sessions |
| 登录时间、最后活跃时间、在线时长 | user_sessions |
| 会话数（该用户当前会话数徽标） | 聚合 |

## 11. 安全与合规

| 项 | 措施 |
|----|------|
| 密码 | bcrypt(rounds=12) 哈希，**永不明文存储/返回**；改密需验证原密码；重置生成随机临时密码 + `must_change_password=1` |
| 传输 | 建议生产环境 HTTPS；Cookie 方案下用 `HttpOnly + Secure + SameSite=Lax` |
| Token | 密钥从 `backend/.env` 的 `SECRET_KEY` 读取（无默认值，缺失启动报错）；refresh token 可吊销 |
| CORS | `server.py:216` 的 `allow_origins=["*"]` **收紧**为白名单（配合 `allow_credentials`） |
| 限流 | 登录接口按 IP + 用户名限流（如 10 次/分钟），防爆破 |
| 越权 | 所有用户/角色/日志接口走权限中间件；**超级管理员角色不可删除、不可取消** |
| 自我防护 | 不能禁用/删除自己；不能取消自己的 `system:*` 权限（防把自己锁死） |
| 审计 | 审计日志**不可编辑/删除**，导出动作本身也记审计 |
| 脱敏 | 日志中密码/密钥类字段统一 `***`；用户列表不返回 `password_hash` |
| 初始化 | 首次启动 seed 内置 `admin` 账号 + `super_admin` 角色，首次登录强制改密 |

## 12. 兼容、灰度与迁移

1. **总开关**：`security_settings.auth_enabled = false` 时中间件全放行，方便本地调试与灰度；默认 `true`。
2. **白名单**：`/api/auth/*`、`/api/health`、`/docs*`、`/openapi.json`、静态资源无需登录。
3. **现有接口零改动**：鉴权靠**中间件**统一拦截，不逐个 router 加 `Depends`；仅极少数需要"当前用户"的接口（如记录 `created_by`）从 `request.state.user` 读取。
4. **存量数据**：无用户数据，无需迁移。历史 `operator` / `created_by` 文本字段**保持不变**，仅在新写入时优先使用真实用户名。
5. **SSE 兼容**：现有 `access_log.py` 已是纯 ASGI 中间件；新的 Auth/Perm 中间件沿用同样写法，**不读取/缓存响应体**，保证 SSE 流式可用。
6. **测试**：`backend/test/` 新增 auth/perm/audit 用例；CI 用 SQLite（注意避免 `ADD COLUMN IF NOT EXISTS`）。

### 16.2 与设计的差异（有意为之，均已验证）

| 项 | 设计描述 | 实际做法 | 原因 |
|----|---------|---------|------|
| 审计中间件记 params | 中间件记录请求参数 | **中间件不读请求体**，只记 method/path/状态码/耗时/IP/UA；params 与 before/after 由业务埋点 `AuditService.record()` 补充 | 读 body 会破坏分片上传与 SSE 流式响应；关键操作（用户/角色/权限/策略变更）已用埋点记录前后快照 |
| 权限点登记方式 | 逐个接口登记 | **模块前缀 + HTTP 动词自动推导**（`resolve()`），仅特殊动作走显式规则表 | 现有 300+ 接口逐个登记不现实；新增业务接口也不会因漏登记而误放行 |
| 超级管理员权限绑定 | 不参与鉴权 | 仍然绑定全部 65 个权限点，仅鉴权时走放行分支 | 便于页面展示与排查 |
| 前端存量接口改造 | 逐个加 token | **`api/interceptor.js` 全局拦截 fetch / EventSource** | `api/index.js` 是 94KB 历史巨型文件，逐个改造风险高；新代码用 `request()` |
| SSE 鉴权 | 未提及 | 支持 `?token=` 查询参数 + 拦截器自动追加 | `EventSource` 无法自定义请求头（通知/监控/文件进度 3 处 SSE） |
| 中间件顺序 | 未细化 | `AccessLog → Auth → Audit → Permission → CORS` | Auth 必须早于 Audit/Permission（否则拿不到用户）；Audit 早于 Permission（越权尝试也要留痕） |
| 口令库 | passlib | 直接用 `bcrypt` | passlib 1.7.4 与 bcrypt 4.x 存在已知兼容问题 |

### 16.3 验证结果

- 单元测试：`backend/test/test_auth_permissions.py`（11 个用例，全部通过）——覆盖路径通配、接口→权限码推导、敏感读保护、脱敏、密码哈希与策略
- 端到端冒烟（已清理测试脚本与脏数据）：
  - 无 token 访问 `/api/kb` → 401 `NOT_LOGIN`
  - 超级管理员访问全部接口 → 200
  - 仅 `viewer` 角色的用户 `POST /api/kb` → 403 `FORBIDDEN (kb:create)`
  - 该用户 `GET /api/users` → 403 `FORBIDDEN (system:user:manage)`
  - 管理员踢人后该用户请求 → 401 `KICKED`
  - 被拒绝的越权请求在审计日志中留痕：`smoke_viewer POST /api/kb fail 403`
- 种子数据：65 个权限点、8 个内置角色

### 16.4 已知限制 / 后续项

1. **数据级权限（Markings）未启用**：`data_markings` 等表按约定只做了预留，未建表。需要时再追加 migration。
2. **登录验证码、双因素**：字段已预留（`captcha_enabled`），未实现。
3. **LDAP / SSO**：未实现，仅保留扩展位（`AuthService.login` 可替换为外部身份源校验）。
4. **多副本部署**：当前踢人依赖进程内缓存，多副本时最多延迟 `AUTH_CACHE_TTL_SECONDS`（默认 10s）。若要严格即时，把 `SessionService` 的缓存换成 Redis 即可，接口不变。
5. **审计日志归档**：提供手动触发接口 `POST /api/audit/archive`，未挂到定时调度；如需自动清理可用现有 `scheduler_engine` 建一条月度计划。
