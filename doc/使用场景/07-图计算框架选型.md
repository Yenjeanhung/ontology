# 图计算框架选型：什么时候该上 GraphX / Plato

> 状态：**待确认** —— 确认后作为 `GraphComputeProvider` 层的实施依据。
> 日期：2026-08-29
> 关联文档：[GDS 实体链接与知识补全设计](../图分析/GDS实体链接与知识补全_功能设计.md)（M0 已规划 GDS 基础层）、[工作流功能设计](../工作流/工作流_功能设计.md)、[定时管理](../定时管理/)
> 关联代码：`backend/providers/graph_store/__init__.py`、`backend/services/scheduler_engine.py`、`backend/services/monitor_service.py`、`backend/config.py`

---

## 0. 一句话结论

**不要为了上框架而上框架。** 按图规模分三档选型；先用 `GraphComputeProvider` 把抽象层立住，
GDS 单机先跑通；只有当图规模真的越过 5000 万边（网安、生物医学、全市场金融图谱）时，GraphX/Plato 才有真实必要性。

---

## 1. 三档选型

```
图规模                选型                                    典型场景
────────────────────────────────────────────────────────────────────────────
< 500 万边      │  Neo4j GDS 单机（在线 + 离线皆可）      │  民航维修、供应链
500 万~5000 万  │  GDS 吃力 / NetworkX 离线批跑           │  金融（单机构）、司法
> 5000 万边     │  GraphX(Spark) / Plato / GraphScope     │  网安、生物医学、全市场金融
```

| 框架 | 优势 | 劣势 | 适用 |
|---|---|---|---|
| **Neo4j GDS** | 与图库一体，投影即用；算法齐全；Cypher 调用方便 | 社区版并发任务 = 1；内存受限；需商业版才能水平扩展 | 中小规模、交互式 |
| **NetworkX** | 纯 Python、零部署、Kùzu 模式的天然降级路径 | 单机内存，百万边以上明显吃力 | 降级路径 / 小图批跑 |
| **GraphX (Spark)** | 与大数据栈一体；Pregel API；可处理十亿边 | 算法库不如 GDS 丰富；Spark 调优成本高；迭代式算法性能一般 | 超大规模离线批跑 |
| **Plato** | 腾讯开源，万亿边级；算法性能强（针对迭代式算法优化） | 部署与运维复杂；生态与文档弱于 Spark | 极致规模的离线批跑 |
| **GraphScope** | 一站式（图分析 + 图查询 + GNN）；兼容 NetworkX/Gremlin API | 相对年轻；运维复杂度高 | 需要图分析 + GNN 一体的场景 |

## 2. 统一抽象：GraphComputeProvider

与现有 `GraphStoreAdapter` 平级新增一个计算层抽象，**保持项目一贯的可插拔设计哲学**：

```
providers/graph_compute/            （新增，与 providers/graph_store/ 平级）
├── __init__.py                     GraphComputeProvider 抽象基类
├── gds_provider.py                 Neo4j GDS 实现
├── networkx_provider.py            单机降级实现
└── graphx_provider.py              Spark GraphX 实现（PySpark 调用）
```

### 抽象基类（草案）

```python
class GraphComputeProvider(ABC):
    """图计算层：只读计算，结果由调用方回写。不触碰权威存储。"""

    @abstractmethod
    def available(self) -> bool:
        """探测计算后端是否可用（GDS 插件 / Spark 集群）。"""

    @abstractmethod
    def ensure_projection(self, kb_id: str) -> str:
        """确保 KB 的计算投影存在（幂等），返回投影名。"""

    @abstractmethod
    def compute(self, kb_id: str, tasks: list[str]) -> dict:
        """批量执行图算法，返回 {task: result}。task 见 §3。"""

    @abstractmethod
    def graph_stats(self, kb_id: str) -> dict:
        """投影指纹（实体数/关系数），供失效判断。"""
```

**设计原则（三条，缺一不可）**

1. **只读计算，结果外挂**：图计算层**绝不直接写图谱**。所有结果返回给调用方，
   由调用方经 `EntityService` 走权威 SQLite 事务落库。与现有「SQLite 权威 + 图库同步」原则一致。
2. **降级即现状**：`available()` 返回 False 或抛异常 → 调用方捕获后跳过该算法，
   行为退回无图计算时的状态，**零回归**。沿用 GDS 设计文档里已确立的思路。
3. **离线批跑，不进在线链路**：图计算由 scheduler 触发（低峰期），
   结果写入实体/关系属性表，在线查询**只读结果**。Spark 永不出现在 OAG 查询链路上，延迟可控。

## 3. 算法任务清单（跨场景通用）

`compute()` 的 `tasks` 参数取值，按场景自由组合：

| task | 算法 | 输出 | 适用场景 |
|---|---|---|---|
| `pagerank` | PageRank（可设边权重） | `{entity_id: score}` | 全场景 |
| `ppr` | Personalized PageRank | `{entity_id: score}` | 金融传导、OAG 实体链接 |
| `betweenness` | 介数中心性 | `{entity_id: score}` | 供应链瓶颈、网安跳板机 |
| `degree` | 加权度中心性 | `{entity_id: score}` | 运维高发部件 |
| `community` | 社区发现（Louvain / LPA） | `{entity_id: community_id}` | 全场景 |
| `embedding` | 图嵌入（FastRP / node2vec） | `{entity_id: [float]}` | 全场景 |
| `knn` | 嵌入近邻 | `{entity_id: [(nbr, sim)]}` | OAG 实体链接、相似案例 |
| `similarity` | 节点相似度（Jaccard 邻居） | `[(a, b, score)]` | 类案、知识补全 |
| `link_prediction` | 链路预测（未连接对打分） | `[(a, b, score)]` | 药物重定位、知识补全 |
| `components` | 连通分量 | `{entity_id: comp_id}` | 网安扩散范围 |
| `articulation` | 割点 / 桥 | `[entity_id]` | 供应链单点依赖 |
| `paths` | 加权最短路径 / 路径枚举 | `[[entity_id]]` | 金融穿透、网安攻击链 |
| `cycles` | 环路检测 | `[[entity_id]]` | 金融循环担保 |

> 各场景具体用哪些算法，见对应场景文档的「图计算算法映射」章节。

## 4. 结果落库与生命周期

### 4.1 结果存哪里

| 结果类型 | 存储位置 | 说明 |
|---|---|---|
| 实体级标量（pagerank / 度 / 社区号 / 中心度） | `entities.compute_scores`（JSON 列）+ 图库节点属性 | 供排序、过滤、可视化上色 |
| 实体级向量（embedding） | `entities.graph_embedding`（JSON）+ 图库节点属性 | 供 KNN 检索；Kùzu 降级路径也复用此列 |
| 关系级建议（链路预测 / 相似度对） | `relation_suggestions` 表（GDS 文档已设计） | 走人工审核闭环 + tombstone 防重推 |

> 前两类**不新增表**，扩展现有 `entities` 表两个 JSON 列即可（SQLite 加列成本低）。
> 第三类直接复用 GDS 设计文档里已规划好的两张表，**零新增设计**。

### 4.2 失效与重算

沿用 GDS 设计文档 4.3 的**指纹失效**机制：

```
指纹 = hash(实体数, 关系数, max(entities.updated_at))
```

- **惰性检查**：任务运行前比对指纹，不一致才重建投影 + 重算
- **主动标脏**：抽取完成、实体/关系 CRUD 成功后使该 KB 指纹失效
- **定时兜底**：由 scheduler 在低峰期统一重算

### 4.3 并发控制

| 后端 | 约束 | 对策 |
|---|---|---|
| GDS 社区版 | 并发任务数 = 1 | 模块级 `_gds_lock` 串行化重操作（仿 `_kuzu_write_lock`）；查询类读投影不加锁 |
| GraphX | Spark 作业排队 | 提交后轮询状态，同一 KB 的任务互斥（运行中不重复提交） |

## 5. 与现有模块的对接

```
[定时管理 /schedules]  cron: 每周日 02:00
        │  触发
        ▼
[工作流]  graph_compute 节点（建议新增节点类型，见 §6）
        │
        ▼
[GraphComputeProvider.compute(kb_id, tasks)]
        ├─ available() == False → 跳过，记日志，监控黄标
        ├─ ensure_projection()（指纹命中则跳过）
        └─ 执行算法 → 返回结果
        │
        ▼
[结果落库]  EntityService 走 SQLite 事务 → best-effort 同步图库属性
        │
        ▼
[通知]  新增建议数 > 0 → notifications（复用现有通知机制）
        │
        ▼
[监控]  /config/monitor 展示：最近一次运行时间、耗时、任务数、降级状态
```

| 需要 | 来自 | 位置 |
|---|---|---|
| 调度触发 | `scheduler_engine` / `scheduler_service` | services/ |
| 图遍历与投影 | `GraphStoreAdapter` | providers/graph_store/\_\_init\_\_.py |
| 结果写实体 | `EntityService` | services/entity_service.py |
| 关系建议审核闭环 | `relation_suggestions` + tombstones | GDS 设计文档 §6.2 |
| 通知 | `notification_hub` | services/notification_hub.py |
| 监控 | `monitor_service` | services/monitor_service.py |

## 6. 需要新增的能力（缺口清单）

| 缺口 | 说明 | 优先级 |
|---|---|---|
| **`graph_compute` 工作流节点类型** | 现有节点类型 `start/end/agent/service/llm/condition/code/human` 中无图计算节点。当前可用 `code` 沙箱节点临时调用，但正式化建议新增该类型 | 高 |
| **`notification` 工作流节点类型** | 通知目前是人工节点与建议闭环的附带行为，不是独立节点 | 中 |
| **结构化数据导入通道** | `StructuredImportService` —— 网安、供应链、生物医学场景的主要数据不是文档，见 [场景三](./03-网络安全攻击链图谱.md) §5 | 高（非本场景） |
| **`entities` 表扩列** | `compute_scores` JSON、`graph_embedding` JSON | 中 |
| **大规模实体相似度** | 现有清洗是 O(n²) 且单类型 600 条上限，需换 MinHash/LSH | 中 |

## 7. 关键决策点

1. **抽象层是否本期就立**？推荐「是」——成本很低（一个基类 + 一个 GDS 实现），
   但能让后续换 GraphX 时业务代码零改动，且本身就是简历亮点。✅/❌
2. **GraphX 实现是否本期做**？推荐「否」——先跑通 GDS 主线，GraphX 等图规模真的越线再说。✅/❌
3. **图计算结果是否进在线查询链路**？推荐「否」——离线批跑 + 结果落库，在线只读。✅/❌
4. **是否新增 `graph_compute` 节点类型**？推荐「是」，但 v1 可先用 `code` 节点过渡。✅/❌
5. **NetworkX 降级是否本期做**？推荐「是」——保证 Kùzu 模式下功能不完全缺失，实现成本不高。✅/❌

## 8. 风险与对策

| 风险 | 对策 |
|---|---|
| 为了上框架而上框架，徒增运维成本 | 严格按 §1 三档执行；先用 GDS 跑出业务价值，越线再迁 |
| 图计算结果写脏图谱 | 计算层只读；结果一律经 `EntityService` 权威事务落库 |
| Spark 作业失败拖垮系统 | Spark 完全在离线链路，失败只影响本次重算，在线功能不受影响 |
| 社区版 GDS 并发 = 1 导致任务排队 | `_gds_lock` 串行 + 任务互斥 + 低峰调度 |
| 小图跑嵌入无意义 | `COMPLETION_MIN_ENTITIES` 类门槛（已有设计），低于阈值跳过并提示 |
