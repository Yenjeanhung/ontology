# 02 - 运行时层设计（函数 / 派生属性 / 工作流 / 定时计划）

> 对应交付物：`backend/scripts/seed_flight_ops_runtime.py`（一个脚本生成全部运行时数据，支持 `--force` 重建、`--verify` 试算验证）。
> 本文所有内容均已生成入库并实测通过（2026-09-09）。

---

## 1. 总览

| 类型 | 数量 | 内容 |
|---|:--:|---|
| 本体函数 | 4 | `flight_duration_min` / `etd_delay_min` / `eta_delay_min` / `leg_phase`（挂航段本体） |
| 派生属性 | 4 | 与函数一一绑定，**virtual 读时模式**（每次读取实时计算） |
| 工作流 | 2 | 航段派生属性定时物化（HTTP×4）/ 单航段运行简报（HTTP + LLM） |
| 定时计划 | 1 | 每 30 分钟触发工作流 A 批量物化 |

分层逻辑：

```
                 计划/预计时间变更（CDM 报文 / 人工修改）
                              │
        ┌─────────────────────┼──────────────────────┐
        ▼ 读时模式（自动）       ▼ 定时模式（工作流 A + 计划）  ▼ 按需模式（工作流 B）
   实体详情页刷新计算          每 30 分钟批量物化到          单航段实时计算
   派生属性即时得到新值         实体属性（列表直读）          + LLM 生成运行简报
```

## 2. 本体函数（4 个）

### 2.1 沙箱执行机制

函数代码在**子进程沙箱**中执行（`service_runtime.execute_service`）：

- 标准库白名单放行 `datetime` / `json`，禁网络、禁文件系统、禁其他 import；
- 单次执行有超时（`timeout_seconds`，默认 10s），超时即杀进程；
- 函数签名固定为 `run(params, entity, context)`：
  - `params`：按 `params_schema` 校验/类型转换后的参数（`coerce_params` 支持 number/boolean/string + default + required）；
  - `entity`：`{id, name, entity_type, ontology_id, properties}`，properties 为属性字典；
  - `context`：`{kb_id, category_id, function_code, triggered_by}`；
- 返回值即派生属性值（返回 `None` 表示"当前无法计算"）。

### 2.2 函数清单

| 函数 | 逻辑 | 参数 | 确定性 |
|---|---|---|:--:|
| **预计飞行时长** `flight_duration_min` | `ETA − ETD`（分钟）；预计时间缺失回退计划时间（ETA→SIBT、ETD→SOBT） | 无 | ✅ |
| **预计起飞延误** `etd_delay_min` | `ETD − SOBT`（分钟）；ETD 为空（无滚动预计）按正点 0 计 | `only_late: bool = false`（true 时提前到达按 0 计） | ✅ |
| **预计到达延误** `eta_delay_min` | `ETA − SIBT`（分钟）；ETA 为空按正点 0 计 | `only_late: bool = false` | ✅ |
| **当前运行阶段** `leg_phase` | now 与 OOOI 里程碑逐一比较推断阶段 | 无 | ❌（依赖当前时刻，`is_deterministic=0`） |

`leg_phase` 的阶段判定优先级（从终态往回推）：

```
取消/备降/返航（直接返回状态）→ 已到达(AIBT) → 落地滑入(ALDT) → 空中飞行(ATOT)
→ 已撤轮档(AOBT) → 待撤轮档(now≥ETD) → 地面保障（ETD−now ≤ 120 分钟，报"约 N 分钟后撤轮档"）
→ 计划中
```

### 2.3 回退语义（关键设计）

种子数据里 **ETD/ETA 仅对延误航段有值**（非延误航段为空 = 按计划运行）。函数因此统一采用回退：

```
ETD 缺失 → 用 SOBT   │  ETA 缺失 → 用 SIBT   │  两者都缺 → 返回 None
```

效果：全量 2,030 个航段（含历史正点航段）都能算出有业务意义的值——正点航段延误 = 0、时长 = 计划时长——而不是大面积空值。

## 3. 派生属性（4 个，读时模式）

| 派生属性 | 编码 | 类型 | 绑定函数 | params |
|---|---|---|---|---|
| 预计飞行时长 | `flight_duration_min` | number | flight_duration_min | — |
| 预计起飞延误 | `etd_delay_min` | number | etd_delay_min | `{"only_late": true}` |
| 预计到达延误 | `eta_delay_min` | number | eta_delay_min | `{"only_late": true}` |
| 当前运行阶段 | `leg_phase` | string | leg_phase | — |

### 3.1 双模式机制

派生属性模型（`OntologyDerivedProperty`）的 `materialize_mode` 有两个状态：

| 模式 | 行为 | 适用 |
|---|---|---|
| **virtual（读时）** | 每次解析实体属性时调用函数实时计算；`GET /api/entities/{id}/derived-properties?refresh=true` 强制重算并刷新缓存 | 计划变动频繁、要求"改了就读到新值" |
| **materialized（物化）** | 值批量写入实体属性，列表/报表直读；物化接口执行后模式自动切换 | 大批量扫描、避免列表页逐条实时计算 |

> 工作流 A 首次物化后 4 个派生属性会变为 `materialized` —— 这是预期行为：值已落库直读；`refresh=true` 与函数试算仍可随时重算。想回到纯读时模式，重新运行 `seed_flight_ops_runtime.py --force` 即可。

## 4. 工作流 A：航段派生属性定时物化

**用途**：把 4 个读时派生属性的计算值批量物化写入航段实体属性，供列表页与报表直读。

```
start ──► http_mat_1 ──► http_mat_2 ──► http_mat_3 ──► http_mat_4 ──► end(summary)
          物化-预计飞行时长  物化-预计起飞延误  物化-预计到达延误  物化-当前运行阶段
```

HTTP 节点配置要点：

```json
{
  "method": "POST",
  "url": "http://127.0.0.1:8000/api/derived-properties/{派生属性id}/materialize",
  "params": {"limit": 5000},
  "timeout_seconds": 120
}
```

- 4 个派生属性的 id 在种子运行时动态填入 URL（`--force` 重建后 id 变化也会随之更新）；
- 后端默认 `WORKFLOW_HTTP_ALLOW_PRIVATE_NET=true` 放行 localhost，工作流可直接自调 API；
- 边为普通串行边 `{"source", "target"}`（无条件分支，不需要 handle）。

## 5. 工作流 B：单航段运行简报

**用途**：输入 `entity_id`，实时计算该航段全部派生属性，并由大模型生成一段面向值班人员的运行简报。

```
start(entity_id) ──► http_dp ──► llm_brief ──► end(report)
                    实时计算        生成运行简报      输出简报文本
```

| 节点 | 配置 |
|---|---|
| `start` | 输入参数 `entity_id`（航段实体 ID）；种子已把默认值填为当日延误航段 CA2885，运行时可改 |
| `http_dp` | `GET /api/entities/{{start.entity_id}}/derived-properties?refresh=true` —— 模板变量从 start 输入取实体 id，`refresh=true` 强制实时计算 |
| `llm_brief` | system：`你是民航运行控制中心（AOC）值班助理…`；prompt：把 `{{http_dp.data}}`（派生属性 JSON 数组）嵌入模板，要求逐项解释、延误为正给关注提示、不编造数据 |
| `end` | 输出 `report = {{llm_brief.text}}` |

LLM 节点使用系统当前激活的模型配置（`create_llm()` 全局配置），无模型激活时该节点会失败——工作流 A 不依赖 LLM，可独立验证。

## 6. 定时计划：航段派生属性物化（每 30 分钟）

| 字段 | 值 |
|---|---|
| 触发方式 | `interval`：每 30 分钟 |
| 关联工作流 | 工作流 A |
| `input_params` | `{}`（工作流 A 无输入） |
| 告警 | `alert_on_failure=1`、连续失败 3 次触发右上角消息中心告警 |

**调度引擎加载机制（重要）**：调度器（`scheduler_engine`）在**后端启动时**从 DB 加载全部 `enabled=1` 的计划。因此：

- 种子生成计划时后端正在运行 → **需重启后端**使计划生效；
- 或在前端「定时计划」页对计划"编辑→保存"一次（走 API 创建路径，会即时 `sync_job` 注册 job）；
- 计划页可直接「立即执行」验证工作流 A，不必等 30 分钟。

## 8. 使用方式速查

| 操作 | 路径 |
|---|---|
| 实时计算某航段派生属性 | `GET /api/entities/{entity_id}/derived-properties?refresh=true` 或实体详情页「刷新计算」 |
| 手动运行简报工作流 | 前端「工作流」页 → 单航段运行简报 → 运行（可改 entity_id） |
| 手动触发批量物化 | 「定时计划」页 → 航段派生属性物化 → 立即执行 |
| 试算验证（不依赖后端运行） | `python scripts/seed_flight_ops_runtime.py --verify` |
| 全量重建运行时层 | `python scripts/seed_flight_ops_runtime.py --force`（清理链：定时计划 → 工作流及运行记录 → 派生属性 → 函数，按名称/编码精准清理，不碰其他类别） |

## 9. 扩展模式

新增一个监控指标的标准三步（无需改任何代码）：

1. **加函数**：前端「本体函数」或种子脚本 FUNCTIONS 追加定义（如 `turnaround_gap_min` 过站裕度 = 衔接后继段 SOBT − 本段 ETA）；
2. **挂派生属性**：派生属性绑定函数、可选固定 params，选 virtual 或 materialized；
3. **建工作流/计划**：HTTP 节点调物化接口 + 定时计划扫描，或 LLM 节点生成告警简报。
