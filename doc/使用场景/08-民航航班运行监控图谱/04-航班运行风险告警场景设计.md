# 04 - 航班运行风险告警场景设计（条件分支 / 代码 / 智能体 / 人工节点实战）

> 状态：**已实施并端到端验证**。方法来源：《G航空公司航班运行风险管理研究》第 5 章——
> 将贝叶斯网络敏感度 Top 风险事件（晚关门/超时未落/机组人员变更）转化为 **规则引擎分级告警 + 分级响应处置**。
> 本设计把该框架完整落进本系统：**本体图谱做风险识别，派生属性做量化评估，工作流做规则告警与分级处置**，
> 并把工作流画布的 **代码 / 条件分支 / 智能体 / 人工** 四类节点全部用上；增强已有「运行告警」本体承载分级口径。

## 0. 实施与验证结论（2026-09-10）

**改动面**（均为种子与文档，框架代码仅 1 处缺陷修复）：

| 文件 | 改动 |
|---|---|
| `seed_flight_ops_ontology.py` / `flight_ops_domain.py` | 运行告警本体增强：`risk_level/trigger_value/lasted_min/handle_dept/advice/related_leg_no` 6 属性 + 新枚举口径；航段加 `is_crew_changed`；新增「涉及机场」关系与约束 |
| `seed_flight_ops_entities.py` | 告警规则升级为论文三级口径（晚关门 10/20/30 分档、超时未落 5/10/15 分档、机组变更低级）；`NOW` 动态化（运行种子的当下，与工作流 `datetime.now()` 时态自洽）；未起飞航段 8% 概率机组变更 |
| `seed_flight_ops_runtime.py` | 新增工作流 G/H/I + 2 条定时计划；代码节点参数注入告警本体 id / 关系定义 id / kb_id |
| `workflow_engine.py`（框架修复） | start 节点执行后将 defaults∪入参 回写 `state["start"]`——修复空参运行（定时触发）时 `{{start.xxx}}` 无法渲染的缺陷 |

**验证记录**（真实后端运行）：

- 工作流 G：`q=20260910` 命中 145 航段 → 规则引擎产出 9 条告警（机组变更/晚关门）→ 条件① true → 智能体逐条研判（真 LLM 输出 `advisories`，含"签派复核变更后机组资质与连飞限制"等建议）→ 条件② false（最高"低"）→ 全量入库 9 条并挂「触发告警」关系；
- 工作流 H：巡检 17 条告警 → 5 条低风险持续 22~34 分钟命中升级 → PUT 写回（低→中、状态=已升级）→ 智能体生成 AOC 格式升级通报（航班号/持续时长/牵头部门齐全）；
- 工作流 I：单告警深度研判——智能体判定"成立"，并指出派生属性 `stale=true`、触发值与预计延误存在 2 分钟偏差需刷新复核，按牵头部门给出动作清单。

**实现期沉淀的工程要点**：

1. 条件分支 simple 模式的比较操作符是 `gt/lt/==/!=/contains/empty`——写 `>` 会落默认 `==` 分支（数字永远"相等"）；
2. 智能体节点绑定 KB 后走 OAG 检索问答，检索空 chunks 会**短路返回兜底话术不调 LLM**；告警 JSON 与向量库语义不匹配必空手，故研判类 agent 不绑 KB、走纯 LLM + 结构化输出；
3. 告警实体的 `alert_no` 含日期+航段号+类型前缀（如 `ALT-20260910-CA5100-20260910-01-晚关`），入库前按编号查重，15 分钟轮询不会产生重复告警；
4. 定时计划的 start defaults 是种子时刻的静态日期——用于演示触发链路足够（种子数据快照即"当下"），生产部署应改 API 动态传参或每日重建 defaults。

## 1. 论文方法 → 系统能力映射

论文闭环：`风险识别（SHEL）→ 风险评估（贝叶斯网络敏感度）→ 风险控制（Drools 规则 + 低中高分级处置）`。

| 论文环节 | 论文载体 | 本系统载体 |
|---|---|---|
| 风险识别 | SHEL 模型风险事件清单 | 12 本体图谱（航段/机场/航线/航空器/机组…）+ 告警本体（本篇新增） |
| 风险量化 | 贝叶斯网络后验概率/敏感度 | 派生属性（延误分钟/等级/衔接风险，02/03 章）+ 代码节点规则评分 |
| 规则匹配 | Drools DRL `when` 条件项 | **代码节点**（本地规则引擎，读上游节点输出）+ **条件分支节点**（规则树） |
| 分级告警 | 告警等级 低/中/高 | 告警实体 `risk_level` 属性 + 条件分支路由 |
| 智能研判 | （人工经验研判） | **智能体节点**（图谱检索 + 归因 + 处置建议，结构化输出） |
| 分级响应处置 | 表 5.2/5.3 责任分工与升级 | **人工节点**（高风险审批挂起，3min 响应 SLA）+ 自动升级巡检工作流 |

**节点选型依据**（引擎语义已核实）：

| 节点 | 引擎行为 | 本场景用途 |
|---|---|---|
| 代码 `code` | 沙箱执行（标准库+requests/httpx），**透传 context 可读上游节点输出**，自定义输出平铺 | 批量规则匹配（7 条告警规则）、聚合统计、httpx 循环写告警实体 |
| 条件分支 `condition` | simple（左/操作符/右）或 advanced（and/or 规则树）；出边按 `handle=true/false` 路由 | 有无告警分流、是否含中高风险分流 |
| 智能体 `agent` | `query_template` 渲染 → 图谱检索 + LLM；支持 `structured_outputs` 强制 JSON 输出 | 逐条告警归因分析 + 处置建议 + 牵头部门判定 |
| 人工 `human` | **挂起等待处理**；approve 模式按通过/驳回走 true/false 分支 | 高风险告警处置审批（表 5.2：总值班室牵头，3 分钟内响应） |
| HTTP `http` | 单请求 | 拉航段/告警实体列表 |

## 2. 本体扩展：第 13 本体「运行告警」

现有 12 本体没有告警承载物，新增（加入 `seed_flight_ops_entities.py` 的领域定义）：

**本体**：`运行告警`（icon 🔔，与航段/机场/航线同级）

**属性**（10 个）：

| 属性 | 编码 | 类型 | 说明 |
|---|---|---|---|
| 告警编号 | `alert_code` | string | `ALT-yyyymmdd-序号`，全局唯一 |
| 告警类型 | `alert_type` | string | 晚关门 / 超时未落 / 机组变更 / 机场聚合 / 航线聚合 / 组合风险 |
| 风险等级 | `risk_level` | string | 低 / 中 / 高（论文表 5.1 口径） |
| 处置状态 | `status` | string | 未解除 / 已解除 / 已升级 |
| 触发时刻 | `trigger_time` | datetime | 规则命中时刻（升级巡检据此算持续时长） |
| 触发数值 | `trigger_value` | number | 超时分钟数 / 聚合次数等量化依据 |
| 已持续分钟 | `lasted_min` | number | 巡检刷新 |
| 牵头部门 | `handle_dept` | string | 论文表 5.3：飞行控制室/运行控制室/签派放行室/总值班室 |
| 处置建议 | `advice` | text | 智能体节点生成 |
| 关联航段号 | `related_leg_no` | string | 冗余存储便于名称检索 |

**关系**（3 条，约束：源=运行告警）：

| 关系 | 源 → 目标 | 语义 |
|---|---|---|
| 针对航段 | 运行告警 → 航段 | 单事件告警的主体 |
| 涉及机场 | 运行告警 → 机场 | 机场维度聚合告警 |
| 涉及航线 | 运行告警 → 航线 | 航线维度聚合告警 |

**航段本体补 1 个属性**：`is_crew_changed`（boolean，是否发生机组变更）——论文第三类风险事件的数据载体；种子脚本对当天未起飞航段以小概率置 true 模拟放行后名单变动。

**告警实体命名规范**（关键工程细节，服务 `q` 检索）：
`GET /api/entities` 的 `q` 只匹配实体名称与描述（已核实 EntityService 实现），故把检索键编码进名称：

```
name = {status}|{risk_level}|{alert_type}|{leg_no}
例：  未解除|中风险|晚关门|CA8248-20260910-01
```

巡检工作流用 `q=未解除` 圈定存量告警，`q=未解除|低风险` 圈定待升级集合，无需按属性过滤 API。

## 3. 论文 7 条告警规则 → 系统实现对照

代码节点内实现的规则表（阈值全部取自论文表 5.1 / 图 5.3~5.9）：

| # | 论文规则 | 论文触发条件 | 本系统实现（数据可行性已核） | 判定等级 |
|:--:|---|---|---|---|
| 1 | 晚关门 | SOBT+10/20/30min 仍未关舱门 | `leg_status ∈ {计划,登机}` 且 `now − sobt` 落入 10~20 / 20~30 / >30（未撤轮档 ⇔ 未关门，语义等价） | 低/中/高 |
| 2 | 超时未落 | ATOT+计划飞行时长+5/10/15min 无落地报 | `leg_status = 巡航` 且 `now − (atot + (sibt−sobt))` 落入 5~10 / 10~15 / >15 | 低/中/高 |
| 3 | 机组变更 | 放行后名单变动 | `is_crew_changed = true`（关键岗位细分无数据源，实现为单档低风险 + 建议人工复核升级） | 低 |
| 4 | 机场维度聚合 | 同一机场 2h 内晚关门 ≥5 次 | 按 `dep_airport` 分组统计窗口内规则 1 命中数 | 中 |
| 5 | 航线维度聚合 | 同一航线当日晚关门 ≥3 次 | 按 `dep_airport-arr_airport` 分组统计当日命中数 | 中 |
| 6 | 组合风险 | 晚关门 + 同航班其他风险事件 ≥1 | 同一航段命中规则数 ≥2 → 整体升为高 | 高 |
| 7 | 持续未解除升级 | 低风险告警持续 >20min 未解除 | 工作流 H：`now − trigger_time > 20min` 且 status=未解除 → 升中；中风险 >30min（处置时限）→ 升高（论文表 5.2 升级要求） | 升级 |

**分级响应口径**（论文表 5.2，写入告警实体 `handle_dept` 与人工节点展示）：
低风险=首响岗位持续关注，无强制时限；中风险=主责部门 **5 分钟内**介入，总值班室协调；高风险=总值班室牵头 **3 分钟内**响应，跨部门联动。

## 4. 工作流 G「运行风险告警扫描」（核心链路，定时 + 手动）

四类节点全上：**HTTP 拉数 → 代码规则引擎 → 条件分支两级分流 → 智能体研判 → 人工审批 → 代码批量入库**。

```
start(scan_date)
  └► http_legs   GET /api/entities?ontology_id={航段本体id}&q={{start.scan_date}}&page_size=200
      └► code_scan   规则引擎：实现上表规则 1~6（context['http_legs'] 读航段列表，
                     输出 alerts 数组 + alert_count + max_level + has_high）
          └► cond_any   条件分支①：{{code_scan.alert_count}} > 0
              ├ false ► end_empty（输出"本轮扫描无告警"）
              └ true ─► agent_judge   智能体研判：逐条告警归因 + 处置建议 + 牵头部门
                        （structured_outputs：advisories/max_level/handle_depts）
                  └► cond_high   条件分支②（advanced 规则树）：{{agent_judge.max_level}} in {中,高}
                      ├ false ► code_save(min_level=低)   httpx 循环 POST 低风险告警实体 + 挂关系
                      └ true ─► human_approve   高风险处置审批（人工节点，挂起等待）
                                展示：告警清单/等级/已持续/建议动作
                          ├ true（通过） ─► code_save(min_level=低)   全部告警入库
                          └ false（驳回）─► code_save(min_level=中)   仅中低风险入库，
                                            高风险标记误报暂缓
```

**关键节点 config 要点**（字段名与引擎对齐，可直接照抄进种子）：

| 节点 | config 核心字段 |
|---|---|
| `code_scan` | `params`: `{today: "{{start.scan_date}}"}`；`code_text`：遍历 items → 7 规则 → `return {"alerts": [...], "alert_count": n, "max_level": "高", "has_high": true}`（自定义字段自动平铺供下游引用） |
| `cond_any` | simple 模式：left=`{{code_scan.alert_count}}`，operator=`>`，right=`0`；true/false 两条出边 |
| `agent_judge` | `query_template`：告警 JSON + 要求输出归因/建议/部门；`structured_outputs`: `[{name:"advisories",type:"array"},{name:"max_level",type:"string"}]`；可绑民航运行 KB 提升专业性 |
| `cond_high` | advanced 模式规则树：`{combinator:"or", rules:[field:"{{agent_judge.max_level}}", operator:"==", value:"高"]}` |
| `human_approve` | `mode: approve`；`display_fields`: 告警摘要/等级/牵头部门/建议（渲染 `{{agent_judge.*}}`）；true/false 出边分别接 min_level 不同的入库节点 |
| `code_save` | `params`: `{min_level: "低"}`（人工驳回分支传 `"中"`）；`code_text`：httpx 按 min_level 过滤 → `POST /api/entities` 建告警实体（名称按第 2 节规范）→ `POST /api/relations` 挂「针对航段/涉及机场」关系 |

> 智能体输出不阻塞入库：即使 LLM 研判失败（`fail_on_error=false`），代码入库节点仍可按规则结果落库，保证告警不丢。

## 5. 工作流 H「告警升级巡检」（定时，实现规则 7 自动升级）

```
start
  └► http_open   GET /api/entities?ontology_id={告警本体id}&q=未解除&page_size=200
      └► code_escalate   逐条算 lasted = now − trigger_time：
                         低风险 >20min → 中；中风险 >30min → 高（论文 5.3 自动升级机制）
                         输出 escalations 数组
          └► cond_esc   有升级？
              ├ false ► end_quiet
              └ true ─► code_upgrade   httpx 循环：改告警实体 risk_level/status/lasted_min，
                        名称同步改写（保持 q 检索语义），输出升级清单
                  └► agent_notify   生成升级通报（等级/原因/新牵头部门/处置要求）
                      └► end(report)
```

定时计划：每 15 分钟（对齐论文"观察时限"粒度）。

## 6. 工作流 I「单告警深度研判」（手动，值班员对单条告警发起）

```
start(alert_id)
  └► http_alert   GET /api/entities/{{start.alert_id}}
      └► http_leg   GET /api/entities/{{http_alert.data.properties.related_leg_id}}/derived-properties?refresh=true
          └► agent_deep   智能体深度研判（绑民航运行 KB）：
                ① 结合派生属性回答"这条告警是否成立/是否误报"
                ② 图谱检索同机场/同航线相邻告警，判断是否局部聚集
                ③ 给出处置动作与解除条件（answer 长文 + structured：confirm/proposal）
                  └► end(advice)
```

与工作流 G 的差别：G 是**批量快筛**（规则驱动、秒级），I 是**单案深挖**（检索驱动、LLM 主导），对应论文"核查—研判—处置—反馈—复盘"的前两步人工深化。

## 8. 与 03 章的关系

03 章是**运行效率视角**的增补（KPI/地面/态势），本篇是**安全风险视角**（论文核心方法），二者共享同一套运行时机制与回退语义；实施时建议按 03 → 04 顺序推进（03 的 `delay_level/eta_delay` 等派生属性物化后，本篇代码规则可直接引用，减少重复计算）。
