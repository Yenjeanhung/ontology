## 0. 一句话结论 ⚠️

**本场景的图规模约 20 万节点 / 93 万边，用 Neo4j GDS 单机完全够用，不需要 GraphX / Plato。**

## 1. 算法与业务问题总览

| # | 算法 | 民航业务问题 | 输出形态 | 优先级 |
|:--:|---|---|---|:--:|
| **A1** | **加权 PageRank** | 哪些是本机队「高频根因」？哪些 LRU 最关键？ | 实体重要性分 | P0 |
| **A2** | **加权度中心性** | 哪些件拆换最多？（高拆换件 / 低 MTBUR 件） | 实体分 | P0 |
| **A3** | **社区发现（Louvain）** | 哪些故障码其实共享同一根因？哪些件属于同一功能模块？ | 社区标签 | P0 |
| **A4** | **图嵌入 + KNN** | 相似故障案例检索；**⭐ 跨机型知识迁移** | 相似边 + 向量 | P0 |
| **A5** | **NFF 识别**（图统计） | 哪些件反复被换却查不出毛病？ | NFF 高风险清单 | **P0** |
| **A6** | **重复性故障检测**（图统计 + 时序） | 哪些故障在反复发生且没修到根因？ | 重复故障清单 | **P0** |
| **A7** | **链路预测** | 某 LRU 是否潜藏尚未在本机型发生的故障？ | 待审建议 | P1 |
| **A8** | **割点分析** | 哪个件一坏就直接 AOG？ | 割点清单 | P1 |
| A9 | 加权最短路径 | FIM 之外的最短排故路径 | 路径 | P2 |

> ⭐ **A5 / A6 是本场景独有的、ROI 最高的两项**。
> 它们严格来说不是"图算法"（更接近图统计 + 时序分析），
> 但**直接命中民航最大的两个成本黑洞（NFF 与重复性故障）**，
> 因此优先级排在 A7/A8 之前。

## 2. 各算法详细设计

### 2.0 投影设计（异构图的关键）

图谱是**异构图**（16+ 种实体类型 + 30 种关系）。必须按算法目的建不同投影：

| 投影 | 节点 | 边 | 方向 | 服务 |
|---|---|---|:--:|---|
| **P_full** | 全部 Entity | 全部 RELATES（**排除计算产出边**） | 无向（加权） | A1 / A2 / A3 / A4 |
| **P_structure** | 仅 部件 + 系统 + 机型 | 仅 `组成` + `包含系统` + `装于` | 无向 | A8（割点） |
| **P_causal** | 故障原因 + 故障模式 + 部件 | `表现为` + `发生于` + `导致` | 有向 | A9（路径） |

#### ⚠️ 必须排除「图计算产出边」（自反馈陷阱）

```
   图嵌入 ──► 相似于边 ──► 进入投影 ──► 新的图嵌入 ──► 新的相似于边 ──► ...
        └──────────────────── 自反馈循环 ─────────────────────┘
```

**规则：投影必须显式排除 `相似于` 与 `潜在故障` 这两类由算法自身产生的边。**

- 它们不是从数据观察来的，是算法推断的；
- 若进入下一轮投影，会**自我强化**（越相似越相似），最终导致嵌入空间坍缩、社区发现失真；
- **症状隐蔽**：不报错，只会让结果越来越"假"。

建议写成硬编码排除列表，并在投影指纹中记录排除集。

#### 边权定义

| 关系 | 权重 | 理由 |
|---|---|---|
| `发生于` | `log(1 + occurrence_count)` | 本机队发生越频繁，关联越强 |
| `表现为` | `confidence` × `evidence_type` 系数 | 换件验证（0.95）> 测试确认（0.85）> 目视（0.8）> 手册（0.7）> 推断（0.5） |
| `导致` | `confidence` | 同上 |
| `组成` / `装于` | 1.0 | 结构关系，恒定 |
| `适用于`（措施→原因） | `effectiveness` | 措施越有效，关联越强 |
| 其他 | 1.0 | 默认 |

> 建议在抽取写入时就维护 `weight` 列（随 `occurrence_count` 变化更新），投影时直接读。

#### 异构图排名要分层

全图 PageRank 得到的是"部件第 3、根因第 7"这种混合排名，对业务无意义。

**做法**：全图跑一次得到 `pagerank_score`，**再按 `entity_type` 分组各自归一化排名**：

```
全局 pagerank_score（保留，用于跨类型比较）
+ 类型内排名 rank_in_type（用于业务榜单：根因 Top10 / 部件 Top10 / 航材 Top10）
```

### A1 · 加权 PageRank —— 本机队高频根因

| 项 | 内容 |
|---|---|
| **业务问题** | 本机队上，哪些根因最"重要"？哪些部件影响面最大？ |
| **投影** | P_full（加权、无向） |
| **参数** | `dampingFactor=0.85`, `maxIterations=20`, `relationshipWeightProperty='weight'` |
| **输出** | `{entity_id: score}` + 类型内排名 |
| **落库** | `entities.pagerank_score` + `rank_in_type` |
| **业务解读** | 根因类 Top10 = **优先治理清单**（推动 EO 工程指令 / 维保策略调整）；部件类 Top10 = **关键件清单**（提高航材安全库存、加密点检） |
| **GDS** | `gds.pageRank.write` |

> **与 FIM 的互补**：FIM 给出"所有可能原因"（无优先级，OEM 全局视角），
> **本机队 PageRank 给出"本机队最可能的原因"**。这正是本方案相对纯手册检索的核心增量。

### A2 · 加权度中心性 —— 高拆换件

| 项 | 内容 |
|---|---|
| **业务问题** | 哪个件拆换得最多？MTBUR 是否低于目标？ |
| **投影** | P_full（加权） |
| **输出** | `{entity_id: weighted_degree}` |
| **落库** | `entities.occurrence_count`；配合边上的 `mtbur_actual` / `mtbur_target` |
| **业务解读** | **MTBUR 低于目标值的件清单** → 航材备货策略、厂家索赔、改装评估（是否有 SB 可改善） |
| **GDS** | `gds.degree.write` |

### A3 · 社区发现（Louvain）—— 故障簇 ⭐

| 项 | 内容 |
|---|---|
| **业务问题** | 哪些故障码其实共享同一根因？ |
| **投影** | P_full（无向、加权） |
| **参数** | `maxLevels=10`, `tolerance=0.0001`, 可选 `seedProperty` 保证可复现 |
| **输出** | `{entity_id: community_id}` |
| **落库** | `entities.community_id` + 前端图谱可视化按社区着色 |
| **GDS** | `gds.louvain.write` |

**业务解读（本场景图计算最有说服力的产出之一）**

若一个社区里同时包含：

```
[根因：EDP 压力口渗漏] + [故障码 29-11341] + [故障码 29-11287] + [故障码 32-45100]
+ [部件：液压泵 PN:65-90751-4] + [航材：封严件 MS28775-222]
```

→ **说明这三个看似不同的故障码，很可能共享同一个根因**（液压内漏导致起落架收放慢也被归到同一簇）。

**这在传统故障统计里看不出来** —— 工单系统里它们分属不同 ATA、不同车间处理。
这类发现能直接推动**合并排故工卡**或**一次性 EO 改装**，一次解决多个故障码。

### A4 · 图嵌入 + KNN —— 相似案例与跨机型迁移 ⭐⭐

| 项 | 内容 |
|---|---|
| **业务问题** | ① 相似故障案例检索；② **跨机型知识迁移** |
| **投影** | P_full（无向、加权） |
| **参数** | `embeddingDimension=128`, `relationshipWeightProperty='weight'` |
| **输出** | 实体向量 + KNN 近邻（`topK=10`, `similarityCutoff=0.75`） |
| **落库** | `entities.graph_embedding` + `相似于` 边（`score` 属性） |
| **GDS** | `gds.fastRP.write` + `gds.knn.write` |

#### ⭐ 跨机型知识迁移（民航特有，价值极高）

同系列机型（A320 / A321、B737-800 / B737-8）共享大量 LRU 与系统架构，
但**经验往往不流通**：A320 上验证过的排故经验，A321 上遇到同类故障却没人知道。

**做法**：

1. 若按机型系列分知识库，**各自计算图嵌入（同一套参数、同一套本体）** ——
   同构本体 + 同构算法 ⇒ 嵌入空间**可对齐**；
2. 用**锚点实体**做空间对齐：跨机型共用的 LRU 件号（PN 相同）天然就是对齐锚点；
3. 对齐后，某机型的故障模式可以在**另一个机型的嵌入空间里找近邻**：

```
[B737-800] 故障模式 X  ──对齐空间近邻──►  [B737-8] 故障模式 Y
                                            └─ 已验证措施：更换 XXX（耗时 1.5h）
→ 提示："该故障在 B737-8 上出现过，处理方式可供参考"
```

> **注意**：跨机型迁移输出的是**参考建议，不是结论** ——
> 必须经工程技术人员确认适用性（构型差异、AD 适用性不同）。

#### ⚠️ 图嵌入的正确用法（沿用 GDS 设计文档的关键决策）

**图嵌入空间与问题文本空间不对齐** —— 不能拿问题的文本向量直接去查图嵌入向量。
图嵌入的职责是**扩展与消歧**，不是直接召回。

### A5 ⭐ NFF 识别 —— 民航最大的隐性成本

> 严格说这不是图算法，而是**图统计 + 时序分析**。但它直接命中 NFF 这个成本黑洞，优先级 P0。

**业务问题**：哪些件反复被拆换，送车间检测却"没毛病"？

**NFF 的三个图信号**：

| 信号 | 图上表现 | 判定 |
|---|---|---|
| **① 高拆换 + 高 NFF 率** | `(部件)-[发生于]-(故障模式)` 边上 `nff_rate` 高（如 > 0.3） | **拆了但没坏** → 根因定位不准 |
| **② 根因缺失** | 该部件有 `发生于` 边，但**没有入向的 `表现为` 边**（即没有确定根因） | **不知道为什么坏就换了** |
| **③ 根因指向"不明"** | 关联的根因 `原因分类 = 不明` 占比高 | 图谱本身没沉淀下根因 |

**判定规则**（可配置阈值）

```python
def is_nff_risk(component) -> bool:
    return (
        component.occurrence_count >= NFF_MIN_REMOVALS          # 默认 5 次
        and component.nff_rate >= NFF_RATE_THRESHOLD            # 默认 0.30
        and (component.root_cause_coverage < 0.6                # 根因覆盖率低
             or component.unknown_cause_ratio > 0.4)
    )
```

**输出与业务动作**

| 输出 | 业务动作 |
|---|---|
| NFF 高风险件清单（按 NFF 次数 × 航材单价排序） | ① 组织专题技术分析（是不是排故工卡有问题？）<br>② 检查 FIM 隔离步骤是否过于激进（一上来就换件）<br>③ 与 OEM 沟通（是否有已知但尚未发布的 SB） |
| 该件的所有 NFF 工单（可从 `sample_workorder_ids` 反查） | 供工程师逐条复盘 |

**ROI 说明**：NFF 占非计划拆换件 30%~50%。
若通过 NFF 识别把 NFF 率降低 5 个百分点，对一家 200 架机队的航司，
通常意味着**每年数百万到数千万元的航材与人工节省**。

### A6 ⭐ 重复性故障检测

> 民航对重复性故障有**强制可靠性监控要求**（CCAR-121 等规章）。
> 重复性故障往往意味着"上次没修到根因"。

**业务问题**：哪些故障在同一架飞机 / 同一机型上反复发生？

**三个检测维度**：

| 维度 | 判定 | 图上依据 |
|---|---|---|
| **同机重复** | 同一 `(航空器, 故障模式)` 在 N 个飞行日/循环内出现 ≥ K 次 | 工单的 `发生于航空器` + 时间窗 |
| **同型重复** | 同一 `(机型, 故障模式)` 在机队范围内高频发生 | 工单的 `发生于航空器` → 机型 + 统计 |
| **换件后复发** | 同一部件更换后，短期内同一故障模式再次出现 | `sample_workorder_ids` 的时间序列 + `涉及部件` |

**关键判定：换件后复发 ⭐**

这是最有价值的信号 —— 它**直接证明上一次的根因判断是错的**：

```
工单 W1: 换 EDP → 结论"已修复"
工单 W2: 7 天后同一注册号、同一故障码再次出现
→ (部件)-[发生于]-(故障模式) 边上的 repeat_count += 1
→ 该边的关联根因置信度应下调，并触发人工复核
```

**业务动作**

| 输出 | 业务动作 |
|---|---|
| 重复性故障清单（按重复次数 × AOG 影响排序） | ① 转入专题可靠性分析<br>② 触发 EO（工程指令）评估<br>③ 上报可靠性委员会（民航规章要求） |
| 换件后复发清单 | **直接点名"上次根因判断错误"** → 最高优先级人工复核 |

### A7 · 链路预测 —— 潜在故障

| 项 | 内容 |
|---|---|
| **业务问题** | 某 LRU 是否潜藏**尚未在本机型发生、但结构上高度暗示**的故障模式？ |
| **投影** | P_full；候选对限定 `(部件) - ? - (故障模式)` 且当前无边 |
| **打分** | `score = 0.6 × jaccard归一 + 0.4 × 嵌入余弦` |
| **过滤** | ① 分数阈值 → ② ATA 章节兼容性校验 → ③ 本体约束校验 → ④ 去重 → ⑤ tombstone 防重推 |
| **LLM 判型** | 对通过过滤的候选，让 LLM 结合部件属性、同邻居部件、跨机型证据判型 + 给理由 |
| **落库** | `relation_suggestions` 表 → **人工审核闭环**（复用 GDS 文档 M2 全套设计） |

**业务解读**

> "件号 A 与件号 B 在结构上高度相似（同 ATA、同厂商、同材质、装于同系列机型），
> B 在 B737-8 上出现过故障模式 M，而 A 在 B737-800 上从未出现过 M
> —— **建议将 M 纳入 A 的点检项 / 预防性检查**。"

这是从"坏了就修"走向**预防性维修**的关键一步，
也是向航司展示价值最有说服力的图计算产出。

> **护栏**：预测关系入库时必须标注 `source = predicted`，
> 与 `source = observed` 严格区分，且**必须经工程技术人员审核**。

### A8 · 割点分析 —— AOG 关键件

| 项 | 内容 |
|---|---|
| **业务问题** | 哪个件一旦失效，直接导致飞机不能放行（AOG）？ |
| **投影** | **P_structure**（部件 + `组成` 边，无向、无权） |
| **输出** | 割点 / 桥 列表 |
| **落库** | `entities.is_articulation` |
| **业务解读** | 结合 `是否可MEL保留` + `航材库存` + `采购交期`，生成 **AOG 高风险件清单** → 决定 AOG 常备件的配置策略 |
| **实现** | GDS 无原生割点算法 → 用 NetworkX `articulation_points` 在导出子图上计算（规模小，无性能压力） |

> 结构子树通常只有几千到几万节点，NetworkX 完全够用，**不必为此引入分布式框架**。

### A9 · 加权最短路径 —— 排故路径

| 项 | 内容 |
|---|---|
| **业务问题** | 从现象到根因，最短（最强）的因果链是什么？ |
| **投影** | **P_causal**（有向） |
| **优先级** | **P2** —— Q1 根因推理用「表现为」1 跳 + 本机队排序已能满足大部分需求；路径分析主要用于**可解释性展示** |

## 3. 业务看板：图计算产出怎么用

图计算算出来的东西如果没人看，等于没算。建议在**图谱洞察页**（[04 §8](./04-工作流与问答设计.md)）提供四张榜：

| 榜单 | 数据来源 | 业务动作 |
|---|---|---|
| **本机队高频根因 Top10** | A1 PageRank（根因类） | 优先治理 → EO / 维保策略 |
| **高拆换件 Top10**（含 MTBUR 对比） | A2 + 边统计 | 航材备货 / 厂家索赔 / SB 评估 |
| **⚠️ NFF 高风险件清单** | **A5** | 专题技术分析 / 排故工卡复审 |
| **⚠️ 重复性故障清单** | **A6** | 可靠性分析 / EO 评估 / 上报 |

> 后两张榜是**民航独有的、最能打动机务工程部门**的产出 ——
> 它们不只是在"展示图谱"，而是在**直接降低航司的两个最大成本黑洞**。

## 4. 规模结论：本场景不需要分布式框架 ⚠️

### 4.1 三档规模

| 项 | 一期（单航司） | 二期（含全量手册/历史机型） | 三期（多航司共享） |
|---|---:|---:|---:|
| 节点 | ~20 万 | ~50 万 | 千万级 |
| 边 | ~93 万 | ~300 万 | 亿级 |
| **选型** | **GDS 单机** | **GDS 单机 + NetworkX 批跑** | **GraphX / Plato** |
| 需要分布式 | ❌ | ❌ | ✅ |

### 4.2 诚实的判断

> **不要为了"用上 GraphX"而把架构复杂化。**
> 20 万节点 / 93 万边的图，Neo4j GDS 单机是毫秒到秒级响应，
> 引入 Spark 只会带来运维复杂度与调试成本，**没有任何收益**。

### 4.3 什么时候才真的需要

| 情况 | 规模 | 说明 |
|---|---|---|
| **多航司 / 全行业共享图谱** | 千万节点 / 亿边 | 多家航司共享故障知识与可靠性数据 —— **GraphX/Plato 的合理登场时机** |
| **坚持把全量工单建成工单相似图** | 300 万工单 × top-20 = 6000 万边 | 若确实需要工单级细粒度检索，这个规模 GraphX 有道理。<br>**但按 [02 §9](./02-抽取与图谱设计.md) 的设计（工单不全量入图，文本走向量库），该需求已被消解** |

### 4.4 建议的实施顺序

```
一期（现在）：GDS 单机跑 A1/A2/A3/A4 + A5/A6 统计    → 出业务价值
      同时：立住 GraphComputeProvider 抽象层          → 低成本，保住扩展性
二期：      A7 链路预测 + A8 割点，完善审核闭环        → 出更高价值
三期：      若做多航司共享图谱 → 实现 GraphXProvider，业务代码零改动
```

## 5. 与 GDS 设计文档的复用关系

[GDS 实体链接与知识补全设计](../../图分析/GDS实体链接与知识补全_功能设计.md) 已规划的内容，**本场景直接复用**：

| GDS 文档已有 | 本场景复用方式 |
|---|---|
| M0 GDS 基础层（投影管理、指纹失效、探测降级） | ✅ 直接复用，仅投影定义不同（异构图需分投影，见 §2.0） |
| `gds_compute_embeddings` / `gds_knn_neighbors` | ✅ A4（含跨机型迁移） |
| `gds_personalized_pagerank` | ✅ A1（本场景用全局 PageRank；PPR 用于 OAG 实体链接） |

| `_gds_lock` 并发控制 | ✅ 复用 |

**本场景需要新增的 GDS 方法**：

| 方法 | 算法 |
|---|---|
| `gds_louvain(kb_id)` | A3 社区发现 |
| `gds_degree(kb_id)` | A2 度中心性 |
| `gds_articulation_points(kb_id)` | A8 割点（NetworkX 实现即可） |

**A5 / A6 不需要 GDS** —— 它们是图统计 + 时序分析，
直接在 SQLite（权威存储）上用 SQL 聚合即可，实现更简单、结果更可控。

> 增量很小 —— 这正是"先把 GDS 基础层做扎实"的价值所在。

## 6. 运行与调度

```
[定时管理 /schedules]  cron: 每周日 02:00
        │
        ▼
[工作流] graph_compute 节点（建议新增节点类型，见 [04 §6](./04-工作流与问答设计.md)）
        │
        ├─ available() == False → 跳过 + 监控黄标 + 日志告警
        ├─ 指纹比对（未变且非强制重算 → 跳过）
        │
        ├─ 建 P_full 投影（⚠️ 排除计算产出边）
        │     → A1 PageRank → A2 Degree → A3 Louvain → A4 FastRP + KNN
        ├─ 建 P_structure 投影 → A8 割点
        ├─ A5 NFF 统计（SQL 聚合，非 GDS）
        ├─ A6 重复性故障统计（SQL + 时序，非 GDS）
        └─ A7 链路预测（候选 → 打分 → ATA 校验 → 约束过滤 → LLM 判型）
        │
        ▼
[落库] EntityService 走 SQLite 事务 → best-effort 同步图库属性
        │
        ▼
[通知] NFF 高风险件 / 重复性故障 / 潜在故障建议 > 0 → notifications
        │
        ▼
[监控] /config/monitor 展示最近一次运行时间、耗时、任务数、降级状态
```

**触发时机**：

| 触发 | 说明 |
|---|---|
| 定时 | 每周低峰期全量重算 |
| 增量标脏 | 抽取完成 / 实体 CRUD 后使指纹失效（沿用 GDS 文档 §4.3） |
| 手动 | 图谱洞察页提供「重新计算」按钮 |
| **事件触发** | 新工单标记为 NFF 或重复性故障 → **立即重算 A5/A6**（不需要等周调度） |

## 7. 验收标准

| # | 标准 |
|---|---|
| 1 | 图谱洞察页可查「本机队高频根因 Top10」「高拆换件 Top10」，排序与机务工程部门经验基本吻合 |
| 2 | **NFF 高风险件清单**至少能识别出 1 个真实存在的高 NFF 率部件，并经工程师确认 |
| 3 | **重复性故障清单**能识别出至少 1 起"换件后复发"案例，并追溯出上次根因判断错误 |
| 4 | 社区发现结果中，至少找到 1 个「多个故障码共享同一根因」的簇，经专家确认成立 |
| 5 | 跨机型迁移（若有同系列机型）返回的相似案例业务相关性 ≥ 纯向量检索基线（需先建 30~50 条评测集） |
| 6 | 链路预测建议进入人工审核闭环；批准后写入图谱并标注 `source=predicted`；拒绝后写 tombstone 不再重推 |
| 7 | 关闭 GDS 开关后，系统行为与当前完全一致（零回归） |
| 8 | 重跑幂等：指纹未变时二次运行不重算；抽取新数据后指纹失效，下次运行会重算 |

## 8. 关键决策点（需确认）

1. **A5/A6 是否优先于 A7/A8 实施**？建议「是」—— NFF 与重复性故障是民航最大的成本黑洞，且**不需要 GDS，实现成本更低**。✅/❌
2. **跨机型迁移是否一期做**？建议「是（若存在同系列机型）」—— 这是民航特有的高价值能力，且复用 A4 已有嵌入。✅/❌
3. **链路预测是否进一期**？建议「否」（放二期）—— 依赖 A4 嵌入，且审核闭环工作量不小。✅/❌
4. **相似度阈值是否按本体类型配置**？建议「是」，件号 0.95（且优先标准化精确匹配）/ 故障模式 0.62。✅/❌
5. **是否本期实现 GraphX Provider**？建议「否」—— 只立抽象层。✅/❌
6. **割点是否用 NetworkX**？建议「是」—— 结构子树规模小。✅/❌
7. **NFF/重复性故障事件是否触发即时重算**？建议「是」—— 这两个指标时效性要求高。✅/❌
