# 场景二：民航维修故障根因图谱

> 状态：**待确认** —— 确认后进入开发。
> 日期：2026-08-30（由通用「复杂装备运维」改写为民航维修具体落点）
> 一句话：**把 IPC 的部件树和 FIM 的故障树缝成一张图，让排故从「翻手册 + 问老师傅」变成图上多跳推理，让机务经验从人脑沉淀成可计算的公司资产。**

---

## 为什么选民航维修作为落点

| 理由 | 说明 |
|---|---|
| **行业自带两套现成的树** ⭐ | **IPC（图解零件目录）= 部件树**，**FIM/TSM（故障隔离手册）= 故障树** —— 通用制造业要辛苦从工单里抽故障树，民航现成就有，零 LLM 成本、100% 准确 |
| **行业标准体系完备** | ATA 章节（21 空调 / 24 电源 / 27 飞控 / 29 液压 / 32 起落架 / 34 导航 / 36 气源 / 49 APU / 71-80 发动机）是天然的分类与校验维度 |
| **锚点数据全是结构化的** | CMS/ECAM/EICAS 故障码、件号 PN、注册号、MEL 条款、AD 编号 —— 全部可规则提取，零 LLM 成本 |
| **ROI 极易算清** | AOG（飞机非计划停场）每小时损失数万至数十万美元；减少一次误换件、少停一小时，账都算得明明白白 |
| **痛点真实且尖锐** | NFF（无故障发现，占非计划拆换件 30%~50%）、重复性故障、间歇性故障 —— 全行业公认的三大成本黑洞 |
| **四个能力全跑满** | 本体约束抽取 ⭐、图谱多跳推理 ⭐、工作流闭环 ⭐、图计算 ⭐，每一环都是刚需 |
| **数据甲方自有** | FLB/TLB、NRC 工单、拆换记录、FIM/AMM/IPC 手册全在航司手里，不依赖外部采购 |

## 核心思想：IPC + FIM 双树合一 ⭐

```
   IPC 部件树（组成 / 装于）              FIM/TSM 故障树（表现为 / 导致）
   ──────────────────────────            ────────────────────────────────
        机型（B737-800）                        故障码 29-11341
             │ 包含系统                              │ 上报代码
        ┌────┴────┐                                  ▼
      ATA 29     ATA 32                      故障模式（B 系统压力低）
      液压       起落架                              ▲ 表现为
        │ 组成                                       │
     ┌──┴───┐                                   中间原因（隔离步骤）
   液压泵  蓄压器                                     ▲ 导致
   PN:65-  PN:                                       │
   90751-4                                      根因（EDP 压力口渗漏）
        │                                            ▲ 导致
        │                                            │
        └──────── 发生于（缝合点）────────────────────┘
                     ⭐ 两棵树在这里缝合

   CMS 故障码 ──上报代码──► 故障模式 ──发生于──► 部件(LRU) ──组成(逆)──► ATA 系统
                                                          │
                              ┌───────────────────────────┼──────────────┐
                              ▼                           ▼              ▼
                        历史 NRC 工单              航材（含互换件）   AD/SB 适用性
                              │                           │
                         维修措施                      库存 / 交期
                              │ 引用
                         AMM 29-21-00/401
```

**推理路径**：`CMS 故障码 → 故障模式 →（发生于）→ LRU 件号 →（组成上溯）→ ATA 系统 → 该机型历史工单 → 措施 + 航材互换件 + AMM 章节 + AD 适用性 + MTBUR 趋势`

这条路径跨 **5 跳、两棵树、六类数据源**，是纯向量检索与 SQL JOIN 都难以支撑的。

## 与现有代码的关系

| 本场景需要 | 复用现有能力 | 需要新增 |
|---|---|---|
| 本体定义与三元组约束 | ✅ 本体管理全套（11 张表已就位） | 只需**录入数据**，不改代码 |
| FIM/AMM/IPC 手册 | ⚠️ 是半结构化文档，现有解析器不认树状结构 | **`ManualTreeParser`（FIM/TSM 树解析）** ⭐ |
| 工单 / FLB 抽取 | ✅ `graph_extraction_service` 约束抽取 | 民航术语词典 + 件号正则 |
| IPC / CMS 码 / MEL / AD 入库 | ❌ 现有抽取面向文档 | **`StructuredImportService`**（关键缺口） |
| 图谱存储与可视化 | ✅ Kùzu/Neo4j + `GraphDataService` | 双树视图切换（前端增强） |
| 图谱清洗 | ✅ 并查集聚簇 + 型号防误合 | **件号标准化**（前置于清洗，见 02 §6） |
| OAG 融合问答 | ✅ `oag_service` 向量 + 图谱融合 | 排故专用 Prompt 与推理面板 |
| 工作流编排 | ✅ LangGraph 引擎 + 8 种节点 | **`graph_compute` 节点类型**（建议新增） |
| 人工审核闭环 | ✅ 人工节点 + 待办中心 + 通知 | 直接用 |
| 定时调度 | ✅ `scheduler` | 直接用 |
| 图计算 | ⚠️ GDS 设计文档已规划 M0 基础层 | 按 [03](./03-图计算设计.md) 选算法子集 |

> **约 80% 可复用。** 新增工作量集中在三处：
> `StructuredImportService`、`ManualTreeParser`（FIM 树解析）、图计算算法落地。
> 其中 **FIM 解析是最高性价比的一项** —— 一次投入，直接得到一棵完整的故障树。

## 关键决策点速览

| # | 决策 | 说明 |
|:--:|---|---|
| 1 | **故障树从 FIM 解析得到，不从工单抽** | 重大降本：FIM 本身就是按故障码组织的决策树，解析即可，准确率高、零 LLM 成本。工单抽取用于**补充与修正** FIM 的机队个体经验。见 [02 §2](./02-抽取与图谱设计.md) |
| 2 | **ATA 章节作为硬性交叉校验** | (故障模式 ATA 29) -发生于-> (部件 ATA 32) 大概率抽错。这条规则能砍掉大量噪声。见 [02 §5](./02-抽取与图谱设计.md) |
| 3 | **百万级 NRC 工单不全量入图** | 文本进向量库、统计进边属性、代表性工单进图。见 [02 §7](./02-抽取与图谱设计.md) |
| 4 | **本场景不需要 GraphX/Plato** | 图规模约 22 万节点 / 90 万边，GDS 单机足够；分布式需求留给「多航司共享图谱」。见 [03 §4](./03-图计算设计.md) |
| 5 | **工作流 v1 无循环节点** | 批量入库用「scheduler 定时触发 + 游标状态」模拟批处理循环。见 [04 §5](./04-工作流与问答设计.md) |
