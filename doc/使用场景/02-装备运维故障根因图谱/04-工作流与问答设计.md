## 1. 工作流总览

| # | 工作流 | 触发 | 性质 | 价值 |
|:--:|---|---|:--:|---|
| **WF-1** | 故障智能排故 | 实时（FLB/TLB 录入、CMS 报文） | 在线 | **缩短排故时长 / 减少 AOG** |
| **WF-2** | 知识自生长闭环 | 实时（工单关闭） | 在线 | 图谱越用越准 |
| **WF-3** ⭐ | **AD/SB 符合性监控** | 定时（每日） | 离线 | **适航合规，避免漏执行** |
| **WF-4** ⭐ | **MEL 保留到期预警** | 定时（每日） | 离线 | **避免保留超期（严重违规）** |
| **WF-5** | 定时图计算 | 定时（每周低峰） | 离线 | 治理与发现 |
| **WF-6** | 历史工单批量入库 | 定时（POC 期间持续） | 离线批处理 | 冷启动 |

> WF-3 / WF-4 是**民航特有的、适航强相关**的两条工作流，
> 通用装备运维场景没有对应物。它们工作量不大，但业务价值极高 ——
> 漏执行 AD、MEL 保留超期都是可能导致适航责任的严重问题。

## 2. WF-1 故障智能排故（在线）⭐

### 2.1 DAG

```
┌─ start ────────────────────────────────────────────────────────┐
│  入参: workorder_text, aircraft_reg, cms_fault_code, flight_phase│
│        ata, station                                             │
└──────────────────────────┬────────────────────────────────────┘
                           ▼
              ┌────────────────────────────┐
              │ code · 规则锚点提取          │
              │ CMS 故障码 / ATA / 件号 PN  │
              │ 注册号 → 机型               │
              └────────────┬───────────────┘
                           ▼
              ┌────────────────────────────┐
              │ code · FIM 章节定位          │
              │ 故障码 → FIM 章节 + 候选根因 │  ← ⭐ 零 LLM，来自手册树
              └────────────┬───────────────┘
                           ▼
              ┌────────────────────────────┐
              │ agent · 排故助手（OAG）      │
              │ 向量召回 + 图谱召回 + RRF    │
              │ + 图谱事实注入               │
              │ + 本机队频次/PageRank 排序   │
              └────────────┬───────────────┘
                           ▼
              ┌────────────────────────────┐
              │ condition · 最高置信 ≥0.85   │
              │  且 有换件验证成功历史 ?      │
              └───┬────────────────────┬───┘
               true│                    │false
                   ▼                    ▼
      ┌────────────────────┐  ┌──────────────────────────────┐
      │ llm · 生成排故建议   │  │ human · 技术支援工程师定案     │
      │ 含: 根因排序/隔离步骤│  │        (form 模式)            │
      │     航材+互换件      │  │  字段: 根因(select)            │
      │     AMM 章节/工时    │  │        措施(textarea)          │
      │     MEL 可保留性     │  │        是否换件(boolean)        │
      └─────────┬──────────┘  │        验证方式(select)         │
                │             │        是否NFF(boolean)         │
                │             └────────────┬───────────────────┘
                │                          ▼
                │             ┌──────────────────────────┐
                │             │ service · 新知识回写入库   │
                │             │ (含 NFF / 重复性标记)      │
                │             └────────────┬───────────────┘
                ▼                          ▼
              ┌────────────────────────────────┐
              │ end · 输出排故建议 + 引用来源     │
              └────────────────────────────────┘
```

### 2.2 节点配置要点

| 节点 | 类型 | 配置 |
|---|---|---|
| 规则锚点提取 | `code` | 沙箱 Python：正则匹配 CMS 故障码（如 `\d{2}-\d{5}`）、ATA（`\b\d{2}\b`）、件号、注册号（如 `B-\d{4}`） |
| **FIM 章节定位** | `code` | 查图谱：`(手册 {manual_code:'FIM'})-[:对应故障]->(故障代码)`，取出该章节下的候选根因列表 —— **零 LLM** |
| 排故助手 | `agent` | 引用「民航排故助手」智能体（KB = 对应机型知识库，技能 = 根因推理 + 航材查询） |
| 条件分支 | `condition` | `{{agent_1.confidence}} >= 0.85 && {{agent_1.has_verified_history}} == true` |
| 技术支援定案 | `human` | `mode=form`；办理人按 `专长系统`/`机型签署` 路由 |
| 新知识回写 | `service` | 实体服务（沙箱动作），走 `EntityService` 双写 |

**技术支援定案表单字段**（`human` 节点 `form` 模式）

| key | 类型 | 说明 |
|---|---|---|
| `root_cause` | select | 选项由 FIM 候选根因 + 图谱召回根因动态注入 |
| `action_taken` | textarea | 实际采取的措施 |
| `parts_replaced` | text | 拆换件号（PN，逗号分隔）—— 用于 `涉及部件` 与 MTBUR 统计 |
| `verification_method` | select | 地面测试 / 试车 / 试飞 / 目视检查 / 无 |
| `is_nff` | boolean | ⭐ **是否无故障发现** —— 直接写入工单 `处理结果`，触发 A5 重算 |
| `is_repeat` | boolean | ⭐ **是否重复性故障** —— 触发 A6 重算 |
| `is_permanent_fix` | boolean | 是否根治 |
| `downtime_hours` | number | ⭐ 停场时长 —— ROI 度量的基础数据 |

### 2.3 为什么人工节点是必须的（适航要求）

民航维修有**持照放行**制度，排故结论必须由持照人员确认，这是**规章要求而非可选项**。
`human` 节点（form 模式）把"机器给建议、人来拍板、拍板结果回流"固化成流程，
与项目一贯的 human-in-the-loop 设计哲学一致，也符合 CCAR-145 的要求。

> 注意：表单里的 `is_nff` / `is_repeat` / `downtime_hours` 三个字段**不是可选的装饰** ——
> 它们是 A5（NFF 识别）、A6（重复性故障检测）与 ROI 度量的**唯一数据来源**。

## 3. WF-2 知识自生长闭环

```
start(工单ID, 工单文本, 结构化字段)
    │
    ▼
service · 本体约束抽取（含 polarity + confidence + evidence_type）
    │
    ▼
code · ATA 章节交叉校验 + 件号白名单校验
    │
    ▼
condition · 通过校验 ?
    │   polarity==affirmative AND confidence>=0.7 AND ATA 兼容 AND 约束匹配
    ├── true  → service · 入库双写 → end
    │
    └── false → condition · 是否 speculative（疑似）?
                    ├── 是 → human · 知识工程师审核 (approve)
                    │          ├── 通过 → service · 入库（verified=true, source='expert'）
                    │          └── 拒绝 → service · 写 tombstone，不再推荐
                    └── 否（negative / NFF / ATA 不兼容）→ end
                          （丢弃，但记录为负样本，供 A5 NFF 分析）
```

**两个民航专属细节**：

1. **NFF / 未再现的工单不生成根因关系**，但会更新边上的 `nff_count` / `nff_rate`；
2. **`replacement_verified`（换件后故障消失）的关系置信度最高**，入库时优先标记为已验证。

## 4. ⭐ WF-3 AD/SB 符合性监控（民航特有）

### 4.1 DAG

```
[scheduler] cron: 0 3 * * *  （每日 03:00）

start()
    │
    ▼
code · 同步外部 AD/SB 源（CAAC / FAA / EASA / OEM 门户）
    │
    ▼
service · 适用性匹配：解析 applicability（机型 + MSN 区间）→ 匹配本机队
    │
    ▼
condition · 影响本机队 ?
    ├── 否 → end
    └── 是 ▼
        service · 图谱关联：写入/更新 (部件)-受控于->(适航文件)，
                 并反查受影响的航空器清单（按 MSN）
        │
        ▼
        condition · 是否有终止措施（terminating action）?
        ├── 有 → llm · 生成改装/换件方案摘要（含 SB 引用的航材与工时）
        └── 无 → llm · 生成重复性执行要求摘要（含间隔与到期日）
        │
        ▼
        human · 工程技术人员确认符合性方案 (form)
        │   字段: 符合性方案(select: 改装/换件/重复检查/不适用)
        │        计划完成日期(date)
        │        所需航材(text)
        │        责任维修站(select)
        ▼
        notification · 通知维修计划 + 航材准备 + 基地
        │
        ▼
        end
```

### 4.2 业务价值

| 风险 | 传统做法 | 工作流化后 |
|---|---|---|
| **漏执行 AD** | 表格 + 人工提醒，容易漏 | 每日自动同步 + 自动匹配机队 + 强制人工确认闭环 |
| **AD 适用性判断错** | 人工解读 applicability 文字 | 解析成机型 + MSN 区间，自动匹配具体注册号 |
| **重复性 AD 到期** | 人工记日历 | 自动生成重复性工作指令与到期日 |
| **AD 影响航材准备不足** | 执行时才发现没件 | 提前反查受影响航空器 + 所需航材，给航材部门准备时间 |

> ⚠️ **合规红线**：AD 符合性结论**必须由持照工程技术人员确认**，
> 系统只做线索提示与方案准备，绝不自动判定"已完成符合性"。

## 5. ⭐ WF-4 MEL 保留到期预警（民航特有）

### 5.1 DAG

```
[scheduler] cron: 0 6 * * *  （每日 06:00）

start()
    │
    ▼
code · 扫描 MEL保留：到期日 - 今天 <= 预警阈值（默认 A/B类 1天，C类 3天，D类 10天）
    │                  并单独列出「已超期」
    │
    ▼
condition · 存在临期 / 超期保留 ?
    ├── 否 → end
    └── 是 ▼
        service · 图谱查询：保留涉及部件 → 修复所需措施/航材/工具/AMM 章节
        │
        ▼
        condition · 存在「已超期」保留 ?
        ├── 是 → notification · **高优先级告警**（超期 = 严重违规）
        └── 否 → 继续
        │
        ▼
        human · 维修计划员安排 (form)
        │   字段: 计划修复日期(date)
        │        计划维修站(select)
        │        航材调配方案(textarea)
        │        是否需要调机(boolean)
        ▼
        notification · 通知基地 + 航材 + 维修计划
        │
        ▼
        end
```

### 5.2 MEL 保留类别与修复期限

| 类别 | 修复期限（标准定义） | 预警提前量建议 |
|:--:|---|:--:|
| **A 类** | 按 MEL 备注栏规定的时限（通常最短，可能限定具体航段） | 按条款，通常**立即** |
| **B 类** | 连续 3 个日历日（72 小时） | 1 天 |
| **C 类** | 连续 10 个日历日（240 小时） | 3 天 |
| **D 类** | 连续 120 个日历日（2880 小时） | 10 天 |

> **超期保留是严重违规**，可能导致适航处罚。
> 这条工作流虽然简单，但业务价值极高 —— 把"人盯表格"变成"系统盯人"。

## 6. WF-5 定时图计算（离线）

```
[scheduler] cron: 0 2 * * 0  （每周日 02:00）

code · 指纹检查（未变且非强制重算 → 直接结束）
    │
    ▼
graph_compute · 建 P_full 投影（⚠️ 排除计算产出边）
    │   → A1 PageRank / A2 Degree / A3 Louvain / A4 FastRP + KNN
    ▼
graph_compute · 建 P_structure 投影 → A8 割点
    │
    ▼
service · A5 NFF 统计（SQL 聚合，非 GDS）
service · A6 重复性故障统计（SQL + 时序）
    │
    ▼
service · A7 链路预测（候选 → 打分 → ATA 校验 → 约束过滤 → LLM 判型）
    │
    ▼
service · 结果落库（EntityService 走 SQLite 事务 → 同步图库属性）
    │
    ▼
condition · NFF高风险 / 重复性故障 / 潜在故障建议 > 0 ?
    ├── 是 → notification · 通知机务工程部门
    └── 否 → end
```

**额外触发**：新工单被标记为 NFF 或重复性故障时，**立即触发 A5/A6 重算**（不等周调度）。

## 7. WF-6 历史工单批量入库（离线批处理）

### 7.1 ⚠️ 约束：工作流 v1 无循环节点

[工作流功能设计](../../工作流/工作流_功能设计.md) §1.3 明确：**v1 不做循环节点（Loop / ForEach）**。

而批量入库天然是个循环。

### 7.2 过渡方案：scheduler 定时触发 + 游标状态（推荐）⭐

```
[scheduler] 每 10 分钟触发一次（POC 期间开启，跑完自动关闭）

start(batch_size=200)
    │
    ▼
code · 读取游标（workorder_ingest_cursor 表）
    │   SELECT * FROM workorders WHERE processed=0 ORDER BY id LIMIT batch_size
    ▼
code · L0 去重（MinHash 比对已处理集合）
    │
    ▼
code · L1 规则锚点提取（CMS 码 / ATA / 件号 / 注册号）
    │
    ▼
code · L2 FIM 优先：故障码命中 FIM 章节 → 取候选根因，跳过 LLM 根因推理
    │
    ▼
service · L3 剩余部分聚合分块 + LLM 约束抽取
    │
    ▼
code · 后处理校验（ATA 交叉校验 + 件号白名单 + 极性过滤）
    │
    ▼
service · 双写入库
    │
    ▼
code · 更新游标 + 记录本批统计（processed / skipped / failed）
    │
    ▼
condition · 本批处理数 == batch_size ?
    ├── 是 → end（等下一次定时触发继续）   ← 用「调度」代替「循环」
    └── 否 → code · 标记导入完成 + 关闭定时计划 → notification · 通知完成
```

**为什么这个方案够用**：

| 优点 | 说明 |
|---|---|
| 零新增节点类型 | 全部用现有 `code` / `service` / `condition` |
| 天然断点续跑 | 游标落库，中断后自动从断点继续 |
| 天然可控并发 | 每批 200 条，不会拖垮单机（解决背压问题） |
| 天然可观测 | 每批统计落库，监控页可见进度曲线 |
| 失败隔离 | 单批失败不影响其他批 |

### 7.3 背压与限流（必须做）

| 参数 | 建议值 | 说明 |
|---|---|---|
| `batch_size` | 200 条/批 | 可按机器性能调 |
| 触发间隔 | 10 分钟 | 与 LLM 供应商限流匹配 |
| 并发上限 | 复用 `GRAPH_EXTRACTION_CONCURRENCY=3` | 现有配置 |
| 失败重试 | 指数退避，最多 3 次 | 超限转人工队列 |
| 全局开关 | 导入进行中不允许重复触发 | 防重入 |

## 8. 现有能力缺口与过渡方案

| 缺口 | 影响 | v1 过渡方案 | 正式方案 |
|---|---|---|---|
| **`graph_compute` 节点类型** | WF-5 无法在图编排 | 用 `code` 沙箱节点调用 `GraphComputeProvider` | 新增 `graph_compute` 节点类型 |
| **`notification` 节点类型** | 通知无法作为独立节点编排（WF-3/WF-4 强依赖） | 用 `code` 节点调 `notification_hub`；或挂在 `human` 节点上 | 新增 `notification` 节点类型 |
| **循环节点（Loop）** | WF-6 批处理 | scheduler 定时触发 + 游标（§7.2） | v2 Loop 节点 |
| **`StructuredImportService`** | IPC/CMS码/MEL/AD 无法入库 | POC 阶段可用一次性脚本导入 | 正式模块（[02 §3](./02-抽取与图谱设计.md)） |
| **`ManualTreeParser`（FIM 解析）** | 无故障树主干 | 手工建少量样例树 | 正式模块（[02 §2](./02-抽取与图谱设计.md)）⭐ |
| **工作流对外暴露为 API** | 无法接入航司 MRO 系统 | 手动触发 | v2（工作流设计文档已列为 v2 目标） |

> 好消息：除 `StructuredImportService` 与 `ManualTreeParser` 外，其余缺口都有过渡方案，**不阻塞一期**。

## 9. OAG 问答设计（民航排故助手）

### 9.1 问题分类与检索策略

| 类型 | 示例问题 | 主用通道 | 图谱路径 |
|---|---|---|---|
| **故障码型** | "29-11341 怎么处理？" | **图谱为主** | 故障码 → 故障模式 → 根因（本机队排序）→ 措施（FIM/AMM 章节） |
| **现象型** | "巡航中 B 系统压力低，可能什么原因？" | **图谱为主** | 故障模式 → 根因（PageRank + 本机队频次排序） |
| **航材型** | "B-1234 换这个件，可用件号有哪些？" | **图谱为主** | 部件 → 航材 → 互换件 + 库存 |
| **可靠性型** | "这个件的 MTBUR 多少？最近趋势？" | **图谱属性** | 边上的 `mtbur_actual` / `nff_rate` / `repeat_count` |
| **签派型** ⭐ | "这个故障能不能保留放行？MEL 哪一条？" | **图谱为主** | 故障模式 → MEL 手册条目 + 保留类别 |
| **适航型** ⭐ | "这个件有没有 AD 要求？" | **图谱为主** | 部件 →（受控于）→ AD/SB |
| **机队型** | "这个故障在 737 机队上出现过几次？" | **图谱统计** | 故障模式 → 部件 → 装于 → 机型，聚合 |
| **相似案例型** | "A321 上有没有类似的处理过？" | **向量 + 图嵌入** | 跨机型嵌入近邻 + 向量召回，RRF 融合 |
| **开放型** | "这架飞机最近状态怎么样？" | 向量为主 + 图谱补充 | 混合 |

### 9.2 图谱事实注入示例（OAG 上下文融合）⭐

```
【图谱事实】
- 故障代码[29-11341]（ATA 29 液压 · CAUTION · 巡航阶段）
  ─ 上报代码 → [HYD SYS B PRESS LOW]（故障模式 · ATA 29）
  ─ MEL 条目 → [MEL 29-20-1]（B 类 · 3 个日历日 · 可保留放行）

- 故障模式[HYD SYS B PRESS LOW]
  ─ 发生于 → [液压泵 PN:65-90751-4]（LRU · ATA 29-21）
      · 本机队 43 次 · 平均排故 2.8h · 平均停场 6.5h
      · MTBUR 实测 6200FH / 目标 8000FH ⚠️ 低于目标
      · NFF 7 次（NFF 率 16%）⚠️ · 重复性 5 次 ⚠️
```

## 15. 风险与对策

| 风险 | 对策 |
|---|---|
| **FIM 手册为 PDF 扫描件，解析困难** | 优先争取 XML/SGML 结构化版本；PDF 场景靠编号模式 + 人工抽检；解析结果**两段式确认**后再入库 |
| IPC 件号体系与航材库不一致 | 导入阶段做件号标准化 + 人工确认；建别名对照表 |
| 工单数据质量差 | P0 阶段先做数据体检（平均字数、非空率、CMS 码覆盖率、拆换记录完整率），不达标先补数据源 |
| 抽取成本超预算 | 五层降本（[02 §7](./02-抽取与图谱设计.md)）；POC 阶段先抽 1 万条验证效果再放量 |
| 图计算结果与机务经验不符 | 结果先"只读展示、不落库"，经工程部门确认后再启用自动写入 |
| **AD/MEL 数据涉及适航责任** | 系统只做线索提示与方案准备，**结论必须由持照人员确认**；所有操作留痕可追溯 |
| 人工节点成为流程瓶颈 | 待办中心 + 通知已具备；设置超时提醒与代办人 |
| 工作流 v1 无循环 | 游标方案（§7.2），且该方案本身有断点续跑等额外好处 |
| 图计算产出边污染下一轮计算 | 投影硬编码排除 `相似于` / `潜在故障`（[03 §2.0](./03-图计算设计.md)） |
| **跨机型迁移给出错误建议** | 输出标注为"参考建议"并注明来源机型与构型差异提示，必须人工确认适用性 |
