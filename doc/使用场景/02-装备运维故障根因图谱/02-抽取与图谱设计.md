## 1. 五条入库通道

### 1.1 现状

```
文档 ──► parser ──► chunker ──► 向量化 ──► LLM 约束抽取 ──► SQLite + 图库
```

只有文档一条路。而民航场景最有价值的数据（IPC、CMS 码字典、FIM 手册、MEL、AD）**都不是普通文档**。

### 1.2 补齐后：五条通道

| 通道 | 数据源 | 方式 | 产出 | 成本 |
|:--:|---|---|---|:--:|
| **A** | IPC / CMS 码字典 / 航材表 / MEL / AD / 构型 | **`StructuredImportService`** ETL | 部件树 + 故障锚点 | **零 LLM** |

| **E** | QAR / ACARS 下行参数 | **不入图谱** | 触发信号 + 统计 | — |

## 2. ⭐ 最高性价比的一项：FIM/TSM 解析直接建故障树

### 2.1 为什么这是关键

通用制造业做故障图谱，最贵的一步是"从零构建故障树"。民航**不用** ——
**FIM/TSM 手册本身就是一棵按故障码组织的决策树**：

```
[FIM 29-21 TASK 801]  ← 故障码 / 任务号
  │  Fault: HYD SYS B PRESS LOW
  │
  ├─ Possible Cause 1: EDP 压力口渗漏
  │     ├─ Isolation Step A: 目视检查 EDP 压力口区域是否有油迹
  │     ├─ Isolation Step B: 增压测试，观察压力保持
  │     └─ Corrective Action: 更换 EDP 压力口封严（AMM 29-21-00/401）
  │
  ├─ Possible Cause 2: 压力传感器故障
  │     ├─ Isolation Step A: 读取 CMS 传感器数值
  │     └─ Corrective Action: 更换压力传感器（AMM 29-21-00/401）
  │
  └─ Possible Cause 3: 系统 B 油箱低油量
        └─ Corrective Action: 补充液压油（AMM 12-13-29/301）
```

**这棵树可以直接解析成图谱子图**：

| FIM 元素 | → 图谱 |
|---|---|
| 故障码 / 任务号 | `故障代码` 实体 + `手册` 节点（FIM 章节），`(手册)-对应故障->(故障代码)` |
| Fault 描述 | `故障模式` 实体，`(故障模式)-上报代码->(故障代码)` |
| Possible Cause | `故障原因` 实体，`(故障原因)-表现为->(故障模式)` |
| Isolation Step | `维修措施`（类型=测试），`(手册)-隔离步骤->(维修措施)` |
| Corrective Action | `维修措施`，`(维修措施)-适用于->(故障原因)`，`(维修措施)-引用->(手册)` |
| 引用的 AMM 章节 | `手册` 节点（AMM 章节） |

### 2.2 `ManualTreeParser` 设计

```python
class ManualTreeParser:
    """FIM / TSM 故障隔离手册树结构解析器。

    产出的是图谱的「OEM 通用故障树」主干 —— 确定性、零 LLM 成本。
    LLM 抽取的工单知识用于在此主干上做补充与修正（机队个体经验）。
    """

    def parse(self, source: dict) -> dict:
        """返回 {'entities': [...], 'relations': [...], 'stats': {...}}"""
```

**解析策略（按数据源格式自适应）**

| 格式 | 策略 |
|---|---|
| **结构化 XML / SGML**（多数 OEM 提供，如 ATA iSpec 2200 / S1000D） | 直接按标签解析 `faultcode` / `fault` / `possibleCause` / `isolationStep` / `correctiveAction`，**准确率接近 100%** |
| **PDF**（扫描件或排版 PDF） | 按标题层级 + 编号模式（如 `A.` `1)` `(a)`）做缩进树还原；置信度较低的转人工确认 |
| **HTML / 电子手册** | 按 DOM 层级 + 类名解析 |

**关键实现点**

| 点 | 说明 |
|---|---|
| **缩进即层级** | FIM 用缩进表达树的父子关系，还原缩进是核心难点；PDF 场景需结合字号/编号模式 |
| **两段式（预览 → 执行）** | 与图谱清洗同一哲学：先解析出树并可视化预览，人工确认层级无误后再入库 |
| **版本与有效性** | FIM 有版本与有效性（ applicability），必须作为属性记录，AD/SB 改版后要能追溯 |
| **复用双写链路** | 走 `EntityService`，保证与 LLM 抽取产出的 schema 完全一致 |
| **溯源属性** | 每条关系记录 `source='fim'` 与手册章节 —— **区分「来自手册」与「来自工单」是后续分析的基础** |

### 2.3 ⭐ 区分来源：这是整个设计的枢纽

图谱里每个三元组都带 `source` 属性：

| source | 含义 | 可信度 | 用途 |
|---|---|:--:|---|
| `ipc` | 来自 IPC（部件树） | 100% | 结构主干 |
| `cms_dict` | 来自 CMS 码字典 | 100% | 故障锚点 |
| `fim` | 来自 FIM/TSM 手册 | 高（OEM 通用） | 故障树主干 |
| `manual` | 来自 AMM/SSM 等 | 高 | 补充 |
| `workorder` | 来自工单 LLM 抽取 | 中（需治理） | **机队个体经验** |
| `expert` | 人工审核确认 | 高 | 修正与确认 |
| `predicted` | 图计算预测 | 低（**必须审核**） | 潜在故障 |

**这个 `source` 字段让一件关键的事成为可能**：

> 问"29-11341 最常见的原因"时，
> FIM 会给出 5 个可能原因（OEM 视角，无优先级），
> 而工单抽取数据会告诉你**本机队实际最常发生的那 1~2 个**。
>
> **FIM 保证不漏（召回），工单数据保证排序准确（精排）。**
> 这就是"标准答案 + 本机队经验"的结合，也正是本方案相对纯 FIM 检索的核心增量。

## 3. 结构化导入通道（`StructuredImportService`）

> 通道 A，与通用装备场景共用同一模块，此处只列民航专属的映射要点。

| 数据源 | 导入产出 | 关键字段 |
|---|---|---|
| **IPC** | `部件` 实体 + `组成` 关系（部件树） | IPC 章节 = ATA；件号 PN = 主键；含互换性代码 |
| **CMS 码字典** | `故障代码` 实体 | 故障码 = 主键；含 ATA、等级、报文文本 |
| **航材表** | `航材` 实体 + `互换` 关系 | PN = 主键；互换性代码决定 `互换` 边方向（ONE-WAY 需注意方向性） |
| **MEL/CDL** | `手册` 实体（MEL 章节） | MEL 项目号、类别 A/B/C/D、修复期限 |
| **AD/SB** | `适航文件` 实体 + `受控于` 关系 | 编号 = 主键；适用性（机型/MSN 范围）需解析 |
| **机队构型** | `航空器` / `机型` 实体 + `属于机型` | 注册号、MSN = 主键 |

**民航专属注意事项**

| 点 | 说明 |
|---|---|
| **互换性是有方向的** | `ONE-WAY`（单向可互换）意味着 A 可替 B 但 B 不可替 A，`互换` 边必须支持方向性 |
| **AD 适用性解析** | AD 的 applicability 常写成 "B737-800, MSN 28000-29999"，需解析成机型 + MSN 区间才能匹配机队 |
| **件号与序号** | `部件`/`航材` 按 PN 唯一（类型级）；SN 是实例级，v1 不建 SN 实例节点（放在工单属性里） |
| **时寿件** | 时寿件的寿命单位可能是 FH（飞行小时）/ FC（飞行循环）/ 日历日，属性设计要能容纳 |

## 4. 工单文本的六个坑（民航专属）⭐

FLB/TLB 与 NRC 工单是**最难抽、也最有价值**的数据源。不加处理直接喂 LLM，质量会很差。

| # | 坑 | 示例 | 应对 |
|---|---|---|---|
| **1** | **缩写密度极高** | EDP / EMDP / LRU / NFF / MEL / CDL / AD / SB / EO / ATA / PN / SN / EGT / N1 / VSV / FOD | Prompt 注入**民航缩略语词典**（新增 `DOMAIN_ABBREV_DICT`），并建 `别名` 属性做实体对齐 |
| **2** | **件号写法五花八门** | `65-90751-4` / `6590751-4` / `65-90751-004` / `65 90751 4` | **件号标准化必须前置于一切处理**（见 §6）—— 去掉分隔符、补零归一、前缀对齐 |
| **3** | **NFF 与否定表述** | "地面测试正常""未再现""NFF""更换后故障消失" | ⭐ 见下方专项说明 |
| **4** | **间歇性与重复性** | "第二次出现""间歇性""巡航阶段偶发""重复性故障" | 抽取时输出 `polarity` 与 `recurrence` 标记；"第 N 次出现"直接映射工单的 `是否重复性故障` |
| **5** | **飞行阶段是强线索** | "起飞滑跑时出现""巡航中消失""进近阶段复现" | `工况` 实体的核心来源；阶段 + 现象组合是根因定位的强信号 |
| **6** | **拆换信息最结构化** | "拆下 PN:65-90751-4 SN:ABC123，装上 PN:65-90751-4 SN:XYZ789" | **优先用正则提取，不走 LLM** —— 这是准确率最高、信息量最大的部分 |

### 4.1 ⭐ NFF 与否定表述的处理（民航专属重点）

工单里的否定词有两**完全相反**的含义，必须区分：

| 表述 | 含义 | 处理 |
|---|---|---|
| "地面测试正常""未再现""NFF" | **排故失败**，问题没找到 | 工单 `处理结果 = NFF/未再现`，**不生成根因关系**；但这是一条**极重要的负样本** |
| "更换 XX 后故障消失""换件后验证正常" | **排故成功**，且**证明了根因** | 生成根因关系，且**置信度很高**（换件验证是最强的因果证据） |

> **"更换后故障消失"是整个图谱里最强的因果证据** ——
> 它相当于一次受控实验：改变一个变量（换件），观察结果（故障消失）。
> 抽取时应给这类关系**高置信度**（如 0.9+），远强于"疑似""可能是"这类推断。

### 4.2 极性 + 置信度抽取契约

要求 LLM 对每条关系输出：

```json
{
  "source": "EDP 压力口渗漏",
  "relation": "表现为",
  "target": "HYD SYS B PRESS LOW",
  "polarity": "affirmative",
  "confidence": 0.93,
  "evidence_type": "replacement_verified",
  "evidence": "更换 EDP 压力口封严后试车，B 系统压力恢复正常",
  "ata": "29",
  "flight_phase": "巡航"
}
```

**`evidence_type` 与置信度映射**（民航专属设计）

| evidence_type | 说明 | 置信度区间 |
|---|---|---|
| `replacement_verified` | 换件后故障消失（受控实验） | 0.90 ~ 0.98 |
| `test_confirmed` | 测试/测量确认（如量得压力低于标准） | 0.85 ~ 0.95 |
| `visual_confirmed` | 目视检查确认（如发现油迹、裂纹） | 0.75 ~ 0.90 |
| `manual_stated` | 手册（FIM）表述，无实测 | 0.60 ~ 0.75 |
| `inferred` | 推断，无直接证据 | 0.40 ~ 0.60 |
| `speculative` | 疑似 / 待观察 | < 0.5（**不入库**） |

**后处理规则**

| polarity / evidence_type | confidence | 处理 |
|---|---|---|
| affirmative | ≥ 0.7 | 直接入库 |
| affirmative | 0.5 ~ 0.7 | 入库但 `verified=false`，进待审列表 |
| affirmative | < 0.5 | **不入库**，转建议 |
| speculative | 任意 | **不入库**，生成建议 → 人工审核 |
| negative（未再现/NFF） | 任意 | **不生成根因关系**；记录为负样本（用于 NFF 分析） |

## 5. ATA 章节交叉校验 ⭐（民航专属，效果显著）

**规则**：一条关系的起终点，其 ATA 章节应当**一致或属于合理的系统关联**。

```
✅ (故障模式 ATA 29) -发生于-> (部件 ATA 29)        正常
✅ (故障模式 ATA 29) -发生于-> (部件 ATA 29-21)     正常（父子章节）
⚠️ (故障模式 ATA 29) -发生于-> (部件 ATA 32)        异常 → 标记待审
❌ (故障模式 ATA 29) -发生于-> (部件 ATA 71)        基本可判定错误 → 丢弃
```

**为什么这条规则特别有效**：

1. ATA 章节是**行业标准**，几乎所有实体（部件、故障码、手册、工单）都带；
2. 跨 ATA 的真实因果确实存在（如 ATA 24 电源故障导致 ATA 27 飞控告警），但**是少数**；
3. LLM 抽取最容易犯的错就是"串台"（一个工单里提到多个系统的件，关系张冠李戴）。

**实现**：

```python
# 章节关系判定
def ata_compatible(a: str, b: str) -> tuple[str, str]:
    """返回 (判定, 原因)。判定: 'ok' | 'warn' | 'reject'"""
    if a == b or is_ancestor(a, b) or is_ancestor(b, a):
        return 'ok', '同章节或父子章节'
    if (a, b) in ATA_CROSS_SYSTEM_ALLOWLIST:   # 人工维护的跨系统白名单
        return 'warn', '已知跨系统关联（如 24 电源 → 27 飞控）'
    return 'reject', f'跨 ATA 章节（{a} vs {b}），疑似抽取错误'
```

- `ATA_CROSS_SYSTEM_ALLOWLIST` 由机务专家维护（如 24→27、29→32、36→21 等真实存在的系统耦合），
  初期可以很小，逐步扩充；
- 判定为 `reject` 的关系**直接丢弃并计入 errors**，`warn` 的入库但标记待审。

> **这是一条投入产出比极高的校验规则** —— 实现只需几十行，
> 但能砍掉相当比例的抽取噪声，且完全不依赖 LLM。

## 6. 件号标准化（前置于实体对齐）⭐

### 6.1 问题

同一个件号在工单里可能有十几种写法：

```
65-90751-4   6590751-4   65-90751-004   65 90751 4
PN 65-90751-4   P/N:65-90751-4   6590751-004
```

不归一化，实体对齐必然失败，图谱里会出现一堆指向同一实物的重复节点。

### 6.2 标准化流程

```
① 大写化 + 去空格/特殊字符
② 提取核心数字段（去掉分隔符）
③ 前导零归一：65-90751-004 → 65-90751-4
④ 前缀对齐（去/补前导零）：065-90751-4 → 65-90751-4
⑤ 与 IPC 权威件号库比对（最长公共前缀匹配 + 校验位）
   命中 → 采用权威写法
   未命中 → 标记待审（很可能是 OCR 错误或工单笔误）
```

> **第 ⑤ 步依赖通道 A 导入的 IPC 件号库** ——
> 又是一个"结构化数据反哺 LLM 抽取质量"的例子。

### 6.3 与现有清洗能力的衔接

现有图谱清洗用 `difflib.SequenceMatcher` + 并查集聚簇，并有 `_are_distinct_products` 做型号防误合。

**民航场景的调参建议**：

| 参数 | 现有默认 | 民航建议 | 理由 |
|---|---|---|---|
| 相似度阈值 | 0.72 | **件号 0.95**（极严） | `65-90751-4` 与 `65-90751-5` 是两个完全不同的件，误合会导致发错航材（**严重问题**）。件号应在标准化阶段就对齐，相似度匹配只作兜底 |
| | | **故障模式 0.62**（较松） | 工单表述差异大："B 系统压力低" vs "液压 B 系统低压" 应合并 |
| 单类型上限 | 600 条 | **必须改造** | 航材/部件轻松破万，O(n²) 会爆 |

> **结论：相似度阈值应支持按本体类型单独配置**（建议本体表新增 `merge_threshold` 字段），
> 且**件号类实体应跳过文本相似度，直接用标准化后的精确匹配**。

### 6.4 大规模相似度计算改造

现有单类型 > 600 条跳过，在航材（5 万+）场景下等于**放弃清洗**。

**改造：MinHash / LSH 分桶 + 块内比对**

```
1. 实体名做字符 3-gram 集合
2. MinHash 降维（128 维签名）
3. LSH 分桶（b 个 band × r 行）
4. 只比对落同桶的实体对
→ O(n²) → 近似 O(n log n)
```

5 万航材：O(n²) = 25 亿次比对 → LSH 后约百万次，**提升 2~3 个数量级**。

> 该改造对所有大数据量场景通用，且本身是很好的技术亮点。

## 7. 分层抽取：把 LLM 成本打下来 ⭐

### 7.1 成本现状（不优化）

200 架机队、3 年数据，FLB/TLB + NRC 工单约 **300 万条**。
去重后约 180 万条。按每条约 250 output token：

```
180 万 × 250 token ≈ 4.5 亿 output token  →  全量 LLM 抽取完全不可行
```

### 7.2 五层降本

| 层 | 手段 | 节省 | 说明 |
|---|---|:--:|---|
| **L0 去重** | 精确去重 + MinHash 相似去重；重复工单命中已有结果直接复用 | **~40%** | 重复性故障导致大量雷同工单，民航场景去重率通常很高 |
| **L1 规则锚点** | 正则提取 CMS 故障码、ATA 号、件号 PN/SN、注册号、航班号、MEL 项号 | **~25%** | 零 LLM；恰好是图谱的**关键锚点** |
| **L2 ⭐ FIM 优先** | 故障码命中 FIM 章节 → **直接从 FIM 树取候选根因**，不让 LLM 推理根因，只让 LLM 确认/排序/补充 | **~45%**（叠加后） | 见下方说明 |
| **L3 聚合分块** | 短工单按「同注册号 + 相邻时间窗」聚合成 500~800 字超块再抽 | **~50% 调用次数** | 见 §7.3 |
| **L4 小模型（可选）** | 微调小模型跑全量，大模型只处理低置信 / 新实体首次出现 | 再降 50%+ | 二期 |

### 7.2.1 ⭐ L2「FIM 优先」是本场景独有的降本手段

**传统做法**：把工单文本扔给 LLM → LLM 自己推理根因。
**本方案**：

```
工单故障码 29-11341
   │
   ├─► 查 FIM 树 → 得到 3 个候选根因 [EDP压力口渗漏, 压力传感器故障, 油箱低油量]
   │
   └─► LLM 的任务从「推理根因」降级为「判断这篇工单对应哪个候选 + 提取证据」
```

**三重收益**：

| 收益 | 说明 |
|---|---|
| **成本更低** | 输出从"自由生成根因"变成"从 3 个选项里选一个"，输出 token 大幅下降 |
| **准确率更高** | LLM 不再幻觉出不存在的根因；选项来自 OEM 权威手册 |
| **schema 天然一致** | 候选根因已在图谱里，只需建立关联，不存在实体对齐问题 |

> 这是"结构化知识（FIM）引导 LLM"的典型范例，
> 与项目一贯的「Prompt 引导 + 代码兜底 = 双保险」一脉相承。

### 7.3 L3 聚合分块的注意事项 ⚠️

聚合省调用次数，但会**破坏 chunk 级 `MENTIONS` 溯源**（现有 OAG 图谱召回依赖 `Chunk -[:MENTIONS]-> Entity`）。

**解决方案**：抽取在聚合块上做，写入时**把关系映射回原始工单 chunk**：

```
聚合块 Block(工单 A + B + C) ──抽取──► 关系 r
                                        ├─► MENTIONS: Block -[:MENTIONS]-> Entity
                                        └─► r.source_workorder_ids = [A, B, C]
```

> 需在 `graph_extraction_service` 写入环节增加「聚合块 → 原始 chunk 列表」回写映射。
> 工作量不大但必须做，否则溯源能力退化。

### 7.4 降本后估算

```
300 万条
  → L0 去重            180 万条
  → L1 规则命中        135 万条走零 LLM 路径（生成锚点实体与关系）
  → 剩余               45 万条需 LLM
  → L2 FIM 优先        其中约 60%（27 万条）命中 FIM，LLM 输出量减半
  → L3 聚合分块        实际调用次数约 12 万次
─────────────────────────────────────────────────
实际 LLM 调用量 ≈ 12 万次，较全量 180 万次 降低约 93%
```

## 9. ⭐ 关键决策：百万级工单不全量入图

### 9.1 问题

300 万条工单若全作为节点入图：

- 图被工单节点**淹没**（工单数 >> 领域实体数），可视化无法看
- 图算法被噪声污染（PageRank、社区发现会被海量"一次性"工单带偏）
- 图规模虚高，但可用信息密度极低

### 9.2 方案：三层各得其所 ⭐

| 层 | 存什么 | 存哪里 | 作用 |
|---|---|---|---|
| **文本层** | 全部工单原文 | **ChromaDB 向量库** | 文本语义检索（OAG 向量通道），**不丢信息** |
| **统计层** | `(故障模式)-[发生于]->(部件)` 边上的聚合属性 | **图库边属性** | 支撑排序与统计 |
| **样例层** | 每个 `(部件, 故障模式)` 组合保留 3~5 条**代表性工单** | **图节点（约 3 万）** | 可解释的样例，供展示与溯源 |

**边上的聚合属性设计（民航专属字段）**

```
(故障模式) -[:发生于]-> (部件)
    occurrence_count        : 43        # 本机队发生次数
    mtbur_actual            : 6200      # 实测非计划拆换平均间隔（FH）
    mtbur_target            : 8000      # 目标 MTBUR（FH）
    avg_repair_hours        : 2.8       # 平均排故工时
    avg_downtime_hours      : 6.5       # 平均停场时长
    nff_count               : 7         # ⭐ NFF 次数（拆换但车间无故障）
    nff_rate                : 0.16      # ⭐ NFF 率
    repeat_count            : 5         # ⭐ 重复性故障次数
    first_seen / last_seen
    sample_workorder_ids    : ["NRC-2024-0813", ...]   # 最多 5 条
```

> `mtbur_actual` / `nff_rate` / `repeat_count` 三个字段是**民航可靠性分析的核心指标**，
> 直接支撑 [Q5 可靠性查询](./01-总体设计与本体清单.md) 与 [03 的 NFF 识别](./03-图计算设计.md)。

**代表性工单选取策略**（每组合 3~5 条）

1. 最近一次（时效性）
2. 处理最详细的一次（含完整拆检描述）
3. **NFF 的一次**（若存在）—— **负面样本最有价值**
4. **重复性故障的一次**（若存在）
5. 换件验证成功的一次（`replacement_verified`）

### 9.3 为什么这个决策值得单独强调

1. **不是所有数据都该进图** —— 图谱价值在结构密度，不在数据量
2. **不同存储各司其职** —— 向量库存文本、图库存结构、属性存统计
3. **负面样本优先保留** —— NFF 与重复性故障工单，比"一次修好"的工单信息量大得多

## 10. 图谱建模补充

### 10.1 关系属性

| 关系 | 属性 | 用途 |
|---|---|---|
| `发生于` | `occurrence_count` `mtbur_actual` `mtbur_target` `nff_count` `nff_rate` `repeat_count` `avg_repair_hours` `avg_downtime_hours` `first_seen` `last_seen` `sample_workorder_ids` | 频次排序、可靠性分析、NFF 识别 |
| `表现为` | `source`（fim / workorder / expert）`confidence` `evidence_type` `polarity` `evidence` `verified` `source_workorder_ids` | 来源区分、置信度过滤、溯源 |
| `适用于` | `effectiveness`（措施有效率 = 非 NFF 且非重复的比例） | 措施推荐排序 |
| `互换` | `interchange_code`（INTERCHANGEABLE / REPLACEABLE / ONE-WAY） | 航材可用性判断 |
| `受控于` | `compliance_status`（符合 / 待执行 / 超期）`due_date` | AD 符合性 |
| `相似于` | `score` `algo` | 图计算产出 |
| `潜在故障` | `score` `evidence` `status` | 链路预测产出，需审核 |

### 10.2 实体级计算属性（图计算回写，见 [03](./03-图计算设计.md)）

> **建议存为独立标量列而非 JSON**，便于 Cypher `ORDER BY` 与索引。

| 列 | 类型 | 来源算法 |
|---|---|---|
| `pagerank_score` | number | PageRank |
| `occurrence_count` | number | 加权度中心性 |
| `nff_rate` | number | 统计（非图算法） |
| `community_id` | string | Louvain |
| `graph_embedding` | JSON | FastRP |
| `is_articulation` | boolean | 割点 |

### 10.3 八类查询的 Cypher 示例

**Q1 根因推理（本机队口径排序）**

```cypher
MATCH (fc:FaultCode {code: $code})<-[:上报代码]-(fm:FailureMode)
MATCH (fm)<-[r:表现为]-(rc:RootCause)
OPTIONAL MATCH (rc)-[:发生于]->(c:Component)
RETURN fm.name AS mode, rc.name AS cause, rc.cause_category AS category,
       c.pn AS pn, r.source AS src, r.confidence AS conf,
       rc.pagerank_score AS pr, r.occurrence_count AS cnt
ORDER BY r.occurrence_count DESC, rc.pagerank_score DESC
LIMIT 10
```

**Q2 影响面分析（ATA 系统下溯）**

```cypher
MATCH (s:System {ata: $ata})<-[:组成]-(c:Component)
MATCH (c)<-[r:发生于]-(fm:FailureMode)
RETURN s.name AS system, c.pn AS pn, c.name AS component,
       fm.name AS mode, fm.ata AS fm_ata, r.occurrence_count AS cnt
ORDER BY r.occurrence_count DESC
```

**Q3 相似案例（含跨机型）**

```cypher
MATCH (fm:FailureMode {name: $mode})-[r:相似于]-(sim:FailureMode)
OPTIONAL MATCH (sim)-[:发生于]->(c:Component)-[:装于]->(t:AircraftType)
RETURN sim.name AS similar_mode, r.score AS score,
       collect(DISTINCT t.type_code) AS aircraft_types
ORDER BY r.score DESC
LIMIT 10
```

**Q4 航材与互换件**

```cypher
MATCH (rc:RootCause {name: $cause})<-[:适用于]-(a:Action)
OPTIONAL MATCH (a)-[:需要]->(sp:SparePart)
OPTIONAL MATCH (sp)-[i:互换]-(alt:SparePart)
RETURN a.name AS action, a.std_hours AS hours, a.is_permanent_fix AS permanent,
       sp.pn AS pn, sp.stock AS stock, sp.interchange_code AS inter,
       collect({pn: alt.pn, code: i.interchange_code}) AS alternatives
ORDER BY a.is_permanent_fix DESC, a.std_hours ASC
```

**Q5 可靠性查询（MTBUR + NFF 趋势）**

```cypher
MATCH (c:Component {pn: $pn})<-[r:发生于]-(fm:FailureMode)
RETURN fm.name AS mode, r.occurrence_count AS cnt,
       r.mtbur_actual AS mtbur_actual, r.mtbur_target AS mtbur_target,
       r.nff_count AS nff, r.nff_rate AS nff_rate,
       r.repeat_count AS repeats, r.last_seen AS last
ORDER BY r.occurrence_count DESC
```

**Q6 跨树反查（故障 → 部件 → ATA 系统 → 机型）**

```cypher
MATCH (fm:FailureMode {name: $mode})-[:发生于]->(c:Component)
MATCH (c)-[:组成*1..4]->(s:System)
MATCH (c)-[:装于]->(t:AircraftType)
RETURN DISTINCT c.pn AS pn, s.ata AS ata, s.name AS system, t.type_code AS type
```

**Q7 适航符合性**

```cypher
MATCH (c:Component {pn: $pn})-[r:受控于]->(ad:AirworthinessDoc)
RETURN ad.doc_no AS doc_no, ad.doc_type AS type, ad.issuer AS issuer,
       ad.effective_date AS effective, ad.is_repetitive AS repetitive,
       ad.has_terminating_action AS terminating, r.compliance_status AS status
ORDER BY ad.effective_date DESC
```

**Q8 签派决策（MEL 可保留性）**

```cypher
MATCH (fm:FailureMode {name: $mode})-[:归属系统]->(s:System)
MATCH (m:Manual {manual_code: 'MEL'})-[:覆盖]->(s)
RETURN m.chapter AS mel_item, m.title AS title, fm.can_defer AS deferrable
```

### 10.4 现有 Kùzu 图模型的适配

现有节点表 `KnowledgeBase / Document / Chunk / Entity / Relation`，边 `MENTIONS / RELATES / HAS_RELATION ...`。

**本场景全部复用，不新增节点表**：

| 本场景概念 | 落位 |
|---|---|
| 机型/航空器/系统/部件/故障码/故障模式/根因/航材/AD/手册… | `Entity` 节点，靠 `entity_type` 区分 |
| `发生于`/`表现为`/`组成`/`互换`/`受控于`… | `Relation` 节点 + `RELATES` 直连边（现有 Reified 建模） |
| 工单原文 | `Chunk`（走向量库），代表性工单额外建 `Entity`（entity_type=维修工单） |
| 边上的 `mtbur_actual` / `nff_rate` 等统计 | `RELATES` 边属性 |
| FIM 手册章节 | `Chunk` + `Entity`（entity_type=手册），保留 `MENTIONS` 溯源 |

> **无需改动图模型** —— 这是现有 Reified 建模（关系带属性）的直接红利。

## 12. 风险与对策

| 风险 | 对策 |
|---|---|
| **FIM 手册格式混乱**（PDF 扫描件占比高） | 优先争取 XML/SGML 结构化版本（多数 OEM 可提供）；PDF 场景靠编号模式 + 人工抽检确认 |
| **FIM 版本与有效性** | 手册实体必须记录版本与有效性；改版后旧树标记失效而非删除（追溯需要） |
| IPC 件号体系与航材库不一致 | 导入阶段做件号标准化 + 人工确认；建立别名与对照表 |
| 工单文本质量差（大量"已处理""正常"） | L1 规则层过滤低信息量工单，只统计不抽取；`GRAPH_MIN_CHARS_FOR_EXTRACTION` 兜底 |
| **LLM 编造件号** | 件号白名单校验（IPC/航材库），不在库中的标记待审 |
| **ATA 跨章关系被误杀** | `ATA_CROSS_SYSTEM_ALLOWLIST` 由机务专家维护，warn 而非 reject；定期回顾被拒关系 |
| 因果方向抽反 | Prompt 明确方向 + `constraint_set` 硬校验 |
| 聚合分块破坏溯源 | 回写 `source_workorder_ids`（§7.3） |
| **适航数据敏感性** | AD/SB 符合性数据涉及适航责任，系统输出只作**线索提示**，结论必须由持照人员确认 |
| 工单含敏感信息（人员、成本） | 导入前脱敏；人员实体只保留工号、执照类别与机型签署 |
