# 使用场景总览

> 本文档回答一个问题：**KnowSource 这套「本体约束抽取 + 知识图谱 + 工作流 + 图计算」的能力，能用在哪些数据量大、有价值、且每一环都跑得满的业务场景上？**
>
> 各场景的详细落地设计见对应子文档；[02-民航维修故障根因图谱](./02-装备运维故障根因图谱/README.md) 已完整展开，可直接作为实施依据。
> 关联文档：[功能说明/00-项目总览](../功能说明/00-项目总览.md)、[图分析/GDS 实体链接与知识补全](../图分析/GDS实体链接与知识补全_功能设计.md)、[OAG 设计](../OAG/design.md)

## 一、先立判据：什么样的场景"配得上"这套系统

不是所有大数据场景都适合。这套栈的成本结构和能力边界决定了三条筛选标准：

| 判据 | 要求 | 为什么 |
|---|---|---|
| **A. 关系密度 + 多跳需求** | 图上必须存在「跨 2~5 跳才有意义」的查询 | 否则向量检索就够，图谱与图计算沦为摆设 |
| **B. 非结构化文本占比高** | 知识藏在文档里，而不是现成的数据库表 | 否则本体约束的 LLM 抽取是杀鸡用牛刀 |
| **C. 图规模能长到单机扛不住** | 目标千万边以上（若要上 GraphX/Plato） | 否则 Neo4j GDS 单机足够，上分布式框架是过度设计 |

三条全中 → 能把「本体 + 抽取 + 图谱 + 工作流 + 图计算」串成一条完整故事线。
只中 A+B（如民航维修）→ 依然是很扎实的落地场景，但**不必上分布式图计算框架**。

## 四、图计算框架分级（详见 [07](./07-图计算框架选型.md))

```
图规模               选型                              典型场景
─────────────────────────────────────────────────────────────────
< 500 万边     │  Neo4j GDS 单机                  │  二（民航维修）、六（供应链）
500 万~5000 万 │  GDS 吃力 / NetworkX 离线批跑     │  一（单机构）、五
> 5000 万边    │  GraphX(Spark) / Plato / GraphScope│  三、四，或一做成全市场图谱
```

统一接入姿势：抽象 `GraphComputeProvider`（与 `GraphStoreAdapter` 平级），三个实现
`GdsComputeProvider` / `NetworkXComputeProvider` / `GraphXComputeProvider`，
**图计算走离线批处理、结果回写 SQLite + 图库属性**，不进在线查询链路。

## 五、三个必须先想清楚的现实问题

### 1. LLM 抽取成本是「大数据量」场景的第一杀手

粗算：一篇 10 页文档 ≈ 30 chunk，100 万 chunk ≈ 3.3 万篇文档。按每 chunk 输出 300 token 计，约 3 亿输出 token——**全量 LLM 抽取在大数据量场景下不可接受。**

必须做**分层抽取**：

```
L0 去重层   精确去重 + MinHash 相似度去重（运维工单重复率常 >30%，直接省 1/3 成本）
L1 规则层   正则/词典提取编码类锚点（故障码、物料号、设备号）—— 零 LLM 成本
L2 小模型层 可选，微调小模型跑全量
L3 大模型层 只处理「高价值 chunk」：新实体首次出现 / 规则未命中 / 小模型低置信
```

### 2. 存储天花板

SQLite + Chroma + Kùzu 这套单机栈，实体过百万、向量过百万就吃紧。
好消息：`providers/` 抽象已就位，切换成本可控。
坏消息：`graph_extraction_service` 目前没有背压与分片，**一次跑几万篇文档会拖垮单机**——批量入库必须先补游标 + 分批 + 并发上限。

### 3. 抽取质量随规模下降

图谱清洗里「单类型 > 600 条跳过」的 O(n²) 护栏，在百万实体场景下直接失效。
大规模场景需换成 **MinHash/LSH 分桶 + 块内比对**，把 O(n²) 降到近似 O(n log n)。这本身就是一个很好的技术亮点。

## 六、推荐路径

| 你的目标 | 建议起步场景 |
|---|---|
| **先跑通、能演示、能落地** | 场景二（民航维修）：行业自带 IPC 部件树与 FIM 故障树两棵现成的树、数据航司自有、ROI 好算（减少 AOG 时长 + 降 NFF 率） |
| **要简历/面试亮点，算法讲得全** | 场景一（金融风控）：图计算的每个经典算法都对应一个可解释的业务问题 |
| **要数据量的绝对规模** | 场景三（网安）或场景四（生物医学）：但前者需补结构化导入通道，后者需换多语言 embedding |

> 场景一与场景二技术栈约 70% 复用，先做二再扩一，是最平滑的路径。
