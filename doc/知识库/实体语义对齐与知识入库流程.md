# 知识入库与实体语义对齐全流程

> 对应实现：`backend/services/file_service.py`（入库主管道）、`backend/services/graph_extraction_service.py`（本体约束抽取）、`backend/services/graph_cleanup_service.py`（清洗与实体对齐）、`backend/services/rag_service.py` / `backend/services/oag_service.py`（检索联动）。
> 存储默认组合：**PostgreSQL**（权威数据）+ **Milvus**（分片向量）+ **Neo4j**（图谱，`GRAPH_STORE_PROVIDER` 可切 Kùzu 嵌入式后端）。

## 0. 全景图

```
文档上传
  │
  ▼

│    策略由「上传自动分析 + 处理确认弹窗」按文件决定并持久化          │
└─────────────────────────────────────────────────────────────┘
  │ 分片(content_hash 去重/增量复用)
  ├──────────────────────────────┐
  ▼                              ▼
┌──────────────────┐   ┌─────────────────────────────────────┐
│ ② 向量入库        │   │ ③ 本体驱动的图谱抽取                   │
│  add_documents    │   │  LLM 约束抽取(本体 prompt)            │
│  → Milvus         │   │  → 类型/属性/关系归一化校验             │
│  Chunk 行(_PG)    │   │  → _entity_id MERGE 入 PostgreSQL     │
```

## 1. 解析与分片（`file_service._process_file_bg`）

1. **解析**：`get_parser(file_path).parse()` 得到正文与元数据（标题层级、页码等）。
2. **增量基线**：补算文件 `sha256` 指纹；为旧分片建 `content_hash → 行` 的索引，供本轮 diff。
3. **分片**：`iter_text_chunks(content, metadata, strategy, params)`。分片策略（`fixed` / `sentence` / `heading` / `recursive` / `semantic`）与参数由上传后的**自动分析 + 处理确认弹窗**按文件决定并持久化，全局 `CHUNK_SIZE=500 / CHUNK_OVERLAP=50` 仅作兜底。
4. **增量 diff**：分片 `content_hash` 未变化的**直接复用已有向量，不重嵌入**，仅刷新 `chunk_index`——同一文件重新处理时，向量写入量只与实际变化量成正比。

> 「清洗」在本阶段的含义是**结构化还原 + 稳定切分**：解析器剥离格式噪声、按策略切出语义完整、内容寻址（hash）稳定的分片，为下游向量库与图谱提供一致的输入。

## 2. 向量入库（Milvus）

- 每个分片生成 `chunk_id = make_chunk_id(file_id, content_hash, dup_seq)`，即**内容寻址 ID**：同内容同 ID，天然去重。
- 分片以 langchain `Document` 批量流式写入：`vectorstore.add_documents(docs, ids=chunk_ids)`——内部经 `providers/embedding` 的 `Embeddings.embed_documents` 编码后写入 **Milvus**（`VECTOR_STORE_PROVIDER` 可切 Chroma），collection 按知识库隔离。
- 同步落 `chunks` 表（PostgreSQL），`embedding_id` 关联向量库主键；`VECTOR_WRITE_BATCH_SIZE` 控制批大小。

## 3. 本体驱动的图谱抽取（`graph_extraction_service`）

以本体为 **schema 蓝本**约束 LLM 抽取，而不是抽取后再修补：

1. **约束化 prompt**：`_build_constrained_system_prompt` 把本体的实体类型、属性定义、关系类型及其两端类型约束渲染进系统提示（`_constraint_summary` / `_build_rule_lines`）；实体名须为简短专有名词，禁整句/长指标名（`_is_low_value_entity_name` 在抽取侧与清洗侧共用同一规则）。
2. **分批抽取**：分片按批送 LLM（`extract` 的 `run_batch`），响应经 `_parse_response → _to_entity/_to_relation` 结构化；**类型不在本体中的实体直接丢弃**，关系类型经通用关系黑名单（`_generic_relation_blocklist`）过滤。
3. **归一化校验**：
   - 关系类型按本体 code 映射归一；属性经 `_normalize_properties/_coerce_property_value` 按属性定义类型收口；
   - `_ensure_entity_from_relation` 补齐仅在关系中出现的实体。
4. **确定性入图（对齐 L1）**：实体 ID 由 `_entity_id = SHA1(kb_id | 类型小写 | 名称小写)` 生成——**同库同类型同名的实体跨分片自动 MERGE 为同一节点**，这是零成本、零误合的对齐主力；关系连同 chunk→实体的 `MENTIONS` 溯源边一并写入，经 `providers/graph_store` 同步到 **Neo4j**（Kùzu 备用）。
5. **复核队列**：未通过规则的抽取结果进入人工审核队列（`extraction_review_service`），不直接入图。

## 4. 实体对齐（`graph_cleanup_service`，建议→人工审核→apply）

三层机制，按成本递增、覆盖面递进：

| 层 | 机制 | 解决什么 | 成本 |
|---|---|---|---|
| L1 | `_entity_id` 确定性 MERGE | 跨分片**字面完全相同**（大小写不敏感）的同类型实体 | 零（入图时完成） |
| L2 | `SequenceMatcher` 名称相似度 ≥0.72 聚簇 + 并查集 | 近形变体（空格/括号差异等） | 低（纯本地） |
| L3★ | **语义对齐：embedding 缓存 + blocking + verification** | 简称/全称/别名等**语义同、字面远**（如「国航」vs「中国国际航空」） | 增量编码 + 矩阵乘 |

### L3 语义通道设计（本文件新增实现）

**四个关键决策**：

1. **向量缓存放派生表，不入向量库**：`entity_vectors`（PostgreSQL，`migration_039`）只服务清洗比对，`vec` 为 float32→base64 文本（方言无关）。十万级实体 × 512 维 ≈ 200MB，绰绰有余。清洗是离线批任务，Milvus 的 ANN 毫秒优势用不上；将来检索侧要做在线语义实体链接时，再从缓存表一次性 backfill 进 Milvus 即可。
2. **惰性失效，增量编码**：`content_hash = sha1(provider|model|名称|描述)`。仅对**缓存缺失/过期**的实体调用嵌入模型——首轮全量，之后每轮成本只随增量线性增长；换嵌入模型时 model 参与哈希，自动全量失效。实体被合并/删除后，`apply_cleanup` 顺手清理对应缓存行。
3. **编码增量、比对全量**：向量有缓存后，比对只是矩阵乘（同类型分桶，`归一化向量矩阵 @ 矩阵.T` 毫秒~百毫秒级）。常规类型每轮全量比对，保证语义建议与字面建议行为一致地「每次都给」（用户未处理不消失）；单类型超过 `GRAPH_CLEANUP_SEMANTIC_TYPE_MATRIX_LIMIT`（默认 5000）才退化为只比增量侧，防超大类型 n² 矩阵内存。
4. **阈值精判 + 防误合**：每个查询实体取 top-k 近邻（`GRAPH_CLEANUP_SEMANTIC_TOPK`），余弦 ≥ `GRAPH_CLEANUP_SEMANTIC_THRESHOLD`（默认 0.90，语义通道从紧控误合）才成边；`_are_distinct_products` 拦截「品牌同、型号编码不同」（享界S9 / 享界G9）这类高相似但语义不同的实体。聚簇后建议标注 `source: "semantic"`（前端徽标区分字面/语义），canonical 选取与字面通道同规则：**度数最高、并列取名字最短**。

**人工审核闭环**：建议不入库（幂等可重复生成）→ 前端勾选审核 → `apply_cleanup` → `EntityService.merge_entities`：关系全部重挂到 canonical、旧名写入 `properties.aliases` 软别名（检索侧词面匹配仍可命中）。

### 与 L2 的去重

字面通道（L2）产出的组与语义组存在成员交集时，语义组整组跳过——宁少勿重，避免同一实体出现在多个建议组导致 apply 时二次合并踩已删实体；字面合并执行后实体消失，语义通道后续轮次自然收敛。

## 5. 检索联动（`rag_service` / `oag_service`）

- **RAG 双路召回**：`_expand_queries` 查询改写 → 每个变体做向量召回（Milvus，阈值过滤）+ BM25 关键词召回 → 多路 `rrf_fuse`（`HYBRID_RRF_K`）→ 可选 Rerank 精排（`RERANK_CANDIDATE_K → RERANK_TOP_N`）。
- **GraphRAG**（`oag_service`）：查询做实体链接（词面匹配 ∪ `MENTIONS` 反查，aliases 参与命中）→ 图上按本体语义做关系扩展与多跳推理 → 与 RAG 结果融合，支撑答案溯源。
- 清洗/对齐直接改善检索：L1 消除重复节点，L2/L3 合并后 aliases 保持旧名可召回，多跳路径不再被重复实体打断。

## 6. 存储一览

| 存储 | 内容 | 角色 |
|---|---|---|
| PostgreSQL | files / chunks / entities / relations / **entity_vectors** / 本体 / 复核队列 | 权威数据 + 派生缓存 |
| Milvus | 分片向量（按 kb 隔离 collection，`embedding_id` 主键） | 在线语义召回 |
| Neo4j | Entity / Relation / MENTIONS 溯源边 | 图检索与多跳推理 |

## 7. 配置项

| 配置 | 默认 | 说明 |
|---|---|---|
| `GRAPH_CLEANUP_SEMANTIC_ENABLED` | `true` | 语义通道总开关 |
| `GRAPH_CLEANUP_SEMANTIC_THRESHOLD` | `0.90` | 余弦阈值，从紧控制误合率 |
| `GRAPH_CLEANUP_SEMANTIC_TOPK` | `5` | 每实体保留的近邻候选数 |
| `GRAPH_CLEANUP_SEMANTIC_MAX_ENTITIES` | `20000` | 参与语义通道的实体总量上限（首跑保护） |
| `GRAPH_CLEANUP_SEMANTIC_TEXT_MAXLEN` | `300` | 「名称+描述」编码文本截断 |
| `GRAPH_CLEANUP_SEMANTIC_TYPE_MATRIX_LIMIT` | `5000` | 单类型全量比对上限，超过只比增量侧 |

## 8. 运维

- **重建向量缓存**：`entity_vectors` 是派生数据，可整表 `DROP` 后由下次清洗自动全量重算；换嵌入模型无需手工干预（model 参与哈希自动失效）。
- **规模演进**：实体十万级时按上表参数即可；若检索侧需要在线语义实体链接（用实体向量替代纯词面匹配做查询实体识别），将 `entity_vectors` 一次性 backfill 到 Milvus 独立 collection，即可复用 ANN 与运维体系。
- **测试**：`backend/test/test_semantic_alignment.py`（假嵌入模型，不依赖网络/本地模型）：`python test/test_semantic_alignment.py`。
