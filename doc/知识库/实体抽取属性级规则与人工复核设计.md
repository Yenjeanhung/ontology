# 实体抽取属性级规则与人工复核队列设计

> 状态：设计稿（待评审）
> 相关代码：`backend/models.py`、`backend/services/graph_extraction_service.py`、`backend/services/ontology_service.py`、`backend/services/entity_service.py`、`backend/services/file_service.py`、`backend/routers/ontology.py`、`backend/routers/entity.py`、`backend/sql/migrations.sql`、`front/src/components/common/AttributeEditor.vue`、`front/src/components/KbDetail.vue`

## 1. 背景与现状

### 1.1 现状问题

文件上传后的实体抽取链路位于 `file_service.py` 的处理流水线中：

```
解析 → 分片 → 向量化 → GraphExtractionService.extract(ontology_constraint) → 落 SQLite + Kùzu
```

知识库绑定本体类别后，`OntologyService.get_kb_extraction_constraints()` 会装载约束并进入**约束模式**。该模式目前只做到**类型级约束**：

| 校验层次 | 现有行为 | 位置 |
|---|---|---|
| 实体类型白名单 | 类型不在本体定义中 → 丢弃实体 | `_merge_payload`（`graph_extraction_service.py:758`） |
| 关系三元组白名单 | `(source, relation, target)` 越界 → 丢弃关系 | `_merge_payload`（`graph_extraction_service.py:793`） |
| 属性键白名单 | 未定义的属性键 → 剔除 | `_normalize_properties`（`graph_extraction_service.py:1013`） |
| 基础类型规整 | number→float、boolean→bool，失败置空 | `_coerce_property_value`（`graph_extraction_service.py:1027`） |
| 全局噪声过滤 | 低价值实体名、通用关系黑名单 | `_is_low_value_entity_name` / `GRAPH_GENERIC_RELATION_BLOCKLIST` |

**缺失的部分正是"属性级抽取规则"：**

1. `OntologyAttribute`（`models.py:151`）上**没有任何约束字段**——没有 `enum_values`、没有正则、没有范围、没有长度限制。枚举目前只存在于 `OntologySharedProperty` / `OntologyInterfaceProperty` / `OntologyRelationProperty`，且**抽取路径完全不使用**。
2. `is_required` 只是拼进 Prompt 文案（"必填"字样），**不参与任何入库校验**。
3. 属性层面对抽取的唯一控制开关是 `is_edit_only`（不进 Prompt），它是**二值的**，表达不了"只有符合某规则的才抽"。
4. `Entity`（`models.py:538`）**没有置信度字段**，抽取结果缺少"把握多大"这一维度。
5. 抽取是**纯自然语言 Prompt + 正则抠 JSON**（`_parse_response`），没有 json_schema / structured output，规则只能靠后置代码兜。
6. **违规数据直接丢弃，无任何留存与提示**——用户不知道被丢了什么、为什么丢。

### 1.2 目标

1. 支持在**本体属性**上配置抽取规则（枚举、正则、范围、长度、必填、置信度）。
2. 支持在**对象类型**上配置实体级规则（名称模式、最低置信度、最少有效属性数）。
3. 抽取结果经**规则引擎校验**后分级处置：通过入库 / 降级丢属性值 / 进入人工复核队列。
4. 违规**不静默丢弃**：记录违背了哪条规则、原始值、来源分片，提供人工复核入口，审核通过后可入库，可驳回。
5. 抽取过程**可观测**：每个文件产出一份抽取报告（违规统计、规则命中分布）。

### 1.3 设计原则

> **规则驱动过滤 + 降级 + 可观测**

- **双写规则**：规则既注入 Prompt（让模型尽量别产出违规值），又在后置代码里做权威校验（不能只信模型）。
- **分级而非一刀切**：单属性值违规不等于实体无效，能降级就降级，避免大规模误杀。
- **违规即留证据**：任何被拦下的对象都进入复核队列，可追溯、可挽回。
- **默认宽容、可选严格**：默认只有实体级违规进队列（避免队列爆炸），知识库可开启严格模式让所有违规都进队列。

### 1.4 非目标（本期不做）

- 不做规则的自动学习与推荐（如从历史抽取结果反推合理枚举范围）。
- 不做正则表达式的可视化构建器（提供常用模板下拉 + 手写输入框）。
- 不做跨属性依赖规则（如"结束日期必须晚于开始日期"），本期只做单属性规则 + 实体级规则。
- 不做关系（`OntologyRelation`）实例的规则校验，本期仅覆盖实体。
- 不改变 SQLite / Kùzu / 向量库的写入职责划分。

## 2. Palantir 的做法（对标调研）

### 2.1 总体结论

Palantir Foundry 中**没有**"在属性上直接写一条规则、抽取时自动只抽符合规则的实体"这种单一能力。它把这个能力**解耦成了三个层次**：

```
┌──────────────────────────────────────────────────────────────┐
│ ① Value Types + Value Type Constraints  → 定义"什么算合法"      │
│    属性不绑基础类型，绑语义值类型（Email / 手机号 / 金额）         │
│    约束在值类型上配一次，跨对象类型、跨管道复用                    │
├──────────────────────────────────────────────────────────────┤
│ ② Data Expectations（Pipeline Builder / 代码仓库）→ 决定"拦不拦" │
│    对数据集输出声明期望，作为 build 的一部分运行，失败可中止构建    │
├──────────────────────────────────────────────────────────────┤
│ ③ AIP Document Intelligence（抽取端）→ 决定"抽什么"             │
│    OCR / 版面检测 + VLM 抽取，schema 驱动，Evaluations 打分迭代  │
└──────────────────────────────────────────────────────────────┘
```

**核心差别必须讲清楚：**

| | Palantir | 我们想要 |
|---|---|---|
| 语义 | **校验端拦截**：规则不满足 → 数据校验失败 / 构建中止 | **生成端过滤**：规则不满足 → 该实体/属性不被抽出来 |
| 失败代价 | 整批数据不可用，需人工修 pipeline | 单条数据被隔离，不影响其他结果 |
| 兜底 | 无"待复核"中间态 | 需要人工复核队列 |

### 2.2 Value Types 与 Value Type Constraints

**Value Type（值类型）** 是对数据集字段类型的**语义包装层**，在基础类型之上附加元数据与约束，用于增强类型安全、提升表达力、实现跨平台复用的数据校验。

与基础类型的对比：

| 维度 | 基础类型（string / integer） | Value Type |
|---|---|---|
| 性质 | 与领域无关的**原始类型** | **领域语义类型**（如"邮箱""手机号"） |
| 含义来源 | 需依赖列名、描述推断 | 含义内建于类型本身 |
| 校验 | 无内建校验 | **内建约束，自动强制校验** |
| 复用 | 每处重复写校验逻辑 | 定义一次，跨对象类型/管道复用 |

**支持的约束类型（完整清单）：**

| 约束 | 说明 | 适用基础类型 |
|---|---|---|
| **Enum (one of)** | 静态允许值集合 | String、Boolean、Decimal、Double、Float、Integer、Short（String 可配大小写敏感/不敏感） |
| **Range** | 最小值 / 最大值 / 允许范围 | Decimal、Double、Float、Integer、Short、Date、Timestamp、String（约束长度）、Array（约束数组大小） |
| **Regex** | 必须匹配的正则表达式，可选配置为"子串匹配即通过" | String |
| **RID** | 必须是有效 rid | String |
| **UUID** | 必须是有效 UUID | String |
| **Uniqueness** | 数组所有元素必须唯一 | Array |
| **Nested** | 约束作用于数组元素本身（如对数组中每个字符串应用 regex） | Array |
| **Element constraints** | 结构体字段标识符 → 值类型引用的映射，对指定字段套用值类型 | Struct |

> 官方文档仅提供上述**内置**约束类型，未开放自定义约束类型的编写能力。

**作用域与治理：** Value Type 不属于 Ontology 本身，而是绑定到平台的 **space**，只能在定义它的 space 内使用（Default ontology 不可用）；有独立权限体系；支持 **breaking / non-breaking** 两类版本化编辑。

**强制执行范围：** 约束会在 **Builder 管道（数据集成）与 Ontology** 中被执行。若把值类型应用到包含不合规值的对象属性上，**该对象类型会校验失败**——这是"拒绝"，不是"过滤"。

### 2.3 Data Expectations

在 Pipeline Builder 或代码仓库中对数据集输出定义"期望（requirements）"，用于：

- **Pipeline protection**：期望作为 build 的一部分运行，失败时可**中止构建**，阻止脏数据流向下游。
- **Change management**：期望定义在代码仓库中，变更需要 code review。

这是 Palantir 里最接近"不合格行不落库"的机制，但它是**构建期的成批拦截**，不是逐条过滤加放行。

### 2.4 AIP Document Intelligence（抽取端）

- **传统提取**：PDF 元数据提取、OCR 检测、版面布局检测，由 media sets v2 的 `transform-media-item` 端点支撑。
- **生成式 AI 配置**：可在 Configuration > Generative AI 中开启 **Preprocess document**——先跑 OCR，再把 OCR 输出**连同文档页面图像**一起喂给 VLM，提供更多上下文。
- **Prompt 迭代**：可对不同的 prompt 和策略做测试，通过 **Evaluations** 快速迭代：每次运行可查看定性评分卡，以所选 VLM 作为评委，对表格抽取、标题抽取等方面从 **1（最差）到 5（最好）** 打分。
- **与本体集成**：可部署为 Python transforms / Python functions，按需结构化地消费本体。

> 官方文档**未提及**抽取时对字段自动套用 value type 约束，也未提供字段级的抽取过滤规则。Evaluations 是**质量评估**，不是自动验证/过滤。

### 2.5 我们必须偏离 Palantir 的三点

1. **Palantir 的"校验失败即中止"在 LLM 抽取场景代价过高。** 模型偶尔抽错是常态，一次违规让整批失败不可接受。
2. **LLM 输出天然带不确定性，必须有置信度维度。** Palantir 的数据来自确定性管道，不需要；我们的数据来自模型生成，必须有。
3. **LLM 抽取需要人工兜底。** 需要 `pending → approved / rejected` 的中间态，而不是"要么进、要么废"。这是本设计第 5 章的内容，Palantir 没有对应物。

**结论：** Palantir 提供的是"**本体定义合法性 + 管道强制校验**"；我们要在它之上补出"**生成端软约束 + 违规降级 + 人工复核挽回**"。这也是本设计相对于 Palantir 的增量部分。

## 3. 规则模型设计

### 3.1 规则分两类

| 类别 | 作用时机 | 失败后果 | 代表字段 |
|---|---|---|---|
| **提示型规则** | 注入 Prompt，影响模型产出 | 无硬后果，靠后置兜底 | `extraction_hint`、`extraction_examples`、`negative_examples` |
| **约束型规则** | 后置校验，权威判定 | 按 §3.4 策略矩阵处置 | `enum_values`、`value_pattern`、`min/max_value`、`min/max_length`、`is_required`、`confidence_threshold` |

### 3.2 属性级新增强制列（`ontology_attributes`）

贴合项目现有风格（`render_hint` / `format` / `unit` / `is_edit_only` 均为独立列），**约束采用独立列而非 JSON blob**，便于 `_serialize_attribute` 直出、前端直绑、后续加索引。

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `enum_values` | TEXT NULL | NULL | JSON 字符串数组，允许值集合；对 `string` 生效 |
| `value_pattern` | VARCHAR(200) | `''` | 正则表达式（Python `re` 语法），对 `string` 生效 |
| `min_value` | VARCHAR(64) | `''` | 下界；`number` 按数值比较，`date/datetime` 按 ISO 字符串比较，空表示不限 |
| `max_value` | VARCHAR(64) | `''` | 上界，同上 |
| `min_length` | INTEGER | 0 | 字符串最小长度，0 表示不限 |
| `max_length` | INTEGER | 0 | 字符串最大长度，0 表示不限 |
| `confidence_threshold` | REAL NULL | NULL | 该属性值的置信度门槛；NULL 表示继承对象类型级 `min_confidence`。置信度**由证据计算得出、非模型自报**（见 §4.5.1） |
| `on_violation` | VARCHAR(16) | `'drop_attribute'` | 违背时处置：`drop_attribute`（丢属性值，默认）/ `review`（整实体进复核队列）/ `drop_entity`（丢实体） |
| `extraction_hint` | TEXT | `''` | 抽取提示，注入 Prompt 的属性行末尾 |
| `extraction_examples` | TEXT NULL | NULL | JSON 字符串数组，正例，注入 Prompt |
| `negative_examples` | TEXT NULL | NULL | JSON 字符串数组，反例，注入 Prompt |

> `is_required` 语义升级：从"仅 Prompt 文案"升级为**真正的入库强制校验**（见 §3.4 R6）。

### 3.3 对象类型级新增列（`ontologies`）

实体是否被抽出来是**实体级**判决，仅有属性规则不够：

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `name_pattern` | VARCHAR(200) | `''` | 实体名称必须匹配的正则，用于过滤"—"、"第3节"、整句等噪声；空表示不限。比现有全局 `_is_low_value_entity_name` 更精准、可按类型定制 |
| `min_confidence` | REAL NULL | NULL | 实体级最低置信度门槛，NULL 表示使用全局配置 `GRAPH_MIN_ENTITY_CONFIDENCE`。置信度**由证据计算得出、非模型自报**（见 §4.5.2） |
| `min_valid_attributes` | INTEGER | 0 | 通过校验的属性数少于该值 → 实体进复核；0 表示不限制 |

### 3.4 违规处置策略矩阵

这是本设计的核心决策点。**不建议"任一违规即丢弃实体"**，按严重度分级：

| # | 违规类型 | 严重度 | 默认处置 | 可配置 |
|---|---|---|---|---|
| R1 | 属性值不在 `enum_values` 内 | 中 | **丢属性值**，实体保留，计 warning | `on_violation` |
| R2 | 属性值不匹配 `value_pattern` | 中 | **丢属性值**，实体保留，计 warning | `on_violation` |
| R3 | 数值/日期超出 `min/max_value` | 中 | **丢属性值**，实体保留，计 warning | `on_violation` |
| R4 | 字符串长度超出 `min/max_length` | 低 | **丢属性值**，实体保留，计 warning | `on_violation` |
| R5 | 属性值置信度 < `confidence_threshold` | 中 | **丢属性值**，实体保留，计 warning | `on_violation` |
| R6 | `is_required` 属性缺失，或其值被丢弃后缺失 | **高** | **进复核队列**（不直接丢） | 否，始终进队列 |
| R7 | 有效属性数 < `min_valid_attributes` | **高** | **进复核队列** | 否 |
| R8 | 实体名不匹配 `name_pattern` | **高** | **进复核队列** | 否 |
| R9 | 实体置信度 < `min_confidence` | 高 | **进复核队列** | 否 |

**为什么 R6~R9 进队列而不是直接丢：** 这类实体往往是"类型判断对了、但信息不全"，人工一眼能补完即可入库，直接丢弃损失最大。

**队列规模控制：** 属性级违规（R1~R5）按各自属性上的 `on_violation` 处置，默认 `drop_attribute`（只丢值 + 计数，不占队列）；显式配置为 `review` 时才进队列。实体级违规（R6~R9）始终进队列。知识库开启**严格模式**（`kb_ontology_bindings.strict_mode`）后，属性级 `drop_attribute` 自动升级为 `review`，便于新规则上线初期观察效果。

### 3.5 与共享属性 `enum_values` 的关系

`OntologySharedProperty` 已有 `enum_values`，挂载后会在 `get_merged_attributes` 中合并出现。规则：

1. 属性自身未配 `enum_values` 时，**继承其共享属性的 `enum_values`**（在 `_serialize_attribute` 合并输出时带上）。
2. 两者都配了 → **以属性自身为准**，并在抽取报告中记一笔覆盖提示。
3. 两者都无 → 不启用枚举校验。

## 4. 规则引擎与校验流水线

### 4.1 流水线位置

在现有 `_normalize_properties` 的位置上扩展为完整规则引擎，位于**模型返回之后、写入 SQLite/Kùzu 之前**：

```
LLM 返回 JSON
   │
   ├─ _parse_response              正则抠 JSON            （已有）
   ├─ _merge_payload               类型白名单 / 三元组白名单（已有）
   │     │
   │     ├─ ❶ _validate_properties  属性级规则校验（新增，包裹 _normalize_properties）
   │     │      ├─ 类型规整（已有 _coerce_property_value）
   │     │      ├─ ConfidenceScorer.attr_score()  证据计算属性置信度（新增，§4.5.1）
   │     │      ├─ enum / pattern / range / length / conf → 逐条出 Violation
   │     │      └─ 按 on_violation 处置：丢值 或 标记
   │     │
   │     └─ ❷ _judge_entity        实体级判决（新增）
   │            ├─ ConfidenceScorer.entity_score()  证据计算实体置信度（新增，§4.5.2）
   │            ├─ required 缺失 / min_valid_attributes / name_pattern / min_confidence
   │            └─ 输出 verdict: pass | review | drop
   │
   ├─ pass   → 正常走 _persist_extraction_to_sqlite（已有）
   ├─ review → 写入 extraction_reviews，等待人工（新增）
   └─ drop   → 丢弃，计入抽取报告（新增）
```

### 4.2 判决结果对象

```python
@dataclass
class Violation:
    level: str        # "attribute" | "entity"
    rule: str         # "enum" | "pattern" | "range" | "length" | "confidence"
                      # | "required" | "name_pattern" | "min_attributes"
    target: str       # 属性名 或 实体名
    code: str         # 属性 code（便于前端精确定位）
    value: Any        # 原始值
    reason: str       # 人类可读原因，如 "值 '待定' 不在允许集合 [正式/试用/离职] 中"
    action: str = "drop_attribute"   # 与 on_violation 同枚举：drop_attribute | review | drop_entity

@dataclass
class EntityVerdict:
    verdict: str              # "pass" | "review" | "drop"
    entity: GraphEntity       # 已按降级结果清洗过 properties 的实体
    violations: list[Violation]
    confidence: float         # 实体级置信度，证据计算得出（§4.5.2）
    attr_confidence: dict[str, float]   # 属性级置信度，证据计算得出（§4.5.1）
```

### 4.3 校验结果的数据流向

| verdict | 去向 | 后续 |
|---|---|---|
| `pass` | `_persist_extraction_to_sqlite` → SQLite + Kùzu | 与现状一致 |
| `review` | `extraction_reviews` 表 | 人工通过后复用 `EntityService.create_entity` 入库 |
| `drop` | 仅计入抽取报告 | 不留存实体，但报告里有计数与样例 |

**幂等性说明：** `EntityService.create_entity` 已实现 `(kb_id, entity_type, name)` 的 upsert 语义（描述取更长、属性增量合并）。复核通过后同样走这条路径，因此**人工入库与自动入库天然不冲突**，重新处理文件也不会产生重复实体。

### 4.4 现有代码改动落点

| 层次 | 文件 : 位置 | 改动 |

### 4.5 置信度计算（证据驱动）

**设计决策：不采用模型自报置信度，改为从抽取证据计算。**

理由：

1. LLM 自报置信度**校准性差**——普遍过度自信（动辄 0.9+），且随 prompt 措辞漂移。
2. 换模型就要重新校准阈值，同一个 `0.6` 门槛在不同模型上含义完全不同。
3. 增加 prompt 复杂度与 token 消耗。
4. **与项目既有实践一致**：现有 confidence 全部来自规则常量或公式计算，无一依赖模型自报：

```python
# graph_inference_service.py:35  传播链置信度 = 公式计算
PROPAGATION_DECAY = 0.8        # confidence = 0.8 ** (n - 1)

# graph_inference_service.py:43  推理规则置信度 = 硬编码常量
{"key": "compose_trans", ..., "conf": 0.95}
{"key": "fault_rollup",  ..., "conf": 0.90}

# core/doc_profiler.py:123  分片策略推荐置信度 = 规则常量
hit("fixed", 0.95, ...)
```

#### 4.5.1 属性级置信度（在 `_validate_properties` 内计算）

```
base = 0.5
+0.3  属性值在来源 chunk 原文中精确出现        （可验证，强证据）
+0.1  类型校验通过且无需强制转换
+0.1  同一 (实体, 属性) 在多个 chunk 中被一致抽到
-0.2  值来自模型推断（原文无精确匹配）
clamp 到 [0, 1]
```

#### 4.5.2 实体级置信度（在 `_judge_entity` 内计算）

```
base = 0.4
+0.3 × (有效属性数 / 本体定义的属性数)         完整度
+0.2  实体名在来源 chunk 原文中精确出现
+0.1  该实体在 ≥2 个 chunk 中被抽到            交叉验证
clamp 到 [0, 1]
```

#### 4.5.3 证据来源（无需额外查询）

- `_merge_payload` 的 `chunk_map: dict[str, ChunkGraphData]` 已携带 `content`（原文），校验时可直接在 `chunk.content` 中做精确匹配。
- "跨 chunk 一致"只需在同一批 `batch_chunks` 内做一次预统计聚合，不跨批次、不查库。

#### 4.5.4 权重标定

上表权重是**初始值，需要一次离线标定**：在几个真实知识库上跑一遍，观察置信度分布后再定 `confidence_threshold` / `min_confidence` 的默认推荐值。

- 标定前默认阈值建议 **0.6**。
- 抽取报告需输出置信度分布（分桶计数），便于调参，见 §7.2 扩展字段 `confidence_histogram`。

#### 4.5.5 可选：模型自报作为补充

配置项 `GRAPH_USE_MODEL_CONFIDENCE`（`config.py`，默认 `false`）。开启后：

- Prompt 追加要求：为每个实体输出 `confidence`（0~1），可选为每个属性输出 `__confidence`。
- `__confidence` 解析后**从 `properties` 中剥离**，不落库、不污染数据。
- 融合规则：`最终置信度 = max(证据计算值, 模型自报值 × 0.9)` —— 对模型自报打折以抵消过度自信。
- 模型未输出时**退化为纯证据计算**（既不补 1.0，也不置 0），保证任何模型下行为一致。

#### 4.5.6 阈值优先级

```
属性 confidence_threshold  >  ontologies.min_confidence  >  GRAPH_MIN_ENTITY_CONFIDENCE（默认 0.0 即关闭）
```

#### 4.5.7 性能评估（实测）

证据计算全部是**内存内字符串查找与 dict 聚合**，无 IO、无模型调用。按真实规模实测（chunk 原文 1000 字符、每 chunk 12 实体 × 8 属性，即 96 次子串匹配）：

| 项目 | 实测耗时 |
|---|---|
| 每分片证据匹配 | **0.014 ms** |
| 1000 分片（约 10 篇中等文档） | 14 ms |
| 10 万分片（大型知识库） | 1.4 s |
| 跨 chunk 一致性预统计（每批 6 分片聚合一次） | < 0.05 ms/批 |

**与现有步骤对比：** 同样规模下，`_normalize_properties` 现已在做的 `json.loads` 耗时 69.5 ms，而新增的证据匹配仅 9.9 ms —— **只有现有步骤的 14%**，比它便宜约 7 倍。

**与端到端对比：** 抽取链路耗时大头是 embedding 与 LLM 调用（`GRAPH_EXTRACTION_BATCH_SIZE=6`，每批一次调用，典型 1~3 秒）。10 万分片约 1.6 万次调用，并发 3 下需 1.5~4.5 小时；证据计算的 1.4 秒**占比约 0.01%，可忽略**。

**唯一的真实性能陷阱：正则重复编译。** 属性配置了 `value_pattern` 时，必须在**装载约束阶段**（`get_kb_extraction_constraints`）就 `re.compile` 并缓存进约束字典，**禁止**在每个属性值上直接调 `re.match(pattern, value)` 依赖模块级缓存（上限 512 条，且带 dict 查找开销）。实现时按此约束编写。

**结论：性能不构成上线阻碍，无需为此砍掉证据计算。**

**这个方案相对模型自报的优势：** 不要求模型配合、任何模型通用、阈值含义稳定不随模型更换而失准、零额外 token、且**可解释**——报告中能写清"因原文无精确匹配被降级"，而不是一个无法追溯的模型臆断值。

## 5. 人工复核队列

### 5.1 为什么用独立表而不是写 `File.detail`

`File.detail` 已用于存放处理详情，但复核队列需要**分页查询、按状态过滤、批量审核、长期留存**，且违规条目量级可达数百上千。写 JSON 会让单条文件记录膨胀且无法高效检索。因此新增独立表。

### 5.2 数据模型

新增表 `extraction_reviews`：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | String PK | 12 位短 id，与项目惯例一致 |
| `kb_id` | String NOT NULL | 知识库 |
| `file_id` | String | 来源文件 |
| `chunk_id` | String | 来源分片，便于回溯原文 |
| `ontology_id` | String | 目标对象类型 |
| `entity_type` | String | 已归一化的类型 code |
| `entity_name` | String | 实体名 |
| `description` | Text | 模型给出的描述 |
| `properties` | Text | **清洗后**的属性 JSON（违规值已按策略处理） |
| `raw_properties` | Text | **原始**属性 JSON（未清洗，供人工对照） |
| `confidence` | REAL | 实体置信度，**由证据计算得出**（见 §4.5.2），非模型自报 |
| `violations` | Text NOT NULL | JSON 数组，元素为 §4.2 的 `Violation`（含 rule/target/value/reason/action） |
| `primary_rule` | String | 汇总主因：`required` / `name_pattern` / `min_confidence` / `min_attributes` / `enum` / `pattern` … |
| `status` | String default `'pending'` | `pending` / `approved` / `rejected` / `expired` |
| `reviewer` | String | 审核人 |
| `review_notes` | Text | 审核备注 |
| `reviewed_at` | String | 审核时间 |
| `created_at` / `updated_at` | String | 时间戳 |

索引建议：`(kb_id, status)`、`(file_id)`、`(kb_id, file_id, created_at)`。

### 5.3 状态机

```
   违规产生
       │
       ▼
   pending ──审核通过──► approved ──► 调用 EntityService.create_entity 入库
       │                               （同步 Kùzu，与 _persist_extraction_to_sqlite 同语义）
       │                               （入库失败则回滚 pending 并附错误信息）
       │
       ├──审核驳回──► rejected（记录 reviewer / review_notes，不入库）
       │
       └──► expired（源文件被重新处理 / 删除，仅留痕，不清数据）
```

要点：

- **审核通过即入库**，不留中间态；入库失败（如本体已被删除）时**回滚为 `pending`** 并带上错误提示，避免静默丢失。
- 审核时**允许修改**实体名、属性值（前端提供编辑），修改后的内容才是入库内容，并记入 `review_notes`。
- 支持**批量通过 / 批量驳回**，按 `file_id` 或 `primary_rule` 过滤后批量操作。
- 文件重新处理时，该文件下所有 `pending` 记录转为 `expired`（不清数据，仅改状态，避免与新一轮抽取的复核项混淆）。

### 5.4 复用现有审核模式

项目中已有 `OntologySuggestion`（`models.py:221`）的审核闭环：`status: generating|ready|approved|rejected` + `approve/reject` 路由（`routers/ontology.py:490`）+ `reviewer/review_notes`。**本设计直接对齐这套模式**：相同的状态词、相同的路由动词、相同的前端交互范式，降低学习与维护成本。

## 9. Prompt 改造

`_build_constrained_system_prompt` 的属性行从：

```
      属性：编码:name、姓名、string、必填；编码:level、职级、string
```

扩展为带规则的形态：

```
      属性：
        - 姓名 (name, string, 必填)
        - 职级 (level, string) 取值仅限 [正式|试用|离职]，请仅在确信时给出
        - 工号 (emp_no, string) 必须匹配正则 ^[A-Z]{2}[0-9]{4}$，例如 AB1234
        - 入职日期 (hire_date, date) 范围 2000-01-01 ~ 2026-12-31
        - 备注 (note, text) 提示：仅抽取明确写明的资质限制条款，请勿抽取推测性描述
```

原则：

- **正向引导优先，不把内部处置策略告诉模型。** 例如不写"违背将丢弃"，而是写"请仅在确信时给出"——避免模型因畏惧惩罚而少抽，导致召回下降。
- 枚举、正则、范围这类**可判定的硬规则**必须写进去（低成本、高收益）。
- `extraction_hint` / `extraction_examples` / `negative_examples` 直接追加在该属性行末尾。
- `is_edit_only` 属性仍排除在外（现状不变）。
- 规则块过长时按必要性截断（优先保留枚举 > 正则 > 范围 > 提示），避免 Prompt 膨胀挤占上下文。
- **默认不要求模型输出 confidence。** 置信度由证据计算得出（§4.5），不占 prompt、不依赖模型配合。仅当 `GRAPH_USE_MODEL_CONFIDENCE=true` 时才在约束块末尾追加：**"为每个实体输出 confidence 字段（0~1），表示你对该实体抽取正确的把握程度。"**

## 10. 边界与降级

| 场景 | 处理 |
|---|---|
| 存量本体未配置任何规则 | 全部字段走默认值，**行为与现状完全一致**，零影响 |
| 置信度证据不足（原文极短 / 无 chunk 内容） | 属性级取 base `0.5`，实体级取 base `0.4`；阈值高于 base 时会进复核队列。不会因缺证据而崩溃 |
| `GRAPH_USE_MODEL_CONFIDENCE=true` 但模型未输出 `confidence` | 退化为纯证据计算，**既不补 1.0 也不置 0**；报告中记 `model_confidence_missing: true` |
| `confidence_threshold` 已配但对象类型无属性定义 | 属性级阈值无从计算，跳过属性级置信度校验，仅保留实体级 |
| 正则非法（历史脏数据绕过前端校验） | 运行时 catch `re.error`，跳过该条规则并记 warning，**不阻断整批抽取** |
| `enum_values` 与共享属性都有值 | 属性自身优先（§3.5） |
| 属性值被丢弃导致实体完全无属性 | 若 `min_valid_attributes = 0` 且无 required，实体仍入库（空属性实体），报告中计 `downgraded_attributes` |
| 复核通过后目标本体已被删除 | 入库失败，状态回滚为 `pending`，返回明确错误信息 |
| 同名实体跨分片多次违规 | 队列按 `(kb_id, entity_type, entity_name)` 去重，保留置信度最高的一条，其余合并其 violations 计数 |
| 自由抽取模式（KB 未绑定本体） | 无属性定义即无规则，规则引擎整体跳过，仅保留现有全局噪声过滤 |
| 队列长期堆积未处理 | 不自动清理，仅提供"清空全部"与"按文件清理"的手动入口；文件重新处理时旧项转 `expired` |
| 抽取批次极大导致 review 写入压力大 | review 分批 commit（每 200 条一批），失败批次记日志但不阻断主流程 |

## 12. 开放问题

1. **置信度权重是一次标定到位，还是先上后调？** §4.5.1 / §4.5.2 的权重（+0.3 / +0.1 / -0.2 等）是经验初值。建议先按初值上线，在 2~3 个真实知识库上跑一遍，结合报告中的 `confidence_histogram` 分布再回调权重并确定默认阈值（标定前建议 0.6）。好处是立刻可用，代价是初期阈值可能偏松或偏紧，**是否接受"先上后调"？**
2. **`on_violation` 默认值定为 `drop_attribute` 是否合适？** 已初步定为 `drop_attribute`（理由：属性级违规数量通常远多于实体级，全部进队列会淹没人工注意力；丢属性值本身已能拦住脏数据）。若业务侧希望"任何被规则拦下的内容都必须有人看一眼"，可通过 KB 严格模式整体切换，无需逐个属性改。**待评审确认。**
3. **`extraction_reviews` 是否需要保留已处理记录多久？** 建议提供配置项 `EXTRACTION_REVIEW_RETENTION_DAYS`（默认 90 天，定时任务清理终态记录）。
4. **规则是否需要版本化？** 本体的规则被修改后，历史抽取结果的判定依据会失真。本期建议不版本化，仅在 `Violation.reason` 中记录当时的规则快照摘要；若后续需要精确审计再补 `rule_snapshot` 列。
5. **是否需要支持"白名单例外"（如某几个已知脏值强制放行）？** 本期不支持，评审时确认是否必要。
