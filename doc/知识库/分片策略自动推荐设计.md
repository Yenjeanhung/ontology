# 分片策略自动推荐设计

> 状态：设计稿（待评审）
> 相关代码：`backend/core/chunker.py`、`backend/config.py`、`backend/services/file_service.py`、`backend/routers/files.py`、`front/src/components/KbDetail.vue`

---

## 1. 背景与现状

### 1.1 现状问题

当前系统的分片策略**全局写死在配置中**，对所有文档一视同仁：

```
# backend/config.py
CHUNK_STRATEGY: Literal["fixed", "semantic", "sentence"] = "fixed"
CHUNK_SIZE: int
CHUNK_OVERLAP: int
```

- 上传重组完成后（`status=uploaded`），用户点击"开始处理"，后端一次性执行 `解析 → 分片(settings.CHUNK_STRATEGY) → 向量化 → 抽取`，**中间没有策略选择与确认环节**。
- 仅支持 3 种基础策略（fixed / sentence / semantic），缺少递归字符切分、标题层级切分、父子分块等生产常用策略。
- 不同形态的文档（教材、FAQ、合同、代码文档、CSV）被同一种策略切分，语义完整性无法保证。

### 1.2 目标

1. **上传后自动分析文档**，提取结构/语义特征，给出**推荐分片策略 + 参数**及推荐理由。
2. 用户在**确认对话框**中查看推荐，可修改策略与参数，可**预览分片效果**，确认后才真正执行分片入库。
3. 策略体系从 3 种扩展为 7 种（含父子分块），参数（chunk_size / overlap）可按文档动态建议。
4. 兼容现有流水线：不改变"分片 → 向量化 → 抽取"主流程，仅在其前置入"分析 → 推荐 → 确认"环节；保留全局配置作为兜底与"跳过确认"的自动模式。

### 1.3 非目标（本期不做）

- 不做分片效果的事后评估与自动调优（如基于检索命中率的 A/B）。
- 不做多文档批量差异化策略（每个文件独立策略，但确认交互按文件逐个进行）。
- 不改变向量库 / 图谱写入逻辑（父子分块除外，见 §5.3）。

## 2. 策略全集

### 2.1 策略注册表

| key | 名称 | 类别 | 实现现状 | 说明 |
|---|---|---|---|---|
| `fixed` | 固定长度切分 | 基础 | 已有 `_iter_fixed_texts` | 按长度硬切，边界回退到最近分隔符。仅推荐用于纯数据/原型验证 |
| `sentence` | 句子/段落切分 | 基础 | 已有 `_iter_sentence_texts` | 按标点断句累积成块，语义边界完整 |
| `recursive` | 递归字符切分 | 基础 | **新增** | 按 `\n\n → \n → 。→ ；→ . → 空格 → 字符` 优先级降级切分（LangChain RecursiveCharacterTextSplitter 思路） |
| `sliding_window` | 滑动窗口/重叠 | 基础 | **作为正交参数实现** | overlap 是 `fixed / recursive / sentence` 的通用参数（默认 10%~20%），不单列为独立执行器，避免策略爆炸 |
| `semantic` | 语义切分 | 进阶 | 已有 `_iter_semantic_texts`（段落级近似）→ **增强** | 相邻句 embedding 相似度突变处切分；成本高，可选开启真实向量检测 |
| `heading` | 层级/标题切分 | 进阶 | **新增** | 解析 Markdown `#`、数字编号（1.1）、中文章节（第X章）等标题层级，按章节切分，可带父路径元数据 |
| `parent_child` | 父子分块 | 进阶 | **新增** | 父块（1000~2000 token）供上下文，子块（200~400 token）供向量检索；父块策略复用 `heading` 或 `recursive` |

> 说明：`sliding_window` 在 UI 上仍呈现为一个可勾选的"策略选项"，但内部映射为 `strategy=recursive/fixed + params.overlap>0`，由推荐引擎负责换算，用户无感知。

### 2.2 策略适用场景速查

| 策略 | 适用文档 | 优点 | 代价 |
|---|---|---|---|
| fixed | CSV、日志、纯数据流 | 极简、快速 | 语义边界差 |
| sentence | 普通文章、邮件、博客 | 边界自然 | 块大小不均 |
| recursive | 大多数普通文本（默认） | 语义与块大小平衡 | 依赖分隔符质量 |
| +overlap | 技术文档、合同 | 防止边界信息丢失 | 存储/向量略增 |
| semantic | FAQ、客服日志、调研报告 | 单块语义最聚焦 | 需全文 embedding，慢且贵 |
| heading | 教材、技术手册、带目录 PDF/MD | 结构对齐、可追溯章节 | 依赖标题质量 |
| parent_child | 长文档 + 高质量检索要求 | 精检索 + 全上下文 | 双倍块管理、检索逻辑改造 |

## 3. 总体流程

### 3.1 状态机扩展

现有状态：`uploading → uploaded → processing → indexed / failed`

新增两个状态：

```
uploading ──► uploaded ──► analyzing ──► analyzed ──► processing ──► indexed
                 │             │              │
                 │             │(分析失败)     │(用户确认，携带策略参数)
                 │             ▼              ▼
                 │          uploaded      processing
                 │
                 └──(自动模式)────────────────────► processing
```

- `analyzing`：后台执行文档解析 + 特征提取 + 推荐（上传重组完成后自动触发，或用户手动触发）。
- `analyzed`：分析完成，等待用户确认策略（前端文件列表显示"待确认策略"）。
- 自动模式（`CHUNK_AUTO_STRATEGY_CONFIRM=false` 或用户勾选"不再确认"）：跳过确认，直接采用推荐结果进入 processing。

### 3.2 端到端时序

```
前端                    后端                          分析器/分片器
 │ 上传分片…重组完成        │                              │
 │ ─────────────────────► │ status=uploaded              │
 │                        │ 自动创建分析任务(异步)          │
 │                        │ ── 解析文档(采样) ──────────► │ 特征提取
 │                        │ ── 规则引擎打分               │ 推荐策略+参数+理由
 │ 轮询状态/SSE            │ status=analyzed              │
 │ ◄───────────────────── │                              │
 │ 弹出确认对话框           │                              │
 │ GET recommendation      │ ◄── 返回特征/推荐/预估分片数    │
 │ (可选) 预览分片          │ POST chunk-preview           │ dry-run 前 N 块
 │ ◄───────────────────── │                              │
 │ 用户确认(或调整参数)      │ POST process?strategy=…&     │
 │ ─────────────────────► │ params=…                      │
 │                        │ status=processing            │
 │                        │ ── iter_text_chunks(strategy) │ 正式分片入库
```

## 4. 文档特征分析器（Document Profiler）

### 4.1 输入与采样

- 输入：重组后的源文件。复用现有 `providers/parser.get_parser(path).parse(path)`。
- **采样策略控制成本**：全文结构特征基于全文统计（正则，开销小）；语义特征仅抽样前 50k 字符、且最多 100 个相邻句对做 embedding 相似度。

### 4.2 特征清单

| 类别 | 特征 | 提取方式 |
|---|---|---|
| 基础 | `ext`、`total_chars`、`language`(中/英混合比) | 文件名后缀 / 正则 |
| 结构 | `heading_count`、`max_heading_depth` | MD `^#{1,6}\s`；编号 `^\d+(\.\d+)*\s`；中文 `^第[一二三…]+[章节篇]` |
| 结构 | `paragraph_count`、`avg_para_len`、`para_len_std` | 按 `\n\n` 分段统计 |
| 结构 | `sentence_count`、`avg_sentence_len` | 按 `。！？.!?` 断句统计 |
| 结构 | `list_line_ratio`、`table_line_ratio`、`code_block_ratio` | 行首 `- * • \d.`；管道符 `\|`；``` 围栏 |
| 语义 | `semantic_break_density`（可选） | 抽样相邻句 embedding 余弦相似度，统计跌落点占比 |
| 语义 | `topic_consistency`（可选，二期 LLM） | LLM 判别文档体裁：教材/FAQ/合同/报告/数据 |

### 4.3 输出结构

```json
{
  "features": {
    "ext": "md", "total_chars": 86000,
    "heading_count": 42, "max_heading_depth": 4,
    "paragraph_count": 310, "avg_para_len": 277, "para_len_std": 180,
    "avg_sentence_len": 48, "list_line_ratio": 0.07,
    "table_line_ratio": 0.02, "code_block_ratio": 0.04,
    "semantic_break_density": 0.18
  },
  "recommendation": {
    "strategy": "parent_child",
    "params": {
      "chunk_size": 800, "overlap": 80,
      "parent_strategy": "heading", "child_size": 300
    },
    "confidence": 0.86,
    "reasons": [
      "检测到 42 个标题，最深 4 级，结构清晰 → 采用标题层级作为父块边界",
      "文档较长(8.6万字)，父子分块兼顾检索精度与上下文完整",
      "语义突变密度较低(0.18)，无需启用高成本语义切分"
    ],
    "candidates": [
      {"strategy": "heading", "confidence": 0.62},
      {"strategy": "recursive", "confidence": 0.55}
    ]
  }
}
```

## 5. 推荐规则引擎

### 5.1 规则表（按优先级短路匹配）

| # | 条件（满足即匹配） | 推荐 | 置信度 |
|---|---|---|---|
| R1 | `total_chars < 500` | `fixed`（单块），size=total | 0.95 |
| R2 | `ext ∈ {csv,json}` 且表格/键值行占比 > 0.5 | `recursive` + `overlap=0` | 0.8 |
| R3 | `max_heading_depth >= 2` 且 `heading_count >= 5` 且 `total_chars > 5000` 且质量要求高（用户勾选"高质量"或 KB 默认） | `parent_child`(parent=`heading`) | 0.85 |
| R4 | `max_heading_depth >= 2` 且 `heading_count >= 5` | `heading` | 0.8 |
| R5 | `semantic_break_density > 0.35`（抽样开启时）或体裁=FAQ/客服 | `semantic` | 0.75 |
| R6 | `avg_sentence_len > 150` 且 `paragraph_count` 低（长句、少分段，合同/法务类） | `recursive` + `overlap=15%` | 0.7 |
| R7 | `avg_para_len ∈ [100, 800]` 且段落分布均匀 | `recursive` + `overlap=10%` | 0.7 |
| R8 | 其余兜底 | `recursive`（继承全局 `CHUNK_SIZE`） | 0.5 |

多条命中时取序号最小者（短路），同时把其余命中项降级为 `candidates` 展示。

### 5.2 参数建议算法

```
chunk_size 建议 = clamp(中文字符数, 300, 1200)
  基准 800 字符（≈512 token 中文）；长文档(>10万字)取上限，短文档按 1/3 文长封顶
overlap 建议   = round(chunk_size * 10%)；合同/技术规范类 15%；CSV/数据类 0
child_size 建议(parent_child) = clamp(200~400 字符, 250)
parent_size 建议(parent_child) = chunk_size * 2
```

### 5.3 parent_child 的数据模型与检索改造

- `Chunk` 表新增可空列：`parent_id`（String，自引用，指向父块 chunk id）、`is_parent`（Boolean）。
- 父块**不入向量库**（或以低优先级元数据存储），仅入库 SQLite；子块正常向量化，metadata 携带 `parent_chunk_id`。
- 检索侧：向量召回命中子块后，按 `parent_chunk_id` 回表取父块内容拼装上下文（Small-to-Big）。本期先在 `rag_service` 的召回组装处实现，不改变召回接口签名。

## 6. API 设计

新增/扩展接口（挂在 `backend/routers/files.py`）：

| 方法 | 路径 | 说明 |
|---|---|---|
| `POST` | `/api/files/{id}/analyze` | 触发（或重新触发）分析。异步执行，立即返回；状态转 `analyzing` |
| `GET` | `/api/files/{id}/recommendation` | 获取分析结果：features + recommendation + 预估分片数。未分析返回 404/空 |
| `POST` | `/api/files/{id}/chunk-preview` | Body: `{"strategy": "recursive", "params": {...}, "limit": 20}`。dry-run 返回前 `limit` 个分片内容 + 统计（总数、平均长度、长度分布），**不落库** |
| `POST` | `/api/files/{id}/process` | **扩展**：Body 增加 `{"strategy": "...", "params": {...}, "use_recommendation": true}`。缺省时使用推荐结果；传 `use_recommendation=false` 时回退全局配置 |
| `POST` | `/api/files/{id}/reprocess` | 同上扩展 |

推荐结果持久化：写入 `File.detail` JSON 的 `analysis` 子对象（复用现有 `_read_detail/_write_detail` 机制，无需迁移）；确认后的最终决策写入 `detail.chunking_decision = {strategy, params, decided_by: "user"|"auto", decided_at}`。

### 6.1 响应示例

```
GET /api/files/{id}/recommendation
{
  "status": "analyzed",
  "features": { ... },
  "recommendation": {
    "strategy": "heading",
    "params": {"chunk_size": 900, "overlap": 90},
    "confidence": 0.8,
    "reasons": ["检测到 12 个二级标题…"],
    "candidates": [...]
  },
  "estimate": {"chunk_count": 96, "avg_chunk_len": 812}
}
```

## 8. 分片器改造（core/chunker.py）

### 8.1 策略执行器统一签名

```python
# 现有 iter_text_chunks 改为参数化入口
def iter_text_chunks(content, metadata=None, *, strategy=None, params=None):
    strategy = strategy or settings.CHUNK_STRATEGY          # 兜底：全局配置
    params   = params or ChunkParams.from_settings(settings)  # 兜底：全局配置
    executor = _STRATEGY_REGISTRY[strategy]
    yield from _records_from_texts(content, executor(content, params), metadata or {})
```

- `ChunkParams`（dataclass）：`chunk_size`、`overlap`、`child_size`、`parent_size`。
- `_iter_fixed_texts/_iter_sentence_texts/_iter_semantic_texts` 内部的 `settings.*` 读取全部改为读 `params`，消除对全局配置的直接依赖。
- 新增 `_iter_recursive_texts`：分隔符层级 `("\n\n", "\n", "。", "！", "？", "；", ".", "!", "?", ";", " ", "")`，超长段递归降级，支持 overlap。
- 新增 `_iter_heading_texts`：先提取标题树（MD/编号/中文章节三套正则），按"同层累积不超限"切分；chunk record 的 `metadata` 附带 `headings: ["第1章","1.2 …"]` 章节路径。
- 父子分块在 `file_service._process_file_bg` 组装层实现：先用父策略产出父块，再对每个父块用 `child_size` 产出子块记录（子块记录带 `parent_id`），子块走向量写入，父块仅入库。

### 8.2 向量化与抽取的影响

- 子块正常进入向量库与图谱抽取（抽取对象仍为分片内容，语义聚焦反而有利于抽取质量）。
- `Chunk` 入库行新增 `parent_id`；向量 metadata 新增 `parent_chunk_id`，供检索回表。

## 9. 边界与降级

| 场景 | 处理 |
|---|---|
| 分析失败（解析异常/超时 30s） | 状态回落 `uploaded`，`detail.analysis.error` 记录原因；确认对话框显示"分析失败，将使用全局默认策略" |
| PDF 扫描件无文本 | 解析结果为空 → 提示"无可解析文本"，沿用现有空内容失败路径 |
| 用户跳过确认（自动模式） | 直接以推荐结果（或全局配置）进入 processing，`decided_by="auto"` |
| heading 策略但文档无标题 | 执行器内部降级为 `recursive`，日志记录降级原因 |
| semantic 抽样 embedding 服务不可用 | 跳过 `semantic_break_density` 特征，规则引擎跳过 R5 |
| 旧文件（无 analysis 数据）重新处理 | process 请求未带策略 → 回退全局 `CHUNK_STRATEGY`，行为与现状一致 |
| 极长单段（> chunk_size×5 无分隔符） | 递归降级到字符硬切，保证必然产出分片 |

## 10. 实施计划

### 第一期：推荐与确认闭环（核心价值）

1. `core/chunker.py` 参数化改造（ChunkParams + 注册表 + settings 解耦），新增 `recursive` 执行器。
2. 新增 `core/doc_profiler.py`：特征提取 + 规则引擎（R1~R8，语义抽样特征可选）。
3. 路由：`analyze` / `recommendation` / `chunk-preview` / `process` 扩展。
4. 状态机扩展（`analyzing` / `analyzed`），上传重组完成后自动触发分析任务。
5. 前端确认对话框 + 状态呈现 + 预览联动。

### 第二期：进阶策略

6. `heading` 执行器（标题树 + 章节路径元数据）。
7. `semantic` 真实向量断点检测增强（可配置开关，控制成本）。
8. `parent_child`：Chunk 表加列、组装层父子生成、`rag_service` 召回回表。

### 第三期：体验优化

9. 批量上传"全部采用推荐"流；"不再询问"偏好持久化（localStorage + 用户配置）。
10. 可选 LLM 体裁判别（教材/FAQ/合同）融入规则引擎；推荐命中率统计面板。

## 11. 开放问题
