## 1. 需求与目标

### 1.1 场景

| 场景 | 模式 | 说明 |
|------|------|------|
| 内容审核 | `approve` | 智能体生成结论后，人工核对再决定是否发布 |
| 结果确认 | `approve` | 实体服务执行写操作前，人工确认参数 |
| 分支裁决 | `approve` | 自动判断拿不准时，交人工决定走哪条分支 |
| 人工补录 | `form` | 自动抽取缺失字段，人工补填（客户等级、授信额度、备注…） |
| 人工分类 | `form` | 人工给数据打标签 / 选择分类后再继续 |

### 1.2 目标（v1）

1. **可拖拽**：节点面板新增「人工」类型，与现有节点一致的拖拽、配置、连线体验；
2. **可挂起**：运行到人工节点时工作流**暂停**，产出一条待办任务，状态 `waiting`；
3. **可处理**：处理人看到待审内容，选择「通过 / 驳回」并填写理由（理由可按结果设置必填），或**填写自定义表单字段**；
4. **可续跑**：提交后工作流从该节点**继续执行**，进度继续以 SSE 回传（编辑器内自动续播）；
5. **可路由**：审批模式支持 `true / false` 双出口，审批结果直接决定后续分支（不必再串条件节点）；
6. **可追溯**：处理人、时间、理由 / 填写内容、待审快照全部落库，可在运行详情中回看。

### 1.3 非目标（v1 明确不做）

- ❌ 用户/角色/权限体系（系统当前无账号体系，见 §9.6）；
- ❌ 多人会签 / 或签 / 逐级联审；
- ❌ 超时自动通过 / 自动驳回（当前无计划，见 §9.5）；
- ❌ 附件上传类表单字段（v1 只做 §3.3 的 6 种基础类型）；
- ❌ 邮件 / IM / Webhook 外发通知（系统尚无渠道，见 §9.7）。

## 2. 核心设计决策：挂起 + 续跑

人工处理耗时不可控（分钟 ~ 天），**不能**用一条 SSE 长连接干等。三个方案对比：

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|------|------|------|------|------|
| A. 长连接等待 | 节点内 `await` 人工结果，SSE 保持打开 | 实现最简 | 代理/浏览器超时必断；进程重启即丢；调度触发场景完全不可用 | ✗ 排除 |
| B. LangGraph `interrupt` + checkpointer | 原生 HITL，`Command(resume=...)` 恢复 | 语义原生、状态自动持久化 | 需启用 `AsyncSqliteSaver` 并改造 `run_stream` 生命周期；恢复仍需新请求触发，收益有限；`GraphState` 序列化约束增多 | △ v2 备选 |
| **C. 挂起 + 快照续跑** | 挂起时把图状态快照落库，结束时 SSE 正常收尾；处理后再开一条流续跑 | 与现有「一次性 SSE 生成器」零冲突；进程重启可恢复；调度触发场景同样适用 | 需自己维护快照与「重放」逻辑 | ✅ **v1 采用** |

### 2.1 续跑机制：重放（replay）+ 注入（inject）

续跑时**不重跑已完成节点**，而是用快照把图状态「预填」回去：

```text
挂起时：workflow_runs.context_snapshot = { "start": {...}, "outputs": { 已完成节点输出... } }
                                          ↑ 即 LangGraph state 全量

续跑时：
  1. 用 definition_snapshot（无则回退当前 definition）重新编译整图
  2. 初始 state = context_snapshot（已完成节点输出已在 state 中）
  3. _Runtime 携带两个映射：
       replay = { 已完成节点 id: 快照输出 }   → 节点函数直接返回快照，emit node_replayed（零成本）
       inject = { 人工节点 id: 处理结果 }     → 节点函数直接返回结果，emit node_resumed
  4. 条件节点路由器从 state.outputs 读上游结果 → 分支语义与首次运行完全一致
  5. 人工节点之后的节点正常执行（并行 / fail-fast / 事件协议全部不变）
```

> 关键收益：**条件路由、并行 superstep、fail-fast、输出投影等现有语义完全复用**，改动集中在 `_Runtime` 与 `_make_node_fn` 两处。

### 2.2 为什么不直接「从人工节点的下游建子图」

子图方案需自己处理「下游连通子图 + 条件分支裁剪 + 多出口扇出」，容易与 LangGraph 的 superstep 语义产生偏差；重放方案把整图交给 LangGraph，已完成节点退化为 O(1) 的 stub，正确性由框架保证，实现更简单。

## 3. 节点定义 `human`

### 3.1 节点一览（新增行）

| type | 名称 | 模式 | 输出 | 说明 |
|------|------|------|------|------|
| `human` | 人工 | `approve` / `form` | approved + decision + data + comment | **挂起等待人工处理**；审批模式可按结果路由 true/false |

### 3.2 两种模式

| 模式 | 交互 | 出口 | 典型用途 |
|------|------|------|----------|
| `approve` 审批 | 只读待审内容 → **通过 / 驳回** + 理由 | 支持 `true` / `false` 双出口 | 审核、确认、裁决 |
| `form` 表单 | 只读待审内容 + **填写自定义字段** → 提交 | 单出口 | 补录、分类、标注 |

### 3.3 `config` 结构

**审批模式（默认）**

```json
{
  "mode": "approve",
  "description": "请核对智能体结论与原文是否一致，再决定是否发布。",
  "display_fields": [
    { "label": "原始问题",   "value": "{{start.question}}", "type": "text" },
    { "label": "智能体结论", "value": "{{agent_1.answer}}",  "type": "text" },
    { "label": "引用片段",   "value": "{{agent_1.chunks}}",  "type": "json" }
  ],
  "decisions": [
    { "key": "approved", "label": "通过", "style": "primary" },
    { "key": "rejected", "label": "驳回", "style": "danger"  }
  ],
  "comment": { "label": "处理意见", "placeholder": "请说明理由…", "required": false, "required_on": ["rejected"] },
  "assignee": "",
  "timeout": { "hours": null, "action": "keep_pending" },
  "output_fields": ["approved", "decision", "comment", "operator", "decided_at"]
}
```

**表单模式**

```json
{
  "mode": "form",
  "description": "请补全客户信息后提交，提交后工作流继续执行。",
  "display_fields": [
    { "label": "抽取结果", "value": "{{agent_1.data}}", "type": "json" }
  ],
  "form_fields": [
    { "key": "customer_name", "label": "客户名称", "type": "text",     "required": true,  "placeholder": "" },
    { "key": "level",         "label": "客户等级", "type": "select",   "required": true,  "options": ["A", "B", "C"] },
    { "key": "credit_limit",  "label": "授信额度", "type": "number",   "required": false, "default": 0 },
    { "key": "remark",        "label": "备注",     "type": "textarea", "required": false },
    { "key": "signed_at",     "label": "签约日期", "type": "date",     "required": false },
    { "key": "vip",           "label": "是否 VIP", "type": "boolean",  "required": false, "default": false }
  ],
  "submit_text": "提交",
  "comment": { "label": "补充说明", "placeholder": "选填…", "required": false },
  "assignee": "",
  "timeout": { "hours": null, "action": "keep_pending" },
  "output_fields": ["data", "comment", "operator", "decided_at"]
}
```

**表单字段类型（`form_fields[].type`）**

| type | 控件 | 值类型 | 校验 |
|------|------|--------|------|
| `text` | 单行输入 | string | `required`、`maxlength` |
| `textarea` | 多行文本 | string | `required`、`maxlength` |
| `number` | 数字输入 | number | `required`、`min` / `max` |
| `select` | 下拉单选 | string | `required`、`options`（非空） |
| `date` | 日期选择 | string(`YYYY-MM-DD`) | `required` |
| `boolean` | 开关 | boolean | — |

**字段通用约束**

- `key` 在同一节点内唯一，且**只允许 `[a-z_][a-z0-9_]*`（英文小写 + 数字 + 下划线，禁止中文、大写与特殊字符）** —— 它直接作为输出字段名参与 `{{human_1.data.<key>}}` 变量引用，中文或特殊字符会造成变量解析歧义；保存校验不通过时给出明确提示（**已确认：不允许中文 key**）；
- `label` 必填，允许中文（仅用于展示）；
- `default` 可选；
- `required` 由**后端**在 `decision` 接口强校验（不依赖前端）。

### 3.4 输出契约（两种模式统一）

```json
{
  "approved": true,
  "decision": "approved",
  "data": {},
  "comment": "结论与原文一致，准予发布",
  "operator": "张三",
  "decided_at": "2026-08-29T10:22:31",
  "task_id": "ht_a1b2c3",
  "timed_out": false
}
```

| 字段 | 审批模式 | 表单模式 |
|------|----------|----------|
| `approved` | `true` / `false`（按决策） | 恒 `true` |
| `decision` | `approved` / `rejected` | 恒 `submitted` |
| `data` | 恒 `{}` | **人工填写的键值对** |
| `comment` | 处理意见 | 补充说明（选填） |
| `operator` / `decided_at` / `task_id` / `timed_out` | 同左 | 同左 |

- `FIXED_OUTPUTS` 增加 `"human": {"approved", "decision", "data", "comment", "operator", "decided_at"}`（强制保留，前端不可删）；
- 下游引用：`{{human_1.approved}}`、`{{human_1.comment}}`、`{{human_1.data.customer_name}}`。

### 3.5 出口与路由

| 模式 | 出口 |
|------|------|
| `approve` | 允许两条出边，`handle` 为 `true`（通过）/ `false`（驳回），与 `condition` 同构：按 `approved` 路由，未选中分支补发 `node_skipped`。**只连一条边时**：无论通过驳回都继续往下走（由后续 `condition` 判断 `{{human_1.approved}}`） |
| `form` | **仅单出口**（`decision` 恒为 `submitted`，无分支语义）。连了两条出边 → 保存校验报错。**不支持「提交并驳回」**（已确认不做）：填表与分支裁决是两个关注点，需要「填完表再决定走哪条分支」时，在表单节点**之后**串一个审批节点（`approve` 模式）或条件节点 |

建图：`_build_graph` 中 `human` 与 `condition` 走同一分支——`g.add_conditional_edges(nid, router)`，`approve` 模式 router 读 `state.outputs[nid].approved`；`form` 模式 router 恒返回该唯一出边。

### 3.6 校验（`validate_definition`）

- `NODE_TYPES` 增加 `"human"`（后端 `workflow_service.py` + `routers/workflow.py` 的 `NODE_TYPES` 列表同步）；
- 新增规则：
  1. `mode` ∈ {`approve`, `form`}；缺省视为 `approve`（兼容）；
  2. `approve` 模式：最多两条出边且 `handle` ∈ {`true`, `false`}；`decisions` 至少两项且 `key` 唯一（缺省自动填 `approved` / `rejected`）；
  3. `form` 模式：**恰好一条出边**；`form_fields` 至少一项、`key` 唯一、`type` 在 §3.3 枚举内、`select` 必须带非空 `options`；
  4. `display_fields[].value` / `description` 中的变量引用必须**拓扑上早于**当前节点（复用现有变量引用校验）。

## 4. 数据模型

### 4.1 新表 `workflow_human_tasks`

```sql
CREATE TABLE IF NOT EXISTS workflow_human_tasks (
    id              VARCHAR PRIMARY KEY,
    run_id          VARCHAR NOT NULL,
    workflow_id     VARCHAR NOT NULL,
    workflow_name   VARCHAR DEFAULT '',
    node_id         VARCHAR NOT NULL,
    node_title      VARCHAR DEFAULT '',
    status          VARCHAR NOT NULL DEFAULT 'pending',   -- pending | approved | rejected | submitted | cancelled | expired
    mode            VARCHAR DEFAULT 'approve',            -- approve | form
    description     TEXT DEFAULT '',                      -- 渲染后的说明文本
    form_schema     TEXT DEFAULT '{}',                    -- JSON: {display_fields, form_fields, decisions, comment, submit_text}
    form_data       TEXT DEFAULT '{}',                    -- JSON: 渲染后的只读待审内容快照
    filled_data     TEXT DEFAULT '{}',                    -- JSON: 人工填写结果（form 模式；approve 模式为 {}）
    comment_required INTEGER NOT NULL DEFAULT 0,          -- 本次是否必填意见（required / required_on 计算后落库）
    decision        VARCHAR,                              -- approved | rejected | submitted
    comment         TEXT DEFAULT '',
    operator        VARCHAR DEFAULT '',
    assignee        VARCHAR DEFAULT '',
    due_at          VARCHAR,                              -- 超时时间点；NULL = 不设超时
    timeout_action  VARCHAR DEFAULT 'keep_pending',
    trigger_source  VARCHAR,                              -- 冗余：manual | schedule（列表展示用）
    created_at      VARCHAR,
    decided_at      VARCHAR,
    updated_at      VARCHAR
);
CREATE INDEX IF NOT EXISTS idx_human_tasks_status ON workflow_human_tasks(status);
CREATE INDEX IF NOT EXISTS idx_human_tasks_run ON workflow_human_tasks(run_id);
CREATE UNIQUE INDEX IF NOT EXISTS idx_human_tasks_node ON workflow_human_tasks(run_id, node_id);
```

> 一条运行 + 一个人工节点 = 一条任务。并行分支上多个人工节点 → 多条任务，各自独立处理。

## 5. 执行流程与状态机

### 5.1 挂起时序

```text
run_stream
  │
  ├─ 节点函数 fn(human 节点)
  │    1. render(description) + render(display_fields) → form_data（渲染失败 = 该节点 failed，与现有变量语义一致）
  │    2. 计算 due_at：timeout.hours 为空 → NULL（不超时）；否则 created_at + hours
  │    3. 落库 workflow_human_tasks(status=pending, mode, form_schema, form_data, comment_required, due_at...)
  │    4. rt.emit({ type:"node_waiting", node_id, task_id, title, mode,
  │                 description, form_data, form_fields, decisions, submit_text,
  │                 comment_required, assignee, due_at })
  │    5. rt.suspend = { node_id, state: {start, outputs} }   ← 关键：状态快照
  │    6. raise _NodeSuspended()            → LangGraph 终止整图
  │
  ├─ _drive 捕获异常：因 rt.suspend 非空 → status = "waiting"（不记为 failed）
  ├─ 落库：context_snapshot / pending_node_id / waiting_at / definition_snapshot
  ├─ 跳过 node_skipped 补发（等待态不判定"未触达"）
  ├─ yield workflow_finished(status="waiting", pending={task_id, node_id})
  └─ yield [DONE]                          ← SSE 连接正常关闭
```

### 5.2 续跑时序

```text
POST /workflow/human-tasks/{id}/decision
      { decision, comment, data, operator, auto_resume }
  │
  ├─ 校验：decision 在节点 decisions 白名单内（form 模式恒 submitted）
  ├─ 校验：comment_required 且 comment 为空 → 400「请填写处理意见」
  ├─ 校验：form 模式按 form_fields 逐字段校验 required / type / select options → 400 并返回字段级错误
  ├─ 乐观锁：UPDATE ... WHERE id=? AND status='pending'（影响行数 0 → 409「该任务已处理」）
  ├─ 写 decision / comment / filled_data / operator / decided_at
  ├─ auto_resume = true（默认，待办中心场景）
  │     └─ asyncio.create_task(后台续跑)：消费 resume 生成器直到 [DONE]，结果落库
  └─ auto_resume = false（编辑器场景，已确认为主路径）
        └─ 前端立即开 SSE：POST /workflows/{id}/runs/{run_id}/resume  { task_id }

resume_run_stream(run_id, task_id)
  ├─ 校验 run.status == 'waiting' 且 task.status ∈ {approved, rejected, submitted}
  │     └─ 用 UPDATE ... WHERE status='waiting' 抢占（影响行数 0 → 409「已恢复或已结束」）
  ├─ 读 context_snapshot / definition_snapshot → 建图
  ├─ 初始 state = snapshot；rt.replay = snapshot.outputs；rt.inject = { node_id: 处理结果 }
  ├─ 已 replay / inject 的节点：emit node_replayed / node_resumed，不重跑
  ├─ 人工节点之后的节点：正常执行 + 正常事件（node_started / progress / finished / failed）
  ├─ 结束时补发 node_skipped（未走到的分支）
  └─ yield workflow_finished(status=succeeded|failed) + [DONE]
```

### 5.3 状态机

```text
                    ┌──────── decision(approved/rejected/submitted) ────────┐
                    │                                                       ▼
[run]  running ──▶ waiting ───────────────────────────────────────▶ running(续跑) ──▶ succeeded / failed
         │            │
         │            ├── cancel（用户取消运行）──────────────────────▶ cancelled
         │            └── 删除运行 ──────────────────────────────────▶ cancelled
         └── 节点抛错 ──▶ failed

[task]  pending ──▶ approved / rejected / submitted ──▶ (驱动续跑)
           └──────▶ cancelled（run 取消/删除）
```

> `expired` 状态保留在枚举中，但 v1 不启用（超时不自动处理，见 §9.5）。

**接口** `POST /workflow/human-tasks/batch-decision`

```json

```

**响应**（部分成功语义，逐条独立处理，单条失败不影响其他）

```json

  "succeeded": ["ht_001", "ht_002"],
  "failed": [ { "id": "ht_003", "reason": "该任务已处理" } ],
  "auto_resumed": ["ht_001", "ht_002"]
}
```

**约束**

| 项 | 规则 |
|----|------|
| 可批量范围 | **仅 `approve` 模式的 `pending` 任务**。`form` 模式任务每条填写内容不同，**不支持批量**（前端禁选并提示「表单任务需逐条填写」） |
| 必填意见 | 若批次内任一任务 `comment_required = 1`（如驳回必填理由），则 `comment` 不能为空 → 整批 400「本批次存在必须填写意见的任务」 |
| 决策一致性 | 整批统一为一个 `decision`，不支持混合通过/驳回（混合请分两次提交） |
| 续跑 | `auto_resume` 默认 `true`，每条成功任务各自后台续跑（互不阻塞）；单条续跑失败只记日志，不影响其他 |
| 并发安全 | 复用单条决策的乐观锁（`WHERE status='pending'`），并发提交同一任务时只有一次成功 |
| 数量上限 | 单批最多 100 条（防滥用），超出 400 |

## 9. 边界与异常

| 场景 | 行为 |
|------|------|
| 变量渲染失败（`{{agent_1.answer}}` 缺字段） | 该人工节点 `failed`，工作流终止（与现有变量语义一致，不静默降级） |
| 挂起期间刷新/关闭浏览器 | 运行记录仍在（`waiting`），可从待办中心继续处理 |
| 挂起期间后端重启 | `context_snapshot` 已落库，重启后续跑不受影响 |
| 重复提交决策 | 乐观锁：第二次返回 409「该任务已处理」 |
| 并发重复续跑 | `UPDATE workflow_runs SET status='running' WHERE id=? AND status='waiting'`，影响行数 0 → 409 |
| 取消 / 删除处于 `waiting` 的运行 | 关联 pending 任务置 `cancelled`；删除运行记录时一并清理任务 |
| 运行记录被自动裁剪 | `WorkflowRunService.trim` **排除 `status='waiting'` 的记录**；任务详情若查不到 run → 提示「运行记录已清理」 |
| 挂起时补发 skipped | **跳过**（等待态不判定未触达），续跑结束时统一补发 |
| 时长统计 | `duration_ms` 只累计实际执行时间，`waiting` 时长不计入（续跑时累加） |
| 表单字段值类型不符（number 传字符串） | 后端按 `type` 强转；无法转换 → 400 并返回字段级错误 |

### 9.3 定义快照（已确认采纳）

挂起期间若用户修改了工作流定义（增删节点、改连线），续跑会出现「图上不存在该节点」的错乱。挂起时把 `definition` 一并快照进 `workflow_runs.definition_snapshot`，续跑**优先使用快照**（无快照时回退当前 definition，兼容存量记录）。顺带解决现存边界问题：历史运行回放时定义已变更导致节点对不上（原文档 §6.3.1 记的是「已删除」兜底）。

### 9.5 超时（已确认：默认关闭，仅标红）

- 节点未配置 `timeout.hours` → `due_at` 为 `NULL`，**永不超时、不标红**，任务一直是普通待办；
- 配置了时长 → 超期后在待办列表与详情显示 **「已超时」红标**，`status` 仍为 `pending`，处理流程与正常任务完全一致（继续 `waiting`，等人处理）；
- 超时判定为**懒判定**（查询待办列表 / 打开详情时按 `due_at` 计算），不引入定时扫描；
- **不做** `auto_approved` / `auto_rejected`（无自动处理、无自动续跑），`timeout_action` 字段保留以兼容未来扩展，UI 中暂不暴露。

### 9.6 处理人（重要限制）

系统当前**无账号/登录体系**（`backend` 无 user 表、无鉴权中间件）。因此：

- 人工节点**不做权限校验**，任何能打开系统的人都可处理；
- `assignee` 仅作展示与归档；提交时填写的 `operator`（处理人姓名）可留空，前端用 `localStorage` 记住上次填写值；
- 若后续需要「指定处理人 / 角色审批」，需先引入账号体系（工作量另计）。

### 9.7 通知渠道：v1 不做外发，但预留对接点（已确认）

**现状**：经代码核查，系统目前**无任何外发通知渠道** —— 既有的"告警"仅是 `scheduler_engine._record_result` 里的一行 `logger.warning`，再经 `GET /notifications/summary` 聚合为站内红点计数；**没有邮件 / Webhook / 企业微信 / 钉钉 / 短信的任何实现，也没有相关配置**（`config.py` 中无 alert 相关项）。

因此 v1 人工节点通知 = **待办中心列表 + 侧边栏角标 + 顶栏消息聚合**；同时按确认结论**预留统一渠道接口**，后续对接外发时不用改业务代码。

**骨架设计**（`backend/services/notification_channel.py`，v1 落代码但为空实现）

```python
class NotificationChannel:
    """外发通知统一出口。v1 无启用渠道时仅打日志；任何异常都吞掉，绝不影响工作流主流程。"""

    @staticmethod
    async def dispatch(event: str, payload: dict) -> None:
        try:
            channels = [c for c in (settings.NOTIFY_CHANNELS or "").split(",") if c]
            if not channels:                       # v1：配置为空 → 仅日志
                logger.info("[notify] %s %s", event, payload)
                return
            for name in channels:                  # v1.1：webhook / email / wecom / dingtalk
                handler = _HANDLERS.get(name)
                if handler:
                    await handler(event, payload)
        except Exception:
            logger.exception("[notify] 外发失败（已忽略）：%s", event)
```

**事件契约**（`payload` 统一结构，后续渠道直接消费）

| 事件 | 触发点 | payload 关键字段 |
|------|--------|-----------------|
| `human_task.created` | 人工节点挂起落库后 | `task_id` / `workflow_id` / `workflow_name` / `node_title` / `mode` / `assignee` / `created_at` / `due_at` / `trigger_source` / `detail_url` |
| `human_task.decided` | 决策落库后（单条 & 批量均触发） | `task_id` / `run_id` / `workflow_name` / `decision` / `operator` / `comment` / `decided_at` |
| `human_task.timeout` | 懒判定首次发现超期时（需去重标记，避免重复外发） | `task_id` / `workflow_name` / `node_title` / `due_at` / `detail_url` |

**配置预留**：`backend/config.py` 增加 `NOTIFY_CHANNELS: str = ""`（逗号分隔，v1 留空）。后续对接只需：加一个 handler + 配置项填渠道名，业务埋点零改动。

## 附：最小可用示例

**审批模式（双出口）**

```text
[start] ─▶ [agent: 财务问答] ─▶ [human: 财务审核] ─┬─ true  ─▶ [service: 发布报告] ─▶ [end]
                                                   └─ false ─▶ [llm: 生成修改建议]  ─▶ [end2]
                                  display_fields:
                                    · 原始问题   {{start.question}}
                                    · 智能体结论 {{agent_1.answer}}
```

运行 → 智能体产出结论 → 人工节点挂起并生成待办 → 处理人点「驳回」并填写「数据口径有误，需用年报数据」→ 工作流走 `false` 分支 → LLM 生成修改建议 → 结束。

**表单模式（单出口）**

```text
[start] ─▶ [agent: 抽取客户信息] ─▶ [human: 补录客户资料] ─▶ [service: 写入客户库] ─▶ [end]
                                     display_fields: · 抽取结果 {{agent_1.data}}
                                     form_fields:
                                       · customer_name  客户名称  text     *
                                       · level          客户等级  select   * [A/B/C]
                                       · credit_limit   授信额度  number
                                       · remark         备注      textarea
```

运行 → 智能体抽取出部分字段 → 人工节点挂起 → 处理人补全客户名称、选择等级 A、填额度 → 提交 → 下游 `service` 节点用 `{{human_1.data.customer_name}}` 写入客户库 → 结束。

**本项目环境中发现并修复的一个真实缺陷**：挂起快照原先由 `context` 反推 outputs，而 `context` 里 `"start"` 键是工作流入参，会覆盖默认 id 为 `start` 的**节点输出**，导致续跑时 start 节点被重复执行。已改为直接取 `state["outputs"]`，并补充了「已完成节点 node_replayed」断言防回归。

### 12.3 与设计的偏差（3 处）

1. **超时通知埋点未做**：`TASK_TIMEOUT` 需额外的「已通知」去重标记，且 v1 无外发渠道，故只保留 `is_overdue` 红标判定；`TASK_CREATED` / `TASK_DECIDED` 两个埋点已接。
2. **建单幂等（设计外补充）**：同一 `run_id + node_id` 已存在任务时，重置为 pending 并复用，避免异常重试挂起时唯一约束报错使工作流失败。
3. **待审快照存储位置**：除任务表外，另在 `node_states` 中冗余一份 `form_data` 快照，保证**运行详情**即使任务记录被清理也能回看（对应决策记录 F）。
