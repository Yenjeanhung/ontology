## 0. 一句话目标

新增一个**可视化编排引擎**：以「节点 + 连线」描述一个 DAG（有向无环图），节点分为**开始/结束**、**智能体（OAG 问答）**、**实体服务（沙箱动作）**、**LLM**、**条件分支**、**代码**等；用户从左侧面板拖拽节点到画布、连线、配置参数，保存后一键运行，执行过程通过 SSE 实时回传每个节点的状态与结果。

---

## 1. 背景与目标

### 1.1 现状

当前系统的两类核心能力是**独立调用**的：

| 能力 | 入口 | 调用方式 |
|------|------|---------|
| 智能体（OAG） | `/api/agent/query` | 单次提问 → SSE 流式返回（`OAGService.query_stream`） |
| 实体服务 | `/api/entities/{id}/services/{sid}/invoke` | 单个实体的单个沙箱动作（`ServiceRuntimeService.invoke`） |

它们彼此不通：无法「先让智能体从知识库回答 → 再拿答案里的实体去调实体服务 → 再让 LLM 汇总」这样串起来。要组合只能人工在多处往返拷贝。

### 1.2 目标（v1）

1. **可视化编排**：画布拖拽节点、连线、配置参数，Dify/Coze 式体验；
2. **复用现有资产**：智能体（OAG + 技能）、实体服务（沙箱动作）作为**节点类型**直接拖入，不重复造轮子；
3. **可执行**：保存后能运行，节点按拓扑顺序执行，变量在节点间传递；
4. **过程透明**：运行过程逐节点 SSE 回传（延续 OAG「推理过程可视化」原则）；
5. **零回归**：不碰现有 `agent/query`、`entity service invoke` 等已有接口的行为；
6. **智能体可配置（前置模块）**：新增「智能体配置」模块，把智能体从全局单例升级为可命名、可复用、可拖入工作流的资产（见 [智能体配置设计](../智能体/智能体配置_功能设计.md)）。

### 1.3 非目标（v1 明确不做）

- ❌ 循环节点（Loop / ForEach）→ v2
- ❌ 子工作流嵌套调用 → v2
- ❌ 工作流发布到「对话/API 端点」对外暴露 → v2（v1 只在工作流页面内运行调试）
- ❌ 版本管理 / 协作 / 权限 → v2
- ❌ 定时触发 / 事件触发（Webhook 等）→ v2

### 1.4 前置依赖：智能体配置模块

需求「把创建好的智能体拖拽过来」隐含前置条件：**智能体必须是可创建、可命名、可复用的资产**，而当前系统没有持久化的智能体实体（只有全局一个 OAG 单例 + 可勾选技能）。因此工作流 v1 依赖一个轻量的「智能体配置模块」——新增 `agents` 表 + `/agents` CRUD，把「KB + 技能 + 人设」打包成可复用智能体。**完整设计见 [智能体配置_功能设计](../智能体/智能体配置_功能设计.md)**，此处只交代与工作流的衔接：

- 智能体配置模块是**独立可用**的（问答页也能用），工作流是它的下游消费者；
- 工作流 `agent` 节点两种绑定方式：**引用智能体**（`agent_id`）或**内联配置**，见 §4.3；
- `GET /workflow/palette` 返回启用中的智能体列表，供节点面板拖拽。

## 2. 核心概念

### 2.1 工作流（Workflow）

> 一个工作流 = 一张 DAG 图 + 运行入口参数。持久化为一个 `definition` JSON（节点数组 + 边数组）。

### 2.2 节点（Node）

节点的统一结构：

```
node = {
  "id": "node_xxx",          // 画布内唯一
  "type": "agent",           // 节点类型（见 §4）
  "title": "财务问答",
  "position": {"x": 100, "y": 200},   // 画布坐标（仅前端使用）
  "config": { ... }          // 类型相关配置（见 §4）
}
```

### 2.3 边（Edge）

```
edge = {
  "id": "edge_xxx",
  "source": "node_a",        // 上游节点 id
  "target": "node_b",        // 下游节点 id
  "source_handle": "default" | "true" | "false",  // 条件节点的分支出口
  "label": ""
}
```

### 2.4 变量上下文（Context）

运行时维护一个扁平字典，键为节点 id，值为该节点的输出：

```
context = {
  "start":  { "question": "...", "kb_id": "..." },  // 开始节点输入
  "node_a": { "answer": "...", "chunks": [...] },   // 智能体节点输出
  "node_b": { "success": true, "data": {...} },     // 实体服务节点输出
}
```

节点配置里用 `{{节点id.字段}}` 引用上游输出（规范见 §9）。

```

│  WorkflowListPage（列表）  WorkflowEditorPage（编辑器）              │
│    · 三栏：左节点面板 / 中画布(Vue Flow) / 右配置抽屉                 │
│    · 拖拽节点 → 连线 → 配置变量 → 运行 → 逐节点日志(SSE)              │
└──────────────┬─────────────────────────────────────────────────────┘
               │ 工作流 CRUD / 运行（POST /api/workflows/{id}/run → SSE）
┌──────────────▼────────────── FastAPI ─────────────────────────────┐
│  routers/workflow.py（新增）                                        │
│    · CRUD + 校验(DAG/环) + 运行 + 运行记录                            │

│    · 编排定义 CRUD                                                  │
│  services/workflow_engine.py（新增）                                │
│    · 拓扑排序调度 + 变量解析 + 逐节点执行 + SSE 事件                  │
└──────┬──────────────────────┬──────────────────┬───────────────────┘
       │ 复用智能体             │ 复用实体服务       │ 复用 LLM/沙箱
┌──────▼──────────┐  ┌────────▼────────┐  ┌───────▼────────────────┐
│ OAGService.run()│  │ServiceRuntimeSvc│  │ build_llm() /           │
│ (新抽非流式接口)  │  │.invoke/test_run │  │ execute_service()      │
└─────────────────┘  └─────────────────┘  └────────────────────────┘
                       │ SQLite (aiosqlite)
┌──────────────────────▼─────────────────────────────┐
│  workflows / workflow_runs 表（新增）                │
└─────────────────────────────────────────────────────┘
```

**设计原则**（延续本项目一贯做法）：

1. **复用不重写**：智能体节点调用 OAG 管线、实体服务节点调用沙箱执行器，编排层只做「调度 + 传参」；
2. **定义与执行分离**：`definition`（JSON 图）只描述结构，`workflow_engine` 只负责执行，二者解耦可单测；
3. **SSE 与 OAG 一致**：运行进度复用本项目 `text/event-stream` + `data: {...}` 协议。

## 4. 节点类型定义（节点面板）

### 4.0 内置节点一览

| type | 名称 | 输入 | 输出 | 说明 |
|------|------|------|------|------|
| `start` | 开始 | — | 用户自定义变量 | 运行入口，声明入参 |
| `end` | 结束 | 若干 | 汇总输出 | 运行出口，汇总结果 |
| `agent` | 智能体 | 问题、KB、技能 | answer + 引用 | 复用 OAG 问答管线 |
| `service` | 实体服务 | 实体、参数 | success + data | 复用沙箱实体动作 |
| `llm` | 大模型 | prompt | text | 通用 LLM 补全 |
| `condition` | 条件分支 | 表达式 | true/false 出口 | 路由分支 |
| `code` | 代码 | params | data | 沙箱 Python（复用 service_runtime） |

### 4.1 开始节点 `start`

- 职责：声明工作流的**输入变量**（运行前用户在运行面板填写）。
- `config`：

```json
{ "inputs": [ { "name": "question", "type": "text", "label": "问题", "required": true } ] }
```

- 输出：`{ "question": "..." }`，供下游用 `{{start.question}}` 引用。

### 4.2 结束节点 `end`

- 职责：聚合要返回的结果。一个工作流至少一个 `end`。
- `config`：

```json
{ "outputs": [ { "name": "answer", "value": "{{agent_1.answer}}" } ] }
```

- 输出：映射后的对象，作为工作流最终结果返回。

### 4.3 智能体节点 `agent`（复用 OAG）

- 职责：拖入一个**智能体**执行问答，两种绑定方式（取决于 `config`）：

```json
// 方式 A · 引用智能体（配合智能体配置模块，推荐）
{ "agent_id": "agent_finance", "query_template": "{{start.question}}" }

// 方式 B · 内联配置（不落库，快速临时）
{ "kb_id": "kb_xxx", "skill_ids": ["skill_a"], "query_template": "请分析：{{start.question}}" }
```

- 输出：

```json
{ "answer": "...", "chunks": [...], "entities": [...], "subgraph": {...} }
```

- 复用方式：见 §11.1，需给 `OAGService` 新增**非流式** `run()` 接口（当前只有 `query_stream`）；方式 A 执行前由引擎按 `agent_id` 展开出 `kb_id + system_prompt + skill_ids`（见 [智能体配置设计](../智能体/智能体配置_功能设计.md) §5.3）。

### 4.4 实体服务节点 `service`（复用沙箱动作）

- 职责：把一个「实体服务」拖入 —— 本质是**选择实体 + 选择该实体的有效服务 + 传参**。
- 两种绑定方式（`config`）：

```json
// 方式 A：绑定具体实体（推荐，语义清晰）
{ "entity_id": "ent_xxx", "service_id": "svc_xxx", "params": { "k": "{{start.k}}" } }

// 方式 B：绑定本体级服务 + 用变量模拟实体（复用 test_run 的 mock_entity）
{ "ontology_id": "ont_xxx", "service_id": "svc_xxx",
  "mock_entity": { "name": "{{agent_1.entity_name}}", "entity_type": "人物", "properties": {} } }
```

- 输出：沙箱执行结果原样透传：

```json
{ "success": true, "data": {...}, "error": null, "stdout": "...", "duration_ms": 12 }
```

- 复用方式：直接调 `ServiceRuntimeService.invoke(db, entity_id, service_id, params)`（方式 A）或 `test_run(db, service_id, req)`（方式 B），执行层已带 import 白名单 + 子进程超时隔离。

### 4.5 大模型节点 `llm`

- 职责：通用 LLM 补全（不检索），用于「汇总/改写/分类」等中间步骤。
- `config`：

```json
{ "system_prompt": "你是...", "prompt_template": "把下面内容整理成要点：{{service_1.data}}", "temperature": 0.3 }
```

- 输出：`{ "text": "..." }`。
- 复用方式：`providers.llm.build_llm()`（当前激活配置），一次性 `ainvoke` 取全文（v1 不流式，v1.5 可选流式）。

### 4.6 条件分支节点 `condition`

- 职责：根据上游变量判断走 `true` 还是 `false` 出口。
- `config`：

```json
{
  "operator": "contains",        // == | != | contains | not_contains | empty | not_empty | gt | lt
  "left": "{{service_1.success}}",
  "right": "true"
}
```

- 输出：`{ "result": true }`，同时决定下游走哪个分支；两个出口 `source_handle` 分别为 `true` / `false`。

### 4.7 代码节点 `code`

- 职责：用户写一段沙箱 Python（复用实体服务的沙箱安全模型），做任意数据处理。
- `config`：

```json
{ "code_text": "def run(params, entity, context):\n    ...", "params": { "x": "{{agent_1.answer}}" } }
```

- 输出：`{ "success": true, "data": {...}, "stdout": "..." }`。
- 复用方式：`services.service_runtime.execute_service()`（import 白名单 + 超时 + 子进程隔离），与实体服务同一条安全路径。

## 5. 数据模型

### 5.1 新增表

```sql
-- ===== 工作流定义（图结构存 JSON，延续项目 JSON blob 惯例）=====
CREATE TABLE IF NOT EXISTS workflows (
    id          VARCHAR PRIMARY KEY,
    name        VARCHAR(100) NOT NULL,
    description TEXT DEFAULT '',
    definition  TEXT NOT NULL DEFAULT '{"nodes":[],"edges":[]}',  -- JSON: {nodes:[...], edges:[...]}
    is_published INTEGER NOT NULL DEFAULT 0,   -- 预留：发布（v2 对端点暴露）
    created_at  VARCHAR,
    updated_at  VARCHAR
);

-- ===== 运行记录（一次执行一行；节点状态存 JSON）=====
CREATE TABLE IF NOT EXISTS workflow_runs (
    id           VARCHAR PRIMARY KEY,
    workflow_id  VARCHAR NOT NULL,
    status       VARCHAR NOT NULL DEFAULT 'running',   -- running | succeeded | failed | cancelled
    inputs       TEXT DEFAULT '{}',   -- JSON: 开始节点入参快照
    outputs      TEXT DEFAULT '{}',   -- JSON: 结束节点输出
    node_states  TEXT DEFAULT '{}',   -- JSON: {node_id: {status, output, error, duration_ms}}
    error        TEXT DEFAULT '',
    started_at   VARCHAR,
    finished_at  VARCHAR,
    duration_ms  INTEGER DEFAULT 0
);
CREATE INDEX IF NOT EXISTS idx_workflow_runs_wf ON workflow_runs(workflow_id);
```

### 5.2 ORM（`backend/models.py`，参照 `LLMConfig` / `AgentSkill` 写法）

```python
class Workflow(Base):
    __tablename__ = "workflows"
    id = Column(String, primary_key=True, default=lambda: uuid.uuid4().hex[:12])
    name = Column(String(100), nullable=False)
    description = Column(Text, default="")
    definition = Column(Text, nullable=False, default='{"nodes":[],"edges":[]}')
    is_published = Column(Integer, nullable=False, default=0)
    created_at = Column(String, default=lambda: datetime.now().isoformat())
    updated_at = Column(String, default=lambda: datetime.now().isoformat())


class WorkflowRun(Base):
    __tablename__ = "workflow_runs"
    id = Column(String, primary_key=True, default=lambda: uuid.uuid4().hex[:12])
    workflow_id = Column(String, nullable=False)
    status = Column(String, nullable=False, default="running")
    inputs = Column(Text, default="{}")
    outputs = Column(Text, default="{}")
    node_states = Column(Text, default="{}")
    error = Column(Text, default="")
    started_at = Column(String, nullable=True)
    finished_at = Column(String, nullable=True)
    duration_ms = Column(Integer, default=0)
```

## 6. 执行引擎（`services/workflow_engine.py`）

### 6.1 保存时校验（`validate_definition`）

在 `POST/PUT /api/workflows` 阶段做静态校验，非法直接 400：

1. 节点 id 唯一；`type` 在合法枚举内；
2. 恰好一个 `start`；至少一个 `end`；
3. 每条边的 `source`/`target` 指向存在的节点；
4. **无环**：对图做拓扑排序，存在环 → 400「工作流存在循环，不能包含环」；
5. 非 `condition` 节点**最多一个出边**（v1：多出边仅 `condition` 允许，作为 true/false 分支）；
6. 变量引用 `{{...}}` 的节点 id 存在、字段名合理（可选：v1 做「引用目标节点必须拓扑上早于当前节点」的静态检查）。

### 6.2 执行流程

```
run(workflow_id, inputs)
  │
  ├─ 1. 载入 definition，校验（同保存校验，防御脏数据）
  ├─ 2. 建 context = {"start": inputs}
  ├─ 3. 拓扑排序 → 得到一个可执行序列（同一层可并行，v1 顺序执行足够）
  ├─ 4. 逐节点执行：
  │      · 先解析 config 里的 {{...}} → 从 context 取实值（缺值 → 该节点失败）
  │      · dispatch(node.type) → 调用对应执行器（§4）
  │      · 把输出写入 context[node.id]
  │      · yield SSE 事件：node_started / node_finished(node_states 增量) / node_failed
  ├─ 5. 命中 end 节点 → 汇总 outputs → status=succeeded
  ├─ 6. 任一节点抛错（非 condition 分支）→ 该节点 failed → 下游未执行 → status=failed
  └─ 7. 落库 workflow_runs（inputs/outputs/node_states/duration_ms）
```

**拓扑排序调度**：`workflow_engine` 先做 Kahn 拓扑排序得到一个节点执行顺序；v1 采用**串行按拓扑序**执行（简单、可预期、易调试），v1.5 再对「同一层无依赖」的节点用 `asyncio.gather` 并行。

**条件分支语义**：`condition` 节点执行后，仅「与 `result` 匹配的出口」的下游节点进入执行序列，另一支及其下游被标记为 `skipped`（不进 node_states 或标 `skipped`）。

### 6.3 SSE 事件协议（与 OAG 对齐）

```
data: {"type":"workflow_started", "run_id":"...", "nodes": 6}
data: {"type":"node_started",  "node_id":"agent_1", "title":"财务问答"}
data: {"type":"node_finished","node_id":"agent_1", "output":{...}, "duration_ms":1234}
data: {"type":"node_started",  "node_id":"service_1", ...}
data: {"type":"node_failed",   "node_id":"service_1", "error":"..."}
data: {"type":"workflow_finished", "status":"succeeded", "outputs":{...}, "duration_ms":2000}
data: [DONE]
```

- `node_finished` 的 `output` 可截断（如 8KB），完整结果在运行记录 `node_states` 里可查；
- 智能体节点 / LLM 节点的**流式 token**（v1.5）可在 `node_started` 后追加 `{"type":"node_token","node_id":"...","content":"..."}` 事件，前端把该节点渲染成流式卡片。

### 6.4 运行上限（config.py 可覆盖）

| 配置 | 默认 | 说明 |
|------|------|------|
| `WORKFLOW_MAX_NODES` | 100 | 单工作流节点数上限 |
| `WORKFLOW_MAX_STEPS` | 200 | 单次运行最多执行节点数（防异常图） |
| `WORKFLOW_RUN_TIMEOUT_SECONDS` | 300 | 单次运行总超时 |
| `WORKFLOW_NODE_OUTPUT_LIMIT` | 8 * 1024 | 节点输出 SSE 回传截断上限 |

## 7. 后端 API（`routers/workflow.py`，前缀 `/api`）

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/workflows` | 工作流列表（含节点/边数统计） |
| POST | `/workflows` | 创建（校验 definition） |
| GET | `/workflows/{id}` | 详情（含 definition） |
| PUT | `/workflows/{id}` | 更新（重校验 definition） |
| DELETE | `/workflows/{id}` | 删除（级联删运行记录） |
| POST | `/workflows/{id}/run` | **运行**（SSE 流式回传进度） |
| GET | `/workflows/{id}/runs` | 运行历史列表 |
| GET | `/workflows/{id}/runs/{run_id}` | 单次运行详情（含 node_states） |
| POST | `/workflows/{id}/runs/{run_id}/cancel` | 取消运行（置 cancelled） |
| GET | `/workflow/palette` | **节点面板数据源**：节点类型清单 + 可选的知识库列表、启用的技能列表、本体/实体及其有效服务列表 |

`palette` 返回结构（前端拖拽面板直接消费）：

```json
{
  "node_types": [ {"type":"agent","name":"智能体","icon":"🤖","description":"..."}, ... ],
  "kbs":     [ {"id":"...","name":"财务知识库"}, ... ],
```

## 9. 变量引用规范

| 写法 | 含义 |
|------|------|
| `{{start.question}}` | 开始节点输入字段 |
| `{{agent_1.answer}}` | 智能体节点输出的 `answer` 字段 |
| `{{service_1.data}}` | 实体服务节点输出的 `data` 字段 |
| `{{service_1.data.price}}` | 输出为 dict 时的深层取值（`.` 逐级访问，`[]` 索引可选） |

- 引用目标是 `context[node_id]` 这个 dict；缺节点/缺字段 → 解析失败，该节点报错并终止（v1 不静默替换，宁可显式失败便于排查）；
- 解析在**后端引擎**统一完成（不依赖前端拼接），保证「前端所见」与「后端执行」用同一份 `definition`；
- 引用目标必须**拓扑上早于**当前节点（保存时静态校验 + 运行时兜底）。

## 10. 安全与边界

| 场景 | 行为 |
|------|------|
| definition 含环 | 保存 400；运行前再次校验兜底 |
| 变量引用缺失 / 拓扑非法 | 保存 400 或运行该节点 failed |
| 实体服务 / 代码节点 | 复用 `service_runtime`：import 白名单 + AST 静态检查 + 子进程隔离 + 超时 kill，**不新增注入面** |
| 智能体节点技能 id 失效 | 复用 `SkillService.resolve` 的「静默跳过」容错，查询不失败 |
| KB 不存在 / 未绑定本体 | 智能体节点走 OAG 既有降级路径（纯向量） |
| 节点输出过大 | SSE 回传截断（`WORKFLOW_NODE_OUTPUT_LIMIT`），完整结果落库 |
| 单次运行节点数 / 总时长超限 | 引擎强制中止 → status=failed，错误写「运行超限」 |
| 删除被工作流引用的 KB/技能/服务 | v1 不级联校验，运行时报错即可（运行前可加「引用完整性」提示）；v2 做引用计数 |

> 提示词注入面评估：`query_template` / `prompt_template` 由本机用户配置（可信），变量实值若来自外部输入（如 `start` 入参），沿用 OAG 既有的「参考资料隔离」边界，不扩大注入面。

## 11. 复用与改动点（关键）

### 11.1 智能体 OAG 抽非流式接口（`oag_service.py` 改造）

当前 `OAGService` 只有 `query_stream`（SSE 生成器），工作流引擎需要「拿到完整结果」而非消费流。**改造方式**：把核心管线抽成协程，返回完整 dict，`query_stream` 变成薄封装：

```python
class OAGService:
    @staticmethod
    async def run(kb_id: str, query: str, kb_name: str,
                  ontology_schema, skills=None) -> dict:
        """非流式：完整执行 7 步管线，返回
        {answer, chunks, entities, subgraph, retrieval_path}"""
        ...

    @staticmethod
    async def query_stream(kb_id, query, kb_name, ontology_schema, skills=None):
        """SSE 封装：调用 run() 后按现有事件结构逐条下发，行为不变"""
        ...
```

- 智能体节点在**路由层预加载** `ontology_schema`、`skills`（沿用 `routers/agent.py` 的预加载模式，db 会话在进入引擎前释放）；
- 工作流引擎不直接碰 db，只拿到已解析好的数据，与「OAG SSE 生命周期边界」同一套路。

### 11.2 实体服务节点复用（`ontology_action_service.py` 无改动）

`ServiceRuntimeService.invoke / test_run` 已返回完整 dict，直接调用即可；仅需在路由层做一次「实体 → 有效服务集」的解析（`resolve_effective`）以校验 service 归属。

### 11.3 其余复用

- LLM 节点：`providers.llm.build_llm()`；
- 代码节点：`services.service_runtime.execute_service()`；
- SSE 协议：照抄 `_sse()` / `StreamingResponse` 头（`Cache-Control: no-cache` + `X-Accel-Buffering: no`）。

## 13. v2 展望

沿同一张 `workflows` 表平滑扩展：

1. **循环节点**（Loop / ForEach）：遍历 `{{service_1.data.list}}` 逐项执行子链路；
2. **子工作流节点**：一个工作流作为节点被另一个工作流调用；
3. **发布为对话端点 / HTTP API**：`is_published` + 独立 `/api/workflows/{id}/chat` 或带签名端点，让外部系统触发工作流；
4. **触发方式**：定时 / Webhook / 文件上传完成事件；
5. **并行执行**：同层无依赖节点 `asyncio.gather` 并行 + 节点级并发上限；
6. **多 KB 智能体**：`agents.kb_id` 支持多知识库（当前单 KB）。
