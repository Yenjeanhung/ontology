# KnowSource 文档解析架构与 Tika 兜底解析器设计

> 目标目录：`doc/文档解析/`
> 涉及代码：`backend/providers/parser/*`、`backend/services/file_service.py`、`backend/requirements.txt`、`backend/.env.example`

---

## 一、背景与目标

### 1.1 现状

文档上传后的文字提取位于 `backend/providers/parser/`，采用**策略模式**：

```
backend/providers/parser/
├── base.py          # DocumentParser 抽象基类 + ParseResult 统一结构
├── __init__.py      # get_parser(file_path) 工厂：按扩展名精确匹配
├── txt_parser.py    # .txt / .md   —— 原生 open() 读取
├── pdf_parser.py    # .pdf         —— pypdfium2，按页提取并记录字符偏移
└── docx_parser.py   # .docx        —— python-docx，拼接段落
```

统一契约（`base.py`）：

```python
@dataclass
class ParseResult:
    filename: str
    format: str
    content: str
    metadata: dict = field(default_factory=dict)

class DocumentParser(ABC):
    def parse(self, file_path: Path) -> ParseResult: ...
    def supported_extensions(self) -> list[str]: ...
```

调用点：`file_service.process_file` 在「解析文档」阶段（约 `file_service.py:587`）

```python
parser = get_parser(file_path)
result = parser.parse(file_path)   # -> ParseResult，后续进入切分/向量化/抽取
```

`get_parser`（`__init__.py`）当前逻辑：遍历 `_parsers` 列表按扩展名精确匹配，**匹配不到直接 `raise ValueError("不支持的文件格式")`**。

### 1.2 局限

仅支持 `.txt / .md / .pdf / .docx` 四类。遇到 `.pptx / .xlsx / .html / .eml / .rtf / .odt / .csv` 等格式，`get_parser` 抛 `ValueError`，文件处理失败。要补齐这些格式，逐个引入专用 Python 库成本高、维护重。

### 1.3 顺带发现的问题（需一并修正）

`requirements.txt` 声明的是 `PyPDF2>=3.0.0`，但 `pdf_parser.py` 实际 `import pypdfium2`，且 `pypdfium2` 未声明。全新环境 `pip install -r requirements.txt` 后 PDF 解析会因 `ModuleNotFoundError` 失败。本次改造一并修正。

### 1.4 目标

1. 新增 **`TikaParser`** 作为**兜底解析器**：`get_parser` 先按扩展名精确匹配轻量库（txt/pdf/docx），匹配不到再 fallback 到 Tika，覆盖 pptx/xlsx/html/eml 等绝大多数剩余格式。
2. **无 JVM 环境时不启动 Tika、不影响应用启动**：Tika 是可选能力，缺失时优雅降级，绝不「启动不起来」。
3. 保持现有 `ParseResult` 契约与策略架构不变，轻量解析路径零回归。
4. 部署友好：支持「外部共享 Tika Server」模式，避免每个后端进程各自拉起 JVM。

### 1.5 设计原则

- **轻量优先**：已知格式永远走专用轻量库（如 PDF 的偏移信息 pypdfium2 比 Tika 更好用），Tika 只兜底。
- **可选 / 可降级 / 可关闭**：Tika 通过配置开关控制，无 JVM 自动降级。
- **Fail-safe，不 Fail-to-start**：探测 JVM 后才决定是否走 Tika；缺失 JVM 时应用正常启动、正常处理已知格式。
- **懒加载**：Tika 与 JVM 相关动作延迟到真正需要时，启动期零开销。

## 二、整体架构

### 2.1 路由流程

```
                       get_parser(file_path)
                               │
                       ext = suffix.lower()
                               │
                ┌──────────────▼──────────────┐
                │ 遍历 _parsers 精确匹配扩展名 │
                │  TxtParser / PdfParser /     │
                │  DocxParser                  │
                └──────────────┬──────────────┘
                       命中?   │
            ┌───────── 是 ─────┴───── 否 ─────────┐
            ▼                                     ▼
     返回轻量 Parser                       _tika_available() ?
                                         ┌──── 是 ────┴──── 否 ────┐
                                         ▼                         ▼
                                  返回 TikaParser         raise ValueError
                                  (兜底解析)              ("不支持的文件格式
                                                          （未启用 Tika 或
                                                           无 JVM 环境）")
```

**关键设计**：`TikaParser` **不进入** `_parsers` 精确匹配列表，而是作为 `get_parser` 末尾的**显式兜底分支**。这样：

- 永远不会和轻量库抢格式（即使未来 Tika 声称能解析 .pdf，轻量库仍优先）；
- 路由语义清晰：精确匹配失败 → 探测兜底可用性 → 降级报错。

### 2.2 模块结构（改造后）

```
backend/providers/parser/
├── base.py            # 不变
├── __init__.py        # 改造：get_parser 增加兜底分支 + _tika_available()
├── tika_runtime.py    # 新增：JVM 探测、Tika 可用性、懒加载（隔离副作用）
├── txt_parser.py      # 不变
├── pdf_parser.py      # 不变
└── docx_parser.py     # 不变
```

把「JVM/Tika 运行时探测」单独抽到 `tika_runtime.py`，避免污染 `__init__.py` 的导入副作用（保证 `import providers.parser` 永远安全、无 JVM 也不报错）。

## 三、JVM 探测与降级策略（核心）

> 这是「无 JVM 不启动 Tika、不崩」的关键章节。

### 3.1 为什么必须显式探测 JVM

`tika-python`（`pip install tika`）本质是 **Tika Server 的 HTTP 客户端**，工作方式：

1. `import tika` —— **安全**，不在导入时启动任何东西；
2. 首次 `tika.parser.from_file()` —— tika-python 尝试用 `java -jar tika-server-*.jar` 拉起本地 Tika Server（首次还会联网下载 JAR 到 `~/.tika` 缓存），再经 localhost HTTP 调用。

**崩溃点在第 2 步**：无 JVM 时 `java` 命令不存在，`from_file` 抛异常。

因此设计准则：**只要在「无 JVM」时不进入 `TikaParser.parse()`，就不会崩**。需要做的是在 `get_parser` 决定走兜底**之前**完成 JVM 探测。

### 3.2 探测实现（`tika_runtime.py`）

```python
import shutil
from functools import lru_cache

@lru_cache(maxsize=1)
def jvm_available(java_path: str = "java") -> bool:
    """进程级缓存：JVM 是否可用（存在性在进程生命周期内稳定）。"""
    resolved = shutil.which(java_path)  # None 表示 PATH 中找不到
    return resolved is not None
```

- 主策略：`shutil.which("java")` —— 跨平台、可靠、零启动开销（不实际执行 java）。
- 可选增强：支持 `TIKA_JAVA_PATH` 显式指定 java 路径后再 `which`。
- **不**用「真的跑一次 `java -version`」作为默认探测，避免启动开销与子进程失败歧义；保留为可选的严格校验。

### 3.3 Tika 可用性判定

```python
def tika_available() -> bool:
    # 1. 配置开关
    if not settings.TIKA_FALLBACK_ENABLED:
        return False
    # 2. 外部 Server 模式：跳过本地 JVM 探测（由独立 sidecar 承担）
    if settings.TIKA_SERVER_ENDPOINT:
        return True          # 健康检查可选，避免每次 get_parser 都打网络
    # 3. 本地模式：必须有 JVM
    return jvm_available(settings.TIKA_JAVA_PATH or "java")
```

> 说明：`tika` 包能否 import 的判定**不做强校验**——若未装 tika 包，`TikaParser.parse` 内懒导入会抛 `ImportError`，该异常会被解析管线统一捕获并标记文件失败；但为给出更友好的早期提示，可在 `tika_available()` 里做一次轻量 `importlib.util.find_spec("tika")` 判定。

### 3.4 降级矩阵

| 上传格式       | 配置/JVM 状态             | `get_parser` 行为        | 结果                         |
| -------------- | ------------------------- | ------------------------ | ---------------------------- |
| .txt/.md/.pdf/.docx | 任意                  | 命中轻量 parser          | 正常解析                     |
| .pptx/.xlsx/...     | 开关开 **且** 有 JVM   | 返回 `TikaParser`        | 经 Tika 解析                 |
| .pptx/.xlsx/...     | 开关关                 | `raise ValueError`       | 文件失败，提示「未启用 Tika」|
| .pptx/.xlsx/...     | 开关开 **但** 无 JVM   | `raise ValueError`       | 文件失败，提示「需安装 JVM」 |
| .pptx/.xlsx/...     | 外部 Server 模式       | 返回 `TikaParser`        | 经外部 Tika Server 解析      |

未知格式失败时，异常文案需**明确指引**，例如：

> `不支持的文件格式: .pptx。如需解析该格式，请安装 JRE 并启用 Tika 兜底（TIKA_FALLBACK_ENABLED=true），或部署外部 Tika Server。`

### 3.5 应用启动安全（验证点）

- `backend/services/file_service.py` → `from providers.parser import get_parser`；
- `providers/parser/__init__.py` → **不**在模块顶层 `import tika`（懒导入置于 `TikaParser.parse` 内）；
- 启动期不触发 JVM 探测，**首次** `get_parser(未知格式)` 时才探测；
- ⇒ **无 JVM 环境下 FastAPI/uvicorn 正常启动，txt/pdf/docx 正常处理**。

这是「不要启动不起来」硬约束的可证伪点，列入测试用例。

## 四、详细设计

### 4.1 `TikaParser`

```python
# backend/providers/parser/tika_parser.py
from pathlib import Path
from providers.parser.base import DocumentParser, ParseResult


class TikaParser(DocumentParser):
    """兜底解析器：基于 Apache Tika（tika-python），覆盖绝大多数文档格式。

    本解析器不参与 get_parser 的精确扩展名匹配，仅作为匹配失败后的兜底分支，
    因此 supported_extensions() 返回空列表。
    """

    def parse(self, file_path: Path) -> ParseResult:
        # 懒导入：保证无 tika 包 / 无 JVM 时，import providers.parser 不报错
        from tika import parser as tika_parser

        parsed = tika_parser.from_file(str(file_path))
        content = (parsed.get("content") or "").strip()
        metadata = parsed.get("metadata") or {}
        return ParseResult(
            filename=file_path.name,
            format=file_path.suffix.lower(),
            content=content,
            metadata=metadata,
        )

    def supported_extensions(self) -> list[str]:
        # 纯兜底，不参与精确匹配；详见 get_parser 兜底分支
        return []
```

`supported_extensions()` 返回 `[]` 的含义：**主动放弃精确匹配**，把裁决权交给 `get_parser` 的兜底分支。这样即便将来有人把 TikaParser 误塞进 `_parsers` 列表，它也不会抢占任何格式。

### 4.2 `get_parser` 改造（`__init__.py`）

```python
from pathlib import Path

from providers.parser.base import DocumentParser
from providers.parser.txt_parser import TxtParser
from providers.parser.pdf_parser import PdfParser
from providers.parser.docx_parser import DocxParser
from providers.parser.tika_parser import TikaParser
from providers.parser.tika_runtime import tika_available

# 精确匹配的轻量解析器（顺序无关，扩展名互斥）
_parsers: list[DocumentParser] = [TxtParser(), PdfParser(), DocxParser()]
_tika_parser = TikaParser()


def get_parser(file_path: Path) -> DocumentParser:
    """根据扩展名选择解析器：先精确匹配轻量库，匹配不到再 fallback 到 Tika。"""
    ext = file_path.suffix.lower()

    # 1) 轻量库精确匹配
    for parser in _parsers:
        if ext in parser.supported_extensions():
            return parser

    # 2) Tika 兜底（仅当启用且 JVM 可用 / 外部 Server 模式）
    if tika_available():
        return _tika_parser

    # 3) 真正不支持
    raise ValueError(
        f"不支持的文件格式: {ext}。如需解析该格式，请安装 JRE 并启用 Tika 兜底"
        f"（TIKA_FALLBACK_ENABLED=true），或部署外部 Tika Server。"
    )
```

### 4.3 配置项（`settings.py` / `.env.example`）

| 配置项                   | 默认值 | 说明                                                       |
| ------------------------ | ------ | ---------------------------------------------------------- |
| `TIKA_FALLBACK_ENABLED`  | `true` | Tika 兜底总开关                                            |
| `TIKA_SERVER_ENDPOINT`   | 空     | 非空时走外部 Tika Server（如 `http://tika:9998`），跳过本地 JVM |
| `TIKA_JAVA_PATH`         | 空     | 显式指定 `java` 可执行路径；空则用 PATH 中的 `java`         |

`.env.example` 追加：

```bash
# 文档解析 Tika 兜底（可选，需 JRE）
TIKA_FALLBACK_ENABLED=true
# TIKA_SERVER_ENDPOINT=http://tika:9998   # 外部共享 Tika Server，设此项可免本地 JVM
# TIKA_JAVA_PATH=                         # 显式 java 路径，留空则用 PATH 中的 java
```

### 4.4 外部 Server 模式（推荐用于生产/多副本）

本地模式下每个后端进程首次解析都会拉起一个 Tika Server JAR（JVM 启动开销 + 首次 JAR 下载需联网）。生产建议：

- 单独跑一个 `apache/tika` Docker 容器（或 `tika-server-standard` JAR）作为 **sidecar**；
- 所有后端副本设 `TIKA_SERVER_ENDPOINT=http://tika:9998`；
- `tika_runtime.tika_available()` 在该模式下跳过本地 JVM 探测（由 sidecar 承担 JVM）；
- `TikaParser.parse` 内通过 `os.environ["TIKA_CLIENT_ONLY"]` / tika-python 的 endpoint 配置指向该地址，**不再本地启动 JAR、不再下载**。

好处：后端镜像可保持无 JVM 的精简；多副本共享一个 Tika 实例；离线环境只需预置 sidecar 镜像。


### 5.2 系统依赖（JRE）

`tika` 是 pip 包，但运行依赖 **JRE 8+**（非 pip 可装）：

- 本地开发：`apt-get install -y default-jre`（Linux）/ 安装 Temurin JRE（Windows/macOS）；
- Docker：基础镜像叠加 `eclipse-temurin:8-jre` 或安装 `openjdk-8-jre-headless`。

**未装 JRE 不是错误**：`tika_available()` 返回 False，Tika 兜底自动关闭，轻量格式照常工作。

## 六、错误处理与日志

- **`TikaParser.parse`** 包裹 `try/except`，将 tika 异常转换为与现有解析一致的错误形态（复用管线已有的「解析失败」处理路径，避免裸抛 tika 内部异常）。
- **探测日志**：首次 `get_parser` 触发兜底判定时，`INFO` 一次性记录判定结果，便于运维定位：
  - `Tika fallback: disabled by config`
  - `Tika fallback: enabled, mode=local, jvm=available|missing`
  - `Tika fallback: enabled, mode=remote, endpoint=...`
- **降级报错**：无 JVM 且上传未知格式时，`ValueError` 文案需明确指引（见 3.4），让用户知道「装 JVM 或开开关即可」，而非看到 `java: command not found`。
- 现有 `file_service` 解析失败 → 文件状态置失败 + 错误信息的统一流程保持不变，本次改造与之衔接，不新增流程。

## 八、部署说明（Docker）

提供两种构建 profile，按环境二选一：

**Profile A — 精简镜像（无 JVM）**

- 仅支持 txt/md/pdf/docx；
- 镜像小、启动快；
- 适合只需这四类格式、或搭配外部 Tika Server 的场景。

**Profile B — 完整镜像（带 JRE + tika）**

- 在精简镜像基础上叠加 JRE 层；
- 支持全部 Tika 覆盖格式；
- 适合单机一站式部署。

**Profile C（推荐生产）— 精简后端 + 外部 Tika Sidecar**

- 后端用精简镜像（无 JVM）；
- `docker-compose` 额外起 `apache/tika` 服务；
- 后端 `TIKA_SERVER_ENDPOINT=http://tika:9998`；
- 后端副本可水平扩展，共享 Tika。

## 九、风险与权衡

| 风险                                       | 缓解                                                                 |
| ------------------------------------------ | -------------------------------------------------------------------- |
| JVM 体积/启动开销                           | 默认兜底（按需），生产用外部 Server 模式                              |
| tika-python 首次下载 JAR 需联网             | 离线环境用 Server 模式 或预置 JAR 到 `~/.tika`                       |
| Tika 文本质量/结构与专用库差异（如 PDF 偏移）| **仅作兜底**，不替换轻量库；已知格式永远走专用库                       |
| 无 JVM 时用户上传 pptx 直接失败体验          | 错误文案明确指引（装 JRE / 开开关 / 用 Server）                       |
| 探测结果与运行时不一致（探测后有 JVM、运行时挂了） | `TikaParser.parse` 仍有 try/except 兜底，转交管线统一失败处理        |
