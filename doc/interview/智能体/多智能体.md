# 多智能体

> 项目实现：`backend/services/multi_agent/engine.py`（业务无关执行引擎）+
> `scenarios/universal.py`（通用智能体团队场景）+ `routers/multi_agent.py`（SSE 出口）。
> 技术底座：LangGraph（StateGraph 超步并行 + 共享状态 reducer），单进程单事件循环，无外部 MQ。

## 总览：本项目的多智能体长什么样

一个任务进来，流水线是这样跑的：

```
用户任务 + 自选组合（Retriever/GraphAgent/Critic 勾选）
        │
   Planner（核心必在，LLM 动态分解 2~4 个并行子任务，15s 超时回落）
        │
 ┌──────┼──────────────┐   同一 superstep 自动并行
 Retriever-1..N    Worker-1..N   GraphAgent        （Retriever 选了→RAG 取证；
 （知识库向量检索）  （纯模型执行）  （图谱事实卡）      没选→Worker 用模型知识直接干）
 └──────┬──────────────┘
        │
   Critic（可选组合，0~1 个；没选则并行节点直通 Synthesizer，引擎零特判）
        │
   Synthesizer（核心必在，汇总黑板流式交付）
```

两条硬规矩：planner/synthesizer 是任何团队必需的核心角色（固定内置），
能力智能体由用户自由勾选组队，流水线按组合动态装配（`build_engine_from_task`）。

## 题一：多智能体设计模式有哪些（如主子 agent 那些）

### 常见模式全景：先分清两个维度（面试先报菜名，别混维度）

**维度一：协作 / 组织模式**——管「任务怎么拆、控制权怎么流」：

| 模式 | 一句话 | 代表 |
|---|---|---|
| 主子 / 编排者-执行者（Orchestrator-Workers / Supervisor） | 一个主 agent 拆任务、派活、收结果，子 agent 只管执行 | 本项目 Planner+Workers；Magentic-One |
| 流水线 / 移交（Pipeline / Handoff） | 按角色工序顺序传递中间产物，像 SOP 装配线 | MetaGPT（产品经理→架构师→工程师） |
| 评审 / 反思（Evaluator-Optimizer / Reflection） | 生成者产出、评审者挑毛病，循环改进 | 本项目 Critic 节点；Reflexion |
| 辩论（Debate） | 两个 agent 各持立场互相攻击，第三个裁判裁决 | 多智能体辩论论文（Du et al.） |
| 层级团队（Hierarchical） | manager agent 下管多个小组，树状拆解 | CrewAI Hierarchical、AutoGen 嵌套 chat |

**维度二：通信机制**——管「信息在 agent 之间怎么流动」：

| 机制 | 一句话 | 代表 |
|---|---|---|
| 点对点直传 | A 干完把结果作为消息参数发给 B | AutoGen send/receive、handoff |
| 黑板（Blackboard） | 大家不互相通信，都读写一块共享状态，各自贡献产出 | 本项目；经典架构模式（Hearsay-II、POSA） |
| 消息队列 / 事件总线 | 异步解耦，发完就走 | Kafka/Redis（跨进程） |
| 群聊（Group Chat） | 共享一个对话历史 + 发言调度 | AutoGen GroupChat |

> 群聊横跨两个维度——共享对话历史是通信形态，"轮到谁发言"是控制策略。
> 黑板在经典软件架构里（POSA）本来就是架构模式，多智能体语境下归入通信机制
> 更准。两个维度**正交、可自由组合**：同样用黑板通信，控制上可以是编排
> （本项目），也可以是群聊（AutoGen 共享 state）。

### 本项目怎么选：协作上「编排者-执行者 + 评审」，通信上「黑板」

1. **协作模式一·主子（Planner → Workers）**：Planner 用 LLM 把任务动态分解成 2~4 个
   可并行子任务（Plan-and-Solve 思路），子任务交给并行节点执行。
   为什么 LLM 分解还要设 15s 超时（PLAN_TIMEOUT）：规划是前置环节，
   卡住会拖死整个流水线——超时回落到规则默认分解（两条兜底 goal），
   "快而稳"优先于"拆得漂亮"。
2. **通信机制·黑板（共享 state）**：所有节点读写 `MultiAgentState`，互不点对点通信（详见题二）。
3. **协作模式二·评审（Critic）**：可选组合。**先确定性硬规则后 LLM**——素材充分性裁定
   （0 条素材不出成果 / <3 条建议人工，保守原则）是纯代码可复现的，
   LLM 只负责把裁定解释成人话（失败静默降级，不阻塞）。
   这是"Evaluator 模式"的工程化落地：不搞反思循环（成本不可控），
   一次裁定 + 人工复核建议就收口。

**为什么不上群聊/辩论**：群聊每轮要把全部历史塞给所有 agent，token 成本随
轮数平方涨，且发言顺序不可控；辩论要多轮对抗。本任务是"一次性交付"形态，
流水线 + 黑板确定性更强、可观测（每个节点产出都留卡）、成本可控。

### 对标开源（面试加分段）

| 开源 | 它的做法 | 本项目对应 |
|---|---|---|
| AutoGen / CrewAI | 角色组合 + 共享状态协作 | 用户自由勾选组合，成员读写共享 state |
| MetaGPT | 流水线 SOP，角色按序传产物 | LangGraph superstep 装配线：并行→评审→合成 |
| Magentic-One | 编排者任务台账 + 重规划 | 首版一次性规划（重规划留迭代），Critic 确定性兜底 |
| Plan-and-Solve | 先规划后执行 | Planner LLM 分解 + 超时回落 |
| RAG / GraphRAG | 检索增强 | Retriever 检索全部知识库，GraphAgent 查实体图谱 |

### 追问点

**Q：组合是用户勾选的，流水线怎么动态装配？**
场景适配器按组合生成 plan（[{id, node, role, goal}]）和节点实现，引擎按 plan 建图：
- 选 Retriever → 子任务角色为 retriever（RAG 取证）；没选 → worker（纯模型执行）；
- 选 GraphAgent → 追加图谱节点；选 Critic → 追加评审节点，且并行节点汇聚到 critic；
  没选 critic → 并行节点直通 synthesizer（`fan_in = critic or synth`，一行代码，引擎零特判）；
- plan 有校验：必须恰好一个 synthesizer、至多一个 critic，节点必须有实现，否则建图直接报错。

**Q：LangGraph 里"同一 superstep 并行"是什么意思？**
图上 planner 同时连出多条边到并行节点，LangGraph（Pregel 模型）的一个超步里
这些节点并发执行，全部完成后汇聚点（critic 或 synthesizer）才执行——
不用自己管线程/协程池，框架保证汇合语义。

**Q：单节点挂了怎么办？**
每层都有降级，任何一层挂都不中断流水线：
- Planner：LLM 15s 超时 → 规则默认分解；
- Retriever：向量库失败逐库跳过；GraphAgent：图谱失败返回空事实；
- Worker：LLM 失败产空卡（「执行失败，无产出」）；
- Critic：LLM 解释失败 → 静默只留硬规则裁定；
- Synthesizer：LLM 失败 → 模板结论确定性拼装 + error 事件告知前端；
- 引擎级：llm_stream 单节点 30s 超时（NODE_TIMEOUT），路由层 try/except 兜底不让 SSE 断流。

**Q：为什么不做成每个 agent 都能自主决策的"真自治"？**
业务要的是可控、可审计、可复现——流水线拓扑固定（并行段除外）、每个产出留卡、
裁定规则可解释。自治多智能体（agent 自主决定调谁）适合开放探索任务，
代价是不可预测；按需取舍。

## 题二：多智能体之间如何传递消息

### 总纲：agent 间通信三条路（先报菜名）

1. **点对点直传**：A 干完把结果作为消息参数发给 B（AutoGen 的 send/receive、
   函数调用传参、handoff 把控制权和上下文一起移交）。直接但耦合——A 必须知道 B 在哪。
2. **共享黑板**：都不互相发消息，各自读写一块共享状态。解耦、可追溯，
   加节点不改别人——本项目主力。
3. **消息队列 / 事件总线**：异步解耦，发完就走（跨进程/跨服务时用 Kafka/Redis），
   单进程内可用内存队列。

### 本项目：黑板为主，两条通道分开

**通道一：agent 间通信 = 共享 state 黑板（LangGraph StateGraph）**

```python
class MultiAgentState(TypedDict):
    context: dict                                                  # 场景上下文（只读）
    plan: list[dict]                                               # Planner 的计划
    evidence: Annotated[dict[str, list[dict]], merge_evidence]     # 证据卡（并行写冲突用 reducer 消解）
    facts: list[dict]                                              # 图谱事实卡
    verdict: dict                                                  # Critic 裁定
    conclusion: str                                                # Synthesizer 结论
```

各节点"只写自己的产出、只读别人的产出"：
- Retriever-i 写 `evidence`（证据卡：来源/分数/摘要）；
- Worker-i 写 `evidence`（行家卡：grade=model_output，标明是模型生成非原文）；
- GraphAgent 写 `facts`（事实卡：实体+关系链）；
- Critic 读 evidence+facts，写 `verdict`（裁定：冲突点/建议/置信度/是否需人工）；
- Synthesizer 读全部，写 `conclusion`。

三个关键设计：

1. **并行写冲突用 reducer 消解**：多个并行节点同 superstep 写同一个 `evidence`
   键，直接覆盖会丢数据——用 `Annotated[..., merge_evidence]` 声明合并函数，
   框架在写冲突时自动按 domain 归并证据卡（LangGraph 的标准机制）。
2. **消息格式是结构化卡片，不是裸文本**：每张卡带 `source`（来源）、`grade`
   （sourced_doc=知识库原文 / model_output=模型生成 / graph_fact=图谱事实）、
   `score`（相似度）、`stance`（立场）。下游和前端都能机器校验，
   引用可追溯到具体知识库/文件/页码——防"幻觉当素材传"。
3. **传递时做瘦身，防上下文爆炸**：Synthesizer 拿到的不是语料全文，而是
   每卡截断 160 字的摘要卡 + 评审意见，由 `_synth_user` 拼成 JSON 塞进 prompt。
   黑板会越长越胖，"下游只取需要的键 + 卡片摘要化"就是黑板模式的代价管理。

### 黑板怎么"跑"起来：reducer + 动态建图 + 一次执行时序

**并行写冲突的合并函数（reducer，engine.py）**——冲突语义写在类型上：

```python
def merge_evidence(left: dict, right: dict) -> dict:
    """并行节点写同一 evidence 键时的 reducer：按域合并证据卡。"""
    out = dict(left or {})
    for domain, cards in (right or {}).items():
        out.setdefault(domain, [])
        out[domain] = out[domain] + list(cards)
    return out
```

**按 plan 动态建图（engine.py `_build`，编排核心）**：

```python
g = StateGraph(MultiAgentState)
g.add_node("planner", self._planner)
for node, fn in self._nodes.items():      # plan 里声明的节点必须有实现，否则建图报错
    g.add_node(node, fn)
g.add_edge(START, "planner")

fan_in = critic or synth                  # 汇聚点：有 critic 汇入 critic，否则直通 synthesizer
for step in parallel_steps:
    g.add_edge("planner", step["node"])   # 同 superstep 自动并行
    g.add_edge(step["node"], fan_in)      # 并行全部完成后汇聚点才执行
if critic:
    g.add_edge(critic, synth)
g.add_edge(synth, END)
```

**一次执行时序**（以告警周报任务 + 默认组合为例）：

1. 入口 `POST /run`（task+agents）→ 组合归一化 → Planner LLM 分解 → 装配 plan（数据驱动建图）；
2. Planner 拆 2~4 个子任务（15s 超时回落规则分解）；
3. 并行写黑板：Retriever-1..N / GraphAgent / DataAgent 同 superstep 并发，各自返回
   部分更新（`return {"evidence": {domain: cards}}`），reducer 归并；
4. Critic 两段式：纯代码硬规则先裁定（可复现），LLM 只解释（失败静默）；
5. Synthesizer 读全黑板 → 素材卡 JSON 进 prompt → 逐 token 流式交付；
   LLM 挂了降级模板结论（确定性拼装，任何情况不断交付）；
6. 全程节点 emit 事件 → `asyncio.Queue` → 路由层转 SSE，前端实时看到每个成员进度与卡片。

**收口金句：结构用代码，语义用提示词**——并行/汇聚/降级是控制流（LangGraph 图），
规划/执行/合成是节点内 prompt。模式 = 图结构，节点 = LLM + 提示词。

**prompt 即信封**：下游通过提示词接收上游产出——Worker 收到「总体任务+你的
子任务」（Planner 的计划下发），Synthesizer 收到素材卡 JSON（黑板读出）。
LLM 节点间没有隐式通信，一切消息都显式过黑板、进 prompt。

**通道二：对人（前端）的过程消息 = emit → 队列 → SSE**

节点调 `engine.emit()` 把过程事件（node_start / node_done / evidence / fact /
conflict / token / error）推进 `asyncio.Queue`，路由层消费转成 SSE 推给前端。
注意这是**可观测通道不是 agent 间通信**——agent 间靠黑板，人看过程靠事件流，
两条通道分开，契约统一（team / plan / node_* / evidence / fact / conflict /
token / error / done，`data: [DONE]` 收尾）。Synthesizer 流式输出时逐 token
emit，前端打字机效果就是这么来的。

### 对比与取舍（面试话术）

- **黑板 vs 点对点**：黑板解耦（成员互不引用，新增智能体=多写一个键）、
  可追溯（每条产出都留卡，复盘时有据可查）、天然支持并行（并行节点只管写
  各自 domain）；代价是状态膨胀（靠摘要瘦身管）和没有私聊（本项目不需要——
  协作是"贡献素材"不是"讨论"，讨论型任务才适合群聊/点对点）。
- **为什么不用 MQ**：单进程单事件循环、生命周期就一次请求，`asyncio.Queue`
  内存队列足够；跨服务拆分后才需要 Kafka/Redis 这类真 MQ。

### 高频追问 Q&A

**Q：并行节点同时写一个键，谁先谁后？**
不需要分先后——reducer 定义了合并语义（按 domain 追加），框架保证不丢。
这是声明式的冲突消解：冲突怎么处理写在类型上，不写在业务代码里。

**Q：上游产出是空的（比如检索全没命中），下游会炸吗？**
不会。空产出就是空卡列表，Critic 的硬规则会把"0 素材"裁定为"需补充素材、
建议人工"，Synthesizer 的模板兜底照样能拼出结构完整的结论——
降级链路见题一的追问，整个设计原则是"缺素材可以，缺结构不行"。

**Q：消息会不会越传越大？**
黑板只在节点间存在一次请求的生命周期内，不落库不跨轮；进 prompt 前做了三层
裁剪：卡片摘要截断（160 字）、素材总量上限（MAX_CHUNKS=8 分片）、
结论字数约束（400 字内）。真正会累积的对话历史不进多智能体流水线
（那是单 agent 聊天的记忆问题，见长短期记忆.md）。

**Q：如果两个 Retriever 取回的素材互相矛盾怎么办？**
Critic 的冲突消解先走确定性规则（素材充分性、保守原则），矛盾点列入
conflicts 显式暴露给用户而不是悄悄取舍，LLM 只解释不裁决——
"让矛盾可见"比"替用户做主"更符合研判场景。

**Q：黑板模式是用 LangGraph 的 StateGraph 实现的吗？**
是——StateGraph 就是黑板的工程载体：`MultiAgentState`（TypedDict）是黑板面，
每个节点是独立读写的知识源，reducer 定义并发写语义，超步调度控制执行节奏。
表述上注意分清：黑板是**通信机制**（思想），StateGraph 是**工程载体**（实现），
类比"用 Redis 实现了消息队列"——别说成"黑板模式就是 StateGraph"。

## 题三：用 LangGraph 不就是"编排"吗？和 Pipeline 有啥区别

### 先分清两件事：框架 vs 模式

**LangGraph 是编排框架（底座），不是模式本身**——它提供图、超步并行、reducer
这些机制，能让任何协作模式跑起来。本项目在它之上落的是「协作上编排者-执行者
+ 评审、通信上黑板」的组合（见题一）。所以别说"我用了 LangGraph 所以是编排模式"，
要说"我用 LangGraph 的图语义落地了编排者-执行者模式"。

### 编排 vs 流水线（一张表说清）

| 维度 | Pipeline（流水线） | Orchestration（编排） |
|---|---|---|
| 拓扑 | 线性链 A→B→C，设计时写死 | 任意图：并行/分支/汇聚，可运行时决定 |
| 工序谁定 | 代码写死的 SOP | 规划器运行时拆任务 → 动态装配 |
| 节点怎么连 | 传参：上一级输出=下一级输入 | 共享黑板：节点互不为输入，只读写 state |
| 并行 | 通常没有（接力式串行） | 一等公民（superstep 并行 + reducer 汇聚） |
| 典型代表 | MetaGPT（产品经理→架构师→工程师） | 本项目；Magentic-One |

判断标准一句话：**拓扑是写死的还是算出来的；节点靠传参连接还是靠共享状态解耦。**

### 本项目为什么是编排不是 pipeline（三条硬理由）

1. **plan 是运行时算出来的**：Planner LLM 分解出 2~4 个子任务，引擎按 plan
   数据建图——选没选 Critic 连汇聚点都不同（`fan_in = critic or synth`）；
   pipeline 的工序是设计时写死的；
2. **并行段不是接力**：Retriever-1..N 互不依赖、同 superstep 并发、reducer
   合并写黑板——pipeline 是一人干完递给下一个；
3. **节点不互为输入**：所有节点只读写黑板，Synthesizer 汇总全体产出——
   pipeline 里每一级只能看到上一级的输出。

再补一层：编排内部还分"计划内容谁产出、计划由谁执行"两层——本项目是
**Planner LLM 定计划、引擎代码跑计划**，动态性和可控性各拿一半，
这也是 Magentic-One（LLM 台账编排）和纯代码工作流（固定 chain）之间的折中。

**面试话术**："宏观主干（规划→并行→评审→合成）形态上像流水线，但主干本身是
按组合和 LLM 计划动态装配的，并行汇聚靠 reducer——机制上是编排者-执行者，
pipeline 只是它的形态近似。"

### 收口：本项目用了哪些设计模式

- **协作模式 2 种**：编排者-执行者（Planner 拆活派活）+ 评审（Critic 质控）；
- **通信机制 1 种**：黑板（共享 state，StateGraph 落地）——细节见题一/题二；
- **形态近似** pipeline，**机制是**编排（见上）；
- **没用**：辩论、群聊、反思循环、层级团队——一次性交付任务不需要多轮
  对抗/讨论，token 成本和不确定性不划算（取舍理由见题一）。

## 题四：用多智能体和用一个智能体使用 skill 完成任务的区别

### 先定义，别偷换概念（面试先立住框架）

**skill/tool 是"手"，agent 是"脑"**——单智能体+skill 是一个脑换着工具用；
多智能体是多个脑分工，各有自己的上下文、prompt 和职责。

| | 单智能体 + skill/工具 | 多智能体 |
|---|---|---|
| **本质** | 一个 LLM 循环，**换着工具用**（ReAct：思考→调工具→观察→再思考） | 多个 LLM 实例，**各自带独立上下文和职责** |
| **控制流** | 同一个大脑决定"下一步调哪个工具" | Planner 拆解 → 各 Agent 执行 → 汇总/仲裁 |
| **上下文** | 全部挤一个上下文窗口 | 每个 Agent 独立窗口 |
| **并发** | 串行（一次一个工具调用） | 天然并行（本项目 Retriever-1..N 同 superstep 并发） |
| **典型形态** | ReAct Agent、function calling 循环 | LangGraph/CrewAI/AutoGen 团队 |

注意边界的说法：ReAct 循环里多步调工具，看起来"多轮"，但**始终是同一个上下文、同一个决策者**——这是它和多智能体的分水岭，别被"轮数"迷惑。

### 核心区别三条

**1. 上下文隔离——最本质的差异（上下文窗口经济学）**

单智能体里，向量检索的原始片段、图谱查询的中间结果、纠错重试的历史**全堆在同一个窗口**：

- 注意力稀释：上下文越长，模型对每段信息的"关注度"越低，后面步骤质量下降；
- 窗口硬顶：128K 看着大，原始语料+多轮工具返回很容易挤爆；
- 中间结果污染：检索回来的半成品文本和最终结论混在一个上下文里互相干扰。

多智能体每个 Agent 只看自己的子任务和返回结果，**中间过程互不污染，只有提炼后的结论进下游**——本项目 Retriever/GraphAgent 各查各的，给 Synthesizer 的是截断 160 字的摘要卡而不是语料全文（瘦身细节见题二）。

**2. 专业化——每个角色独立的 prompt / 模型 / 校验规则**

单智能体是一套"通才"prompt 硬扛所有环节，质检要求只能混在主 prompt 里，容易被忽略。
多智能体每个角色可以完全不同：本项目 Critic 的"素材充足性裁定"（0 素材不出成果、
<3 条建议人工）是独立成型的确定性规则，不依赖主 prompt 的自觉——这在国际上叫
**角色专精（role specialization）**，MetaGPT 的 SOP 流水线就是典型。

**3. 失败域与可观测性——重试粒度和归因清晰度**

- 多智能体：哪个 Agent 错了是明确的——Critic 打回可以**指定谁补查重试**；
  LangSmith trace 里每个 Agent 是独立子树，哪个环节慢/错一眼定位；
- 单智能体：中间某步出问题往往只能**整体重来**，trace 是一条长链，归因靠翻。

### 代价（必须主动说，才显得客观）

| 代价 | 具体内容 | 本项目的防法 |
|---|---|---|
| **成本高数倍** | 每个 Agent 都是完整 LLM 会话，token 消耗比单智能体高 3~10 倍 | Critic 硬规则裁定（不额外烧 LLM 反思循环）、卡片截断 160 字 |
| **协调复杂度** | Planner 拆错、Agent 结论冲突、循环打回死循环 | Critic 仲裁 + 冲突显式暴露 + 每层降级（见题一追问） |
| **延迟** | 并行能缓解，但规划/汇聚/评审本身有开销 | Planner 15s 超时回落规则分解 |

简单任务上多智能体**反而更慢更贵**——这是选型的第一道否决线。

### 什么时候用哪个（选型结论）

> **上下文装得下、工具少于十几个、无需并行 → 单智能体+工具，永远更简单更便宜。**
> 出现三个信号才上多智能体：
> ① **异构信息源并行汇聚**（本项目：向量库+图谱+台账三路并行取证）；
> ② **独立质检仲裁**（Critic 与生成者利益分离，自己查自己不可靠）；
> ③ **环节专业化**（检索、研判、合成需要完全不同的 prompt 策略）。

本项目命中全部三条：告警研判任务天然是"三路检索并行 + 汇总成文 + 证据充足性仲裁"，
这是单智能体串行工具调用给不了的效率和质量结构。

### 追问 Q&A

**Q：Agent 是不是越多越智能？**
不是。每加一个 Agent 就是加一份协调成本和失败点，收益来自**职责边界清晰**而不是数量。
本项目的组合哲学就是最小必要：核心固定两个（Planner/Synthesizer），能力角色按任务勾选，
没选 Critic 时并行节点直通合成——不为"显得智能"堆角色。

**Q：单智能体用 sub-agent / 工作流也能模拟多智能体，边界在哪？**
边界就是**上下文是否隔离**：sub-agent 如果共享同一个上下文窗口（比如把子任务结果
拼回主循环），本质还是单智能体；只有子任务在独立上下文里执行、只回传提炼结果，
才算真多智能体。工程判据一句话：**中间过程进不进主上下文**。

**Q：你项目里有没有其实单智能体就够的环节？**
有，而且刻意保留了——Worker 就是单智能体形态（纯模型执行一个子任务，没有工具循环）；
日常问答走单 agent 聊天链路，根本不进多智能体流水线（见题二"消息会不会越传越大"）。
多智能体只用在研判交付这类值得付协调税的任务上——**按任务选形态，不全栈一套**。

**Q：成本差异能量化吗？**
量级上：同样完成一次告警研判，单智能体串行约 5~8 次 LLM 调用（每次都带全量历史），
多智能体并行 10~15 次但每次上下文小而专；总 token 多 3~10 倍，换来的是
延迟更低（并行段）、质量结构更好（独立仲裁+可溯源）。LangSmith 的 per-node
token 统计可以直接验证这个数。

## 附：完整话术（2 分钟串讲，把四道题连起来说）

### 标准版

> 我的多智能体系统是基于 LangGraph 的通用协作团队。**协作模式上是两种的组合，
> 通信机制上是一种**：协作主干是**编排者-执行者**——一个 Planner 用 LLM 把任务
> 动态分解成 2~4 个可并行的子任务，派给并行节点执行；质控上是**评审模式**——
> 一个可选的 Critic 节点，两段式：先纯代码硬规则裁定（可复现），LLM 只负责解释，
> 不搞反思循环，成本可控；**通信机制是黑板**——agent 之间不点对点发消息，而是
> 各自读写一块共享 state，我写我的产出、读别人的产出，解耦而且每条产出都留卡
> 可追溯——工程载体就是 LangGraph 的 StateGraph：TypedDict 定义黑板面、reducer
> 定义并发写语义，各节点就是图上独立读写的知识源。整体形态上
> 宏观主干（规划→并行→评审→合成）像流水线，但机制上是编排——因为计划是
> 运行时算出来的，并行汇聚靠 reducer，节点互不依赖。
>
> **【智能体组合】** 角色一共设计了 7 类，分两组。**固定内置两个**：Planner 拆任务
> 定计划，Synthesizer 汇总各角色产出、流式交付——任何团队都必有这两个；
> **自由勾选五个**：Retriever 做知识库向量检索，取带出处的证据卡；DataAgent 查
> 实体台账，做结构化数据统计；GraphAgent 查知识图谱，产出实体关系事实卡；
> Critic 评审素材充分性、标冲突给建议；Worker 是纯模型执行者。Retriever 和
> Worker 是并行节点上按组合二选一的角色——每个子任务生成一个并行节点，选了
> Retriever 走 RAG 取证，没选就 Worker 直接用模型知识干。用户按任务勾选组合，
> 同一份引擎代码装配出不同的流水线。
>
> **架构上分三层**：路由层管 SSE 出口；引擎层是业务无关的执行引擎，管建图、
> 超步并行、超时降级；场景层定义角色和提示词。核心是一张 StateGraph：
> Planner 起手，并行节点在同一超步并发跑，可选 Critic 汇聚，最后 Synthesizer
> 汇总流式交付。拓扑不是写死的，按用户勾选的组合动态装配——没选 Critic 就
> 直通合成节点，引擎零特判。
>
> **消息传递两条通道分开**：agent 之间靠共享 state 黑板，消息格式是结构化卡片
> ——带来源、可信等级、相似度分数，下游和前端都能机器校验，防止幻觉当素材传；
> 对人靠事件流——节点 emit 事件进内存队列，路由层转 SSE 推前端。另外传递时
> 做瘦身：进 prompt 前每张卡截断成摘要，防止上下文爆炸。
>
> **冲突消解分两层**：数据层的写冲突——多个并行节点同超步写同一个 state 键，
> 用 reducer 声明式合并，合并语义写在类型上不写在业务代码里，框架保证不丢；
> 语义层的内容冲突——比如两路检索素材矛盾，Critic 先走确定性规则，矛盾点
> 显式暴露给用户而不是悄悄取舍，LLM 只解释不裁决。整个系统的底线是
> "缺素材可以，缺结构不行"——每层都有降级，最坏情况也能拼出结构完整的结论。
>
> **【单 vs 多】** 最后补一句选型判断：这一切的前提是任务配得上多智能体——
> 上下文装得下、工具少、无需并行的任务，单智能体+工具永远更简单更便宜。
> 我这个任务要三路异构检索并行汇聚 + 独立仲裁，是单智能体串行工具调用
> 给不了的结构；而日常问答我走的还是单 agent 聊天链路——按任务选形态。

### 30 秒极简版（开场先给结论）

> 协作模式两种：编排者-执行者（Planner 动态拆任务派活）+ 评审（Critic 先硬规则
> 后 LLM）；通信机制一种：黑板（LangGraph StateGraph 共享 state，不点对点）。
> 角色固定 Planner/Synthesizer 两个核心，Retriever/DataAgent/GraphAgent/
> Worker/Critic 五个按任务勾选，拓扑动态装配，并行节点同超步并发。消息是
> 结构化卡片过黑板、过程事件走 SSE 给前端；写冲突用 reducer 合并，内容矛盾
> 由 Critic 显式暴露。每层有降级，保证任何情况都能交付。
