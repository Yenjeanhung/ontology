# 长短期记忆

> 对应代码：`backend/routers/agent.py`（`_persist_turn`、查询主链路）、`backend/services/chat_service.py`（短期记忆）、`backend/services/memory_store.py`（长期记忆门面）、`backend/config.py:144-150`（参数）。

## 总览：双层记忆架构

| 维度 | 短期记忆 | 长期记忆 |
|---|---|---|
| 范围 | 单个会话内 | 跨会话，智能体级共享 |
| 载体 | 关系库 `chat_messages` 表 + `chat_sessions.summary` | mem0 + 向量库（Milvus，collection `agent_memories`） |
| 写入时机 | 用户消息进请求立即落库；助手消息回答流结束后落库 | 每轮问答结束后台异步触发 |
| 注入时机 | 每轮提问前装填最近 N 轮 + 摘要 | 每轮提问前向量检索 top-k 相关事实 |
| 隔离维度 | `session_id` | `user_id = agent_id` |
| 失败策略 | 落库失败记日志，不影响已下发回答 | 全链路 try/except，降级为"无长期记忆" |

一轮对话的完整时序（`agent.py` 查询主链路）：

```
用户提问
 ├─ 1. append_message("user", query)        ← 用户消息立即落库（短期）
 ├─ 2. load_history()                        ← 装填最近6轮+滚动摘要（短期注入）
 ├─ 3. MemoryStore.search(query)             ← 向量检索相关事实（长期注入）
 ├─ 4. 流式生成 SSE 回答给前端
 └─ 5. _persist_turn()                       ← 回答完整下发后：
       ├─ append_message("assistant")        ← 助手消息落库（短期）
       ├─ maybe_summarize()                  ← 触发滚动摘要（短期）
       └─ MemoryStore.add_background()       ← 后台异步写入（长期）
```

## 短期记忆（会话内）

### 存储与写入时机

- **用户消息**：请求一进来就落库（`agent.py:680`），即使后续生成失败也有记录。
- **助手消息**：SSE 流式回答**完整结束后**由 `_persist_turn`（`agent.py:627-643`）统一落库——因为流式过程中答案是一段段 token，只有在收尾处拼接完整。
- `_persist_turn` 自开新的 DB 会话（路由的 session 在 SSE 生成器执行时已释放），全部尽力而为，失败只记日志，不影响已下发的回答。
- 附带逻辑：首条用户消息自动截取为会话标题。

### 注入策略（`load_history`，防止上下文爆炸的核心）

> 代码位置：`backend/services/chat_service.py:120-152` `ChatService.load_history()`，查询主链路在 `backend/routers/agent.py:683` 调用（每轮提问、调 LLM 之前）。

不是把会话全部历史塞进 prompt，而是三重限制：

1. **轮数窗口**：只取最近 `CHAT_SESSION_WINDOW_TURNS = 6` 轮（一轮 = 用户一问 + 助手一答）；
2. **字符预算**：总字符超 `CHAT_SESSION_CHAR_BUDGET = 6000`（约 2k token）时从最旧开始丢弃；
3. **最新截尾**：最新一条本身超预算时截尾保留（宁可短也不丢最近上下文）。

```python
# backend/services/chat_service.py — ChatService.load_history()
async def load_history(db: AsyncSession, session_id: str) -> dict:
    """装填注入 prompt 的历史，返回 {history, summary}。"""
    session = await db.get(ChatSession, session_id)
    summary = ""
    if session and settings.CHAT_SUMMARY_ENABLED:
        summary = (session.summary or "").strip()          # 摘要注入（滚动摘要产出）

    messages = await ChatService.get_messages(db, session_id)
    window = max(0, settings.CHAT_SESSION_WINDOW_TURNS) * 2
    candidates = messages[-window:] if window > 0 else []  # ① 轮数窗口：6 轮 = 12 条

    budget = max(0, settings.CHAT_SESSION_CHAR_BUDGET)
    picked: list[dict] = []
    used = 0
    for msg in reversed(candidates):                       # ② 从最新往旧装填
        cost = len(msg.content or "")
        if used + cost > budget and picked:
            break                                          #    预算满：更旧的整条丢弃
        picked.append({"role": msg.role, "content": msg.content or ""})
        used += cost
    picked.reverse()                                       #    还原为从旧到新

    if picked and 0 < budget < len(picked[-1]["content"]):
        picked[-1]["content"] = "…" + picked[-1]["content"][-budget:]  # ③ 最新一条截尾保留

    return {"history": picked, "summary": summary}
```

参数定义在 `backend/config.py:144-150`：

```python
CHAT_SESSION_WINDOW_TURNS: int = 6     # 注入 prompt 的最近轮数（一轮 = 一问一答）
CHAT_SESSION_CHAR_BUDGET: int = 6000   # 历史注入总字符预算（约 2k token）
CHAT_SUMMARY_ENABLED: bool = True      # 超长滚动摘要总开关
CHAT_SUMMARY_TRIGGER_TURNS: int = 20   # 累计用户消息数超过该值触发滚动摘要
CHAT_SUMMARY_MAX_CHARS: int = 1000     # 滚动摘要字符上限
```

### 滚动摘要（`maybe_summarize`，超长会话的兜底）

> 代码位置：`backend/services/chat_service.py:156-213` `ChatService.maybe_summarize()`，由 `_persist_turn` 在每轮回答落库后调用（`backend/routers/agent.py:636`）。摘要存 `chat_sessions.summary`，游标存 `chat_sessions.summary_until_id`。

- 触发条件：会话累计用户消息数 > `CHAT_SUMMARY_TRIGGER_TURNS = 20` 轮；
- 做法：把**窗口外**的旧轮次与旧摘要一起交给 LLM 压缩，结果写回 `session.summary`，上限 `CHAT_SUMMARY_MAX_CHARS = 1000` 字符；
- 幂等：`summary_until_id` 记录已计入摘要的最后一条消息，重复调用不重复摘要；
- LLM 未配置或调用失败时静默跳过，不阻塞主链路。

```python
# backend/services/chat_service.py — ChatService.maybe_summarize()（节选关键段）
async def maybe_summarize(db: AsyncSession, session_id: str) -> None:
    if not settings.CHAT_SUMMARY_ENABLED:
        return
    session = await db.get(ChatSession, session_id)
    messages = await ChatService.get_messages(db, session_id)
    trigger = max(1, settings.CHAT_SUMMARY_TRIGGER_TURNS) * 2
    if len(messages) < trigger:            # ① 未到 20 轮：不压缩（短会话省一次 LLM）
        return

    window = max(0, settings.CHAT_SESSION_WINDOW_TURNS) * 2
    if session.summary_until_id:
        # ② 幂等游标：从上次已摘要消息之后，取到当前窗口左边界为止
        idx = next((i for i, m in enumerate(messages) if m.id == session.summary_until_id), -1)
        older = messages[idx + 1: len(messages) - window] if idx >= 0 else messages[: len(messages) - window]
    else:
        older = messages[: len(messages) - window]     # ③ 首次：窗口外全部旧轮次
    if not older:
        return                                          #    窗口外没有新内容：无事可做

    transcript = "\n".join(
        f"{'用户' if m.role == 'user' else '助手'}：{m.content}" for m in older
    )
    if len(transcript) > 8000:                          # ④ 待压缩文本自身超长时中段省略
        transcript = transcript[:4000] + "\n…（中间省略）…\n" + transcript[-4000:]

    prompt = (
        "请把下面这段多轮对话压缩成一份要点摘要，作为后续对话的背景知识。\n"
        "要求：只保留事实、结论、关键实体与数字；不评价、不复述原句；"
        f"总长不超过 {settings.CHAT_SUMMARY_MAX_CHARS} 字。\n\n"
        f"已有摘要（若有，请在其基础上合并更新）：\n{(session.summary or '（无）')}\n\n"
        f"新增对话：\n{transcript}"
    )
    llm = create_llm()
    if llm is None:
        return                                          # ⑤ 未配置 LLM：静默跳过
    resp = await llm.ainvoke(prompt)
    text = (getattr(resp, "content", "") or "").strip()
    if not text:
        return
    session.summary = text[: settings.CHAT_SUMMARY_MAX_CHARS]
    session.summary_until_id = older[-1].id             # ⑥ 推进幂等游标
    await db.commit()
    # 整体 try/except：失败只记日志（logger.exception），不阻塞主链路
```

### 游标机制：增量压缩与幂等（面试重点）

`summary_until_id` 本质是**压缩进度书签**（类比 Kafka 的消费 offset）：记录"已经压进摘要的最后一条消息 id"。它的作用是把窗口外的内容切成两段，每次只压增量：

```
窗口 = 6 轮 = 12 条消息。当前会话 44 条消息，游标 summary_until_id = #30：

messages:  #1 ──────── #30 │ #31 #32 │ #33 ──────── #44
           已压过（跳过）    │ 新出窗    │ 近 6 轮窗口
           游标在这 ──┘     │ =本次要压 │ 原文注入，永不去压

本次压缩范围 older = messages[游标下一条 : 总数−12] = #31~#32
压缩完成后游标推进：summary_until_id = older[-1].id = #32
```

即：**压缩范围 = 游标之后 → 窗口左边界之前**。窗口参数（6 轮）回答"注入多少原文"，游标回答"压缩从哪续"——两个是独立机制，右边界永远由窗口定，左边界由游标定。

三种情况：

| 时机 | 游标 | 本次压谁 |
|---|---|---|
| 首次触发（累计 21 轮，游标为空） | 空 | 窗口外**全部**：`messages[:len−12]` |
| 后续某轮（游标 #30，新出窗 #31~#32） | #30 | 只有 #31~#32（2 条增量） |
| 窗口外全压过、无新出窗 | — | `older` 为空 → 直接 return，LLM 都不调 |

**为什么必须有游标**——`_persist_turn` 每轮回答结束都会调 `maybe_summarize`，若无游标：
1. 每轮都把窗口外**全部**旧消息重压一遍 → 每轮白调一次 LLM，成本随会话长度线性涨；
2. 摘要被反复重写 → 每重写一次多丢一层细节，质量衰减成倍加快。

有游标后：已压过的跳过、无增量时零副作用——**同一批内容只压一次，重复调用幂等**。游标随摘要同事务写回（`db.commit()`），进程重启也不丢进度。

### 触发节奏与合并压缩（两个常见追问）

**① 是超过 20 轮后每轮都压，还是攒够增量才压？——过门槛后每轮压一次，每次压 1 轮。**
20 是开始压缩的门槛，不是攒批大小。窗口固定 6 轮，总数每 +2 条（1 轮）窗口左边界右移 2 条，而游标停在上次压缩位置——刚掉出窗口的恰好就是游标之后那 2 条：

```
40 条（20 轮）：首次触发，older = messages[0:28]  → 全量压 14 轮，游标 → #28
42 条（21 轮）：older = messages[28:30]           → 只压 #29~#30（刚出窗的 1 轮）
44 条（22 轮）：older = messages[30:32]           → 只压 1 轮
```

若"攒 20 轮再压"，中间 14 轮内容会在摘要里断档——所以天然批大小就是每轮出窗量（1 轮）。`older` 为空直接 return 的分支是防御性的（游标错位/配置变更兜底），正常时序走不到。

**② 每次压缩会带上次的 summary 一起压吗？——会，滚动合并，输出钳制 ≤1000 字。**

prompt 结构：`已有摘要（若有，请在其基础上合并更新）：{summary}` + `新增对话：{transcript}`，要求"总长不超过 1000 字"，写回时 `text[:1000]` 硬钳制。即 `新 summary = LLM(旧摘要 + 增量)` 整体覆盖，不是追加。

推论（诚实面对缺陷）：旧摘要涨满 1000 字后，每融一轮新内容，LLM 只能在 1000 字内重新分配——等于每轮挤出最旧/最不重要的要点，这是摘要"有损衰减"的具体发生机制。兜底三件套：原始消息全量在 `chat_messages` 不删、关键事实走长期记忆（mem0 每轮抽取）、近 6 轮窗口保精确近期上下文。

### 为什么这么设计（面试话术）

- 消息**全量落库**保证可回溯（前端能翻完整历史），但**注入只取窗口**，因为 LLM 上下文有限且中间内容注意力稀释（lost in the middle）；
- 摘要解决"窗口外信息彻底丢失"的问题：20 轮前的内容以压缩形式继续参与对话，token 成本可控。

## 长期记忆（跨会话）

### 写入时机：回答结束后台异步

`_persist_turn` 末尾调用 `MemoryStore.add_background(query, answer, agent_id, session_id)`（`agent.py:641`）：

- **fire-and-forget**：`asyncio.create_task` + `asyncio.to_thread`，不阻塞响应下发；无事件循环时直接跳过；
- **每轮都调用，但不是每轮都真的写入**——mem0 内部两步判决：
  1. **事实抽取**（约 1 次 LLM 调用）：从本轮问答中抽取值得记住的事实性内容；
  2. **更新判决**（约 1 次 LLM 调用）：与该智能体已有记忆比对，产出 `ADD`（新增）/ `UPDATE`（修正旧记忆）/ `DELETE`（删除过时记忆）/ `NONE`（不值得记，如寒暄）；
- 所以写入量远小于对话量，且新旧记忆冲突在写入时就被消解。

### 隔离与溯源

- 隔离维度是 `user_id = agent_id`（智能体），**不是会话**——同一智能体的所有会话共享记忆，这是"换了个会话它还记得我"的来源；
- `metadata.session_id` 仅作溯源标记，不参与隔离；
- 检索：`MemoryStore.search(query, agent_id)`，`asyncio.to_thread` 调 mem0，`filters={"user_id": agent_id}` + `top_k = MEM0_SEARCH_LIMIT`，失败降级为空列表。

### 注入时机

每轮提问时用**当前问题**做向量检索（`agent.py:685-686`），只把 top-k 相关事实拼进 prompt。**不是全量加载**——无关记忆不进上下文，效果与 token 成本都可控，记忆多了也不会劣化。

## 会话删除后记忆的处理

现状（`routers/chat.py:81-85` → `ChatService.delete`）：

- ✅ **删短期**：该会话全部 `chat_messages` + `chat_sessions`（含滚动摘要）一并删除；
- ❌ **不删长期**：长期记忆按智能体隔离、跨会话共享，删除单个会话不影响已沉淀的事实，该智能体的其他会话/新会话仍可召回——这是设计意图（记忆属于智能体而非会话）；
- 目前**没有**按会话/按智能体清理长期记忆的入口。若要支持"删会话连带清记忆"：按 `metadata.session_id` 过滤 `get_all` 拿到 memory_id 列表，逐条 `mem.delete(memory_id)` 即可（增量成本：删除接口 + 删除确认策略，如二次确认/保留天数）。

## 高频追问 Q&A

**Q：短期记忆为什么不放向量库？**
A：会话内消息是强时序、精确原文，需要"最近 N 轮"这种确定性的窗口语义，关系库按时间排序直接取即可；向量检索适合模糊语义召回，放到跨会话的长期记忆那层才发挥价值。两层各取所长。

**Q：长期记忆为什么不全量加载？全量会怎样？**
A：全量注入会撑爆上下文、增加延迟和成本，且大量无关记忆会稀释注意力反而降低回答质量。用"当前问题 → 向量检索 → top-k 相关事实"的按需召回，无论记忆积累多少，单次注入规模恒定。

**Q：每轮问答都调 mem0.add，会不会很慢/很贵？**
A：不会阻塞用户——它是回答下发后的后台异步任务（create_task），慢的是后台；成本上每次约 2 次 LLM 调用（抽取+判决），且判决为 NONE 时不产生存储写入。

**Q：新记忆和老记忆冲突怎么办？**
A：交给 mem0 的更新判决：新事实与旧记忆语义相近时判 UPDATE（合并/改写），旧记忆失效时判 DELETE，避免同一事实存多份矛盾版本。这发生在写入时，而不是检索时。

**Q：记忆在什么时候被用到？**
A：只在提问时用——短期记忆装填最近窗口+摘要，长期记忆按当前问题检索 top-k，两者拼进 system/prompt 后再调 LLM；写入路径与读取路径完全解耦。

**Q：滚动摘要的"旧摘要"怎么存的？会话一直变长，旧摘要会被丢弃吗？**
A：存在 `chat_sessions.summary`（TEXT 列）+ `summary_until_id`（幂等游标）两个字段，单字段覆盖式、无历史版本——每次新摘要 = LLM(旧摘要全文 + 新出窗轮次)，prompt 要求"在已有摘要基础上合并更新"，旧摘要通过合并存续而非被顶掉。超限处理分三层：① 正常情况 LLM 守住 1000 字约束，旧信息融入新摘要；② 兜底 `text[:1000]` 硬截断，LLM 超长时盲切尾部有小概率丢失；③ 本质上滚动摘要是有损压缩，会话无限长细节必然衰减——但原始消息全量保留在 `chat_messages`（有损只发生在注入 prompt 的浓缩视图层），且关键事实每轮已被 mem0 抽进长期记忆，检索召回不依赖摘要质量。改进方向：超限不再硬截断，改为分级摘要（久远摘要再压缩成历史要点，近期摘要保留细节）。

**Q：mem0 和自己维护一张"事实表"的取舍？**
A：mem0 白拿了抽取/去重/更新判决这套流水线和向量库适配；代价是黑盒判决不可控、依赖 openai 兼容协议的 LLM。自维护事实表可控性强但要自己解决"什么时候记、记什么、冲突怎么办"。项目当前用 mem0 + 统一门面（`MemoryStore`）封装，降级路径清晰（初始化失败/检索失败都静默降级为无记忆）。
