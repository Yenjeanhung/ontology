# 长短期记忆

> 对应代码：`backend/routers/agent.py`（`_persist_turn`、查询主链路）、`backend/services/chat_service.py`（短期记忆）、`backend/services/memory_store.py`（长期记忆门面）、`backend/config.py:144-150`（参数）。

## 总览：双层记忆架构

| 维度 | 短期记忆 | 长期记忆 |
|---|---|---|
| 范围 | 单个会话内 | 跨会话，同一「用户 × 智能体」内共享 |
| 载体 | 关系库 `chat_messages` 表 + `chat_sessions.summary` | mem0 + 向量库（Milvus，collection `agent_memories`） |
| 写入时机 | 用户消息进请求立即落库；助手消息回答流结束后落库 | 每轮问答结束后台异步触发 |
| 注入时机 | 每轮提问前装填最近 N 轮 + 摘要 | 每轮提问前向量检索 top-k 相关事实 |
| 隔离维度 | `session_id`（会话归属 `chat_sessions.user_id`） | `user:{uid}:agent:{aid}` 复合键 |
| 失败策略 | 落库失败记日志，不影响已下发回答 | 全链路 try/except，降级为"无长期记忆" |

一轮对话的完整时序（`agent.py` 查询主链路）：

```
用户提问
 ├─ 1. append_message("user", query)        ← 用户消息立即落库（短期）
 ├─ 2. load_history()                        ← 装填最近6轮+滚动摘要（短期注入）
 ├─ 3. MemoryStore.search(query)             ← 向量检索相关事实（长期注入）
 ├─ 4. 流式生成 SSE 回答给前端
 └─ 5. _persist_turn()                       ← 回答完整下发后：
       ├─ append_message("assistant")        ← 助手消息落库（短期）
       ├─ maybe_summarize()                  ← 触发滚动摘要（短期）
       └─ MemoryStore.add_background()       ← 后台异步写入（长期）
```

## 短期记忆（会话内）

### 存储与写入时机

- **用户消息**：请求一进来就落库（`agent.py:680`），即使后续生成失败也有记录。
- **助手消息**：SSE 流式回答**完整结束后**由 `_persist_turn`（`agent.py:627-643`）统一落库——因为流式过程中答案是一段段 token，只有在收尾处拼接完整。
- `_persist_turn` 自开新的 DB 会话（路由的 session 在 SSE 生成器执行时已释放），全部尽力而为，失败只记日志，不影响已下发的回答。
- 附带逻辑：首条用户消息自动截取为会话标题。

### 注入策略（`load_history`，防止上下文爆炸的核心）

> 代码位置：`backend/services/chat_service.py:120-152` `ChatService.load_history()`，查询主链路在 `backend/routers/agent.py:683` 调用（每轮提问、调 LLM 之前）。

不是把会话全部历史塞进 prompt，而是三重限制：

1. **轮数窗口**：只取最近 `CHAT_SESSION_WINDOW_TURNS = 6` 轮（一轮 = 用户一问 + 助手一答）；
2. **字符预算**：总字符超 `CHAT_SESSION_CHAR_BUDGET = 6000`（约 2k token）时从最旧开始丢弃；
3. **最新截尾**：最新一条本身超预算时截尾保留（宁可短也不丢最近上下文）。

```python
# backend/services/chat_service.py — ChatService.load_history()
async def load_history(db: AsyncSession, session_id: str) -> dict:
    """装填注入 prompt 的历史，返回 {history, summary}。"""
    session = await db.get(ChatSession, session_id)
    summary = ""
    if session and settings.CHAT_SUMMARY_ENABLED:
        summary = (session.summary or "").strip()          # 摘要注入（滚动摘要产出）

    messages = await ChatService.get_messages(db, session_id)
    window = max(0, settings.CHAT_SESSION_WINDOW_TURNS) * 2
    candidates = messages[-window:] if window > 0 else []  # ① 轮数窗口：6 轮 = 12 条

    budget = max(0, settings.CHAT_SESSION_CHAR_BUDGET)
    picked: list[dict] = []
    used = 0
    for msg in reversed(candidates):                       # ② 从最新往旧装填
        cost = len(msg.content or "")
        if used + cost > budget and picked:
            break                                          #    预算满：更旧的整条丢弃
        picked.append({"role": msg.role, "content": msg.content or ""})
        used += cost
    picked.reverse()                                       #    还原为从旧到新

    if picked and 0 < budget < len(picked[-1]["content"]):
        picked[-1]["content"] = "…" + picked[-1]["content"][-budget:]  # ③ 最新一条截尾保留

    return {"history": picked, "summary": summary}
```

参数定义在 `backend/config.py:144-150`：

```python
CHAT_SESSION_WINDOW_TURNS: int = 6     # 注入 prompt 的最近轮数（一轮 = 一问一答）
CHAT_SESSION_CHAR_BUDGET: int = 6000   # 历史注入总字符预算（约 2k token）
CHAT_SUMMARY_ENABLED: bool = True      # 超长滚动摘要总开关
CHAT_SUMMARY_TRIGGER_TURNS: int = 20   # 累计用户消息数超过该值触发滚动摘要
CHAT_SUMMARY_MAX_CHARS: int = 1000     # 滚动摘要字符上限
```

### 滚动摘要（`maybe_summarize`，超长会话的兜底）

> 代码位置：`backend/services/chat_service.py:156-213` `ChatService.maybe_summarize()`，由 `_persist_turn` 在每轮回答落库后调用（`backend/routers/agent.py:636`）。摘要存 `chat_sessions.summary`，游标存 `chat_sessions.summary_until_id`。

- 触发条件：会话累计用户消息数 > `CHAT_SUMMARY_TRIGGER_TURNS = 20` 轮；
- 做法：把**窗口外**的旧轮次与旧摘要一起交给 LLM 压缩，结果写回 `session.summary`，上限 `CHAT_SUMMARY_MAX_CHARS = 1000` 字符；
- 幂等：`summary_until_id` 记录已计入摘要的最后一条消息，重复调用不重复摘要；
- LLM 未配置或调用失败时静默跳过，不阻塞主链路。

```python
# backend/services/chat_service.py — ChatService.maybe_summarize()（节选关键段）
async def maybe_summarize(db: AsyncSession, session_id: str) -> None:
    if not settings.CHAT_SUMMARY_ENABLED:
        return
    session = await db.get(ChatSession, session_id)
    messages = await ChatService.get_messages(db, session_id)
    trigger = max(1, settings.CHAT_SUMMARY_TRIGGER_TURNS) * 2
    if len(messages) < trigger:            # ① 未到 20 轮：不压缩（短会话省一次 LLM）
        return

    window = max(0, settings.CHAT_SESSION_WINDOW_TURNS) * 2
    if session.summary_until_id:
        # ② 幂等游标：从上次已摘要消息之后，取到当前窗口左边界为止
        idx = next((i for i, m in enumerate(messages) if m.id == session.summary_until_id), -1)
        older = messages[idx + 1: len(messages) - window] if idx >= 0 else messages[: len(messages) - window]
    else:
        older = messages[: len(messages) - window]     # ③ 首次：窗口外全部旧轮次
    if not older:
        return                                          #    窗口外没有新内容：无事可做

    transcript = "\n".join(
        f"{'用户' if m.role == 'user' else '助手'}：{m.content}" for m in older
    )
    if len(transcript) > 8000:                          # ④ 待压缩文本自身超长时中段省略
        transcript = transcript[:4000] + "\n…（中间省略）…\n" + transcript[-4000:]

    prompt = (
        "请把下面这段多轮对话压缩成一份要点摘要，作为后续对话的背景知识。\n"
        "要求：只保留事实、结论、关键实体与数字；不评价、不复述原句；"
        f"总长不超过 {settings.CHAT_SUMMARY_MAX_CHARS} 字。\n\n"
        f"已有摘要（若有，请在其基础上合并更新）：\n{(session.summary or '（无）')}\n\n"
        f"新增对话：\n{transcript}"
    )
    llm = create_llm()
    if llm is None:
        return                                          # ⑤ 未配置 LLM：静默跳过
    resp = await llm.ainvoke(prompt)
    text = (getattr(resp, "content", "") or "").strip()
    if not text:
        return
    session.summary = text[: settings.CHAT_SUMMARY_MAX_CHARS]
    session.summary_until_id = older[-1].id             # ⑥ 推进幂等游标
    await db.commit()
    # 整体 try/except：失败只记日志（logger.exception），不阻塞主链路
```

### 游标机制：增量压缩与幂等（面试重点）

`summary_until_id` 本质是**压缩进度书签**（类比 Kafka 的消费 offset）：记录"已经压进摘要的最后一条消息 id"。它的作用是把窗口外的内容切成两段，每次只压增量：

```
窗口 = 6 轮 = 12 条消息。当前会话 44 条消息，游标 summary_until_id = #30：

messages:  #1 ──────── #30 │ #31 #32 │ #33 ──────── #44
           已压过（跳过）    │ 新出窗    │ 近 6 轮窗口
           游标在这 ──┘     │ =本次要压 │ 原文注入，永不去压

本次压缩范围 older = messages[游标下一条 : 总数−12] = #31~#32
压缩完成后游标推进：summary_until_id = older[-1].id = #32
```

即：**压缩范围 = 游标之后 → 窗口左边界之前**。窗口参数（6 轮）回答"注入多少原文"，游标回答"压缩从哪续"——两个是独立机制，右边界永远由窗口定，左边界由游标定。

三种情况：

| 时机 | 游标 | 本次压谁 |
|---|---|---|
| 首次触发（累计 21 轮，游标为空） | 空 | 窗口外**全部**：`messages[:len−12]` |
| 后续某轮（游标 #30，新出窗 #31~#32） | #30 | 只有 #31~#32（2 条增量） |
| 窗口外全压过、无新出窗 | — | `older` 为空 → 直接 return，LLM 都不调 |

**为什么必须有游标**——`_persist_turn` 每轮回答结束都会调 `maybe_summarize`，若无游标：
1. 每轮都把窗口外**全部**旧消息重压一遍 → 每轮白调一次 LLM，成本随会话长度线性涨；
2. 摘要被反复重写 → 每重写一次多丢一层细节，质量衰减成倍加快。

有游标后：已压过的跳过、无增量时零副作用——**同一批内容只压一次，重复调用幂等**。游标随摘要同事务写回（`db.commit()`），进程重启也不丢进度。

### 触发节奏与合并压缩（两个常见追问）

**① 是超过 20 轮后每轮都压，还是攒够增量才压？——过门槛后每轮压一次，每次压 1 轮。**
20 是开始压缩的门槛，不是攒批大小。窗口固定 6 轮，总数每 +2 条（1 轮）窗口左边界右移 2 条，而游标停在上次压缩位置——刚掉出窗口的恰好就是游标之后那 2 条：

```
40 条（20 轮）：首次触发，older = messages[0:28]  → 全量压 14 轮，游标 → #28
42 条（21 轮）：older = messages[28:30]           → 只压 #29~#30（刚出窗的 1 轮）
44 条（22 轮）：older = messages[30:32]           → 只压 1 轮
```

若"攒 20 轮再压"，中间 14 轮内容会在摘要里断档——所以天然批大小就是每轮出窗量（1 轮）。`older` 为空直接 return 的分支是防御性的（游标错位/配置变更兜底），正常时序走不到。

**② 每次压缩会带上次的 summary 一起压吗？——会，滚动合并，输出钳制 ≤1000 字。**

prompt 结构：`已有摘要（若有，请在其基础上合并更新）：{summary}` + `新增对话：{transcript}`，要求"总长不超过 1000 字"，写回时 `text[:1000]` 硬钳制。即 `新 summary = LLM(旧摘要 + 增量)` 整体覆盖，不是追加。

推论（诚实面对缺陷）：旧摘要涨满 1000 字后，每融一轮新内容，LLM 只能在 1000 字内重新分配——等于每轮挤出最旧/最不重要的要点，这是摘要"有损衰减"的具体发生机制。兜底三件套：原始消息全量在 `chat_messages` 不删、关键事实走长期记忆（mem0 每轮抽取）、近 6 轮窗口保精确近期上下文。

### 为什么这么设计（面试话术）

- 消息**全量落库**保证可回溯（前端能翻完整历史），但**注入只取窗口**，因为 LLM 上下文有限且中间内容注意力稀释（lost in the middle）；
- 摘要解决"窗口外信息彻底丢失"的问题：20 轮前的内容以压缩形式继续参与对话，token 成本可控。

## 长期记忆（跨会话）

### 写入时机：回答结束后台异步

`_persist_turn` 末尾调用 `MemoryStore.add_background(query, answer, agent_id, session_id)`（`agent.py:641`）：

- **fire-and-forget**：`asyncio.create_task` + `asyncio.to_thread`，不阻塞响应下发；无事件循环时直接跳过；
- **每轮都调用，但不是每轮都真的写入**——mem0 内部两步判决：
  1. **事实抽取**（约 1 次 LLM 调用）：从本轮问答中抽取值得记住的事实性内容；
  2. **更新判决**（约 1 次 LLM 调用）：与同命名空间（同用户同智能体）已有记忆比对，产出 `ADD`（新增）/ `UPDATE`（修正旧记忆）/ `DELETE`（删除过时记忆）/ `NONE`（不值得记，如寒暄）；
- 所以写入量远小于对话量，且新旧记忆冲突在写入时就被消解。（以上为经典两阶段口径；当前 mem0ai 2.0.20 实际为单次抽取调用，见下文"版本现实核查"）

### 写入流水线：事实抽取 + 更新判决（ADD/UPDATE/DELETE/NONE）

> 项目侧代码：`backend/services/memory_store.py:25-51`（`_FACT_EXTRACTION_PROMPT` / `_UPDATE_MEMORY_PROMPT` 两个自定义中文 prompt）、`memory_store.py:198-222`（`add_background`）。设计口径见 `doc/智能体/智能体会话_功能设计.md` 5.2 节。本节讲 **mem0 经典两阶段模型**（抽取+判决两次 LLM 调用）——mem0 论文与多数版本的实际形态、面试标准答案；**当前安装的 mem0ai 2.0.20 实际执行的管线与此不同，见下文"版本现实核查"**。

```text
SSE 回答流结束
 └─ _persist_turn()
     └─ MemoryStore.add_background(query, answer, agent_id, user_id, session_id)
         └─ asyncio.create_task + asyncio.to_thread(mem.add)   ← 后台异步，不阻塞响应
             ① 事实抽取（LLM 调用 1，_FACT_EXTRACTION_PROMPT）
                 从「用户问 + 助手答」中抽取跨会话仍成立的长期事实：
                 偏好/约定/背景/结论；单条一句话、主谓宾完整、指代词还原；
                 寒暄、临时上下文、会话内才成立的内容直接丢弃；
                 抽不出 → 空列表，本轮直接结束（连第二次 LLM 都不调）
             ② 更新判决（LLM 调用 2，_UPDATE_MEMORY_PROMPT）
                 对每条新事实，先用它向量检索本命名空间
                 （user:{uid}:agent:{aid}，写入检索同键）下语义相近的已有记忆，
                 再由 LLM 逐条比对，产出操作序列：ADD / UPDATE / DELETE / NONE
             ③ 按判决结果落 Milvus（agent_memories collection）
```

四种判决的含义与存储动作：

| 判决 | 触发条件 | 存储动作 |
|---|---|---|
| ADD | 全新事实，库里没有相近记忆 | embed 后插入 Milvus |
| UPDATE | 与某条旧记忆**同主体、内容有变化** | 用合并后的完整新表述替换旧条（删旧向量、写新向量） |
| DELETE | 与某条旧记忆**直接矛盾**，以新事实为准 | 删除旧记忆向量 |
| NONE | 与旧记忆重复，或无信息量 | 不做任何写入 |

**判决代码在哪**（冲突消解的执行体在 mem0 包内，项目侧只提供入口与自定义 prompt）：

- 判决 prompt 组装：mem0 包 `configs/prompts.py:406` `get_update_memory_messages()`——把"现有记忆 + 新抽取事实"拼进判决 prompt；默认英文判决 prompt `DEFAULT_UPDATE_MEMORY_PROMPT` 在同文件 176 行；
- 判决执行与存储分发：mem0 包 `memory/main.py`——`_create_memory()`（:1961，ADD：embed 后插入向量库）、`_update_memory()`（:2038，UPDATE：删旧向量写新向量）、`delete()`（:1869，DELETE：删旧记忆）；
- 项目侧入口：`memory_store.py:198-222` `add_background()`（后台调 `mem.add`）；自定义判决 prompt：`memory_store.py:38-51` `_UPDATE_MEMORY_PROMPT`（ADD/UPDATE/DELETE/NONE 四分类的中文定义就在这段 prompt 里）。

跨会话示例（同一命名空间）：

- 旧记忆"用户偏好轻量部署" → 新事实"已改用 K8s 集群部署"：同主体内容变化 → **UPDATE**；
- 旧记忆"用户不用 Docker" → 新事实"我们的服务全跑在 Docker 里"：直接矛盾 → **DELETE**（新的赢）；
- 用户说"谢谢你，明白了"：抽不出事实，或与已有记忆重复 → **NONE**，零写入。

三个设计点（面试话术）：

1. **冲突消解发生在写入时，不是检索时**——同一事实永远只存一份不矛盾的版本；检索端只管 top-k 语义召回，无需再做裁决。附带收益：记忆条目数不随对话轮数线性膨胀，同类信息反复出现只会 UPDATE 一条而不是插 N 条。
2. **写入量远小于对话量**——每轮都调 `add`，但寒暄/重复/临时内容都判 NONE 不落库，Milvus 里沉淀的都是高信息密度事实。
3. **异步 + 全链路降级**——2 次 LLM 调用有延迟和成本，但在 `create_task` 后台跑，用户早已拿到回答；失败只记日志，降级为"无长期记忆"，绝不影响主链路。

诚实面对缺陷——判决不是 100% 可靠：

- 判决的前提是**向量检索能召回语义相近的旧记忆**：若旧记忆 embedding 相似度低没进候选，LLM 无从比对，可能把变体事实误判为 ADD，库中残留两半截矛盾版本；
- 判决本身是 LLM 语义判断，存在误判（该 UPDATE 的判 ADD、该 DELETE 的判 NONE 等），且 prompt 黑盒不可控；
- 兜底在检索端：即使漏网，检索注入 prompt 后，生成 LLM 面对两条矛盾事实会自行取舍——**冲突消解有两道防线：写入时消解为主，prompt 层兜底**；
- mem0 的 `history_db_path`（SQLite）记录每次 ADD/UPDATE/DELETE 事件流水，记忆变更可审计、可回溯。

### 存储形态：存的是"事实原子"，不是压缩摘要（"也是 LLM 压缩吗"标准答案）

> 面试官问"长期记忆也是用 LLM 压缩吗"，是在试探你分不分得清两种 LLM 加工——答"是压缩"就把短期摘要和长期记忆混为一谈了。

**Milvus 里的一条记忆长这样**（`agent_memories` collection，schema 实测：id / vectors / metadata / text / sparse）：

| 字段 | 内容 | 谁生产 |
|---|---|---|
| text | 事实原文，一句话（如"用户负责签派放行室的复核放行职责"） | **LLM 抽取** |
| vectors | 事实文本的 embedding 向量 | **embedding 模型（非 LLM）** |
| metadata | 命名空间（user_id/agent_id）等隔离与溯源字段 | 代码写入 |

**"LLM 加工" ≠ "压缩"，两者目的相反**：

| | 压缩（短期摘要） | 抽取（长期记忆） |
|---|---|---|
| 输入→输出 | 一大段对话 → 一小段摘要 | 一轮问答 → N 条原子事实 |
| 信息量 | 有损（主动丢弃细节） | 保真改写（不丢内容，只改形态） |
| 粒度 | 粗（一段话） | 细（一事一条） |
| 服务对象 | 上下文预算（给 LLM 读） | 向量检索命中率（给 embedding"读"） |

**为什么必须原子化——向量检索的命中率取决于条目粒度**：

向量检索是"整条 embedding vs 查询 embedding"算相似度。把整轮问答存成一条，向量语义被问答双方稀释，用户之后问"我在哪个部门"根本命中不了；抽成"用户是签派放行室的放行控制岗"独立一条，查询向量与它直接对齐，top-k 才召回得准。反过来说这也是摘要不能当长期记忆用的原因：**压在一起的事实无法被单独召回**。

**流程串起来**：LLM 抽取事实（保真改写，事实抽取这步两个 mem0 版本都在）→ embedding 模型向量化（LLM 不参与这步）→ text + vector + metadata 一行写入 Milvus、命名空间隔离；判决/去重在写入管线里先走完，寒暄重复不落库——向量库里沉淀的都是高信息密度事实，条目数远小于对话轮数。

一句话：**短期摘要是"有损压缩、给 LLM 读"；长期记忆是"保真改写、给检索读"——都用了 LLM，但一个为了少装，一个为了找得到。**

### 版本现实核查：mem0ai 2.0.20 实际执行的是 V3 管线（诚实面对）

`requirements.txt` 只约束 `mem0ai>=0.1.0`，当前实际安装 **2.0.20**（`D:\installedSoftware\Python3129\Lib\site-packages\mem0`）。读包源码确认：经典"两次调用 + 四判决"管线在该版本已被 **V3 分阶段批处理管线**取代（`memory/main.py:879` `_add_to_vector_store`）：

| | 经典两阶段模型（mem0 论文/多数版本，面试标准答案） | 2.0.20 V3 管线（当前实际运行） |
|---|---|---|
| LLM 调用 | 2 次：抽取 → 判决 | **1 次**：`ADDITIVE_EXTRACTION_PROMPT`（`configs/prompts.py:468`）把 top-10 相似旧记忆一并喂入（`main.py:926-962`），抽取时直接语义去重——"新信息与已有记忆语义等价就跳过" |
| 判决 | LLM 产出 ADD/UPDATE/DELETE/NONE | 无独立判决调用；精确重复由 MD5 哈希去重兜底（`main.py:1020-1024`） |
| 事件 | ADD / UPDATE / DELETE / NONE | 全部是 ADD（`main.py:1070`）；与旧记忆相关则打 `linked_memory_ids` 关联标（`prompts.py:513`），**矛盾旧记忆不会被改写/删除，新旧叠加** |
| 成本 | 每轮 ≈2 次 LLM | 每轮 ≈1 次 LLM |

对项目侧的后果：

1. `memory_store.py` 传给 mem0 的 `custom_fact_extraction_prompt` / `custom_update_memory_prompt` 在 2.0.20 是**死配置**——两个键在全包中无任何调用方，静默忽略；当前抽取/去重质量完全由默认英文 prompt 决定，我们调优的中文 prompt 并未生效；
2. "写入时冲突消解"在当前版本实际弱化为"写入时去重"：UPDATE/DELETE 不再发生，矛盾事实的消解退到 prompt 层兜底——上文"两道防线"当前只剩一道硬的；
3. 可选处置：① 升级/更换到保留经典判决管线的 mem0ai 版本（需同步回退 `MemoryStore` 适配层——2.0.x 的 `search(filters/top_k)` 与旧版签名不同）；② 保持 2.0.20（省一半 LLM 调用，接受叠加式记忆 + 关联标记）；③ 在 `MemoryStore` 自研判决层补回 UPDATE/DELETE（加锁可自己掌控）。
4. **面试策略：按经典模型答概念（四判决是 mem0 的标志性设计），被追问实现细节时主动说明版本差异——这是加分项，暴露"读过装到本地那份源码"。**

### 隔离与溯源（双层隔离）

- 记忆按「用户 × 智能体」复合键隔离：mem0 只有一个 user_id 隔离维度，把它编码成
  `user:{uid}:agent:{aid}` 命名空间（`memory_store._namespace`）——写入和检索用同一个键，
  不同用户与同一智能体的记忆互不可见；同一用户同一智能体的所有会话共享记忆
  （"换了个会话它还记得我"仍然成立，但只认主人）；
- **公共知识不进记忆**：产品事实、业务流程等公共内容走知识库 KB/RAG 检索（可运营、可更新、
  全员共享），mem0 只承载个人记忆（偏好、个人信息、跨会话结论）——语义分工：公共知识归 KB，
  个人记忆归 mem0；
- user_id 来源：问答接口 `Depends(get_current_user_id)` 从登录态取（系统 RBAC），
  会话创建时同步写 `chat_sessions.user_id`（短期记忆归属也可审计）；
- `metadata.session_id` 仅作溯源标记，不参与隔离；
- 检索：`MemoryStore.search(query, agent_id, user_id)`，`asyncio.to_thread` 调 mem0，
  `filters={"user_id": 复合键}` + `top_k = MEM0_SEARCH_LIMIT`，失败降级为空列表；
- 存量迁移：早期只有 agent_id 单层隔离，多用户下 A 说的偏好会被召回进 B 的对话
  （隐私泄露 + 回答污染）；存量数据用 `scripts/migrate_mem0_namespace.py` 一次性归入
  admin——pymilvus 读全量行改 user_id 字段后 upsert 回写，向量原样保留不重抽，幂等可重跑。

### 注入时机

每轮提问时用**当前问题**做向量检索（`agent.py:685-686`），只把 top-k 相关事实拼进 prompt。**不是全量加载**——无关记忆不进上下文，效果与 token 成本都可控，记忆多了也不会劣化。

## 会话删除后记忆的处理

现状（`routers/chat.py:81-85` → `ChatService.delete`）：

- ✅ **删短期**：该会话全部 `chat_messages` + `chat_sessions`（含滚动摘要）一并删除；
- ❌ **不删长期**：长期记忆按「用户 × 智能体」复合键隔离、跨会话共享，删除单个会话不影响已沉淀的事实，同一用户同一智能体的其他会话/新会话仍可召回——这是设计意图（记忆属于"用户×智能体"而非会话）；
- 目前**没有**按会话/按智能体清理长期记忆的入口。若要支持"删会话连带清记忆"：按 `metadata.session_id` 过滤 `get_all` 拿到 memory_id 列表，逐条 `mem.delete(memory_id)` 即可（增量成本：删除接口 + 删除确认策略，如二次确认/保留天数）。

## 长尾 bad case 与治理（面试重点：暴露真实踩坑 + 设计权衡）

> 面试官问法："召回了不相关的历史怎么办？压缩把重要信息抹了怎么办？"——考的不是"有没有 bug"，是**有没有真用过、错误有没有边界、能不能讲出发生机制**。

### Case 1：召回不相关（三类，全部真实发生）

**① 命名空间串用户（真踩过的坑，最值得讲）**
早期长期记忆命名空间只有 `agent_id` 单层，多用户下 A 的偏好事实被向量检索召进 B 的对话——既是隐私泄露又是回答污染。B 问"告警怎么处置"，prompt 里带着 A 的个人偏好，回答被带偏。
修复：`user:{uid}:agent:{aid}` 复合键隔离，写入和检索同一把键；存量记忆用 `scripts/migrate_mem0_namespace.py` 脚本迁移归位（pymilvus 改 metadata.user_id，向量原样保留不重抽，幂等可重跑）。

**② 矛盾记忆并存（版本现实引入的）**
mem0ai 2.0.20 把经典 UPDATE/DELETE 判决合并成"矛盾叠加+关联标记"——同主体新旧两条记忆都在库里。检索时可能同时召回新旧两版（比如用户改了流程/偏好），回答新旧混杂。
兜底：两条都进 prompt，生成 LLM 现场取舍（写入时消解弱化后，prompt 层是最后防线）；写入侧仍有 MD5 哈希精确去重挡住完全重复。改进方向：召回加时间戳、新者优先，或在 MemoryStore 层自研回 UPDATE/DELETE 判决。

**③ 公共知识被"记忆化"**
某次问答里的通用处置流程被 mem0 当"事实"抽进个人记忆；之后知识库里的公共知识更新了，旧的个人记忆还在召回路径上误导。
治理是分工：**公共知识只走 KB/RAG 检索（永远最新），mem0 只存个人事实**（偏好/个人信息/跨会话结论）——写入侧的抽取 prompt 已按这个口径约束。

### Case 2：压缩抹掉重要信息（机制明确，损失有边界）

**发生机制（能指到代码）**：
- 滚动摘要硬钳制 1000 字（`CHAT_SUMMARY_MAX_CHARS`），涨满后每融一轮新内容，LLM 只能在 1000 字内重新分配——等于**每轮挤出最旧/最不重要的要点**（"有损衰减"的具体机制）；
- LLM 摘要天然爱抽象化：**数字、专名、时间条件**最容易被泛化抹掉（"备降油量标准"压成"有相关规定"）；
- 摘要是 LLM 的一次主观判断——它判"不重要"≠对用户不重要，且错了用户无感知。

**三层兜底：让抹掉可控、可恢复**
| 兜底层 | 作用 |
|---|---|
| 原始消息全量落库（`chat_messages` 永不删） | 压缩**只作用于注入层，不作用于存储层**——历史可回溯，摘要随时可用原文重建 |
| 关键事实走长期记忆（mem0 每轮异步抽取事实原子） | 重要信息**不依赖摘要存活**，跨会话也有独立载体 |
| 近 6 轮窗口永远注入原文 | 用户正在聊的（最重要的）近期上下文零损失 |

一句话：摘要是**缓存不是存储**，抹掉的是缓存里的表示，不是事实本身。

### 追问：怎么进一步优化（加分项）

- **记忆条目带时间戳/置信度**，召回时新者优先、低置信度降权；
- **显式强写入通道**：用户说"记住 X"时不走抽取判决，直接确定写入并标记高置信；
- **摘要实体对齐校验**：压完摘要后用正则/NER 比对原文，数字/专名丢了就补回（结构化字段规则先行，见冲突消解一节的混合判决思路）；
- **召回阈值硬闸**：相似度低于阈值不进 prompt，宁缺勿滥。

### 面试话术（60 秒版）

"遇到过，两类都有真实案例。召回不相关最典型的是早期命名空间只有智能体维度，A 的偏好被召回进 B 的对话，后来改成用户×智能体复合键隔离加存量迁移；另外实际装的 mem0 2.0 把改写判决合并成了矛盾叠加，新旧记忆并存，我们靠 prompt 层让模型现场取舍。压缩抹信息是滚动摘要 1000 字钳制的有损衰减，数字专名最容易被抹——我们的设计是压缩只作用于注入层，存储层全量可回溯，关键事实走长期记忆不依赖摘要存活，近期上下文永远原文。所以我们的思路不是保证不出错，而是让每个错误都有边界、有兜底、可恢复。"

## 高频追问 Q&A

**Q：短期记忆为什么不放向量库？**
A：会话内消息是强时序、精确原文，需要"最近 N 轮"这种确定性的窗口语义，关系库按时间排序直接取即可；向量检索适合模糊语义召回，放到跨会话的长期记忆那层才发挥价值。两层各取所长。

**Q：长期记忆为什么不全量加载？全量会怎样？**
A：全量注入会撑爆上下文、增加延迟和成本，且大量无关记忆会稀释注意力反而降低回答质量。用"当前问题 → 向量检索 → top-k 相关事实"的按需召回，无论记忆积累多少，单次注入规模恒定。

**Q：每轮问答都调 mem0.add，会不会很慢/很贵？**
A：不会阻塞用户——它是回答下发后的后台异步任务（create_task），慢的是后台；成本上经典两阶段模型约 2 次 LLM 调用（抽取+判决，判决为 NONE 时不产生存储写入），当前安装的 2.0.20 已合并为单次抽取调用（见"版本现实核查"），更省。

**Q：新记忆和老记忆冲突怎么办？（这就是记忆的冲突消解吗？）**
A：是的，就是写入时的更新判决（ADD/UPDATE/DELETE/NONE，详见上文"写入流水线"一节）：新事实先向量检索本命名空间语义相近的旧记忆，LLM 逐条比对——全新 ADD；同主体有变化 UPDATE（合并改写替换旧条）；直接矛盾 DELETE（以新为准删旧条）；重复/无价值 NONE 不写。冲突消解按时机分"写入时消解"与"读取时消解"两种范式，项目选前者：库里永远只留一份不矛盾版本，检索端只管 top-k 召回不再裁决。漏判兜底：判决依赖向量检索召回相近旧记忆，漏召回会误判 ADD——此时矛盾两条都进 prompt，由生成 LLM 自行取舍。即写入时消解为主、prompt 层兜底，两道防线。版本注：四判决是 mem0 经典判决模型；实际安装的 2.0.20 已把判决折叠进单次抽取调用+哈希去重——UPDATE/DELETE 不再发生，消解弱化为去重（详见"版本现实核查"）。

**Q：记忆在什么时候被用到？**
A：只在提问时用——短期记忆装填最近窗口+摘要，长期记忆按当前问题检索 top-k，两者拼进 system/prompt 后再调 LLM；写入路径与读取路径完全解耦。

**Q：滚动摘要的"旧摘要"怎么存的？会话一直变长，旧摘要会被丢弃吗？**
A：存在 `chat_sessions.summary`（TEXT 列）+ `summary_until_id`（幂等游标）两个字段，单字段覆盖式、无历史版本——每次新摘要 = LLM(旧摘要全文 + 新出窗轮次)，prompt 要求"在已有摘要基础上合并更新"，旧摘要通过合并存续而非被顶掉。超限处理分三层：① 正常情况 LLM 守住 1000 字约束，旧信息融入新摘要；② 兜底 `text[:1000]` 硬截断，LLM 超长时盲切尾部有小概率丢失；③ 本质上滚动摘要是有损压缩，会话无限长细节必然衰减——但原始消息全量保留在 `chat_messages`（有损只发生在注入 prompt 的浓缩视图层），且关键事实每轮已被 mem0 抽进长期记忆，检索召回不依赖摘要质量。改进方向：超限不再硬截断，改为分级摘要（久远摘要再压缩成历史要点，近期摘要保留细节）。

**Q：记忆怎么隔离的？多用户下会不会互相看到？**
A：双层键隔离——mem0 的 user_id 维度编码为 `user:{uid}:agent:{aid}`，写入与检索同键，不同用户对同一智能体的记忆互不可见；短期记忆按 session 隔离且会话记录归属用户。公共知识（产品事实/业务流程）不进 mem0，走 KB 检索全员共享。踩坑复盘：早期只按 agent_id 单层隔离，A 说的"我对花生过敏"会被召回进 B 的 prompt——隐私泄露+回答污染；补 user 层后存量数据一次性迁移归 admin（改 user_id 字段、向量不动）。

**Q：mem0 和自己维护一张"事实表"的取舍？**
A：mem0 白拿了抽取/去重/更新判决这套流水线和向量库适配；代价是黑盒判决不可控、依赖 openai 兼容协议的 LLM。自维护事实表可控性强但要自己解决"什么时候记、记什么、冲突怎么办"。项目当前用 mem0 + 统一门面（`MemoryStore`）封装，降级路径清晰（初始化失败/检索失败都静默降级为无记忆）。
