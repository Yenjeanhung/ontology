# 记忆
## 长短期记忆怎么存的
我的项目里分两层，一轮问答的处理流程是：
① 用户提问进来，用户消息立即落库。短期记忆两张表：
    chat_messages 全量存消息（session_id/role/content/meta/created_at，挂 session_id 索引），
    chat_sessions 存会话级字段（title/summary 滚动摘要/summary_until_id 压缩游标，
    摘要与会话 1:1，放主表省 join）
② 注入（提问时，三块拼装；只有摘要是压缩产物，其余都是原文）：
    · 近 6 轮原文：load_history 装填，总字符预算 6000，超了从最旧丢，
        最新一条自己超预算就截尾保尾
    · 长期记忆事实：用当前问题做向量检索，取 top-k 条事实原文——
        不压缩、不全量加载，无关记忆不进 prompt
    · 旧摘要：session.summary（窗口外旧轮次的压缩产物）
    组装：长期记忆事实 + 摘要拼进 system prompt 作背景知识，
    近 6 轮作消息历史，当前问题放最后
③ SSE 回答流结束后收尾（_persist_turn）：助手消息落库；
    若会话累计超 20 轮，把窗口外旧内容用 LLM 压缩进 summary（≤1000 字）。
    summary_until_id 是压缩进度书签：每轮收尾都会调压缩，但有书签在，
    已压过的跳过、每次只压新出窗的增量——重复调用不重复压缩（幂等）
    追问点1——20 是门槛不是批大小：过 20 轮后每新增一轮就压一次，
    每次只压刚掉出窗口的那 1 轮（窗口右移量 = 游标之后的新增量）；
    追问点2——压缩是滚动合并不是追加：新 summary = LLM(旧摘要全文 + 增量)
    整体覆盖、硬钳制 1000 字，摘要永不超长；涨满后每轮挤占旧要点
    （有损衰减），靠消息全量在库 + 长期记忆兜底
④ 同一个收尾里，把本轮问答对交给 mem0 后台异步写长期记忆（create_task 不阻塞响应）：
    mem0 先用 LLM 抽取事实，再与该命名空间已有记忆比对做 ADD/UPDATE/DELETE/NONE 判决：
    ADD=全新事实入库；UPDATE=同主体有变化，合并改写替换旧条；DELETE=直接矛盾以新为准删旧条；
    NONE=重复/无价值不写。判决即写入时冲突消解，同一事实只留一份不矛盾版本——
    写入 Milvus（agent_memories），按「用户×智能体」复合键隔离
    追问点1——判决代码在 mem0 包内（configs/prompts.py 组装判决 prompt + memory/main.py
    按判决分发增删改），项目侧只提供入口和自定义中文 prompt
    追问点2——实际装的 mem0ai 2.0.20 已把判决折叠进单次抽取调用+MD5 哈希去重
    （UPDATE/DELETE 不再发生，矛盾叠加+linked_memory_ids 关联标记），
    自定义判决 prompt 在该版本暂不生效——面试按经典模型答概念，追问时主动讲版本差异
删会话只删短期（messages + summary），长期记忆属智能体不随会话删。
    （详细见：长短期记忆.md）


## 记忆是如何隔离的
三层各管各的：
· 短期记忆按 session_id 隔离——会话即上下文边界，会话创建时记录归属用户
    （chat_sessions.user_id，问答接口从登录态取）
· 长期记忆按「用户 × 智能体」复合键隔离：mem0 只有一个 user_id 隔离维度，
    把两者编码成 user:{uid}:agent:{aid} 做命名空间——写入和检索用同一个键，
    不同用户与同一智能体的记忆互不可见
· 公共知识不进记忆：走知识库 KB/RAG 检索，mem0 只存个人记忆
    （偏好/个人信息/跨会话结论）——分工：公共知识归 KB，个人记忆归 mem0
踩坑：早期只有 agent_id 单层，多用户下 A 说的偏好会被召回进 B 的对话
（隐私泄露+回答污染）；补 user 层后存量数据用脚本一次性迁移归 admin
（pymilvus 改 user_id 字段，向量原样保留不重抽）

## 冲突消解
就是长期记忆写入时的"更新判决"（ADD/UPDATE/DELETE/NONE，见上 ④）：
新事实先向量检索本命名空间语义相近的旧记忆，LLM 逐条比对——
全新 ADD；同主体有变化 UPDATE（合并改写替换旧条）；直接矛盾 DELETE（以新为准）；
重复/无信息量 NONE 不写。按发生时机分两派：写入时消解 vs 读取时消解，项目选前者——
库里永远只留一份不矛盾版本，检索端只管 top-k 召回不再裁决，
还防了记忆条目随轮数膨胀（同类信息反复出现只 UPDATE 一条，不插 N 条）。
兜底：判决依赖向量检索召回相近旧记忆，漏召回会误判 ADD——此时矛盾两条
都进 prompt，由生成 LLM 自行取舍。两道防线：写入时消解为主，prompt 层兜底。
版本注：四判决是 mem0 经典模型；实际装的 2.0.20 已合并为单次抽取调用+哈希
去重，UPDATE/DELETE 不再发生——消解弱化为去重，兜底靠 prompt 层。
术语注：第四种操作论文里叫 NOOP（arXiv 2504.19413 §2.1/Algorithm 1，"No operation performed"），
代码 prompt 里叫 NONE（GitHub prompts.py 的 DEFAULT_UPDATE_MEMORY_PROMPT："NONE: Make no change"，
输出注释 Must be ADD/UPDATE/DELETE/NONE）——同一语义两个名字，论文与代码没统一；
论文解读类文章（知乎等）按论文写 NOOP，项目自定义 prompt 跟代码口径用 NONE。
面试说 NONE（与项目代码一致），被论文派追问就点破这个差异——论文+源码都读过，是加分点。
追问——冲突消解全靠提示词吗？不是，链路三段式，只有中段是提示词：
| 环节 | 靠什么 | 说明 |
|---|---|---|
| ① 检索闸门 | 代码·向量检索 top-k | 圈定 LLM 可见的旧记忆候选；漏召回→无从比对→误判 ADD |
| ② 语义判决 | 提示词·LLM | 判同主体/矛盾/重复——唯一"软"环节，只影响"判得准不准" |
| ③ 执行落库 | 代码·确定性增删改 | LLM 只输出 JSON 决策，删旧写新由 mem0 代码执行 |

另有两道纯代码硬闸：MD5 哈希精确去重、序号→UUID 映射防幻觉（LLM 编不出不存在的记忆 ID）。
版本现实：2.0.20 里项目自定义判决 prompt 是死配置（全包无调用方），实际生效
≈默认英文抽取 prompt+MD5 哈希——当前状态反而接近"全靠默认提示词+一个哈希兜底"，要主动说破。
降 prompt 依赖的思路（规则+语义混合判决，加分）：相似度阈值硬闸（低分不进判决直接 ADD）、
实体对齐强制候选（缓解漏召回）、结构化字段（日期/金额/版本号）正则先行、
同主体冲突时间戳新者胜；prompt 层兜底不变。
（详细见：长短期记忆.md）

## 遇到过哪些 bad case（召回不相关 / 压缩抹信息）
遇到过，都有真实案例。我的思路不是"保证不发生"，而是让错误有边界、可恢复。
· 召回不相关——三个真实 case：
    ①命名空间串用户（真踩坑）：早期长期记忆只有 agent_id 单层，A 的偏好被召回进
        B 的对话（隐私泄露+回答污染）；改成「用户×智能体」复合键隔离+存量脚本迁移
    ②矛盾记忆并存：实际装的 mem0 2.0 把 UPDATE/DELETE 判决合并成"矛盾叠加"，
        新旧两条记忆都在库里，检索可能同时召回——兜底：两条都进 prompt，
        生成 LLM 现场取舍（写入侧消解弱化后的防线）
    ③公共知识被"记忆化"：某次问答里的通用流程被抽成个人记忆，之后公共知识
        已更新但旧记忆还在误导——分工治理：公共知识只走 KB/RAG，mem0 只存个人事实
· 压缩抹信息——机制明确，设计上有兜底：
    滚动摘要 1000 字硬钳制，涨满后每融一轮新内容就挤出旧要点（有损衰减的具体机制）；
    且 LLM 摘要爱抽象化，数字/专名/时间最容易被抹掉；"摘要判不重要"≠对用户不重要。
    三层兜底让损失可控可恢复：
    ①压缩只作用于注入层——原始消息全量落库永不删，可回溯、摘要可重建
    ②关键事实走长期记忆——mem0 每轮异步抽取事实原子，重要信息不依赖摘要存活
    ③近 6 轮窗口永远原文——最重要的近期上下文零损失
· 追问——怎么进一步优化（加分）：记忆条目带时间戳/置信度、新者优先；
    用户显式说"记住X"走强写入通道；摘要前后做关键实体对齐校验（数字专名丢了补回）；
    召回加相似度阈值硬闸，低分不进 prompt
（详细见：长短期记忆.md）

## 长期记忆怎么写入向量库的（也是LLM压缩吗）
LLM 加工了，但不是"压缩"，是"抽取"——存进去的不是对话的压缩版，是离散的事实原子。
· 流程：本轮问答对 → LLM 抽取跨会话仍成立的事实（一条一句话、第三人称、
    主谓宾完整、指代还原，如"用户负责签派放行室的复核放行职责"）
    → embedding 模型向量化 → 事实原文+向量+命名空间 metadata 一行写入 Milvus
· 为什么不是压缩：压缩面向省上下文预算（短期摘要干的事），抽取面向检索可命中。
    向量检索命中率取决于条目粒度——整轮问答拿去 embedding，语义被稀释，
    之后问"用户在哪个部门"根本命中不了；一事一条的原子事实才能被精确召回。
    这也是为什么摘要不能当记忆用：压在一起的事实无法被单独召回
· 向量化这步不是 LLM：LLM 只管抽取事实，embedding 用专门的向量化模型，各干各的
· 判决也在写入管线里先走完（抽取+去重，见「mem0记忆更新方式」）——
    寒暄/重复不落库，向量库里沉淀的都是高信息密度事实，条目数远小于对话轮数
· 一句话对比：短期摘要是"有损压缩、给 LLM 读"；长期记忆是"保真改写、给检索读"
（详细见：长短期记忆.md）

## mem0记忆更新方式
两个入口：写入时更新（入库时 LLM 判决增删改）和读取时更新（查出来再现场裁决），
本项目选写入时。
① 关键就一条：不堵塞回答——写入时更新的开销是抽取+判决那 1~2 次 LLM 调用，
   发生在 add() 里，而 add() 是回答下发之后 create_task 后台异步跑的，
   用户早就拿到回答了，多贵多慢都无感
② 读取时更新反过来：把裁决塞进每次提问的必经之路，检索完还得先去重、裁矛盾
   才能拼 prompt，SSE 首字延迟直接受影响——贵的环节放错了地方
③ 附带好处：库始终只有一份不矛盾版本，检索只管 top-k 召回，不用每次读都裁决
④ 代价：判错会固化（漏召回就误判 ADD），所以生成时 prompt 层再兜一道
（详细见：长短期记忆.md）

# 多智能体
## 多智能体设计模式有哪些
常见模式（行业叫法）：

- **编排者-执行者**（Orchestrator-Workers，即主子 Agent / Supervisor）
- **流水线**（Pipeline / Sequential Handoff，角色按 SOP 顺序传递中间产物）
- **黑板**（Blackboard，各智能体读写同一块共享状态，互不直接通信）
- **评审-优化**（Evaluator-Optimizer / Reflection，生成者与评审者迭代改进）
- **辩论**（Multi-Agent Debate，多智能体对抗、裁判裁决）
- **群聊**（Group Chat，共享对话历史轮流发言，AutoGen GroupChat）

本项目 = **编排者-执行者 + 黑板 + 评审**的组合（LangGraph 实现）：

1. **Planner（编排者）**：LLM 把任务动态分解成 2~4 个并行子任务，15s 超时回落默认分解；
2. **执行者（并行）**：Retriever（知识库取证）/ Worker（纯模型执行）/ GraphAgent（图谱事实）同一 superstep 自动并行——选了 Retriever 走 RAG，没选就纯模型执行；
3. **Critic（评审，可选组合）**：先确定性硬规则裁定（0 素材不出成果、<3 条建议人工，可复现），LLM 只解释不裁决；未选 Critic 时并行节点直通 Synthesizer；
4. **Synthesizer（合成，必在）**：汇总黑板素材流式交付。

组合由用户自由勾选、流水线动态装配，对标 AutoGen/CrewAI（角色组合+共享状态）、MetaGPT（流水线 SOP）、Magentic-One（编排者）。
追问——为什么不上群聊/辩论：token 随轮数平方涨、发言顺序不可控；一次性交付任务用流水线+黑板更可控、可审计、每条产出可追溯。
（详细见：多智能体.md）

## 多智能体之间如何传递消息
业界三条路：

- **点对点直传**：A 把结果作为消息发给 B（AutoGen send/receive、Handoff 移交）；
- **共享黑板**：各智能体读写同一块共享状态（Blackboard）；
- **消息队列/事件总线**：异步解耦，跨进程/跨服务时用。

本项目以**黑板模式**为主：

1. **共享 state 黑板**：Retriever 写证据卡、GraphAgent 写事实卡、Critic 读了写裁定、Synthesizer 读了出结论——下游不认识上游，只认卡片格式，加节点不用改别人；
2. **并行写冲突用 reducer 消解**：多个并行节点写同一 evidence 键，声明合并函数按 domain 自动归并，不覆盖、不丢数据；
3. **消息是结构化卡片不是裸文本**：带来源/等级/相似度（知识库原文/模型生成/图谱事实），机器可校验、引用可追溯，防幻觉当素材传；
4. **传递时瘦身**：给 Synthesizer 的是截断 160 字的摘要卡 JSON，不是全文——防上下文爆炸；
5. **另有一条“对人”的通道**：节点 emit 事件 → asyncio.Queue → SSE 推前端（过程可视化），和 agent 间通信是两条通道，分开的。

追问——为什么选黑板不选点对点：解耦（成员互不引用）、可追溯（每条产出留卡）、天然支持并行；代价是状态膨胀，靠卡片截断+下游只取需要的键来控。
追问——单节点挂了：每层降级（Planner 超时回落规则分解、Retriever 逐库跳过、Synthesizer 模板兜底），任何一层挂都不中断流水线。
（详细见：多智能体.md）

## 用多智能体和用一个智能体使用skill完成任务区别
本质：单智能体+skill 是**一个 LLM 循环"换着工具用"**；多智能体是**多个 LLM 实例，各带独立上下文和职责**——skill 是"手"，agent 是"脑"。
三条核心差异：
① 上下文隔离（最本质）：单智能体所有工具的中间结果挤同一个上下文窗口——检索原始数据
    越堆越多，注意力稀释、窗口迟早爆；多智能体各 Agent 独立窗口，只有提炼后的结论进下游
    ——我项目里 Retriever/GraphAgent 各查各的，中间过程互不污染
② 专业化：单智能体一套 prompt 硬扛全流程；多智能体每个角色独立 prompt/模型/校验规则
    ——Critic 的"素材充足性裁定"独立成型，不会淹没在主 prompt 里被忽略
③ 失败域与可观测：多智能体重试粒度清晰——Critic 打回能指定哪个 Agent 补查，
    LangSmith 里每个 Agent 是独立子树好归因；单智能体出错往往只能整体重来
代价（主动说才显得客观）：token 高 3~10 倍（每个 Agent 都是完整 LLM 会话）、
    协调复杂（拆解错误/结论冲突/循环打回，靠 Critic+最大轮数防）、
    协调本身有开销——简单任务多智能体反而更慢更贵
选型结论：上下文装得下、工具少于十几个、无需并行 → 单智能体+工具永远更简单更便宜；
    需要异构源并行汇聚（我项目：向量+图谱+台账三路并行）、独立质检仲裁（Critic）、
    环节专业化时才值得上多智能体——告警研判天然是"三路检索并行+汇总成文+证据仲裁"，
    这是单智能体串行工具调用给不了的效率和质量结构
（详细见：多智能体.md）


# Agent 评测
## langSmith 接入及功能

**定位一句话**：LangSmith 是 LangChain 家的可观测/评测平台，我项目当前用的是它的 **tracing（链路追踪）**——多智能体每次运行自动上报一条完整 Trace，用来定位慢环节、核对各阶段输入输出、排查产出质量。

**接入方式（零侵入）**：业务代码一行没写。langsmith SDK 走 langchain-core 原生回调体系自动上报，我只做了两件事：requirements 引入 `langsmith`；config.py 加三个配置（`LANGSMITH_TRACING` 总开关 / `LANGSMITH_API_KEY` / `LANGSMITH_PROJECT=ontology-multi-agent`），并在 Settings 读完后统一注入进程环境变量（langchain-core 运行时按 LANGSMITH_* 环境变量决定是否上报，Settings 是唯一事实源）。.env 设 true 即开启，关掉或没 Key 静默跳过，不影响本地运行。

**一条 Trace 能看到什么**（多智能体一次运行 = 一条 Trace）：

1. **瀑布图**：LangGraph 根节点 = 总耗时，其下按执行顺序展开 planner → data_agent / graph_agent / worker_1~N 并行 → critic → synthesizer，每个节点标各自耗时；
2. **LLM 调用单独成节点**：显示模型名与 token 消耗——实测 synthesizer 一步 36.6s、3.9K tokens，占总耗时 90%+，慢在哪一目了然；
3. **节点 Input/Output 快照**：点开 synthesizer 能看到它吃到的完整黑板 state（evidence / facts / plan / verdict）和产出的 conclusion 成稿——排查「prompt 里到底传了什么」最直接的入口。

追问——和打日志的区别：日志是平面文本，trace 是结构化树——层级耗时 + 每步输入输出快照，能按节点聚合、跨 run 对比。
追问——为什么能零侵入：LangChain/LangGraph 所有组件统一走 langchain-core 的回调体系，SDK 挂环境变量即挂载回调，业务代码不用改。
追问——别人接入还配 tags/metadata/run_name，我有吗：没有——纯环境变量上报，trace 是"裸"的。这三个是挂在根 run 上、整棵树自动继承的检索维度：tags 供筛选分组（如成员角色）、metadata 存业务键值（任务截断/团队/时间戳）、run_name 让 trace 列表认得出是哪次任务。多人多任务多组合混一个项目时就筛不出来。补法一处改动：engine.run() 的 ainvoke 传 config dict，零侵入不破；metadata 只放检索键，state 全量本来就在节点 input/output 快照里。
追问——为啥只有 synthesizer 节点下挂着 ChatOpenAI（模型名/token），其它节点没有：LangSmith 的规则是「节点内真的发起一次 ChatModel 调用，才长一个 ChatOpenAI 子节点」。这次运行里只有 synthesizer 在节点内调了 LLM；Retriever/DataAgent/GraphAgent 是查向量库/台账/图谱的纯工具节点、critic 是纯代码硬规则裁定，本来就不调模型。planner 0.10s 最典型——图里的 planner 节点只是把算好的 plan 发出去，真正的 LLM 分解在图运行**之前**的场景装配阶段（_plan_goals，plan 作参数传进引擎），不在图执行栈里，所以它是一条独立的根 trace——trace 列表里 LangGraph 和 ChatOpenAI 交替出现，那个 ChatOpenAI 就是 planner。反证：组合勾 Worker（纯模型执行者）时每个 worker 节点下都会挂自己的 ChatOpenAI。这恰好是架构写照——取数用工具，花钱的只有成稿。
追问——成本：免费 Developer 计划 5k traces/月、14 天保留，开发调试够用；生产/内网可换 Langfuse 等自建方案。
追问——评测（另一半能力）：LangSmith 支持数据集 + 评估器做 LLM 评测（datasets/experiments），我项目已落地：任务库预置任务当测试集（30 条）跑批，三个评估器打分，UI 出分可跨实验对比（见下节）。

## 评测跑批：30 条回归结果（已落地）
OpenEvals 内置评估器本质是英文 Prompt 模板 + 调 LLM 的封装；它也提供纯代码评估器；因为判分逻辑全在 Prompt 里，所以我保留工厂、换掉 Prompt，就得到了领域定制的中文裁判

评测是我自己搭的：用 openevals 的 judge 工厂自定义了三个评估器——
1、trajectory_valid 轨迹符合度/路径有效性（LLM judge 看执行过程：分解/顺序/有无空转）：看智能体有没有按设置的流程执行：规则->查向量、图谱数据->评审->合成，这个全是1，说明体执行顺序没问题；  
2、citation_valid 引用有效性（纯代码校验结论里的 [事实N] 引用真实存在，防"挂着引用说瞎话"）：看生成的答案是不是存在，不是瞎编的；    
3、factuality 事实一致性（LLM judge 拿结论和参考答案逐点比对）：结论和测试集参考答案逐点比对，看是不是一致；  


Prompt 没用内置的通用英文版，全是自写领域定制版（中文裁判人设，"允许同义重组、只罚事实相悖"）。测试集就是任务库预置的 30 条任务，每条真跑一遍多智能体团队打分上报 LangSmith experiments，UI 可跨实验对比。第一次全量回归：编排零回归（trajectory 1.0 + error 0%，含 4 个检索器全未命中靠台账/图谱兜底收敛的逆境样本），  

citation 和 factuality 各 0.67，延迟 P50 64s / P99 106s，丢分全部可归因——citation 是没写引用不是引错（格式问题，加硬约束就能修），factuality 丢三类：部门细节相悖 / 语料缺失如实说"素材未呈现" / 开放题自由发挥。亮点：30 条 Critic 内审全放行，外部 judge 拦下 10 条事实不一致——内审会放水，外审必须独立。
