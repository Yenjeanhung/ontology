# 昆仑智平台                   
项目描述：昆仑智平台是以本体（Ontology）为核心、事件驱动的企业级数据底座：将多个业务系统按系统手动建模为本体——一个系统即一个本体，其下模块对应实体，模块代码封装为实体服务；各系统数据经连接器统一接入，数字线程引擎完成孪生体建模、服务执行与事件发布，经统一网关以 API/SSE 实时推送至知识图谱、组装应用等上层应用。本人负责 kl-dt-engine（数字线程引擎）与 kl-dt-gateway（统一网关）两大核心模块的设计与研发。
平台作为公司的数据底座，已沉淀多领域本体资产供各部门复用：其它系统可直接引用平台中的本体、实体及关系定义快速构建业务应用，避免重复建模与语义不一致，让全公司业务在统一语义标准下协同运转。
技术栈：SpringBoot、Ignite、Kafka、ZooKeeper、Drools、FileBeat、Elasticsearch、OpenTSDB、HBase、NebulaGraph、ManticoreSearch、MySQL/达梦/KingBase、Vue3、Ambari
责任描述：
1）主导平台本体元模型的设计与落地：建立「本体类别 → 本体（类型定义）→ 属性」三级模型与「起点本体 + 关系 + 终点本体」三元组约束体系，把业务知识抽象为可管理、可复用、可校验的语义模型；本体定义与实例数据分层存储，完成 MySQL/达梦/KingBase 信创多数据库适配，支撑平台作为全公司统一数据底座；

2）构建本体语义复用机制：将人员基础信息等共性语义沉淀为全局属性模板，本体按「模板属性 + 自有属性」组合派生，同一语义跨领域只定义一次、口径全局一致，显著降低多领域本体建模成本，避免各系统各自建模造成的语义漂移；

3）负责引擎模块：设计本体服务全生命周期管理（预构建→激活→替换→回滚），本体包含Drools动态规则、Rhino脚本服务执行器，业务逻辑在线定义、即时生效；服务支持编排引用函数，本体函数绑定实体自动派生计算值（派生属性），读时实时计算与定时物化双模式；

4）设计平台事件驱动架构（EDA）：构建「定义→订阅→触发→响应」全链路事件模型，内置属性变更、关系变化、服务执行、实体上下线、生命周期、定时调度事件并支持用户自定义扩展，订阅按实体集（ALL/STATIC/RULE）声明式圈定，回调对接 JS 脚本/数字线程/规则引擎三类处理器异步执行；基于 Ignite Messaging 构建分布式事件总线，设计「能力中心→事件源→事件→订阅者」多级发布订阅匹配树替代广播遍历，事件集群组播毫秒级扇出至各引擎节点；网关侧 SSE 长连接实时推送，会话多级索引缓存 + 心跳探活保障高可用，跨实例会话寻址自动转发，支撑多产品线客户端低延迟订阅；

6）独立负责 kl-dt-gateway 统一 API 网关：基于 ZooKeeper 服务发现与引擎集群轮询负载均衡，孪生体服务粘性路由、节点下线自动漂移重建，多实例水平扩展；封装对外 REST 门面与 MCP 协议透传，AOP 状态锁幂等防重（超时自动解锁），traceId 全链路 MDC 追踪，支持云端/边缘双部署形态。


# 问题及回答

## 4）事件驱动架构（EDA）

### Q1：为什么用 Ignite Messaging 做事件总线，而不是 Kafka？

**答**：看场景分工，两条链路各有定位：
- 事件总线这条是**集群内引擎节点间的实时通知**，要求毫秒级延迟。Ignite Messaging 跑在我们已有的 Ignite Server Node 集群里，进程内通信、发布即扇出，省掉外部 broker 的序列化 + 网络往返开销；
- 事件本质是**状态变化通知**，不是要长期存储的数据——实体/属性真源在运行时数据库，用不到 Kafka 的持久化和回放能力；
- Kafka 用在数据接入侧：连接器把各业务系统数据经 Kafka 削峰、缓冲后接入平台，那是跨系统、需要回放的集成链路。

一句话：集群内低延迟通知用 Ignite Messaging，跨系统数据集成用 Kafka。

### Q2：多级发布订阅匹配树怎么设计的？为什么不直接遍历订阅表？

**答**：
- 订阅的归属关系天然是一棵树：**能力中心 → 事件源（孪生体）→ 事件 → 订阅者**。订阅注册时按这个层级挂到树的分支上；
- 发布事件时携带完整编码路径（能力中心编码 / 事件源编码 / 事件编码），沿树定位，复杂度是 **O(树深)**；遍历订阅表是 O(订阅总数)，订阅量到几千上万条时尾延迟不可控；
- 匹配到事件节点后，节点下挂着命中的订阅集合以及每个订阅者所在的 **Ignite 实例 id**，直接得到跨节点投递目标，不用二次查找。

### Q3：一条事件从产生到前端收到，完整链路是什么？

**答**：
1. **触发**：引擎在数据变更切面（属性更新）、生命周期迁移（preStage→postStage）、服务执行时自动触发内置事件；用户也可通过 API / JS 脚本主动发布自定义事件；
2. **发布**：按事件定义生成事件消息（abilityCode / eventCode / triggerCode / eventData），交给 EventBus；
3. **匹配**：沿发布订阅匹配树定位订阅集合，`async` 标识的丢线程池异步执行；
4. **投递**：按「订阅者 → Ignite 实例 id」通过 ClusterGroup 组播到目标引擎节点，节点按 processorType 路由到 JS 脚本 / 数字线程 / 规则引擎处理器执行；
5. **推送**：涉及前端订阅的，网关经 SSE 长连接实时推给客户端。全链路毫秒级。

### Q4：Ignite Messaging 是 fire-and-forget，不保证可靠投递，消息丢了怎么办？

**答**：定位决定设计——事件总线承载的是**通知，不是账本**：
- 状态数据的真源在运行时数据库，事件丢了数据不丢，业务状态不受影响；
- 对可靠性有要求的下游不依赖单次事件：如派生属性物化走定时调度兜底，相当于周期性对账补偿；
- 回调失败统一异常捕获 → 告警 → FileBeat 收集到 ES，可追溯可重放。

所以敢用 at-most-once 换延迟；真正要可靠投递的场景（对接外部系统）走 Kafka 链路。

### Q5：推送为什么选 SSE 不用 WebSocket？

**答**：场景是**服务端单向推送**，SSE 更轻：
- 复用 HTTP，网关不需要协议升级，鉴权、网关转发逻辑全部沿用；
- 浏览器 EventSource 原生支持**断线自动重连**，重连、Last-Event-ID 续传机制不用自己实现；
- WebSocket 适合双向交互（协作编辑类），方案里对这类客户端也预留了 WebSocket 通道，按客户端形态二选一。

### Q6：网关多实例部署，用户连接在实例 A，事件却到了实例 B，怎么推到用户？

**答**：靠「会话多级索引缓存 + 跨实例寻址转发」：
- SSE 会话建立时，按 **产品线 / 用户 / 订阅主题** 建多级索引缓存；推送时先查本地，命中直接推；
- 查不到（会话在别的实例上）时，按索引定位会话所在实例，**内部转发**给持有会话的实例推送，用户无感；
- **心跳探活**：服务端定期巡检会话 last-active 时间戳，超时未活跃的死链主动关闭、释放资源，防止连接泄漏；
- 网关节点下线时，客户端 EventSource 自动重连到存活实例并重新登记索引。因此网关可水平扩容，推送能力随实例数线性扩展。

### Q7：JS 脚本 / 数字线程 / 规则引擎三类回调处理器，怎么统一调度？

**答**：订阅定义里回调抽象为 `processorType + processorCode`：
- 三类处理器（JS 脚本、数字线程编排、Drools 规则）实现同一个回调接口，事件分发时按 type 路由到对应执行器；
- `async` 标识决定同步执行还是丢异步线程池，避免慢回调阻塞事件分发线程；
- 对订阅方来说是**配置即接入**：选处理器类型、填编码即可，不需要写任何接入代码，这也是「一站式配置、可视化编排」的落点。

### Q8：事件模型怎么做到内置事件和自定义事件的统一？

**答**：事件定义元数据化，一套结构描述两类事件：
- 事件定义包含 `code / kind（BUILD-IN、USER-DEF）/ type（PROPERTY、RELATION、SERVICE、ENTITY…）/ fieldDefinitions（参数定义）`；
- 内置事件（属性变更、关系变化、服务执行、上下线、生命周期、定时调度）由引擎在数据变更、生命周期迁移等**切面自动触发**；自定义事件开放 API / JS 主动触发；
- 两类事件走同一套定义结构、同一个匹配树和投递链路，订阅方对两者无感知差别——新增一种内置事件对订阅体系零改动。
