# 昆仑智平台                   
项目描述：昆仑智平台是一个本体构建与管理的企业级平台，以本体（Ontology）为核心组织业务知识，定义领域中的本体、实体、属性、关系以及约束规则，把信息组织成可推理、可检索的知识结构，为业务系统提供统一语义基础。平台通过函数、服务、MCP工具配置，将本体知识与能力封装为可调用的服务接口。通过数字线程将本体服务编排，可实现多系统、复杂业务流程组合。该平台作为公司的数据底座，已为多个央企、科研机构项目提供本体建模基础。上层系统可直接复用平台中已沉淀的本体知	识和服务，快速构建业务应用，避免重复建模和语义不一致，让各系统在统一数据标准下协同运转。

技术栈：SpringBoot、Ignite、Kafka、ZooKeeper、Drools、FileBeat、Elasticsearch、OpenTSDB、HBase、NebulaGraph、ManticoreSearch、MySQL/达梦/KingBase、Vue3、Ambari

责任描述：
1）团队管理: 作为核心组长，参与平台0到1整体架构设计以及持续演进，与部门总监共同推进平台研发进度。
2）主导平台本体元模型的设计：建立本体类别、本体、属性三级模型与关系约束体系，把业务知识抽象为可管理、可复用的语义模型；本体可定义公共函数与服务，其下实体自动继承、也可覆写或自定义；本体定义存储层完成MySQL/达梦/KingBase信创多数据库适配，支撑平台作为全公司统一数据底座；
3）本体服务执行引擎与本体网关模块开发：执行引擎分布式部署、云端/边缘双形态，内置Drools规则与Rhino脚本执行器，业务逻辑在线定义、即时生效；网关承接本体服务定义上线后的统一下发与分流调度，管理本体全生命周期（构建→更新→销毁）与节点分布，基于ZooKeeper服务发现按引擎集群负载分流请求，引擎节点故障时服务实例自动转移重建、调用方无感，支持多实例水平扩展；对外封装REST与MCP协议透传，traceId全链路MDC追踪；
4）设计并实现平台事件驱动架构（EDA）：构建「定义→订阅→触发→响应」全链路事件模型，可用于数据接入、实体属性值变更、关系变化、服务执行、实体上下线等场景。基于Ignite Messaging构建分布式事件总线，设计本体类别→本体→实体→订阅者多级发布订阅匹配树，事件发出后动态查找订阅者毫秒级组播至各引擎节点；网关侧SSE长连接实时推送，会话多级索引缓存+心跳探活保障高可用，跨实例会话寻址自动转发，支撑多产品线客户端低延迟订阅；
3）构建本体语义复用机制与派生属性：共性语义沉淀为全局属性模板，本体按「模板属性+自有属性」组合派生，跨领域只定义一次、口径全局一致；属性值需要运行时动态计算的为派生属性（如健康度、状态等），建模时将其绑定函数即完成定义，函数使用订阅机制接收到数据后完成实时计算；

# 问题及回答

## 4）事件驱动服务务构（EA）

### Q1：为什么用Ignite Messaging做事件总线，而不是Kafka？

**答**：看场景分工，两条链路各有定位：
- 事件总线这条是**集群内引擎节点间的实时通知**，要求毫秒级延迟。Ignite Messaging跑在我们已有的Ignite Server Node集群里，进程内通信、发布即扇出，省掉外部broker的序列化 + 网络往返开销；
- 事件本质是**状态变化通知**，不是要长期存储的数据——实体/属性真源在运行时数据库，用不到Kafka的持久化和回放能力；
- Kafka用在数据接入侧：连接器把各业务系统数据经Kafka削峰、缓冲后接入平台，那是跨系统、需要回放的集成链路。

一句话：集群内低延迟通知用Ignite Messaging，跨系统数据集成用Kafka。

### Q2：多级发布订阅匹配树怎么设计的？为什么不直接遍历订阅表？

**答**：
- 订阅的归属关系天然是一棵树：**本体类别 → 本体 → 实体（事件源）→ 事件 → 订阅者**。发布事件时范围可选——发布到本体类别、本体或具体实体；订阅注册时挂到对应层级的节点上；
- 发布事件时携带完整编码路径（本体类别编码 / 事件源编码 / 事件编码），沿树定位，复杂度是**O(树深)**；遍历订阅表是O(订阅总数)，订阅量到几千上万条时尾延迟不可控；
- 匹配到事件节点后，节点下挂着命中的订阅集合以及每个订阅者所在的**Ignite实例id**，直接得到跨节点投递目标，不用二次查找。

> **追问：那建一张「订阅编码 → 订阅者」的哈希绑定表，O(1)一下命中，不是更快吗？干嘛非用树？**
>
> 单条**精确订阅**的点查，哈希表确实最快。但事件匹配的难点不在点查，在三件事：
> 1. **发布范围本身是三级可选的**：发布事件时可以选发布到「本体类别 → 本体 → 具体实体」任意一层。订阅挂在树的各层节点上，事件发布后沿树查找，把命中范围内的订阅者**动态汇总**——订阅者数量是这一次发布才算出来的，不是注册时固定的；
> 2. **订阅者是运行时才展开的**：订阅者实体集分ALL / STATIC / RULE三类——ALL圈全量、RULE规则动态圈定，注册时算不出结果，静态绑定表只能存STATIC编码。树节点挂**订阅声明**，投递时才展开成「具体订阅者 → Ignite实例id」，声明与运行态分离；
> 3. **一次发布是一对多扇出，不是一查一**：同一节点下挂着多个订阅（不同订阅者集、不同处理器类型），树沿路径一遍全命中；绑定表一次get只回一个值，循环get合并去重把O(1)做成了O(k)。
>
> 实现上并不排斥哈希：**树的每一级子节点本身就是哈希map索引**，定位一个节点是常数级跳转——树方案实际是「哈希寻址 + 树结构组织」。
> 一句话：绑定表的key只有一个粒度，表达不了「发布到本体级、其下所有实体的订阅者都要收到」的范围语义；树把发布粒度、订阅挂载、订阅者动态展开统一在同一个结构里。

### Q3：一条事件从产生到前端收到，完整链路是什么？

**答**：
1. **触发**：引擎在数据变更切面（属性更新）、生命周期迁移（preStage→postStage）、服务执行时自动触发内置事件；用户也可通过API / JS脚本主动发布自定义事件；
2. **发布**：按事件定义生成事件消息（abilityCode / eventCode / triggerCode / eventData），交给EventBus；
3. **匹配**：沿发布订阅匹配树定位订阅集合，`async`标识的丢线程池异步执行；
4. **投递**：按「订阅者 → Ignite实例id」通过ClusterGroup组播到目标引擎节点，节点按processorType路由到JS脚本 / 数字线程 / 规则引擎处理器执行；
5. **推送**：涉及前端订阅的，网关经SSE长连接实时推给客户端。全链路毫秒级。

### Q4：Ignite Messaging是fire-and-forget，不保证可靠投递，消息丢了怎么办？

**答**：定位决定设计——事件总线承载的是**通知，不是账本**：
- 状态数据的真源在运行时数据库，事件丢了数据不丢，业务状态不受影响；
- 对可靠性有要求的下游不依赖单次事件：如派生属性物化走定时调度兜底，相当于周期性对账补偿；
- 回调失败统一异常捕获 → 告警 → FileBeat收集到ES，可追溯可重放。

所以敢用at-most-once换延迟；真正要可靠投递的场景（对接外部系统）走Kafka链路。

### Q5：推送为什么选SSE不用WebSocket？

**答**：场景是**服务端单向推送**，SSE更轻：
- 复用HTTP，网关不需要协议升级，鉴权、网关转发逻辑全部沿用；
- 浏览器EventSource原生支持**断线自动重连**，重连、Last-Event-ID续传机制不用自己实现；
- WebSocket适合双向交互（协作编辑类），方案里对这类客户端也预留了WebSocket通道，按客户端形态二选一。

### Q6：网关多实例部署，用户连接在实例A，事件却到了实例B，怎么推到用户？

**答**：靠「会话多级索引缓存 + 跨实例寻址转发」：
- SSE会话建立时，按**产品线 / 用户 / 订阅主题**建多级索引缓存；推送时先查本地，命中直接推；
- 查不到（会话在别的实例上）时，按索引定位会话所在实例，**内部转发**给持有会话的实例推送，用户无感；
- **心跳探活**：服务端定期巡检会话last-active时间戳，超时未活跃的死链主动关闭、释放资源，防止连接泄漏；
- 网关节点下线时，客户端EventSource自动重连到存活实例并重新登记索引。因此网关可水平扩容，推送能力随实例数线性扩展。

### Q7：JS脚本 / 数字线程 / 规则引擎三类回调处理器，怎么统一调度？

**答**：订阅定义里回调抽象为 `processorType + processorCode`：
- 三类处理器（JS脚本、数字线程编排、Drools规则）实现同一个回调接口，事件分发时按type路由到对应执行器；
- `async`标识决定同步执行还是丢异步线程池，避免慢回调阻塞事件分发线程；
- 对订阅方来说是**配置即接入**：选处理器类型、填编码即可，不需要写任何接入代码，这也是「一站式配置、可视化编排」的落点。

### Q8：事件模型怎么做到内置事件和自定义事件的统一？

**答**：事件定义元数据化，一套结构描述两类事件：
- 事件定义包含 `code / kind（BUILD-IN、USER-DEF）/ type（PROPERTY、RELATION、SERVICE、ENTITY…）/ fieldDefinitions（参数定义）`；
- 内置事件（属性变更、关系变化、服务执行、上下线、生命周期、定时调度）由引擎在数据变更、生命周期迁移等**切面自动触发**；自定义事件开放API / JS主动触发；
- 两类事件走同一套定义结构、同一个匹配树和投递链路，订阅方对两者无感知差别——新增一种内置事件对订阅体系零改动。
