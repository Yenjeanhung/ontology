## 一、检索侧评估（衡量"能不能找到正确的文档片段"）

### Q1：检索侧有哪些核心指标？

**精简回答**：Recall@K 看有没有找到，Precision@K 看找到的准不准，MRR 看正确结果排第几，NDCG 看整体排序质量。

**展开**：
1. **Recall@K（召回率）**：正确答案出现在 top-K 结果中的比例，衡量"相关内容有没有被找到"。
2. **Precision@K（精准率）**：top-K 结果中相关内容的比例，衡量"找到的内容有多少是相关的"。
3. **MRR**：第一个正确结果排名倒数的均值，衡量"最相关的结果排在第几"。
4. **NDCG**：考虑排序位置和相关度等级的综合排序质量指标。

### Q2：结合你的项目，检索链路怎么评估？

**精简回答**：建「问题+标准chunk」评估集，分层测向量/BM25/混合三路的 Recall 定位瓶颈，对比 RRF 序 vs Rerank 序验证精排收益。

**展开**：我的检索链路是 **查询改写（Multi-Query）→ 向量 + BM25 混合召回 → RRF 融合 → Rerank 精排**，评估思路：

- **先建评估集**：抽样「问题 + 标准 chunk」标注对，人工标注或用 LLM 辅助标注正确来源。
- **分层评估定位瓶颈**：分别测向量单路、BM25 单路、混合后的 Recall@50，判断混合检索是否带来增益。我的实现里每个分片带 `retrieval` 字段（`vector`/`bm25`/`both`），可以统计各通道贡献——被两路同时召回（`both`）的 chunk 相关性通常更高。
- **验证 Rerank 收益**：对比 RRF 融合序 vs Rerank 后序的 MRR/NDCG，若精排只是把 TOP_N 内部重排而候选池太小，收益有限（所以我设置了 `RERANK_CANDIDATE_K` 保证精排候选池足够大）。
- **阈值调参**：`SIMILARITY_THRESHOLD` 过滤低分结果，需要在 Precision 和 Recall 之间权衡——阈值过高会漏召回，压低 Recall@K。

### Q3：多路召回为什么要用 RRF 而不是分数加权？

**精简回答**：两路分数量纲不同没法直接加，RRF 只用排名倒数融合，无量纲问题、无需调参、鲁棒。

**展开**：向量相似度和 BM25 分数量纲不同（余弦相似度 0~1，BM25 无上界），直接加权需要归一化且对参数敏感。**RRF 只用排名倒数融合（1/(k+rank)），对量纲不敏感、无需调参**，鲁棒性更好。

## 二、生成侧评估（衡量"最终答案质量"）

### RAGAS 是什么？生成侧有哪些核心指标？

**精简回答**：RAGAS 是专为 RAG 设计的开源自动化评估框架，核心思路是用 LLM 当裁判（LLM-as-a-Judge）自动打分；四指标 = Faithfulness（无幻觉）、Answer Relevancy（答到点上）、Context Relevancy（上下文有用）、Context Recall（信息没漏在上下文），前两个评答案，后两个评上下文。

**展开**：

**RAGAS (Retrieval Augmented Generation Assessment) 是什么：**

- 出身：面向 RAG 场景的开源评估框架（GitHub 开源，可 pip 安装直接用），解决了 RAG 评估的两大痛点——**缺标注数据**（传统评估要人工标注标准答案，成本高）和**生成答案没有唯一正确解**（不能像分类任务那样算准确率）。
- 核心机制：**LLM-as-a-Judge**——用强模型代替人工做判定（拆解声明、核对上下文、反向出题等），只需提供 `question + contexts + answer`（部分指标加可选 `ground_truth`）即可全自动打分。
- 定位：RAGAS 是最常用的基准选择；同类还有 TruLens、DeepEval、LangSmith 评估套件，思路相近（本质都是 LLM 判分 + 维度化指标）。面试说"我用 RAGAS 的四指标思路，工程上也可以自研同款 prompt 用 LLM 判分"即可，不必绑定框架。

**四个指标详解（含计算方法与低分诊断）：**

1. **Faithfulness（忠实度）**：答案是否忠于检索到的上下文，有没有幻觉。
   - 计算方法：LLM 先把答案**拆成一条条原子声明 (claims)**，逐条判定"能否从检索上下文推断出来"，得分 = 能被支持的声明数 / 总声明数。
   - 得分低 → 答案夹带了上下文中没有的信息，即幻觉。
2. **Answer Relevancy（答案相关性）**：答案是否真正回答了用户的问题。
   - 计算方法：LLM **从答案反向生成 N 个它可能回答的问题**，计算这些问题与原 query 的**余弦相似度均值**。
   - 得分低 → 答案跑题、含糊其辞、答非所问（"我不知道"式回避也会拉低分数）。
3. **Context Relevancy（上下文相关性 / Context Precision）**：检索到的上下文对回答问题是否有用。
   - 计算方法：LLM 判定每个检索 chunk 是否与问题相关，并看**相关 chunk 是否排在候选前面**（排序加权的相关占比）。
   - 得分低 → 召回混入噪声，或相关内容被排在末尾（Rerank 失效信号）。
4. **Context Recall（上下文召回）**：生成答案所需的关键信息是否都在检索到的上下文中。
   - 计算方法：拿**标准答案 (ground truth)** 的每条关键声明，检查是否都能归因到检索上下文，得分 = 能归因的声明数 / 标准答案声明总数。
   - 得分低 → 检索漏了关键内容，答案必然不完整——这是**检索侧 L1 问题**，改生成没有意义。

> 记忆：Faithfulness/Answer Relevancy 评 **答案**，Context Relevancy/Context Recall 评 **上下文**。
>
> **数据要求**：前三个只需 `question + contexts + answer`；**Context Recall 需要标注的标准答案**——线上没有标注时，用 LLM 基于 chunk 反向生成 QA 对作 golden set（见 Q6）。
>
> **诊断映射**：Faithfulness 低 → 改 prompt 约束/降温/换模型（生成侧问题）；Context Recall 低 → 回头改检索（分块/embedding/召回）；Context Precision 低 → 排序问题（上 Rerank）；Answer Relevancy 低 → prompt 或上下文噪声。

### 结合你的项目，生成质量怎么保障和评估？

**精简回答**：Prompt 约束 + 强制 `[来源N]` 引用可程序化校验忠实度 + 空检索直接拒答；RAGAS 评估时按指标低分归因到检索侧或生成侧。

**展开**：
- **防幻觉设计**：System Prompt 明确要求"资料中没有相关信息就如实说明，不要编造"。
- **强制引用溯源**：要求答案标注 `[来源N]`，一方面方便用户核查，另一方面可以**程序化评估 Faithfulness**——校验答案中的断言是否都有对应来源支撑，无引用的句子占比可作为幻觉的代理指标。
- **拒答机制**：检索结果为空时直接返回"未找到相关内容"，不走 LLM 生成，从源头避免无上下文幻觉。
- **评估方式**：用 RAGAS 跑评估集，重点看 Faithfulness 和 Answer Relevancy；若 Faithfulness 低是 prompt/模型问题，若 Context Recall 低则要回头优化检索（说明问题在 L1 不在 L2）。

## 三、综合追问

### Q6：线上没有标注数据，怎么快速评估？

**精简回答**：用 LLM 基于 chunk 反向生成 QA 对构建 golden set，再用 LLM-as-a-Judge 打分，加上用户反馈闭环。

**展开**：
- **构建 golden set**：从知识库文档反向生成 QA 对（用 LLM 基于 chunk 出题），天然自带标准答案和正确来源。
- **LLM-as-a-Judge**：无参考答案时，让强模型按维度打分（准确性、引用正确性）。
- **用户反馈闭环**：点赞/点踩、追问率作为 L3 端到端信号。

### Q7：检索指标差，怎么定位和优化？

**精简回答**：按链路归因——Recall 低是召回问题（模型/分块/改写），Recall 高但排序指标低是排序问题（上 Rerank），关键词 query 差就补 BM25。

**展开**：按链路逐段归因：
1. **Recall@K 低** → 召回问题：查 embedding 模型对中文/领域词的效果（我用 `bge-small-zh-v1.5`）、分块策略、是否需要查询改写扩充召回面（我的 Multi-Query 就是为这个）。
2. **Recall 高但 MRR/NDCG 低** → 排序问题：上 Rerank 精排、调 RRF k 值。
3. **关键词类 query 差** → 向量语义匹配的短板，补 BM25 通道（专有名词、编号类查询 BM25 更强）。
