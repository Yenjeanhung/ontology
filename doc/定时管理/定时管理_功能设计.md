## 0. 一句话目标

在工作流模块之上，新增一个**轻量定时调度引擎**，让用户可以「选一个工作流 → 配一个触发规则（每天/每周/一次性/cron）→ 启用」，**到点自动跑工作流**，并把每次触发产生的运行记录、状态、失败告警集中管理。

---

## 1. 背景与目标

### 1.1 现状

工作流模块（`doc/工作流/工作流_功能设计.md`）已实现：

- 可视化编排 DAG，节点含 `start` / `agent` / `service` / `llm` / `condition` / `code`；
- 执行引擎 `workflow_engine.run_stream(workflow_id, definition, inputs)` 支持 SSE 流式进度，已落地 `workflow_runs` 运行记录表；
- 工作流 v1 明确把 **「定时触发 / 事件触发（Webhook）」列为 v2 待办**（见工作流文档 §1.3、§13 第 4 点）。

**当前缺口**：工作流只能**人工在页面点「运行」触发**，无法按时间自动执行。用户需要「每天 8 点让财务问答工作流跑一遍」「每周一汇总上周知识库新增实体」这类无人值守的定时任务。

### 1.2 目标（v1）

1. **定时调度**：支持 cron 表达式、周期（每 N 分钟/小时/天）、一次性（指定时间点）三类触发；
2. **复用工作流**：调度计划绑定一个已有工作流 + 一组固定入参（等价 `start` 节点入参），到点调用 `workflow_engine` 执行，**不重写执行逻辑**；
3. **调度生命周期管理**：启停、编辑、删除、立即执行（手动触发一次）、暂停（mute）；
4. **运行可观测**：每次触发复用 `workflow_runs` 落库，列表展示「下次运行时间 / 上次状态 / 连续失败次数」；
5. **失败告警**：连续失败 N 次或运行异常时写通知（复用现有 `notifications` 模块），并在前端**右上角消息中心**弹出提示；
6. **轻量无外部依赖**：采用进程内调度器 **APScheduler**（已确认选型），不引入 Redis / RabbitMQ 等中间件，**单机部署**（已确认）；
7. **可视化 cron 构建器**（已确认）：编辑页提供图形化 cron 勾选界面，降低配置门槛；
8. **入参强校验**（已确认）：计划保存时强制校验 `input_params` 与关联工作流 `start` 节点声明入参一致。

### 1.3 非目标（v1 明确不做）

- ❌ Webhook / 文件上传事件等**外部事件触发** → 后续独立模块；
- ❌ 分布式高可用调度（跨多机 failover、精确一次语义）→ v2；
- ❌ 调度计划自身的版本管理 / 权限 / 协作；
- ❌ 工作流的暂停/断点续跑由调度层控制（调度只负责「触发」，执行仍由 workflow_engine 负责）。

### 1.4 设计原则（延续项目一贯做法）

1. **复用不重写**：调度层只做「按时触发 + 拼装入参 + 调 `workflow_engine`」，执行引擎、SSE、运行记录全部复用；
2. **配置即数据**：调度计划持久化到 `schedules` 表，服务重启后由调度器从 DB 全量重建，无需外部状态；
3. **轻量零中间件**：采用 APScheduler `AsyncIOScheduler` + 内存 jobstore，启动即从 DB 恢复；**单机部署**，无需分布式协调。

## 2. 核心概念

| 概念 | 说明 |
|------|------|
| **调度计划（Schedule）** | 一条定时任务记录 = 绑定工作流 + 触发规则（cron/interval/once）+ 固定入参 + 启用状态 |
| **触发器（Trigger）** | 三类：`cron`（标准 5~6 字段 cron）、`interval`（每 N 单位）、`once`（指定一次时间） |
| **运行实例（Run）** | 每次触发产生一次工作流运行，复用 `workflow_runs` 表（`trigger=schedule` 标记来源） |
| **下次运行时间（next_run_at）** | 由触发器计算，落库便于列表展示与排序 |
| **连续失败（consecutive_failures）** | 计数器，达到阈值（默认 3）触发告警并可选自动停用 |

┌──────▼────────────────────┐              ┌─────────▼──────────────┐

└────────────────────────────┘              └─────────────────────────┘
       │ 失败信息                          │ 告警

└────────────────────────────┘

**关键说明**：

- 调度引擎在 FastAPI `lifespan` 启动（`scheduler_engine.start()`），从 `schedules` 表加载所有 `enabled` 计划，注册为 APScheduler job；
- 触发回调 `on_trigger(schedule)` 异步调用 `workflow_engine` 执行，**不阻塞调度线程**；
- 单实例时 APScheduler 内存 jobstore 足够；多实例部署时通过 `schedules` 表 `last_trigger_at` + 行锁（见 §6.3）去重，避免每个实例都触发一次。

## 4. 触发器类型

统一抽象为 `trigger` 字段 + `trigger_config` JSON：

### 4.1 cron（标准表达式）

```json
{ "trigger": "cron",
  "trigger_config": { "minute": "0", "hour": "8", "day_of_week": "*", "day": "*", "month": "*" } }
```

- 等价于 Linux crontab（字段：`minute hour day month day_of_week`）；
- 支持 APScheduler 扩展语法（`*/5`、`0-30/10`、`mon-fri`）。
- 示例：「每天 8 点」→ `hour=8, minute=0`；「每 15 分钟」→ `minute="*/15"`。

### 4.2 interval（周期）

```json
{ "trigger": "interval",
  "trigger_config": { "every": 30, "unit": "minutes" } }   // unit ∈ minutes|hours|days
```

### 4.3 once（一次性）

```json
{ "trigger": "once",
  "trigger_config": { "run_at": "2026-09-01T09:00:00" } }   // ISO 时间，到点执行一次后自动标记 completed
```

### 4.4 时区

- 统一使用 `settings.TIMEZONE`（新增配置，默认 `Asia/Shanghai`）；
- cron / interval / once 均按此时区计算 `next_run_at`。

## 5. 数据模型

### 5.1 新增表 `schedules`

```sql
CREATE TABLE IF NOT EXISTS schedules (
    id                  VARCHAR PRIMARY KEY,
    name                VARCHAR(100) NOT NULL,
    description         TEXT DEFAULT '',
    workflow_id         VARCHAR NOT NULL,          -- 关联 workflows.id
    trigger             VARCHAR NOT NULL,          -- cron | interval | once
    trigger_config      TEXT NOT NULL DEFAULT '{}',-- JSON: 见 §4
    input_params        TEXT NOT NULL DEFAULT '{}',-- JSON: start 节点固定入参
    enabled             INTEGER NOT NULL DEFAULT 1,-- 1 启用 / 0 停用
    muted               INTEGER NOT NULL DEFAULT 0,-- 1 静默（不告警，仍执行）
    next_run_at         VARCHAR,                   -- 下次运行时间（ISO），便于展示
    last_run_at         VARCHAR,                   -- 上次触发时间
    last_status         VARCHAR,                   -- succeeded | failed | running | none
    consecutive_failures INTEGER NOT NULL DEFAULT 0,
    max_failures_alert  INTEGER NOT NULL DEFAULT 3,-- 连续失败达此值告警
    alert_on_failure    INTEGER NOT NULL DEFAULT 1,-- 失败是否发通知
    created_at          VARCHAR,
    updated_at          VARCHAR
);
CREATE INDEX IF NOT EXISTS idx_schedules_wf ON schedules(workflow_id);
CREATE INDEX IF NOT EXISTS idx_schedules_enabled ON schedules(enabled);
```

## 6. 调度引擎（`services/scheduler_engine.py`）

### 6.1 技术选型

| 项 | 方案 |
|----|------|
| 调度框架 | [APScheduler](https://github.com/agronholm/apscheduler) `AsyncIOScheduler`（与 FastAPI 事件循环同线程，天然异步友好） |
| Jobstore | 默认 `MemoryJobStore`（进程内）；`schedules` 表为**真相源**，启动时从 DB 重建 job |
| 触发回调 | `on_trigger(schedule)` 异步 `asyncio.create_task(workflow_engine.run_stream(...))` |
| 时区 | `ZoneInfo(settings.TIMEZONE)` |
| 失败处理 | 捕获异常 → 更新 `consecutive_failures` → 达阈值且 `alert_on_failure` 则调 `notifications` |

### 6.2 生命周期

```
启动（lifespan）：
  scheduler_engine.start()
    ├─ 创建 AsyncIOScheduler(timezone=...)
    ├─ 从 DB 读所有 enabled=1 的 schedules
    ├─ 逐条 _register_job(schedule)：按 trigger 类型 add_job(on_trigger, trigger, id=schedule.id, args=(schedule.id,))
    ├─ scheduler.start()
    └─ 记录 logger "Scheduler started with N jobs"

关闭（lifespan 退出）：
  scheduler_engine.shutdown()
    └─ scheduler.shutdown(wait=False)

新增/更新计划（scheduler_service）：
  _sync_job(schedule)
    ├─ 若已注册同 id job → scheduler.remove_job(id)
    ├─ 若 enabled → scheduler.add_job(...) 并刷新 next_run_at
    └─ 更新 DB 的 next_run_at / updated_at

触发回调 on_trigger(schedule_id)：
  async def on_trigger(schedule_id):
    schedule = await SchedulerService.get(db, schedule_id)
    if not schedule or not schedule.enabled: return
    definition = 工作流 definition（从 workflows 表取）
    inputs = json.loads(schedule.input_params)
    # 调执行引擎（忽略 SSE，仅取最终 status；或落库即可）
    status, error = await run_workflow_sync(workflow_id, definition, inputs, schedule_id)
    # 更新 schedule 的 last_run_at / last_status / consecutive_failures
    # 失败且达阈值 → 发通知（除非 muted）
    # once 类型执行完 → enabled=0, next_run_at=None
```

### 6.3 单机部署与幂等

**已确认：单机部署。** 因此无需多实例去重协调，APScheduler 进程内 jobstore 即可保证每个计划只触发一次。

仅需防御两类单机误触发：

- **misfire 补偿**：服务短暂重启/挂起后错过触发点，在 `misfire_grace_seconds`（默认 300s）窗口内由 APScheduler 自动补触发一次（`coalesce=true` 合并多次错过为一次）；
- **run-now 与定时撞车**：`run-now` 与到点触发可能同时发生，由 `SCHEDULER_MAX_CONCURRENT_RUNS` 限流；同一计划在极短时间窗内的重复执行不视为错误，仅在 UI 展示两条运行记录。

> 注：若未来升级为多实例，可在此处补「行锁抢 `last_run_at`」方案（见 v2 展望），v1 不涉及。

### 6.4 与 workflow_engine 的对接

`workflow_engine.run_stream` 是 SSE 生成器。调度触发无需流式，封装一个同步等待版本：

```python
async def run_workflow_sync(workflow_id, definition, inputs, schedule_id=None):
    """消费 run_stream 直到 [DONE]，返回 (status, error)。"""
    status, error = "failed", None
    async for s in run_stream(workflow_id, definition, inputs, trigger_source="schedule", schedule_id=schedule_id):
        # 解析 workflow_finished 事件取最终 status/error
        ...
    return status, error
```

> 复用 `run_stream` 的好处：运行记录、节点状态、裁剪逻辑全部自动落库，调度层零额外存储代码。需在 `run_stream` 签名增加可选 `trigger_source` / `schedule_id` 参数写入 `WorkflowRun`（轻量改动）。

## 7. 后端 API（`routers/scheduler.py`，前缀 `/api`）

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/schedules` | 调度计划列表（含 `next_run_at` / `last_status` / 关联工作流名） |
| POST | `/schedules` | 创建计划（校验 trigger + 工作流存在 + 入参结构） |
| GET | `/schedules/{id}` | 计划详情 |
| PUT | `/schedules/{id}` | 更新（重算 next_run_at，同步调度器 job） |
| DELETE | `/schedules/{id}` | 删除（从调度器移除 job） |
| POST | `/schedules/{id}/toggle` | 启用/停用（同步 job 注册/移除） |
| POST | `/schedules/{id}/run-now` | 立即执行一次（手动触发，不依赖时间） |
| GET | `/schedules/{id}/runs` | 该计划的运行历史（查 `workflow_runs` WHERE `schedule_id`） |

**入参校验**：

- `trigger` ∈ {cron, interval, once}；
- `trigger_config` 字段按类型校验（cron 字段合法、interval `every>0`、once `run_at` 为未来时间）；
- `workflow_id` 必须存在于 `workflows`；
- **`input_params` 强校验（已确认）**：从关联工作流的 `start` 节点取出声明入参列表（`config.inputs`，含字段名与是否必填），校验要求：
  - 必填字段**必须**出现在 `input_params` 中且类型匹配（字符串/数字/布尔/对象），缺失或类型不符 → 返回 `422` 并指明缺哪个字段；
  - `input_params` 中**不应**出现工作流未声明的字段，出现多余字段 → 返回 `422` 提示「未知入参 xxx」（避免静默失效）；
  - 校验在服务端 `scheduler_service.validate_inputs(workflow_id, input_params)` 统一实现，前端编辑页在保存前也会先做同样规则的前端提示，但**以服务端为准**；
  - 校验发生在创建与更新两个写接口；若关联工作流后续被改版（删了必填入参），计划保存时会报错，提醒用户先修正计划入参。

## 10. 安全与边界

| 场景 | 行为 |
|------|------|
| 关联工作流被删除 | 计划启用时触发 → `run_workflow_sync` 报错 → 计失败；列表页展示「工作流不存在」并建议停用 |
| 工作流 definition 非法（含环） | `run_stream` 建图失败 → status=failed → 计入连续失败 |
| 入参缺失 / 类型错 | **保存时强校验拦截**（见 §7）：必填字段缺失或类型不符、`input_params` 含未声明字段 → 创建/更新接口直接 `422` 拒绝，不会让计划带着非法入参运行；运行时若工作流改版导致入参不再匹配，触发执行报错并计失败 |
| 服务重启 | 启动时从 DB 全量重建 job；`misfire_grace` 内补触发错过的任务 |
| 单次运行超时 | 复用 `WORKFLOW_RUN_TIMEOUT_SECONDS`，超时由 workflow_engine 中止 |
| 并发触发过多 | `SCHEDULER_MAX_CONCURRENT_RUNS` 限流，超出排队或丢弃（记日志） |
| 连续失败告警 | `consecutive_failures >= max_failures_alert` 且 `alert_on_failure=1` 且 `muted=0` → 调 notifications 模块发通知 |
| once 类型执行后 | 自动 `enabled=0`，不再注册 job，列表标记「已完成（一次性）」 |
