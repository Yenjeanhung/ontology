> 需求来源：`doc/本体管理/本体服务/本体服务_需求.md`

---

## 1. 背景与目标

当前本体只描述"实体是什么"（属性、关系约束），缺少"实体能做什么"。本功能为本体引入**服务（Service）= 一组动作（Action）**的概念：

- 本体可定义通用服务（如"设备"本体挂"远程控制"服务），其下**所有实体自动继承**，可直接调用；
- 实体可定义**个性化服务**，仅自己可见；
- 动作以 **Python 代码**实现（调用 API、处理数据等），预留多语言扩展。

一句话：`本体定义 → 实体继承/覆盖 → 用户(及后续智能体)以参数调用 → 沙箱执行返回结果`。

## 2. 需求逐条对照

| # | 需求 | 设计方案 | 章节 |
|---|------|----------|------|
| 1 | 本体可增加通用动作 | `ontology_services` 表挂在本体下，本体编辑器新增"服务"区块 | §4 / §7.2 |

| 4 | 动作用 Python 代码实现，预留多语言 | 子进程沙箱执行器，`language` 字段预留 | §6 |

## 3. 总体架构

```
┌─────────────────────────── 前端 ───────────────────────────┐
│  本体编辑器(OntologyEditor)      实体详情页(EntityDetailPage) │
│   └ 服务区块: CRUD/测试运行       └ 服务区块: 继承+自定义/执行  │
└──────────────┬─────────────────────────────┬───────────────┘
               │ REST                        │ REST
┌──────────────▼─────────────────────────────▼───────────────┐
│  routers/ontology_service.py                                │
│  ├─ OntologyServiceService（CRUD / 继承解析）                │
│  └─ ServiceRuntimeService（测试运行 / 实体调用执行）          │
│       └─ services/service_runtime.py（沙箱执行器，子进程）     │
└──────────────┬──────────────────────────────────────────────┘
               │ SQLite（定义层惯例：无外键，逻辑关联）
        ontology_services 表（本体服务 + 实体服务统一存储）
```

- 图数据库（Kùzu/Neo4j）**不感知服务**，与属性模板等定义层一致，仅存 SQLite；
- 执行器为独立子进程，与 Web 进程隔离。

## 4. 数据模型

新表 `ontology_services`（同步修改 `models.py`、`sql/schema.sql`、`sql/migrations.sql` 三处）：

| 字段 | 类型 | 说明 |
|------|------|------|
| id | INTEGER PK | |
| owner_type | TEXT | `'ontology'` / `'entity'` |
| ontology_id | INTEGER | owner_type=ontology 时必填；entity 服务也冗余记录所属本体（便于展示来源） |
| entity_id | INTEGER | owner_type=entity 时必填 |
| name | TEXT | 展示名，如"查询天气" |
| code | TEXT | 动作标识，如 `weather.query`；**同一 owner 下唯一**（本体下 / 实体下） |
| description | TEXT | 动作说明（供人与后续 LLM 理解用途） |
| params_schema | TEXT(JSON) | 参数定义数组：`[{name,label,type,required,default,description}]`，type 沿用属性类型 string/number/boolean/date/datetime/text |
| code_text | TEXT | Python 源码（表字段名避开 `code` 冲突） |
| language | TEXT | 默认 `python`，预留扩展 |
| timeout_seconds | INTEGER | 默认 30，上限 120 |
| is_enabled | INTEGER | 停用后不参与继承与调用 |
| sort_order | INTEGER | |
| created_at / updated_at | TEXT | |

设计取舍：
- **一表两态**（owner_type 区分本体/实体服务）而非两张表：继承合并逻辑只需一次查询，与 `get_merged_attributes` 范式一致；
- 本体删除时级联删除其服务；实体删除时级联删除实体服务；`delete_entity` / `delete_ontology` 各加一处清理。

## 5. 服务继承机制（核心）

参照 `get_merged_attributes` 的"自有覆盖模板"范式：

```python
def get_effective_services(db, entity) -> list[EffectiveService]:
    # 1) 本体服务：owner_type='ontology' AND ontology_id=entity.ontology_id AND is_enabled
    # 2) 实体服务：owner_type='entity' AND entity_id=entity.id AND is_enabled
    # 3) 按 code 合并：实体服务覆盖同 code 本体服务
    # 返回项携带 source: 'ontology' | 'entity' | 'entity_override'
```

- 前端据此分组展示：「继承自本体」「自定义」（覆盖项标注"已覆盖本体动作"）；
- 实体手动创建与某本体动作同 `code` 的服务 = 显式覆盖，语义与属性覆盖一致，无需额外机制。

## 6. Python 执行引擎（安全设计重点）

### 6.1 执行契约

代码必须定义入口函数，执行器注入三个变量：

```python
def run(params: dict, entity: dict, context: dict) -> dict:
    """
    params:  调用参数（按 params_schema 校验后传入）
    entity:  {id, name, entity_type, ontology_id, properties}  # 本体级测试运行时为 {}
    context: {kb_id, service_code, triggered_by}
    返回:    可 JSON 序列化的 dict（失败直接 raise，执行器捕获）
    """
    import requests
    r = requests.get("https://api.example.com/weather", params={"city": params["city"]}, timeout=10)
    return {"weather": r.json()["now"]}
```

执行结果统一结构：

```json
{ "success": true, "data": {...}, "error": null, "stdout": "...", "duration_ms": 812 }
```

### 6.2 沙箱方案（推荐：子进程隔离，不上 Docker）

| 措施 | 实现 |
|------|------|
| 进程隔离 | `subprocess` 启动 `sys.executable -I -c <runner>`（`-I` 隔离模式：不加载用户 site-packages、不设 PYTHONPATH） |
| 代码传递 | 通过 **stdin** 传 JSON payload（代码+入参），避免命令行转义与长度限制 |
| 危险 import 拦截 | 执行前 AST 静态检查 import 白名单（见下），命中黑名单直接拒绝并提示 |
| import 白名单 | 标准库：json/re/math/datetime/time/random/collections/itertools/functools/typing/hashlib/base64/urllib/textwrap/statistics/decimal/fractions；第三方：requests/httpx（随项目依赖） |
| 超时 | `timeout_seconds`（默认 30s，上限 120s），超时 kill 进程返回 timeout 错误 |
| 输出限制 | stdout/stderr 截断（默认 64KB），结果 JSON 截断（256KB） |
| 文件/网络 | 一期**不限制**网络（动作的主要用途就是调 API）；通过禁 import `os/subprocess/socket(open?)` 等阻止任意文件/进程操作——`socket` 是否放开见 §11 待确认 |
| 运行目录 | 临时工作目录，进程结束即弃 |

> 说明：项目为本地/内网部署的单机应用，Docker 沙箱收益低、部署负担重，故一期采用"子进程 + AST 白名单 + 超时 + 输出限制"。如未来开放多租户/公网，可平替为容器执行器（执行器接口不变）。

### 6.3 执行入口

- **测试运行**（编辑服务时）：`POST /api/ontology-services/{id}/test`，body 传手填参数，可附带模拟 entity；
- **实体调用**：`POST /api/entities/{entity_id}/services/{service_id}/invoke`，body 传参数；服务必须属于该实体的有效服务集（本体或自己），否则 403。

一期不持久化执行历史（见 §11-3）。

## 7. API 设计（`routers/ontology_service.py`，前缀 `/api`）

### 7.1 本体服务 CRUD

```
GET    /ontology-categories/{cid}/ontologies/{oid}/services     列表
POST   /ontology-categories/{cid}/ontologies/{oid}/services     创建（code 同本体下唯一）
PUT    /ontology-services/{id}                                  更新
DELETE /ontology-services/{id}                                  删除
POST   /ontology-services/{id}/test                             测试运行 {params, mock_entity?}
```

### 7.2 实体服务

```
GET    /entities/{eid}/services                                 有效服务集（含继承，带 source 标记）
POST   /entities/{eid}/services                                 创建实体自定义（code 在该实体下唯一）
PUT    /ontology-services/{id}                                  复用（仅 owner 为该实体的可改）
DELETE /ontology-services/{id}                                  复用
POST   /entities/{eid}/services/{sid}/invoke                    执行 {params}
```

## 8. 前端设计

### 8.1 本体编辑器（OntologyEditor.vue 卡片新增第 5 个 section）

- 服务列表：名称、code、参数摘要、启停开关、编辑/删除/测试运行；
- 新建/编辑 Modal：名称、code、描述、超时；**参数定义**（复用属性编辑的 key-value 行风格：名称/类型/必填/默认值）；**代码编辑**（一期用等宽 textarea + 行号美化，预留 CodeMirror 升级位）；内置参数模板按钮（"调用 HTTP API"示例）；
- 测试运行 Modal：按 params_schema 动态生成表单 → 执行 → 展示 data/stdout/错误/耗时。

### 8.2 实体详情页（EntityDetailPage.vue 属性区与关系区之间新增区块）

- 两个分组：「继承自本体」（含覆盖标记）、「自定义」；
- 每个服务一行：执行按钮 → 动态参数表单 Modal → 结果面板（JSON 树 + stdout + 错误）；
- 「自定义」分组提供"新建服务"（同 8.1 编辑 Modal 复用为子组件 `ServiceEditorDialog.vue`）；继承服务提供"复制为自定义"（一键覆盖起点）。

### 8.3 组件复用与路由

- 新组件：`ontology/ServiceEditorDialog.vue`（编辑+测试运行）、`entity/ServiceInvokeDialog.vue`（执行）；
- API 封装追加至 `front/src/api/index.js`；
- 不新增侧边栏菜单（服务内聚在本体编辑与实体详情，避免菜单膨胀）。

## 11. 待确认问题（开发前请拍板）

1. **执行安全级别**：一期采用"子进程 + AST import 白名单 + 超时"，不引入 Docker——是否接受？
2. **网络访问**：动作需调外部 API，故放行 `requests/httpx`；`socket`（底层网络）是否也放行，还是仅高级库？（建议：仅高级库）

4. **本体删除级联**：本体删除时其服务连同删除、实体继承随之消失——是否符合预期？
5. **参数类型**：沿用属性类型（string/number/boolean/date/datetime/text）是否够用？是否需要 array/object？
6. **测试运行的 mock entity**：本体级测试运行时允许手动填模拟实体属性（便于调试依赖实体数据的代码），是否需要？
