# 本体服务（动作）函数编排 功能设计文档

> 需求来源：对标 Palantir Foundry **Function-backed Action**（动作的核心逻辑由函数提供）
> 关联文档：`doc/本体管理/本体服务/本体服务_功能设计.md`、`doc/本体管理/本体能力对标Palantir_补强设计.md` §4.3 / §4.4
> 状态：**已实现（待联调验收）** —— 实现记录见 §13
> 日期：2026-09-10

---

## 1. 背景与目标

### 1.1 现状痛点

动作（本体服务）与函数（本体函数）当前**完全割裂**：

- 函数只能在 UI 上被单独调用（实体详情 / 批量解析 / 派生属性），**动作代码里用不了**；
- 沙箱 context 只注入了 `var()`，无函数调用入口，且子进程 `-I` 隔离拿不到 DB 会话：

```python
# backend/services/service_runtime.py
g = {
    "__name__": "__sandbox__",
    "var": lambda node, field=None, default=None: _var(context, node, field, default),
}
```

- 结果：同一段"算"的逻辑在动作里被复制粘贴，函数改了动作不跟着变，也无法统一缓存与审计。

### 1.2 目标

1. **动作可引用函数**：一个动作能组合多个只读函数，把"算"交给函数，动作只管"审 + 写"；
2. **可视化组合**：页面上**拖拽**函数节点 → 连线 → 配置参数 → 保存，零代码或少量代码完成动作编排；
3. **可观测**：测试运行与线上执行都能看到每个节点的输入、输出、耗时、成败；
4. **向后兼容**：现有纯代码动作行为完全不变。

### 1.3 非目标（明确不做）

| 不做 | 原因 |
|---|---|
| 动作调动作 | 会产生递归写与事务嵌套，v1 禁止；函数调函数可用编排图表达 |
| 循环 / 并行节点 | v1 只支持 DAG 串行，语义简单、可拓扑排序、易排障 |
| HTTP / 通知节点 | 这两类已有「规则 + 副作用」承担，代码模式也能做 |
| 编排图版本分支 | 沿用本体提案/版本（P1-4），本功能只存 JSON 快照 + `schema_version` |

## 3. 总体架构

```
┌────────────────────────── 前端 ──────────────────────────┐
│ ServiceEditorPage.vue                                     │
│  ┌──────────┬──────────────────────┬───────────────────┐ │
│  │ 函数面板 │   Vue Flow 编排画布   │  节点属性面板     │ │
│  │（可拖拽）│（拖拽落点/连线/校验） │（参数/分支/输出） │ │
│  └──────────┴──────────────────────┴───────────────────┘ │
│  页签：[ 代码模式 ] [ 编排模式 ]   ← execution_mode       │
└────────────────────────┬──────────────────────────────────┘
                         │ REST（保存 flow JSON / 测试运行）
┌────────────────────────▼──────────────────────────────────┐
│ routers/ontology_service.py                                │
│  ├─ OntologyServiceService（CRUD / 继承解析，新增 flow 字段）│
│  └─ ActionFlowService（新增）                               │
│       ├─ 图校验（DAG / 节点数 / 引用存在性）                │
│       ├─ 拓扑排序 → 逐节点执行                              │
│       │    ├ function  → FunctionService._run（沙箱）       │
│       │    ├ code      → execute_service（沙箱）            │
│       │    └ condition → workflow_engine._eval_rule_tree    │
│       └─ 产出 result / edits / trace                        │
│  然后复用 ActionEnhanceService：规则 → 编排 → 写回 → 副作用 │
└────────────────────────────────────────────────────────────┘
```

关键点：**编排在主进程调度，计算仍在沙箱子进程**。函数节点走 `FunctionService._run`（与现有函数调用同一条路径，缓存与调用记录自动生效），安全模型不变。

## 4. 数据模型

### 4.1 扩表 `ontology_services`（`models.py` / `sql/schema.sql` / `sql/migrations.sql` 三处同步）

| 新增字段 | 类型 | 说明 |
|---|---|---|
| `execution_mode` | VARCHAR(10) NOT NULL DEFAULT `'code'` | `code` 纯代码（现状）/ `flow` 编排 |
| `flow` | TEXT DEFAULT NULL | 编排图 JSON，见 §4.2；`execution_mode='flow'` 时必填 |

不改 `code_text` 语义：`flow` 模式下 `code_text` 允许为空，也可作为 `end` 节点前的收尾片段（v1 不启用，留白）。

### 4.2 编排图 JSON

```json
{
  "schema_version": 1,
  "nodes": [
    { "id": "start", "type": "start", "title": "开始" },
    {
      "id": "f1", "type": "function", "title": "预计起飞延误",
      "config": {
        "function_id": "a1b2c3d4e5f6",
        "function_code": "etd_delay_min",
        "params": { "only_late": true }
      }
    },
    {
      "id": "c1", "type": "condition", "title": "延误是否超阈值",
      "config": {
        "rule": { "op": ">=", "left": { "var": "f1.value" }, "right": 30 },
        "on_false": "abort",
        "abort_message": "过站裕度不足，禁止放行"
      }
    },
    { "id": "end", "type": "end", "title": "放行",
      "config": {
        "result": { "delay_min": "{{ f1.value }}" },
        "edits": [ { "op": "set_property", "property_code": "leg_status", "value": "released" } ]
      }
    }
  ],
  "edges": [
    { "source": "start", "target": "f1" },
    { "source": "f1", "target": "c1" },
    { "source": "c1", "target": "end", "source_handle": "true" }
  ],
  "layout": { "f1": { "x": 260, "y": 120 } }
}
```

### 4.3 节点类型

| 类型 | 作用 | 输出（供下游引用） |
|---|---|---|
| `start` | 固定起点，暴露 `entity` / `params` | `entity.*`、`params.*` |
| `function` | 调用一个本体函数（按 `function_id` 引用，`function_code` 冗余展示） | `value`（返回值整体）、`ok`、`error`、`duration_ms` |
| `code` | 内联 Python 片段（复用 `run(params, entity, context)` 契约），供"编排里还想写两行"的场景 | `value` |
| `condition` | 规则树判断（复用 `services/workflow_engine._eval_rule_tree`），`true` / `false` 两个出口 | `passed` |
| `end` | 终止节点：产出 `result`（返回数据）、`edits`（写回）、或 `abort`（带消息终止，等价于 raise） | — |

> `function` 节点引用的是**只读函数**，天然满足"动作编排中不得写数据"的约束；写操作只发生在 `end.edits` 与既有副作用里。

## 5. 执行语义

### 5.1 编排结果上下文

后端维护一张运行时表，键为节点 id：

```python
ctx = {
    "entity": {...},                  # 实体快照
    "params": {...},                  # 动作入参
    "nodes": {
        "f1": {"type": "function", "ok": True, "value": 42, "duration_ms": 13},
        "c1": {"type": "condition", "passed": True},
    },
}
```

模板 `{{ f1.value }}` 在节点执行前求值，支持点路径与默认值 `{{ f1.value | 0 }}`（v1 支持 `.` 路径与 `| default`）。

### 5.2 function 节点

```python
fn = await db.get(OntologyFunction, node.config["function_id"])
res = await FunctionService._run(db, fn, entity, resolved_params, mock_entity, "action_flow")
```

- 复用现有 `_run`：参数校验、沙箱、超时、调用记录（`ontology_runtime_invocations.kind='function'`）全链路一致；
- `triggered_by='action_flow'`，便于在日志里区分是被动作编排调用还是被 UI 调用；
- 失败时按节点配置 `on_error`：`fail`（默认，整个动作失败）/ `continue`（`ok=false` 继续，供条件节点判断）。

### 5.3 参数绑定

节点 `config.params` 的每个值可以是：

- 常量：`true` / `30` / `"CA1234"`；
- 变量：`{{ f1.value }}`、`{{ entity.properties.sobt }}`、`{{ params.threshold }}`；
- 混合：`{{ f1.value }}` 出现在字符串中间时整体替换为字符串拼接（v1 仅支持整值替换，非整值报错提示）。

### 5.4 condition 节点

表达式复用工作流的规则树（**不新造语法、不 eval 任意代码**）：

```python
from services.workflow_engine import _eval_rule_tree
ok = _eval_rule_tree(node.config["rule"], {"entity": ..., "params": ..., "nodes": ctx["nodes"]})
```

变量节点形如 `{"var": "f1.value"}`，由规则树按路径取值。

### 5.5 end 节点

- `result`：动作返回值（写进 `invocation.result`，也返回给调用方）；
- `edits`：交给 `ActionEnhanceService` 的既有写回通道（`set_property` / `add_relation`），撤销前像照旧记录；
- `abort`：立即终止，`status=error`，`error=abort_message`，**不执行后续副作用、不写回**（语义等价于代码里 `raise ValueError(...)`）。

### 5.6 完整执行流程（编排模式）

```
1) 加载动作 → execution_mode='flow' → 解析并校验 flow
2) DAG 校验（无环 / 单 start / 至少 1 个 end / 节点数 ≤ 50 / 引用函数存在且启用）
3) precondition / validation 规则        ← 既有
4) 拓扑序逐节点执行，累计耗时，超出 timeout_seconds 立即终止
5) end 节点产出 result / edits / abort
6) post 规则                             ← 既有
7) 副作用（notify / webhook / update_property / create_relation） ← 既有
8) 写入 ontology_service_invocations（result 内附 trace）
```

即：**编排只是替换了第 4~5 步的"代码执行"，其余（规则、副作用、日志、撤销、批量）完全复用**，这也是本次改动能保持小面的原因。

### 5.7 trace 结构（测试运行与执行记录共用）

```json
{
  "success": true,
  "data": { "delay_min": 42 },
  "trace": [
    { "node": "f1", "type": "function", "title": "预计起飞延误",
      "ok": true, "duration_ms": 13, "input": {"only_late": true}, "output": 42 },
    { "node": "c1", "type": "condition", "ok": true, "passed": true },
    { "node": "end", "type": "end", "ok": true, "edits": [...] }
  ]
}
```

## 6. 前端交互（拖拽编排）

### 6.1 位置

`front/src/components/ontology/ServiceEditorPage.vue`，代码区上方加模式切换：

```
代码（Python，定义 run 函数）   [ 代码模式 | 编排模式 ]   ✦ AI 辅助 · 示例
```

- 编排模式下：隐藏 `PythonEditor`，显示 `ActionFlowCanvas.vue`（新组件）；
- 模式切换时提示：切到编排会保留但暂不执行 `code_text`（不丢数据，可切回）。

### 6.2 布局（沿用页面现有三栏风格）

```
┌─────────────┬──────────────────────────────┬──────────────┐
│ 函数/节点    │        Vue Flow 画布          │ 节点属性面板  │
│ - 可用函数   │  start → f1 → c1 → end        │ - 名称       │
│   （搜索）   │  拖拽落点 / 连线 / 删除        │ - 函数选择   │
│ - 逻辑节点   │  节点状态着色（测试运行后）    │ - 参数绑定   │
│   条件/代码/结束│                             │ - 分支/输出  │
└─────────────┴──────────────────────────────┴──────────────┘
```

### 6.3 拖拽实现（复用已有技术栈）

- 画布用 **`@vue-flow/core` 1.42**（`front/package.json` 已有依赖，工作流编辑器同款）；
- 左侧面板 → 画布：HTML5 `dragstart`/`drop`，落点用 `screenToFlowCoordinate` 换算坐标（与 `WorkflowEditorPage.vue` 一致）；
- 画布内排序沿用 `ObjectViewManager.vue` 已有的 `onDragStart/onDragOver/onDrop` 模式（本项目既有拖拽范式，风格统一）；
- 连线：`@vue-flow/core` 的 handle，`condition` 节点两个源 handle（`true` / `false`）；
- 校验前移：非法连线（成环、function→start、多入 end）在前端即时拦截并 toast，后端再兜底一次。

### 6.4 节点面板数据来源

```
GET /api/ontology-categories/{category_id}/functions?ontology_id={oid}
```

展示 `name / code / description / 参数`；已停用的函数置灰不可拖。函数节点拖入后自动带出 `params_schema` 默认值，属性面板可改。

### 6.5 测试运行

编排模式下「测试运行」直接调 `/ontology-services/{id}/test-flow`，返回后：

- 画布上每个节点按 `trace` 着色（成功绿 / 失败红 / 跳过灰）；
- hover 节点显示 input / output / 耗时；
- 底部保留现有结果区（返回数据 / stdout）。

## 7. API

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/ontology-services/{id}/flow` | 取编排图（无则返回 `{schema_version:1,nodes:[],edges:[]}`） |
| PUT | `/ontology-services/{id}/flow` | 保存编排图（校验 DAG / 引用 / 节点数） |
| POST | `/ontology-services/{id}/validate-flow` | 只校验不保存（前端实时校验复用） |
| POST | `/ontology-services/{id}/test-flow` | 用 mock 实体跑编排，返回 `success/data/error/trace` |
| POST | `/ontology-categories/{cid}/functions?ontology_id=` | 已有，编排面板复用 |

执行入口不变：`POST /entities/{id}/services/{sid}/invoke` 与 `/ontology-services/{sid}/batch-invoke` 自动按 `execution_mode` 分流到代码或编排。

## 8. 向后兼容与迁移

- `execution_mode` 默认 `'code'`、**存量数据全部是代码模式**，行为零变化；
- 迁移脚本只加列，不回填：
  ```sql
  ALTER TABLE ontology_services ADD COLUMN IF NOT EXISTS execution_mode VARCHAR(10) NOT NULL DEFAULT 'code';
  ALTER TABLE ontology_services ADD COLUMN IF NOT EXISTS flow TEXT DEFAULT NULL;
  ```
- `flow` JSON 带 `schema_version`，未来结构调整时按版本兼容解析；
- 实体级服务（owner_type='entity'）同样支持编排，继承/覆盖规则不变（仍按 `code` 合并）；
- 函数被删除时：编排里引用它的动作在保存/执行时报错提示（不做级联改写，避免静默改语义），并在函数列表给出「被 N 个动作引用」提示（可复用 `UsageAnalysis`）。

## 9. 示例：航班放行复核（航段本体）

```
start ──▶ [f1 预计起飞延误 etd_delay_min(only_late=true)]
             │
             ▼
        [c1 延误 ≥ 30 ?]──false──▶ [end_abort 提示"禁止放行"]
             │true
             ▼
        [f2 当前运行阶段 leg_phase]
             │
             ▼
        [end 写回] edits: set_property leg_status = "released"
                   result: { delay_min: "{{ f1.value }}", phase: "{{ f2.value }}" }
```

对应 Palantir 语义：`etd_delay_min` / `leg_phase` 是 **Function**，整个图是 **Function-backed Action**（含校验分支），`edits` 是动作的事务性写回。

## 11. 风险与取舍

| 风险 | 应对 |
|---|---|
| 编排在主进程调度，节点过多拖慢请求 | 节点数上限 50、总超时复用 `timeout_seconds`、串行执行 |
| 函数嵌套调用导致递归 | 函数只能调只读函数、不能调动作；`function` 节点引用的函数体不允许再引用动作（静态扫描函数代码无 `call_action`） |
| 模板注入 | `{{ }}` 只做取值替换，不做 `eval`；非整值替换直接报错 |
| 图 JSON 手改损坏 | 保存前强校验 + `schema_version`，非法则拒绝保存并给出节点级错误 |
| 与 AI 辅助代码生成的边界 | 编排模式不启用 AI 生成代码；后续可做「自然语言 → 编排草图」，不在本期 |

## 12. 验收标准


1. 新建一个编排模式动作，拖入 2 个函数 + 1 个条件，保存后重新打开图完整还原；
2. 测试运行能看到每个节点的输入/输出/耗时，条件为 false 时动作按 `abort` 终止且不写回；
3. 在实体详情执行该动作，属性按 `edits` 写回，执行记录里能看到 `trace`，撤销能回滚属性；
4. 把一个存量代码模式动作切换到编排再切回，代码与参数不丢失，执行结果不变；
5. 引用已删除/停用函数时，保存与执行都给出明确错误提示。

### 13.2 与设计的偏差（均为实现便利，语义不变）

1. **新增 `/api/ontology-functions?ontology_id=`**：原设计直接复用 `GET /ontology-categories/{cid}/functions`，但服务编辑器在**编辑态**只拿得到 `ontology_id`（路由不带 categoryId），故补一个按本体查函数的接口（全局函数 + 同类别的类别级/本体级函数）。
2. **`function` 节点的 `triggered_by`**：沿用调用来源语义（`test` / `entity` / `flow`），调用记录仍落在公共表 `ontology_runtime_invocations`，可用 `triggered_by + ref_id` 区分。
3. **`end` 节点配置字段**：`{mode: output|abort, result: {}, edits: [], abort_message}`；`result` 与 `edits` 都走 `render` 后再分别作为返回数据与写回指令。
4. **`PUT /flow` 会把执行模式置为 `flow`**：画布保存即代表使用编排；切回代码模式通过正常保存接口传 `execution_mode='code'`（此时 `code_text` 恢复必填，且原代码保留未丢）。

### 13.3 附加能力：AI 辅助生成编排草图

flow 模式下「✦ AI 辅助」可用（按钮标题变为「AI 辅助（生成草图）」），按自然语言生成可直接落到画布的编排图。

- **接口**：`POST /api/ontology-services/ai-assist-flow`（SSE，与代码生成同构：`thinking`/`delta`/`done`/`error`）
- **入参**：`prompt`、`name/code/description/owner_name`、`current_flow`（多轮修改的基线）、`available_functions`（前端把已加载的函数清单带过来）、`history`
- **防幻觉三道闸**：
  1. System Prompt 里以「可用函数清单（id/code/入参/说明）」的形式注入可选函数，并强制 `function_id` 必须来自清单；
  2. `_normalize_flow` 按 `function_code` 回填/纠正 `function_id`，匹配不上直接报错（不静默替换）；
  3. 复用 `validate_structure` 校验 DAG / 起止节点 / 节点数，不通过则把错误回传给用户重试。
- **输出**：`{explanation, flow, params}`，前端「应用到画布」写入编排图，并同步动作入参定义。
- 编排模式下聊天面板不展示代码 diff，改为展示「已通过结构校验 · N 个节点」。
