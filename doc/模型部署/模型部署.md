# 基于 AutoDL + vLLM 部署手册（Qwen3.5-9B · Qwen3-Embedding-8B · Qwen3-Reranker-8B）

> 三个模型，一条链路，正好覆盖大模型部署的三大角色：
>
> | 模型 | 角色 | 对应本项目环节 | 典型显存（BF16） |
> |---|---|---|---|
> | **Qwen3.5-9B** | 对话/生成大模型（原生多模态、262K 原生上下文、思考模式） | `LLM_MODEL`（问答、改写、抽取、摘要全走它） | 权重 ~18G，**24G 单卡直跑** |
> | **Qwen3-Embedding-8B** | 向量嵌入（4096 维，指令感知） | `EMBEDDING_MODEL`（向量召回，替代 bge-small） | ~16G，24G 单卡可跑 |
> | **Qwen3-Reranker-8B** | 相关性精排（query-doc 打分，输出 0~1） | `RERANK_MODEL`（RRF 融合后二次排序，替代 bge-reranker-base） | ~16G，24G 单卡可跑 |
>
> 全程在 AutoDL 云 GPU 上完成（本机显卡只做客户端验证），推理框架用 **vLLM**（PagedAttention +
> 连续批处理，OpenAI 兼容 API 开箱即用）。

---

## 0. 全流程一览（先建立全局感）

```
① 租卡装环境      AutoDL 租实例 + vLLM ≥0.17        （§1~§2，一次性 ~20 分钟）
② 下载模型        ModelScope 三个模型 → 数据盘       （§3，~50G 权重）
③ 部署主模型      vllm serve Qwen3.5-9B → :8000     （§4）
④ 部署嵌入模型    vllm serve --task embed → :8100   （§5）
⑤ 部署精排模型    vllm serve --task score → :8200   （§6）
⑥ 验证与编排      curl 三连 + nohup 保活脚本         （§7）
⑦ 接入平台        改 backend/.env 指向 vLLM 端点     （§8）
```

**GPU 选型决策表：**

| 方案 | AutoDL 实例配置 | 分配方案 | 适合 |
|---|---|---|---|
| **默认（本文档主线）** | **1× RTX 4090 24G**（~¥2/时） | 9B BF16 直跑整卡；Embedding/Reranker 用 **0.6B 小杯**（各 ~1.5G）分时验证 | 部署实验、跑通全流程 |
| 同卡三服务 | 1× RTX 4090 24G | LLM 换 9B **Int4** 量化版（~6G）+ 0.6B×2，三服务同卡并存（总权重 ~9G） | 极致省钱、流程演示 |
| 满血档 | **3× 4090** 或 **2× L20 48G** | GPU0：9B BF16（要长上下文可加卡升 TP）；GPU1：Embedding-8B；GPU2：Reranker-8B（L20 则 8B 双件套同卡各占半） | 中小并发、8B 满配 |

> 显存估算公式：**权重字节数 ≈ 参数量 × 精度字节数**（BF16×2、Int4×0.5），再留 30%~50% 给
> KV cache 与激活。9B BF16 ≈ 18G（单卡 24G 直跑）；Int4 ≈ 5~6G；8B 嵌入/精排各 ≈ 16G。
> 27B BF16 ≈ 54G 就必须量化或多卡了——这正是当初从 27B 换 9B 的原因。

## 1. AutoDL 实例准备

> 控制台：https://www.autodl.com/console →「我的实例」→「租用新实例」。

1. **计费方式**：按量计费（关机即停止计费，精确到秒）；
2. **GPU**：对照 §0 决策表选卡；同实例多卡必须同型号，按「有货 + 价格」选地区；

   「vLLM」省去安装，注意核对其 vLLM 版本 ≥0.17）；
4. **数据盘**：三个模型 BF16 权重合计 ~50G（9B 18G + 8B×2），数据盘**扩到 60G 以上**（无卡模式扩容，费用极低）；
5. **连接**：控制台复制 SSH 指令（`ssh -p 39678 root@connect.nmb2.seetacloud.com`，以自己实例为准），
   或「JupyterLab」→ 终端；推荐 VSCode Remote-SSH 远程开发。

**实例内必备环境设置（每个新终端执行，或写进 `~/.bashrc`）：**

```bash
# 学术加速：访问 GitHub/HuggingFace/pip 官方源前执行
source /etc/network_turbo
```

## 4. 部署 Qwen3.5-9B（主模型）

### 4.1 启动命令

**默认方案（单卡 4090 24G，BF16 直跑）：**

```bash
vllm serve /root/autodl-tmp/models/Qwen3.5-9B \
  --host 0.0.0.0 --port 8000 \
  --served-model-name qwen3.5-9b \
  --max-model-len 32768 \
  --gpu-memory-utilization 0.90 \
  --enable-prefix-caching
```

> 9B BF16 权重 ~18G，单卡 24G 直接装下——这就是选 9B 做部署实验的原因：**不量化、不并行、
> 一条命令起服务**。32K 上下文时 KV cache 约占 3~4G，宽裕；想再长就加卡。

**进阶方案（多卡并行，撑长上下文）：**

```bash
vllm serve /root/autodl-tmp/models/Qwen3.5-9B \
  --host 0.0.0.0 --port 8000 \
  --served-model-name qwen3.5-9b \
  --tensor-parallel-size 2 \
  --max-model-len 65536 \
  --gpu-memory-utilization 0.90 \
  --enable-prefix-caching
```

**同卡三服务方案（一张 4090 同时跑全链路）：** LLM 换 9B **GPTQ-Int4** 量化版（权重 ~6G），
Embedding/Reranker 换 0.6B 小杯（各 ~1.5G），三服务总权重 ~9G 同卡并存——见 §7 脚本注释，
租金省三分之二，代价是主模型能力打折（仅流程验证够用）。

### 4.2 关键参数速查

| 参数 | 说明 |
|---|---|
| `--served-model-name` | API 请求体里的 `model` 字段，起个短名方便客户端配置 |
| `--tensor-parallel-size` | 张量并行卡数，必须 ≤ 实例卡数。9B 单卡就能装下、默认不用 TP；27B 级别才必须多卡切分 |
| `--max-model-len` | 最大序列长度。模型原生支持 262K（可扩 1M），**按显存裁剪**：KV cache 随长度线性涨，24G 单卡建议 16K~32K |
| `--gpu-memory-utilization` | vLLM 可占显存比例（0.8~0.95）。OOM 就往下调；同卡跑多服务时必须显式调低 |
| `--kv-cache-dtype fp8` | KV cache 压到 FP8，显存减半，质量损失可忽略 |
| `--enable-prefix-caching` | 前缀缓存，多轮对话/固定 system prompt 命中后首 token 延迟大幅下降 |

### 4.3 验证

```bash
curl -s http://127.0.0.1:8000/v1/models | head -c 300   # 返回模型 JSON 即成功

# OpenAI 兼容对话
curl http://127.0.0.1:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model": "qwen3.5-9b",
       "messages": [{"role": "user", "content": "用一句话解释 vLLM 的 PagedAttention"}]}'
```

> **思考模式**：Qwen3.5 是推理模型，默认输出带思考段。要快、要省 token 的场景（如意图路由）
> 在请求体加 `"chat_template_kwargs": {"enable_thinking": false}` 关闭；复杂推理场景保留默认。
> **采样温度**建议 0.6~0.7（思考模式）或 0.7~1.0（非思考），太低反而容易出现重复循环。

## 5. 部署 Qwen3-Embedding-8B（向量嵌入）

嵌入模型在 vLLM 里不是对话模型，要用 **`--task embed`** 声明池化任务（last-token pooling）：

```bash
vllm serve /root/autodl-tmp/models/Qwen3-Embedding-8B \
  --host 0.0.0.0 --port 8100 \
  --served-model-name qwen3-embedding-8b \
  --task embed \
  --max-model-len 8192 \
  --gpu-memory-utilization 0.85
```

验证（OpenAI 兼容 `/v1/embeddings`）：

```bash
curl http://127.0.0.1:8100/v1/embeddings \
  -H "Content-Type: application/json" \
  -d '{"model": "qwen3-embedding-8b", "input": " ontology 平台"}'
# 返回 data[0].embedding，长度 4096（8B 规格：0.6B=1024 / 4B=2560 / 8B=4096 维）
```

**两个必须理解的特性：**

1. **指令感知（instruction-aware）**：官方推荐查询侧带任务指令、文档侧不带（非对称检索），
   召回更准。vLLM 的通用接口不会替你拼，需在客户端做：

   ```python
   instruction = "Given a knowledge base search query, retrieve relevant passages that answer the query"
   query_vec = client.embeddings.create(model=..., input=f"{instruction}\n{query}")
   doc_vecs  = client.embeddings.create(model=..., input=docs)   # 文档侧原样
   ```

   简单接入可两边都不加（有少量精度损失）。

2. **MRL 套娃维度**：支持输出降维（32~4096 任取），`/v1/embeddings` 请求加
   `"dimensions": 1024` 即可换更小的向量——存储/精度折中的旋钮。**换维度必须全库重建**，
   新旧维度向量不可比。

## 6. 部署 Qwen3-Reranker-8B（相关性精排）

精排模型是「query-doc 对 → 分数」的判别式用法，在 vLLM 中按**序列分类**加载，
**必须用 `--hf_overrides` 覆盖三个字段**（缺了会加载失败或分数全错）：

```bash
vllm serve /root/autodl-tmp/models/Qwen3-Reranker-8B \
  --host 0.0.0.0 --port 8200 \
  --served-model-name qwen3-reranker-8b \
  --task score \
  --max-model-len 4096 \
  --gpu-memory-utilization 0.85 \
  --hf_overrides '{"architectures": ["Qwen3ForSequenceClassification"],
                   "classifier_from_token": ["no", "yes"],
                   "is_original_qwen3_reranker": true}'
```

| 字段 | 作用 |
|---|---|
| `architectures` | 让 vLLM 按分类头（而非生成模型）加载，取 "yes" 的 logit 当分数 |
| `classifier_from_token` | 声明分类标签 token：`no`/`yes`，输出 = P(yes) ∈ [0,1] |
| `is_original_qwen3_reranker` | 激活官方 prompt 构造逻辑（chat 模板 + 指令包裹），客户端**直接传原始文本** |

验证（vLLM ≥0.9.2 内置 `/v1/rerank`、`/v1/score`，模板由服务端处理）：

```bash
curl http://127.0.0.1:8200/v1/rerank \
  -H "Content-Type: application/json" \
  -d '{
    "model": "qwen3-reranker-8b",
    "query": "MU5307 航班的正常率",
    "documents": [
      "MU5307 航班今日准点率 92%，平均延误 8 分钟",
      "浦东机场行李提取流程说明",
      "东方航空会员积分规则"
    ]
  }'
# 返回 results: [{index, relevance_score, document}]，按分数降序；index 是原 documents 下标
```

> **判别式 vs 生成式**：Qwen3-Reranker 本质是 Qwen3 底座加分类头，不产文字只产分数——
> 正是 RAG 精排要的形态：`score = P("yes" | query, doc)`，越接近 1 越相关。
> `--max-model-len` 给 4K 足够（query+chunk 拼对），给太大反而浪费 KV cache。

## 7. 三服务编排与对外访问

### 7.1 一键启动脚本（nohup 保活）

`/root/start_vllm.sh`（默认「满血档」三卡分配；单卡方案按下文注释改）：

```bash
#!/bin/bash
# 用法: bash /root/start_vllm.sh [主模型路径] [嵌入路径] [精排路径]
# ── 单卡同卡三服务方案：去掉三处 CUDA_VISIBLE_DEVICES 前缀，改用显存配比：
#    LLM 用 9B-Int4（util 0.55）、嵌入/精排换 0.6B 小杯（各 util 0.15）
M=${1:-/root/autodl-tmp/models/Qwen3.5-9B}
E=${2:-/root/autodl-tmp/models/Qwen3-Embedding-8B}
R=${3:-/root/autodl-tmp/models/Qwen3-Reranker-8B}
LOG=/root/autodl-tmp/logs; mkdir -p $LOG

# 主模型：GPU0
nohup CUDA_VISIBLE_DEVICES=0 vllm serve $M --host 0.0.0.0 --port 8000 \
  --served-model-name qwen3.5-9b --max-model-len 32768 \
  --gpu-memory-utilization 0.90 --enable-prefix-caching > $LOG/llm.log 2>&1 &

# 嵌入：GPU1
nohup CUDA_VISIBLE_DEVICES=1 vllm serve $E --host 0.0.0.0 --port 8100 \
  --served-model-name qwen3-embedding-8b --task embed \
  --max-model-len 8192 --gpu-memory-utilization 0.85 > $LOG/embed.log 2>&1 &

# 精排：GPU2
nohup CUDA_VISIBLE_DEVICES=2 vllm serve $R --host 0.0.0.0 --port 8200 \
  --served-model-name qwen3-reranker-8b --task score \
  --max-model-len 4096 --gpu-memory-utilization 0.85 \
  --hf_overrides '{"architectures":["Qwen3ForSequenceClassification"],"classifier_from_token":["no","yes"],"is_original_qwen3_reranker":true}' \
  > $LOG/rerank.log 2>&1 &

echo "启动中… 三个服务各 1~2 分钟内陆续就绪，用 §7.2 轮询"
```

> 默认方案（单卡 4090）跑本脚本时：只保留主模型那段，Embedding/Reranker 那两段换成
> `Qwen3-Embedding-0.6B` / `Qwen3-Reranker-0.6B` 路径 + `--served-model-name qwen3-embedding-0.6b`
> 等小杯名，与主模型**分时**跑（LLM 验证完 `kill` 掉再起检索对），或者干脆检索对放本机跑。

### 7.2 就绪轮询

```bash
for p in 8000 8100 8200; do
  echo -n "port $p: "; curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:$p/health
done   # 三个 200 即全部就绪；看日志: tail -50 /root/autodl-tmp/logs/*.log
```

### 7.3 外部访问（关键差异：AutoDL 只映射一个业务端口）

AutoDL 每个实例只开放 **SSH 端口 + 一个「自定义服务」端口**，8100/8200 不会直接暴露公网：

- **本地临时验证（推荐）**：SSH 隧道一次带走三个端口——
  ```bash
  ssh -p 39678 -L 8000:127.0.0.1:8000 -L 8100:127.0.0.1:8100 -L 8200:127.0.0.1:8200 \
      root@connect.nmb2.seetacloud.com -N
  # 本机随后直接访问 http://127.0.0.1:8000 / 8100 / 8200
  ```
- **长期共用**：控制台「自定义服务」把 8000 映射出去（得到 `https://xxx.seetacloud.com` 形式地址），
  Embedding/Reranker 用 Nginx 反代到该端口路径下，或干脆**换 0.6B 小杯模型放本机跑**（见 §8）。

> 省钱技巧：vLLM 自带 `/metrics`（Prometheus 格式），联调期看 TTFT/吞吐/显存很有用；
> 用完在控制台**关机**，数据盘内容保留，下次开机直接 `bash /root/start_vllm.sh`。

## 8. 接入本体平台（backend/.env）

三个 vLLM 服务都是 OpenAI 兼容接口，本项目接入成本主要在配置：

```ini
# ── 主模型：指向 vLLM（LLM_PROVIDER 保持 openai 即可，OpenAI 兼容）──
LLM_PROVIDER=openai
OPENAI_BASE_URL=http://127.0.0.1:8000/v1        # 隧道/映射后的地址
OPENAI_API_KEY=empty                            # vLLM 不校验，非空即可
LLM_MODEL=qwen3.5-9b                            # 对应 --served-model-name

# ── 嵌入：local → openai（走 vLLM /v1/embeddings）──
EMBEDDING_PROVIDER=openai
OPENAI_EMBEDDING_MODEL=qwen3-embedding-8b
OPENAI_EMBEDDING_DIMENSION=4096

# ── 精排：两条路二选一 ──
# 路 A（vLLM 服务）：/v1/rerank 不是 OpenAI 标准接口，平台当前 rerank provider
#    未覆盖，需按 providers/rerank/__init__.py 加一个 http provider；
# 路 B（零改动）：Reranker 走本地 cross-encoder 档——RERANK_MODEL 指向
#    Qwen3-Reranker-8B 本地路径，sentence-transformers 可直接按 CrossEncoder 加载
#    （HF_CACHE_DIR 放权重后离线可用），平台 RERANK_PROVIDER=cross-encoder 原样工作
```

**接入必读的三个坑：**

1. **换嵌入模型 = 全库重建向量**。维度从 bge-small 的 512 → 4096，且不同模型的向量空间完全不兼容：
   Milvus/Chroma 里的旧 collection 必须删掉重新入库，否则检索结果全是噪声。后台管理页删除并
   重建知识库，或清空向量库后批量重新处理文档；
2. **`OPENAI_BASE_URL` 必须以 `/v1` 结尾**（langchain_openai 会在其后拼 `/embeddings`、`/chat/completions`）；
3. **本机低显存（3080Ti 12G）的替代方案**：主模型/Embedding 用云上 vLLM 服务，
   Reranker 单独换 Qwen3-Reranker-0.6B 本地跑（~2G 显存），或维持现有 bge-reranker-base 不动——
   精排模型与主模型没有耦合，可独立替换、独立验证。

## 9. 常见问题排查（速查表）

| 现象 | 原因 | 解决 |
|---|---|---|
| 启动报 `Architecture xxx not supported` | vLLM 版本过旧，不认识 Qwen3.5 | 升级 `pip install -U vllm --torch-backend=auto`（≥0.17） |
| OOM（`CUDA out of memory`） | 权重+KV 超显存 | 降 `--gpu-memory-utilization`、砍 `--max-model-len`、加 `--kv-cache-dtype fp8`、量化（GPTQ-Int4）或加卡升 TP |
| Reranker 分数全 0 或报错 | 缺 `--hf_overrides` 三字段 | 按 §6 原样补上；检查 `--task score` |
| Reranker 结果明显不合理 | 客户端自行拼了模板 | `is_original_qwen3_reranker: true` 时服务端已包模板，客户端传原始文本即可 |
| HF 下载 401 / 大文件挂起 | Xet 协议与镜像不兼容 | `export HF_HUB_DISABLE_XET=1`（或 `pip uninstall -y hf_xet`），走 ModelScope 最稳 |
| `CUDA_VISIBLE_DEVICES` 设置无效 | vLLM 启动太早读了环境 | 放在命令最前面：`CUDA_VISIBLE_DEVICES=1 vllm serve …` |
| 加载卡在 Loading 很久后失败 | 模型目录不完整/路径错 | 回 §3 验完整性；`vllm serve` 后必须绝对路径 |
| 并发一高就慢 | 批处理参数保守 | 调 `--max-num-seqs`、`--max-num-batched-tokens`；确认开了 prefix caching |
| 关机再开服务没了 | nohup 进程不跨关机 | 数据在、进程不在：重新 `bash /root/start_vllm.sh` |

## 10. 部署知识小结（面试视角）

- **为什么用 vLLM**：PagedAttention 把 KV cache 按 block 分页管理（类比操作系统虚拟内存），
  显存碎片极小、吞吐数倍于 transformers 原生推理；continuous batching 请求随到随批；
  OpenAI 兼容 API 让客户端零改动迁移；
- **三种模型三种部署形态**：对话模型（generate）、嵌入模型（`--task embed`，池化出向量）、
  精排模型（`--task score`，分类头出分数）——同一个引擎按任务类型切换加载方式与 API；
- **张量并行（TP）**：把单层权重矩阵切到多卡同时算，解决「装不下」；卡间用 NVLink/PCIe 通信，
  是权重并行，与流水线并行的区别要能说清。9B 单卡即装下无需 TP，27B 级别才必须多卡切分——
  「模型大小决定部署形态」最直观的例子；
- **量化三板斧**：权重量化（GPTQ/AWQ Int4，下载现成量化版最省事）、KV cache 量化（`--kv-cache-dtype fp8`）、
  在线 FP8（`--quantization fp8`，需 Ampere+ 架构）——显存、精度、成本的三角权衡；
- **显存估算**：权重 = 参数量 × 精度字节，另留 KV cache（随并发×上下文线性涨）与激活值；
  这是选卡的第一性公式，比背「XX 模型要 XX 卡」更本质。
